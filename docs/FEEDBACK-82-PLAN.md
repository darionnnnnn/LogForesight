# FEEDBACK 第 82 輪規劃：PRTG 數值自動補抓與上一輪留下的三類待辦

> 狀態：規劃中（第二版；設計已依使用者回覆定案，第 9 節是定案紀錄，只剩 D-2 一項要使用者提供資料，不擋開工）
> 基準：dev@021d1ce4（1.0.81.9；測試基線 Windows 13,014 通過／17 略過、macOS 13,009 通過／32 略過）
> 來源：使用者詢問 PRTG 偶發不回應時能不能在事後補足資料，讀碼評估後決定規劃自動補抓；另併入 `docs/BACKLOG.md`「下一輪預定」的三類待辦（待決的已知缺陷、升級期一次性機制退場、儀表板摘要效能）。
> 分支：`feature/feedback-82`（自 dev@021d1ce4 開出）。版號 1.0.82.0。

## 1. 目的

PRTG 的 API 偶爾不回應或回應失敗時，事件類資料（結構、狀態變更）會在同日後續窗口或隔晚自動補回並重評；數值類資料（趨勢規則的輸入）不會，只能由人到維護頁手動回填。這一輪讓數值缺口自動、緩慢地補回，並把上一輪留下的三類待辦各推進到「做完」或「拿到做決定需要的資料」。

使用者對補抓的三個要求，是批次 B 的設計前提：

1. 不能等到最後一刻才發現缺口，影響隔天的判定。
2. 分散進行，每次補一點。
3. 不得快速且大量地向 PRTG 要資料。

**完成的定義**：第 8 節逐項驗收對照表的每一列都通過，兩個平台全量測試綠；需要正式站台資料才能決定的項目（批次 D、E），以「取得資料的工具已交付並在測試環境驗證」為本輪完成，後續動作在第 10 節列明。

## 3. 批次 A：PRTG 數值寫入的覆蓋規則

### 現況與核對結果

- `EfPrtgStore.UpsertValues`（`LogForesight.Core/Persistence/Sql/EfPrtgStore.cs:785`）對已存在的（sensor, 小時）列無條件覆蓋數值與品質欄位。
- 呼叫端只有一處：`PrtgFetchService.TryFetchSensorValuesAsync`（`PrtgFetchService.cs:1520`），夜間取數、觸發式取數、手動回填都經過它。
- `nodata`／`unknown` 只由 historicdata 解析寫出（`PrtgFetchService.cs:1805`、`:1810`、`:1820`）；快照只寫 `sampled`（`PrtgSnapshotAccumulator.cs:206`）。
- 快照樣本取自感測器清單的最近值（`lastvalue_raw`），只檢查 `status`、`lastcheck` 欄位存在（`PrtgSnapshotResponseContract.cs:51`），不檢查感測器狀態，也不檢查最近值是多久以前量到的（`PrtgSnapshotHostedService.cs` 的 `AccumulateSensorRow`）。

第一版把「空值蓋掉快照值」列為缺陷，重新評估後撤回一半：

| 情況 | 現行結果 | 判斷 |
|---|---|---|
| historicdata 的空值蓋掉既有 `ok` | `ok` 被清空 | **缺陷**。兩者都出自 PRTG 自己的小時紀錄，先前回過值、之後回空，只可能是 PRTG 端的歷史資料已過期清除；先前的值是真的 |
| historicdata 的空值蓋掉既有 `sampled` | `sampled` 被清空 | **維持現行**。historicdata 是 PRTG 自己對那個小時的紀錄；快照樣本無法證明比它新（上方最後一條）。PRTG 說那個小時沒有量到時，沒有依據認定快照值才是對的 |

### 定案

| 寫入 ＼ 既有 | 無 | `ok` | `sampled` | `nodata`／`unknown` |
|---|---|---|---|---|
| `ok` | 新增 | 覆蓋 | 覆蓋 | 覆蓋 |
| `nodata`／`unknown` | 新增 | **不動（本輪改）** | 覆蓋 | 覆蓋 |

- 被擋下的列不更新 `CreatedAt`（保留期依它清理，沒寫入就不該延長）；回傳值只計實際寫入的列數。
- `MergeSampledValues` 不改：`sampled` 不取代既有的 `nodata`／`unknown`，與上表同一個理由（PRTG 自己的紀錄優先）。
- 不修補既有資料。
- 批次 B 的補抓每次記下補抓前後的可用小時數；補完反而變少時寫 Warn。這是用實機資料檢驗「空值蓋掉快照值」是否合理的觀察點。

不選的方案：空值一律不蓋 `sampled`。它保住了資料，但也會保住「感測器其實沒在量、快照卻一直記到舊值」的小時，沒有證據支持。快照不檢查樣本新鮮度本身列進 BACKLOG（第 10 節），要以環境探測在實機確認停止回報的感測器回什麼。

### 改動

- 範圍：`EfPrtgStore.UpsertValues` 一個方法。判定在讀回既有列之後以 C# 進行，兩個資料庫後端同一段程式。
- 相依：`PrtgFetchService` 以回傳值累計「寫入筆數」印在執行輸出，語意變成「實際寫入」；回填水位看失敗數、不看筆數。實作時 grep 回傳值的全部消費點再確認。
- 文件：`docs/PRTG-SPEC.md` §2 覆蓋規則、`docs/DB-SPEC.md` 對應段落。

### 測試／驗收

- 上表 8 格各一例，另加「被擋下時 `CreatedAt` 不變、回傳值不計」。
- 先寫測試，在未修改的建置確認「空值蓋 `ok`」那一格是紅的，再改。主代理突變：把「不動」改回覆蓋，確認轉紅。
- SQLite 以測試驗證；SQL Server 只到 EF 翻譯層（專案既有限制）。
- 定向篩選：`EfPrtgStoreTests|PrtgFetchServiceTests|PrtgBackfillRunnerTests|PrtgBackfillRangeRunnerTests|PrtgTriggeredValueFetcherTests|RunNowPrtgValuesTests`（開工時實跑確認命中數與新測試在內）。

## 4. 批次 B：PRTG 數值缺口自動補抓

### 現況與核對結果

| 事實 | 證據 |
|---|---|
| 補數值的入口只有手動回填與「立即執行」勾選的接續回填，排程不會觸發 | `PrtgBackfillAdminController.cs:166`、`:203`；`AnalysisOrchestrator.cs:845` |
| 數值取數失敗只把該日標成部分完成，不列入補評估 | `PrtgDailyPipeline.cs:1062` |
| 保守策略（預設）夜間不取數值，數值全由快照供應 | `PrtgDailyPipeline.cs:857`；PRTG-SPEC §3b |
| 快照單批失敗不重試；退避時期望樣本數仍以原間隔計 | `PrtgSnapshotHostedService.cs:289`、`:1789` |
| 可用列＝`ok` 或 `sampled` 且涵蓋率 ≥75；一天 12 個可用小時才是有效日；趨勢規則要 35 日窗內 28 個有效日 | PRTG-SPEC §2、§9a、§9b |
| 趨勢只評估最新已完成日，讀已落盤資料 | PRTG-SPEC §9a |
| historicdata 回零列時視為成功、不寫任何列 | `PrtgFetchService.cs:1517` |
| historicdata 配額每 60 秒 5 次，全程序共用 | `PrtgRequestBudget` |
| 逐日目標解析有共用入口，可指定範圍 | `PrtgFullBackfillPlanBuilder.ResolveDay`（`PrtgFullBackfillPlan.cs:41`） |
| 指定 sensor 取一天數值有入口，只回筆數與失敗數；失敗時在呼叫內等 15 秒起跳再補抓一次 | `PrtgFetchService.FetchValuesForSensorsAsync`（`:694`）、`PrtgValueFetchRetryPolicy` |
| 數值表自然鍵是（sensor, 小時） | `UpsertValues` 摘要；以時間範圍單獨篩選沒有對應索引（BACKLOG「需要資料表、欄位或索引變更」） |
| PRTG 狀態類資料表已有先例 | `lf_prtg_sampled_batches`：`LfDbContext`、`SchemaUpgrader`、`EfPrtgStore`、`SchemaUpgraderModelParityTests`、`SchemaUpgraderTypeParityTests`、`SchemaUpgraderPrtgTests` |
| 一次 historicdata 請求涵蓋多天是否可行 | **未實測** |

**缺口什麼時候影響判定**（回答「最後一刻才發現會不會影響隔天」）：

- 一個日子可用小時不足 12 就不是有效日，趨勢評估不計它；補回之後的下一次評估才計入。所以缺口造成的影響是「那一天晚幾天才被算進去」，延後的長度＝發現的延遲＋補完需要的時間。
- 趨勢規則容許 35 天裡有 7 天無效。延後幾天通常不改變判定；只有該 sensor 的有效日數剛好貼著 28 天時，才會讓 finding 晚幾天出現。
- 第一版只在排程趟尾段、而且只看已結束的日子，等於當天的缺口最快也要隔一晚才開始補。這一版改成常駐、當天就開始補（定案 2、4）。
- 大範圍中斷時補完需要時間（下方「速率與補完時間」），這是「不大量向 PRTG 要資料」的代價，兩者不可兼得；大量補回仍走手動回填。

`docs/BACKLOG.md`「持續出現的提示」一條寫 sensor 取數逾時會「隔日重試」，與程式不符（隔晚只取新的一天）；本批完成後才有事後補回，文件一併改正。

### 定案

1. **形式**：一個常駐的低速補抓服務，獨立於排程趟。每分鐘檢查一次，條件允許時**最多送出 1 次** historicdata 請求（暫定）。不在排程趟內執行、不佔執行鎖。
2. **什麼算一個缺口**：一個「sensor × 日」，日期從今天往前到第 35 天（引用趨勢窗常數，暫定；不早於數值保留期）。判定式只有一條：

   > 已結算小時中的可用小時數 ＋ 尚未結算的小時數 ＜ 12

   - 「已結算」＝該小時結束已超過 1 小時（暫定）。留這段時間讓快照與 PRTG 自己的小時彙總都落定。
   - 過去的日子 24 小時都已結算，式子就是「可用小時少於 12」。
   - 今天的式子意思是「就算今天剩下的小時全部正常，也湊不滿 12」，也就是已經確定會是無效日，當天就進清單，不必等到隔天。
   - 12 引用 `MinDailyUsableHours`，不另寫數字。一列都沒有也算缺口。
3. **補哪些 sensor**：該日全部 `ok` 對應主機上、型別在白名單內、未暫停的 sensor（兩種策略相同，趨勢規則評估的是全部已對應的 sensor）。目標解析走 `PrtgFullBackfillPlanBuilder.ResolveDay`，不另寫一份。
4. **順序**：日期新的先補（今天最先），同一天依 sensor objid。
5. **每個缺口只問一次**：送出前先查紀錄（定案 8），已有紀錄的 sensor 日不再問。逾時、連線失敗、5xx、429 不寫紀錄，之後再試。
6. **寫入範圍**：只寫入請求當下已結算的小時；PRTG 回了尚未結算或未來的小時，一律丟棄不寫。理由是空值會蓋掉之後才到的快照值，進行中的小時也不能當成整小時平均寫成 `ok`。
7. **不送請求的條件**（每一條有對應的狀態文字）：PRTG 未啟用或憑證不齊；白名單為空；取數執行正在跑 PRTG 階段；手動回填、結構同步或環境探測執行中；資源守門判定 PRTG 主機忙碌；自己在退避中；沒有缺口。
8. **紀錄**：新增資料表 `lf_prtg_value_fill_attempts`，主鍵（sensor_objid, day），欄位：詢問時刻、結果、補抓前可用小時數、補抓後可用小時數。
   - 結果三種：`filled`（補到 12 以上）、`still_short`（PRTG 成功回應但仍不足，即 PRTG 也沒有這段資料）、`rejected`（明確不成立的 4xx，例如感測器已刪除）。
   - 出口：日期早於範圍的列每日清除一次；感測器被範圍清除時連帶刪除（`PrtgScopePurgeStore`）；數值保留期清除時連帶處理。
   - 繞過：手動回填與指定主機補值不讀這張表，照常重取。缺口門檻常數改動時，升級步驟清空這張表（門檻變了，先前「仍不足」的結論不再成立）。
   - 不放進診斷資料傳輸的匯出匯入（它是本站台的作業狀態，不是量測資料）。
9. **失敗與退避**：一次請求可重試失敗後，檢查間隔加倍（1→2→4…上限 60 分鐘，暫定），成功一次恢復。呼叫內既有的短暫等待與單次補抓照舊（`PrtgValueFetchRetryPolicy`），不另寫重試。
10. **缺口清單的計算成本**：今天與昨天每小時重算一次，更早的日子每天重算一次（暫定）；每次只取接下來用得到的量（暫定 120 筆）。查詢以 sensor 分批、走（sensor, 小時）鍵，不得只以時間範圍篩選；加慢操作埋點。服務裡的待補清單是有界的（上限即上述筆數），登錄進 `LongLivedCollectionGuardTests`。
11. **看得到**：PRTG 維護頁「鏡像狀態」多一行「數值缺口補抓：運作中／暫停（原因）、待補 N、近 24 小時補回 K、確認無資料 X」，併入該頁既有的狀態回應，不新增端點；診斷匯出多一節同樣的數字。補完反而變少時寫 Warn（批次 A 的觀察點）。不新增設定、不新增健康警示。
12. **啟用**：PRTG 啟用且憑證齊備就運作，沒有開關。

**速率與補完時間**（暫定值下的估算，供實測後調整）：

| 情境 | 缺口數 | 補完時間 |
|---|---|---|
| 偶發漏幾輪快照 | 0（每小時 4 筆樣本少 1 筆仍可用；少於 13 個小時不可用就仍是有效日） | 不補 |
| 2,000 顆 sensor、某天中斷 13 小時以上 | 2,000 | 約 33 小時 |
| 15,000 顆 sensor、某天中斷 13 小時以上 | 15,000 | 約 10 天 |

- 每分鐘 1 次＝每天最多 1,440 次，是 historicdata 配額（每天約 7,200 次）的兩成，而且一次只有一個請求在途。
- 15,000 顆規模下補完一天的缺口要 10 天，仍在趨勢規則容許的 7 個無效日附近；這種規模的整天中斷應以手動回填處理，維護頁那一行的「待補 N」就是判斷依據。

不選的方案與理由：

- **排程趟尾段一次補一批**（第一版）：集中在一小段時間送幾百次請求，與「不快速大量」相反；還會拉長執行鎖被佔住的時間。
- **不滿 24 小時就補**：請求數多一個量級，趨勢判定只看有效日，換不到判定上的差別。
- **以 JSON blob 存紀錄**（第一版）：有長期停止回報的感測器時，每天每顆都會多一筆「確認無資料」，穩定下來是數千到數萬筆；blob 每寫一筆要整份讀出再寫回，而且查不到、清不掉單筆。資料表可以逐列寫入、以鍵查詢、隨保留期與範圍清除一起清。
- **掛在快照服務裡**：快照服務會因待寫檔問題停止採集，補抓不該跟著停；兩者各自常駐，共用的只有請求配額。
- **以「距離跌破 28 個有效日的遠近」排序**：要先為每顆 sensor 算整窗有效日，成本高；最新日優先已對應「先補會影響今晚判定的」。

### 改動

- **B1 資料層**：`lf_prtg_value_fill_attempts`（`LfDbContext`、`SchemaUpgrader` 兩個後端）；`EfPrtgStore` 新增「指定 sensor 集合在日期範圍內各 sensor 日的已結算可用小時數」查詢（可用列判定只用 `PrtgValueRowUsability.Usable`）、紀錄的寫入與查詢、過期清除；`PrtgScopePurgeStore` 與保留期清除連帶刪除。
- **B2 規劃與執行（Core）**：缺口規劃（純函式：目標 sensor、各 sensor 日的可用小時數、紀錄、現在時刻 → 依序的待補清單）；單次補抓（取數 → 丟棄未結算小時 → 重算可用小時 → 寫紀錄）。`FetchValuesForSensorsAsync` 擴充為回報逐顆結果與失敗種類，並接受「只寫入早於某時刻的小時」；既有呼叫端行為不變。

## 11. 複檢

第二版寫完後回頭檢查的結果：

- **與既有設計的衝突**：PRTG-SPEC §5 寫回填「不掛排程」——手動回填仍不掛排程，自動補抓是另一個只補缺口的常駐機制，文件分開寫。PRTG-SPEC §3b 寫所有 PRTG 請求共用請求配額——補抓經 `PrtgClientFactory`，同受限制。專案規則「外部輪詢要有逾時、上限與取消」——每次只送 1 個有逾時的請求，服務迴圈接受取消。專案規則「不在不可信範圍做清除」——補抓只寫入、不清除量測資料。
- **保護生效之前的路徑**：紀錄在請求成功後才寫；請求送出後、紀錄寫入前若行程結束，重啟後會再問同一個 sensor 日一次，寫入是冪等的，可接受。
- **什麼算一個／一個都沒有**：缺口單位、零列、沒有缺口時的狀態顯示都已寫進定案與驗收。
- **單向閘門的繞過**：「只問一次」的繞過路徑（手動回填、門檻改動時清表、範圍外清除）已寫。
- **收緊類**：批次 A 讓空值不再蓋掉 `ok`；「原本可行、收緊後被擋」的情境是有人想靠重做回填把某小時改成空值，沒有這種需求的入口。
- **破壞性判準**：補抓寫入的空值會蓋掉快照值。長得像「PRTG 沒有資料」的合法情況是 PRTG 在高負載下回了不完整的資料；防線有三道：只對確定無效的日子發問（每個 sensor 日最多損失不到 12 個可用小時）、PRTG 忙碌或失敗時暫停與退避、補完變少時寫 Warn 供實機檢驗。
- **多個行程同時存在**（站台重疊回收）：短時間內兩個行程各自每分鐘 1 次，可能對同一個 sensor 日各問一次；寫入冪等、紀錄表以主鍵擋重複，不另做跨行程協調。
- **批次之間**：A、B 都動 `PrtgFetchService` 與 `EfPrtgStore`，順序固定 A 先；B4 與 D0 都動診斷匯出，B4 先；C7 動快照封存，與 A、B 不同檔。
- **目標對得上定案**：使用者三個要求分別對應定案 2（當天發現）、定案 1（每分鐘一點）、定案 1 與 9（速率上限與退避）。「不影響隔天」無法在大範圍中斷時完全做到，已在第 4 節說明這是低速的代價。
- **尚未實跑的東西**：各批的定向篩選詞只核對過測試類別檔名存在，命中數要在開工時實跑；「已結算延遲 1 小時足夠」與速率估算沒有實機資料；本版沒有任何程式改動。
