# FEEDBACK 第 82 輪規劃：PRTG 數值自動補抓與上一輪留下的三類待辦

> 狀態：規劃中（第一版，待使用者定案；第 9 節是需要決定的事）
> 基準：dev@021d1ce4（1.0.81.9；測試基線 Windows 13,014 通過／17 略過、macOS 13,009 通過／32 略過）
> 來源：使用者詢問 PRTG 偶發不回應時能不能在事後補足資料，讀碼評估後決定規劃自動補抓；另併入 `docs/BACKLOG.md`「下一輪預定」的三類待辦（待決的已知缺陷、升級期一次性機制退場、儀表板摘要效能）。
> 分支：`feature/feedback-82`（自 dev@021d1ce4 開出）。版號 1.0.82.0。

## 1. 目的

PRTG 的 API 偶爾不回應或回應失敗時，事件類資料（結構、狀態變更）會在同日後續窗口或隔晚自動補回並重評；數值類資料（趨勢規則的輸入）不會，只能由人到維護頁手動回填。這一輪讓數值缺口也自動補回，並把上一輪留下的三類待辦各推進到「做完」或「拿到做決定需要的資料」。

**完成的定義**：第 8 節逐項驗收對照表的每一列都通過，兩個平台全量測試綠；需要正式站台資料才能決定的項目（批次 D、E），以「取得資料的工具已交付並在測試環境驗證」為本輪完成，後續動作在第 10 節列明。

## 3. 批次 A：PRTG 數值寫入的品質覆蓋規則

### 現況與核對結果

- `EfPrtgStore.UpsertValues`（`LogForesight.Core/Persistence/Sql/EfPrtgStore.cs:785`）對已存在的（sensor, 小時）列無條件覆蓋數值與品質欄位。
- 呼叫端只有一處：`PrtgFetchService.TryFetchSensorValuesAsync`（`PrtgFetchService.cs:1520`），夜間取數、觸發式取數、手動回填都經過它。
- `nodata`／`unknown` 只由 historicdata 解析寫出（`PrtgFetchService.cs:1805`、`:1810`、`:1820`）；快照只寫 `sampled`（`PrtgSnapshotAccumulator.cs:206`）。
- `MergeSampledValues` 遇到既有列不是 `sampled` 時不動（`EfPrtgStore.cs:845` 的摘要第 3 條）。
- 兩件事合起來的後果：PRTG 對某小時回 `nodata` 或 `unknown` 時，原本可用的 `sampled` 值被換成空值，之後也補不回來；PRTG 端的歷史資料過了它自己的保留期後重做回填，既有的 `ok` 值同樣會被空值蓋掉。手動回填現在就有這個問題，自動補抓會大量碰到「快照已有部分資料」的小時。

### 定案（建議）

品質有高低：`ok` 高於 `sampled`，`sampled` 高於 `nodata`／`unknown`。寫入時**低的不覆蓋高的**：

| 寫入 ＼ 既有 | 無 | `ok` | `sampled` | `nodata`／`unknown` |
|---|---|---|---|---|
| `ok` | 新增 | 覆蓋 | 覆蓋 | 覆蓋 |
| `nodata`／`unknown` | 新增 | **不動** | **不動** | 覆蓋 |

- 被擋下的列不更新 `CreatedAt`（保留期依它清理，沒寫入就不該延長）。
- 回傳值只計實際寫入的列數。
- `MergeSampledValues` 不改（`sampled` 不取代既有的 `nodata`／`unknown`）；是否放寬列在第 9 節待決 A-1。
- 不修補既有資料：已經被空值蓋掉的小時無從還原，由批次 B 的補抓或手動回填重新取得。

不選的方案：只擋「可用的 `sampled`（涵蓋率 ≥75）」。涵蓋率不足的 `sampled` 列之後仍可能被待寫檔重播（`PrtgSnapshotJournal`，30 日內）合併成可用，先被空值取代就合併不進去。

### 改動

- 範圍：`EfPrtgStore.UpsertValues` 一個方法。判定在讀回既有列之後以 C# 進行，兩個資料庫後端同一段程式。
- 相依：`PrtgFetchService` 以回傳值累計「寫入筆數」印在執行輸出，語意變成「實際寫入」；回填水位以「每顆目標 sensor 都取到」判定（看失敗數，不看筆數），不受影響——實作時 grep `UpsertValues` 回傳值的全部消費點再確認一次。
- 文件：`docs/PRTG-SPEC.md` §2 品質旗標的覆蓋規則、`docs/DB-SPEC.md` 對應段落。

### 測試／驗收

- 上表每一格各一個案例（8 格），另加「被擋下時 `CreatedAt` 不變、回傳值不計」。
- 先寫測試、在未修改的建置確認「`nodata` 蓋 `sampled`」「`nodata` 蓋 `ok`」兩格是紅的，再改。
- 主代理突變：把「不動」改回覆蓋，確認轉紅。
- SQLite 以測試驗證；SQL Server 只到 EF 翻譯層（專案既有限制）。
- 定向篩選：`EfPrtgStoreTests|PrtgFetchServiceTests|PrtgBackfillRunnerTests|PrtgBackfillRangeRunnerTests|PrtgTriggeredValueFetcherTests|RunNowPrtgValuesTests`（開工時實跑確認命中數與新測試在內）。

## 4. 批次 B：PRTG 數值缺口自動補抓

### 現況與核對結果

| 事實 | 證據 |
|---|---|
| 補數值的入口只有手動回填與「立即執行」勾選的接續回填，排程不會觸發 | `PrtgBackfillAdminController.cs:166`、`:203`；`AnalysisOrchestrator.cs:845`（`PrtgBackfillDays > 0` 才進，排程趟一律 0） |
| 數值取數失敗只把該日標成部分完成，不列入補評估 | `PrtgDailyPipeline.cs:1062` 的 `NeedsReevaluation` 不含失敗 sensor 數 |
| 保守策略（預設）夜間不取數值，數值全由快照供應 | `PrtgDailyPipeline.cs:857`；PRTG-SPEC §3b |
| 快照單批失敗不重試；退避時期望樣本數仍以原間隔計，涵蓋率照實變低 | `PrtgSnapshotHostedService.cs:289`、`:1789` |
| 可用列＝`ok` 或 `sampled` 且涵蓋率 ≥75；一天要 12 個可用小時才是有效日；趨勢規則要 35 日窗內 28 個有效日 | PRTG-SPEC §2、§9a、§9b；`PrtgTrendThresholds` |
| 趨勢只評估最新已完成日，讀已落盤資料 | PRTG-SPEC §9a。補進過去的值，下一晚評估自然用到，不必重評過去日 |
| historicdata 回零列時視為成功、不寫任何列 | `PrtgFetchService.cs:1517`（`rows.Count > 0` 才寫） |
| 排程趟有窗口結束時刻，到點優雅停止 | `RunRequest.WindowEnd`（`AnalysisOrchestrator.cs:44`） |
| 逐日目標解析已有共用入口，可指定範圍 | `PrtgFullBackfillPlanBuilder.ResolveDay`（`PrtgFullBackfillPlan.cs:41`，參數 `scope`） |
| 指定 sensor 取一天數值已有入口，但只回筆數與失敗數 | `PrtgFetchService.FetchValuesForSensorsAsync`（`PrtgFetchService.cs:694`） |
| historicdata 配額每 60 秒 5 次，全程序共用 | `PrtgRequestBudget`；補 1 顆 sensor 的 1 天＝1 次請求 |
| 一次 historicdata 請求涵蓋多天是否可行 | **未實測**。程式一律逐日查，實機 PRTG 對長區間的限制沒有驗證過 |

前一版草案有一條不成立，已改掉：原想以「該 sensor 該日已有 historicdata 寫的列」判斷「已經問過 PRTG」，但 PRTG 回零列時不會留下任何列，這種 sensor 日會每趟重問、佔滿每趟的請求上限，把真正補得回來的缺口擠到後面。改用獨立的紀錄（下方定案 7）。

`docs/BACKLOG.md`「持續出現的提示」一條寫 sensor 取數逾時會「隔日重試」，與程式不符（隔晚只取新的一天）；本批完成後這句才成立，文件在本批一併改正。

### 定案（建議）

1. **補哪些 sensor**：該日全部 `ok` 對應主機上、型別在白名單內、未暫停的 sensor。兩種策略都用這個範圍，因為趨勢規則評估的是全部已對應的 sensor，不只觸發主機。目標解析走 `PrtgFullBackfillPlanBuilder.ResolveDay`，不另寫一份。白名單為空時不執行並印出原因，用語與回填的 `BackfillBlockedReason` 一致。
2. **什麼算一個缺口**：一個「sensor × 日」。日期範圍是今天往前 1 到 35 天（35 引用趨勢窗常數，暫定），且不早於數值保留期。該 sensor 該日的可用小時數少於 12（引用 `MinDailyUsableHours`，不另寫數字）即為缺口；一列都沒有也算。可用小時 12 以上不補。
3. **順序**：日期新的先補，同一天依 sensor objid。
4. **時機**：排程觸發且範圍為全部主機的那一趟，在分析、派工、體檢之後多一段「自動補數值」（與現有接續回填同一個位置）。手動趟不跑（手動趟已有勾選式的接續回填）。同一趟若使用者勾了接續回填，以接續回填為準、不再跑自動補抓。
5. **不跑的條件**（每一條都在執行輸出印一行原因）：PRTG 未啟用或憑證不齊；白名單為空；本趟 PRTG 路徑結局為失敗，或數值取數正在停損冷卻中（PRTG 正在出問題時不加壓）；手動回填或結構同步執行中；已過窗口結束時刻；沒有缺口。
6. **上限**：每趟最多 300 次請求（暫定），最長 60 分鐘（暫定），且不超過窗口結束時刻；任一先到即停，印出剩餘缺口數。沒補完的不另外記帳，下一趟重新計算缺口後接著補。
7. **已確認無資料的紀錄**（避免每趟重問）：PRTG 對某 sensor 日成功回應並解析完成後，重算該 sensor 日的可用小時；仍少於 12 就記入紀錄，之後不再挑它。
   - 只有「成功回應」才記。逾時、連線失敗、停損後沒送出的都不記，下一趟再試。
   - 儲存在一份 JSON blob（比照 `PrtgBackfillWatermarkStore` 的 `JsonBlobSingleton`），不新增資料表。
   - 出口：超出 35 天範圍的條目每趟清除；條目數上限 50,000（暫定），超過時先丟最舊日期的。
   - 繞過：手動回填與指定主機補值不讀這份紀錄，照常重取；紀錄帶版本欄，缺口門檻常數改動時整份作廢。
8. **取數路徑**：一律經 `FetchValuesForSensorsAsync`，沿用同一個暫停閘、停損、冷卻與請求配額，不新增 HTTP 路徑。該方法擴充為能回報「哪幾顆成功、哪幾顆失敗」，供定案 7 判斷。
9. **結局**：這一段的成敗不影響整趟判定（與接續回填相同）；使用者按停止時照一般取消處理。
10. **看得到**：執行輸出一行「自動補數值：缺口 N 個 sensor 日、本趟查詢 M、補到可用 K、確認無資料 X、剩餘 R」；執行計時多一個階段。不新增畫面、不新增設定。

不選的方案與理由：

- **不滿 24 小時就補**：請求數多一個量級，而趨勢判定只看有效日，多花的配額換不到判定上的差別。
- **獨立背景服務在離峰執行**：要另外處理與取數、回填、同步的互斥；排程趟尾段已經在互斥之內。
- **以「距離跌破 28 個有效日的遠近」排序**：要先為每顆 sensor 算整窗有效日，成本與複雜度高；每趟 300 次、最新日優先，在一般缺口量下幾趟就補完。
- **新增啟用開關**：補抓只在有缺口時才動、每趟有上限，沒有需要關掉的情境；專案規則是不新增沒有必要的設定。

### 改動

- `LogForesight.Core/Service/`：新增缺口規劃（純函式：輸入目標 sensor、各 sensor 日的可用小時數、紀錄、今天；輸出依序的待補清單與統計）與執行段（逐日呼叫取數、套上限、寫紀錄、印彙總）。
- `LogForesight.Core/Persistence/`：新增紀錄 store；`EfPrtgStore` 新增「指定 sensor 集合在日期範圍內各 sensor 日的可用小時數」查詢（可用列判定只用 `PrtgValueRowUsability.Usable`）。
- `PrtgFetchService.FetchValuesForSensorsAsync`：回傳值擴充逐顆結果；既有呼叫端（觸發式取數）照舊只用筆數與失敗數。
- `AnalysisOrchestrator`：尾段掛接。Core 不認識 Web 的回填服務，掛接方式比照 `IPrtgBackfillTail`（由 Web 注入）；「現在」一律走 `backend.Clock`。
- `RunTimingPhases`：新增階段名；`docs/WEB-SPEC.md` 若列舉階段名則同步。
- 文件：`docs/PRTG-SPEC.md` §3（新增「數值缺口自動補抓」小節）、§5（手動回填與自動補抓的分工）；`docs/BACKLOG.md` 改正「隔日重試」一句，並新增一條「多天合併成一次 historicdata 請求（未實測）」；`LogForesight.Web/HelpContent/` 有 14 處提到回填，逐處核對是否寫了「數值只能手動補」之類的敘述。

不變的行為：手動回填、指定主機補值、接續回填、觸發式取數、快照服務、狀態規則與補評估規劃。

### 測試／驗收

- **缺口門檻兩側**：可用小時 11 的 sensor 日被挑中、12 的不被挑；0 列的被挑中。
- **日期範圍兩側**：往前第 35 天在內、第 36 天不在；今天不在、昨天在。
- **上限**：缺口 301 個時本趟只送 300、印剩餘 1；時間上限與窗口結束時刻各一例（固定時鐘）。
- **紀錄**：成功回應後仍不足 → 記入、下一趟不挑；逾時失敗 → 不記、下一趟仍挑；成功且補到可用 → 不記也不再是缺口；超出範圍的條目被清；條目上限兩側；版本不同整份作廢。
- **不跑的條件**：定案 5 每一條各一例，斷言零請求且輸出含原因。
- **沒有缺口**：零請求、輸出「沒有缺口」，不是空白也不是成功補了 0 個。
- **與批次 A 的接線**：補抓遇到 PRTG 回 `nodata` 的小時，既有 `sampled` 不被蓋掉。
- **端到端一例**：模擬 PRTG 中斷 13 小時造成整天無效 → 排程趟尾段補抓 → 該 sensor 日可用小時 ≥12 → 下一趟趨勢評估的有效日數加一。
- **手動趟與指定主機更新不跑**各一例。
- 主代理突變：門檻 12 改成 24、上限判斷拿掉、紀錄改成失敗也記，各確認轉紅。
- 測試一律 `new PrtgRequestBudget(new AcceleratedPrtgClock())`，時間用固定時鐘。
- 定向篩選：批次 A 的篩選加 `PrtgDailyPipelineTests|PrtgValueAssessmentTests|PrtgValueFetchRetryPolicyTests|AnalysisOrchestrator`，再加全專案掃描型守門 `Guard|DocNarrative|ControllerRouteSnapshot`（開工時實跑確認命中數）。

## 6. 批次 D：升級期一次性機制退場

### 現況與核對結果

`docs/BACKLOG.md`「升級期一次性機制與退場條件」列了八組機制與各自的完成依據。移除的前提是每個正式站台都升級過且旗標都完成，這只有正式機答得出來。完成依據的形式不一：有的是狀態 blob、有的是資料表查詢（`CountPending()` 為 0、每列版本達標）、有一項（首見日種子合併）是行程內狀態。

### 定案（建議）

- **D0（本輪做）**：交付一份唯讀的「升級期機制完成狀態」查核，逐項列出該表每一組機制在這個站台是「已完成／未完成／無法判定」與依據值。出口待決（第 9 節 D-1），建議放進診斷匯出：使用者本來就從正式站台取診斷匯出，不必另外開資料庫連線；行程內狀態也讀得到。
- **D1（條件成立才做）**：使用者提供正式站台清單並回傳每台的查核結果，全部「已完成」的機制才移除；任何一台未完成或無法判定，該機制留著。移除時依表內「退場條件」欄一併拿掉相依物（`MigrationGateMiddleware` 的分支與註冊、`export` 目錄概念、就緒前以原鍵比對的查詢路徑）。

### 測試／驗收

- D0：測試環境分別布置「全部完成」與「其中一項未完成」的資料，查核輸出逐項正確；無法判定時輸出「無法判定」而不是「已完成」。
- D1：被移除的類別、中介層分支、註冊在全專案零命中（含測試與文件）；移除前先 grep 每個對象的全部呼叫點與測試依賴，列進該段規格；`ControllerRouteSnapshotTests`、`Authorization` 類守門綠；兩平台全量綠。

## 11. 複檢

第一版寫完後回頭檢查的結果：

- **與既有設計的衝突**：批次 A 改變手動回填的寫入結果（空值不再蓋掉既有值），屬於修正，PRTG-SPEC §2「`ok` 覆蓋 `sampled`」的既有敘述不變、另補一句低不蓋高。批次 B 定案 4 與 PRTG-SPEC §5「回填不掛排程」並存：手動回填仍不掛排程，自動補抓是另一個只補缺口的機制，文件要把兩者分開寫。
- **批次之間**：A、B 都動 `PrtgFetchService` 與 `EfPrtgStore`，順序固定 A 先；C7 動快照封存，與 A、B 不同檔。C1 動指紋，與其他批次無交集。
- **什麼算一個／一個都沒有**：缺口單位、零列、沒有缺口時的輸出都已寫進定案與驗收。
- **單向閘門的繞過**：「已確認無資料」紀錄的繞過路徑（手動回填、版本欄、範圍外清除）已寫。
- **收緊類**：批次 A 是收緊寫入，「原本可行、收緊後被擋」的情境是「使用者刻意重做回填想把某小時改成空值」——沒有這種需求的入口，不提供。
- **目標數字**：每趟 300 次在每分鐘 5 次的配額下約 60 分鐘，與時間上限一致；激進策略的夜間取數在同一趟先跑完才進尾段，不同時搶配額。
- **尚未實跑的東西**：各批的定向篩選詞只核對過測試類別檔名存在，命中數要在開工時實跑；本版沒有任何程式改動。
