## 版本沿革

**第三版**（本次，依「以兩千台規模視角檢視」）：

   與舊 SQLite 999 的參數上限。**S3 是本輪 §6 引入的**（統一標記逐筆寫入未用 SaveMany）。
7. 新增 **§8「UI/UX 管不管得動」**（X1~X7）——結論是
   **看得懂 2000 台的狀況（監控面成熟），但做不動 2000 台的維護（設定面與批次面缺規模工具）**。
8. §0 的「兩千台規模未驗證」一列，其推測在第三版已由讀碼**證實為真實缺陷**，
   不再只是「沒測到」——但**實機壓測仍未做**，S2／S6 的實際劣化曲線需要造資料才能確認。

**第四版**（本次，依「首頁與報表改以問題重要性呈現」的要求）：
9. 新增 **§10 規劃提案**：首頁與報表改以「問題的重要性」而非數量呈現。
   核心是補上目前**完全沒有的「時間形狀」維度**（涵蓋範圍／出現密度／新出現／變化幅度／
   是否仍在發生），並把首頁的一張排行榜改成三個問句（今天有什麼不一樣／什麼最急／什麼最廣）。

   會讓已標成「已知雜訊」的問題**永遠霸佔首頁 Top 5**——這在 1 台環境看不出來。

## 零、這份體檢**沒有**測到什麼（先講限制，再看結論）

第一版報告只列了「找到的問題」，沒有交代覆蓋範圍——那會讓人誤以為「沒列到的就是沒問題」。
第二版補上這一節：以下區域**尚未被實際驗證**，修完上述項目也不代表這些地方是好的。
排在前面的是「實務上一定會遇到、但這次測不到」的。

| 未驗證區域 | 為什麼這次測不到 | 為什麼它重要 | 建議怎麼補 |
|---|---|---|---|
| **兩千台規模** | 測試環境只有 **1 台**主機 | 全站的排行、分頁、autocomplete、批次 modal 都是為 2000 台設計的；N=1 時「主機數」欄恆為 1，排序與截斷邏輯等於沒被執行過 | 造 500~2000 筆假主機與紀錄跑一次；重點看批次 modal（見 M10）、主機 autocomplete、群組概況 |
| **逾期整條動線** | 逾期＝「設了未來期限，時間過去」，測試環境無法快轉；API 正確擋下過去日期，**無法人工製造** | 逾期是待辦與工作頁的核心紅字指標（KPI 逾期數、清單紅字、`overdue` 篩選、觀察到期），目前**完全沒有被眼睛看過** | 直接改 DB 的 `DueDate` 造出逾期資料再看畫面；或實測時挑一件設「明天到期」，隔天回來確認 |
| **跨日案件自動掛接** | 需要隔天批次跑完才會發生 | 案件制的核心承諾是「明天的新紀錄自動掛進案件」；沒驗證等於整個 IssueCase 機制只驗了一半 | 實測期間連續看兩天同一個案件的「涵蓋範圍」有沒有往後長 |
| **NetIQ 取數路徑** | 沒有可連線的 Sentinel | 正式環境**主要**資料來源是 NetIQ，本機直讀只是開發用 | 依 BACKLOG 既有的試點計畫（2~3 台實機、2~3 晚） |
| **Linux 主機** | 環境內沒有 Linux 主機 | 規則面已就緒但取數未串（BACKLOG 已列） | 同上，接入後跑 NetIQ 維護頁的「診斷」 |
| **全新空環境的第一天** | 現有環境已有 3 個月資料 | 「第一次就能上手」最關鍵的就是這一天——空狀態文案、引導、設定順序 | 用另一個空 DataRoot 啟一份，從 serverAdmin 登入走完「建 admin → 建群組 → 授權 → 等第一晚批次」 |
| **併發衝突** | 單人測試 | 兩個人同時標記同一個問題、同時改派、同時跑排程，各自會看到什麼？ | 兩個瀏覽器同時操作同一筆 |
| **列印／存成 PDF** | 未執行實際列印 | 這是公司管理者**最可能真正使用**的輸出方式（報表頁有專屬按鈕、CSS 有 `@media print`） | 實際列印一次報表與風險日詳情，看分頁切點與圖表是否完整 |
| **長時間執行中的畫面** | 沒有觸發實際分析 | 排程執行中的進度條、輪詢自我調速、優雅停止 | 手動觸發一次「立即執行」全程觀察 |
| **AD 登入** | 環境為 Stub 免密碼 | 正式環境一律 AD；首次登入自動補顯示名稱／Email 的行為沒被驗證 | 接上測試網域跑一次 |

### 方法論本身的三個偏差（影響結論的可信度）

1. **我用 API 建資料、用 API 切帳號**，沒有用 UI 走完整的設定流程。
   所以「第一次上手最痛的那一段」——新增部門群組 → 建主機群組 → 勾授權矩陣 → 指定負責人 → 指派案件
   ——的**實際步驟數、來回次數、卡點**沒有被體驗到。這是下一輪最該補的。
2. **測的是「有沒有壞」，不是「好不好用」**。所有項目都能完成，但完成一件事要點幾下、
   要在幾個頁面之間跳、要不要記住上一頁的資訊——這些沒有量化。
3. **分級用的是技術嚴重度，不是業務痛感**（第二版已在第五節重排，見下）。
   對一個內網 5~10 人的維運團隊，「找不到我今天要做什麼」的痛感很可能高於無障礙缺陷。

## 一、高：會造成誤用或功能不可達

### H1. 可以把問題指派給「沒有處理能力」的人，且完全沒有警告

- **實測**：以 admin 把 `Microsoft-Windows-Kernel-Power 41` 指派給王主管（manager，只有 ViewAll）。
  API 回 `created:1、assigneeNoAccess:[]`（毫無提示）；王主管的「我的交辦」確實出現這件案件；
  他按「回覆處理狀態」→ **HTTP 403 `您沒有使用這項功能的權限`**，稽核留下一筆 `denied`。
- **問題**：指派前的檢查只做了「他看得到這台主機嗎」（回饋第十輪 §7 的 `assigneeNoAccess`），
  沒做「他動得了嗎」。交辦出去的工作進了對方清單、對方做不了任何事，指派的人也不知情。
- **影響角色**：系統管理者（誤派）、公司管理者／任何無 Handle 者（收到做不了的工作）。
- **建議**：`BulkAssignIssueCase`／日層級指派解析處理人時，一併以 `RoleCapabilityMap`
  （含回饋第十一輪的負責人隱含能力）檢查對方是否具 `Handle`；沒有的話比照 `assigneeNoAccess`
  回一份 `assigneeCannotHandle` 清單，前端在指派 modal 顯性提示（不擋，但要講）。
- **性質**：既有缺口（第十輪引入指派檢查時只做了一半）。

### H2. 「回覆處理狀態」是死按鈕——無 `Handle` 能力者也看得到

- **實測**：王主管進自己的 `/handlers/2`，「進行中案件」列右側出現「回覆處理狀態」按鈕；
  按下去必定 403。
- **問題**：前端顯示條件只判斷「這是不是我自己的頁面 / 處理人清單是否含自己」，沒有判斷
  `hasCapability(currentUser,'Handle')`；後端才是真正的防線。
- **影響角色**：任何被指派但無 Handle 的人（manager／dev／未分群組且非負責人的帳號）。
- **建議**：`handler-detail.js` 的 `issueReplyButton` 與 `records.js` 的同名入口都加上能力判斷；
  無能力時不顯示按鈕（或顯示但停用並說明原因）。
- **性質**：**本輪（§7）引入**——把 modal 抽成共用元件時沿用了「只看是不是自己」的舊條件。

### H3. 使用者清單對「只靠負責人身分」的帳號寫「無任何權限」——與事實相反

- **實測**：劉負責人（無任何群組、是 DESKTOP-DU66932 的負責人）在
  `/admin/users` 的群組欄顯示 **「未指派（無任何權限）」**；
  但點進 `/admin/users/5` 的同一個人顯示「能力：ConfirmPermission、Handle、可見主機 1 台（來源：負責人）」。
- **問題**：清單頁的文案寫死在「沒有群組」這個條件上，回饋第十一輪 §2b 讓負責人成為第二條
  授權路徑之後就不再成立。系統管理者掃清單會誤判「這個人沒權限，可以不用管」。
- **影響角色**：系統管理者（權限盤點誤判）。
- **建議**：清單頁的群組欄改成「未指派群組」（陳述事實即可，不下權限結論）；
  另可在清單加一個「負責主機數」欄或徽章，讓兩條授權路徑在同一張表上都看得見。
- **性質**：**本輪（§2b）引入**——新增授權路徑時沒回頭校對既有文案。

### H4. 使用者詳細頁同一畫面用了兩套可見範圍規則，數字自相矛盾

- **實測**：以 **serverAdmin（`svc-lfadmin`）** 開 `/admin/users/5`（劉負責人）：
  - 上方 KPI 顯示 **「處理中案件 0」**、「處理中項目」區塊顯示「進行中案件（0）目前沒有進行中案件」
  - 下方「被指派歷程」卻**列出 2 筆狀態為「處理中」的案件**（VSS 13、EventLog 6008）
- **成因**：同一頁打了兩支 API，各自的可見範圍規則不同——
  `api/handlers/{id}/workload` 依 §9.4a **以檢視者的可見範圍過濾**（serverAdmin 依 §6.2 沒有任何
  業務資料範圍 → 回 0）；`api/admin/users/{id}/detail` 則**以被查看者為準**（→ 2 筆）。
  兩者都符合各自的規格，湊在同一頁就變成畫面說謊。
- **為什麼第一版沒抓到**：我全程用 `demo-admin`（ViewAll）看這頁——ViewAll 下兩套規則結果相同，
  矛盾被完全掩蓋。這是測試矩陣缺了「**檢視者範圍 < 被查看者範圍**」這個維度。
- **影響角色**：**serverAdmin 首當其衝**——它是正式部署第一天唯一能登入的帳號，也是 AD 停擺時的
  救援入口，卻剛好是「有 Maintain 能進這頁、但沒有任何業務可見範圍」的唯一組合。
  受限的部門管理者看跨部門同事時也會踩到（工作量顯示不完整且無提示）。
- **建議**（三選一，建議第 2 案）：
  1. 使用者詳細頁的工作負載改由 `detail` 端點以**被查看者**為準一併回傳（語意一致，但要新增投影）；
  2. **維持兩支 API，但畫面要誠實**：工作負載區塊加一行「以您的可見範圍顯示，可能不完整」，
     並在檢視者範圍為空時直接改成說明卡而不是「0」；
  3. 對 serverAdmin 隱藏工作負載區塊（同儀表板引導卡的既有處理）。
- **性質**：**本輪（§3）引入**——規劃時刻意選了「兩支 API 各司其職、不重複投影」，
  沒推演到「兩套範圍規則同框」的後果。

### H5. 整列可點的表格列，鍵盤使用者完全無法操作

- **實測**：`tr.lf-row-link`／`tr.lf-row-expandable` 只有 `cursor:pointer` 與 click 監聽，
  **沒有 `tabindex`、`role`、`aria-expanded`，也沒有鍵盤事件**（CSS 僅 `styles.css:1304/1307` 兩行游標樣式）。
- **問題**：全站主要下鑽動線都靠整列點擊——問題查詢四視角、儀表板重點問題卡與主機排行、
  我的交辦、排程作業每日展開、使用者清單進詳細頁。鍵盤／輔助技術使用者到不了這些功能。
  部分列因為列內另有 `<a>`（主機名、日期）還走得到，但**儀表板重點問題卡、依問題視角的展開列
  完全沒有列內連結**，等於功能不存在。
- **準則**：ui-ux-pro-max 優先序 1「Keyboard Navigation：All functionality accessible via keyboard／
  Don't: Unreachable elements」（Severity: High）。
- **參考做法就在專案內**：風險日詳情的報告卡 header（`lf-card__header--clickable`）已經做對了
  ——`role="button"`＋`aria-expanded`＋鍵盤支援＋`:focus-visible`。把同一套搬到 `renderTable` 即可一次修完全站。
- **性質**：既有（隨 `renderTable` 的整列點擊機制一路累積）。

### H6. 篩選 chip 沒有任何鍵盤焦點指示

- **實測**：`.lf-chip` 聚焦後 `outlineStyle:none`、`boxShadow:none`（實際量測，非推論）。
  CSS 只定義了 `:hover`／`.active`／`:disabled`，**沒有 `:focus-visible`**；
  而 `.btn:focus-visible` 的既有樣式選不到 chip（它不是 `.btn`）。
- **問題**：chip 是全站最主要的篩選元件（問題查詢、主機、規則、使用者、報表、我的交辦視角切換）。
  鍵盤使用者 Tab 過去看不到自己在哪裡。
- **準則**：優先序 1「Focus States：Don't remove focus outline without replacement」（Severity: High）。
- **建議**：`.lf-chip:focus-visible { box-shadow: var(--lf-focus-ring) }`——變數已經有了，一行的事。
  側欄的「系統管理」收合鈕（`.lf-sidebar__section--toggle`）同樣沒有焦點樣式，一併處理。
- **性質**：既有。

## 二、中：可用性明顯受損，但有替代路徑

### M1. 查無資料時顯示「載入失敗／請重新整理頁面後再試」——錯誤的復原指引

- **實測**：`/admin/users/999`（不存在的使用者）→ 三個區塊各顯示一次「載入失敗／請重新整理頁面後再試；
  若持續失敗請聯絡系統管理員」，標題區整片空白。但 API 其實回的是
  `404 not_found：找不到這個使用者，可能已被刪除。`
- **問題**：`guardLoad` 把所有失敗一視同仁。「重新整理再試」對 404 永遠不會成功，是誤導；
  而後端已經給了可直接顯示的中文訊息卻被丟掉（toast 幾秒後就消失）。
- **準則**：優先序 8「Error Recovery：Provide clear next steps／Don't: Error without recovery path」。
- **建議**：`guardLoad` 區分 404 與其他失敗——404 顯示 API 回的訊息＋「返回清單」連結；
  其餘維持現況。同時讓一次載入失敗只呈現一塊訊息，而不是每個容器各喊一次。
- **性質**：**本輪（§3）新頁最明顯**，但 `guardLoad` 是全站共用，其他頁面同樣行為。

### M2. 1024×768 下，「依問題」視角的操作按鈕看不到，且沒有可捲動的提示

- **實測**：1024 寬視窗下，問題查詢依問題視角表格內容寬 1307px、可視寬 705px。
  「處理人」與「指派／統一標記／回覆處理狀態」整欄在畫面外。
  `.lf-table-wrap` 有 `overflow-x:auto`（頁面本身不溢出 ✅），但**沒有任何視覺提示可以左右捲**。
- **問題**：1024×768 是遠端桌面、投影、舊筆電的常見解析度。第一次使用的人會直接認定
  「這個視角沒有指派功能」。
- **建議**：捲動容器加漸層陰影／「← 可左右捲動」提示；或在窄視窗把動作欄改為列末固定
  （sticky last column），或把三顆按鈕收成一顆「⋯」選單。
- **性質**：既有（欄位數隨第四視角與第十一輪按鈕增加而惡化）。

### M3. 手機 375px 下，篩選列佔掉 80% 的畫面高度

- **實測**：問題查詢頁在 375×812 下，`.lf-toolbar` 高度 **655px**——要捲過將近一整屏才看得到結果。
  （頁面本身無水平溢出 ✅，表格橫捲處理正確 ✅。）
- **建議**：手機斷點把篩選列預設收合成一顆「篩選（3）」按鈕，展開才顯示；
  或只保留期間＋風險層級兩組，其餘收進「更多條件」。
- **性質**：既有。

### M4. 「他人處理中」的說明掛在 disabled 元素上，實務上看不到

- **實測**：他人案件的問題列 checkbox `disabled` 且帶
  `title="此問題由 劉負責人(DOMAIN\owner-liu) 的案件處理中，如需接手請由管理者改派"`。
  文案本身寫得很好，但**瀏覽器對 disabled 元素不派送滑鼠事件，tooltip 不會出現**。
- **問題**：使用者看到的是一個勾不動、也沒有解釋的 checkbox。
- **建議**：把 `title` 移到外層 `.lf-status-cell__wrap`（非 disabled 元素），
  或直接在狀態欄顯示一行小字「他人處理中，需改派才能接手」。
- **性質**：既有（第十輪 §8）。

### M5. 報表六張圖表對輔助技術完全不存在

- **實測**：`trend-chart`／`category-chart`／`host-chart`／`risk-chart`／`affected-hosts-chart`／
  `handling-progress-chart` 六個 `<canvas>` **全部沒有 `role`、`aria-label`、也沒有 fallback 內容**。
- **緩解**：每張圖都有「表格」切換鈕（很好的設計），占比圖另有文字條列常駐——
  資訊本身沒有只靠圖表傳達 ✅。缺的是讓輔助技術知道「這裡有一張圖、它在講什麼、可以切成表格」。
- **建議**：canvas 加 `role="img"` ＋ `aria-label="<標題>：<一句摘要>"`；
  「表格」切換鈕補 `aria-pressed`。
- **性質**：既有。

### M6. Modal 開啟後焦點沒有移進對話框，也沒有可讀的標題關聯

- **實測**：開啟「統一標記」modal 後 `document.activeElement` 仍是 `<body>`；
  modal 有 `role="dialog"` 但沒有 `aria-labelledby`／`aria-label`。
- **問題**：鍵盤使用者按 Tab 是從頁面最上方開始，而不是 modal 內；螢幕閱讀器不會唸出對話框標題。
- **建議**：`showDetailModal` 開啟後把焦點移到 modal 的第一個可聚焦元素（或 modal 容器本身），
  關閉時還給觸發按鈕；標題元素加 id 並以 `aria-labelledby` 指向。全站 modal 共用同一個工廠，改一處即可。
- **性質**：既有（共用元件）。

### M7. 儀表板沒有任何「我手上有幾件」的個人化入口

- **實測**：陳工程師手上有 2 件進行中案件，登入後儀表板 KPI 顯示「未處理 **0**」
  （因為指派後日狀態已推進成處理中），側欄「我的交辦」也沒有任何數字。
  他唯一知道自己有工作的方法是主動點進「我的交辦」。
- **問題**：一般使用者是每天用得最頻繁的角色，首頁卻沒有回答他最關心的問題「今天輪到我做什麼」。
- **建議**：側欄「我的交辦」加未結案數 badge（資料現成：`handlers/{id}/workload` 的 KPI），
  或儀表板待辦區加一張「我的交辦 N 件」卡（點擊直達）。
- **性質**：既有。

### M8. 用 emoji 當圖示（專案已有 SVG icon sprite）

- **實測**：風險日詳情的「🔗 關聯訊號（程式確定性比對）」與「⚠ 本日部分偵測未執行」。
- **準則**：ui-ux-pro-max 優先序 4 明列 anti-pattern「Emoji as icons」——
  跨平台字形不一致、無語意、無法用 `currentColor` 跟著主題走。
- **建議**：改用既有的 `/img/icons.svg` sprite（`link-45deg`／`exclamation-triangle` 都已在用），
  走 `icon()` helper。
- **性質**：既有。

### M9. 授權矩陣與部門群組的說明沒有提到「負責人」這條授權路徑

- **實測**：群組頁寫「部門群組：決定成員能看見哪些主機——實際授權在『授權矩陣』頁籤勾選」，
  授權矩陣寫「勾選＝該部門可看見該群組的主機」。兩處都沒有提到：
  **一台主機只要指定了負責人，那個人不必進矩陣也看得到，而且自動取得處理能力。**
- **問題**：系統管理者依矩陣盤點「誰看得到哪些主機」會漏算負責人路徑。
- **建議**：兩處說明各補一句，並在矩陣頁加一個連往主機頁「負責人」欄的提示。
- **性質**：**本輪（§2b）引入**。

### M10. 批次指派／統一標記的預覽 modal 沒有筆數上限——兩千台規模會塞爆

- **實測（讀碼確認）**：`PreviewIssueCaseAssign` 與 `PreviewBulkClose` 都回傳**全部**受影響主機
  （服務層無 `Take`）；前端 `renderTable({ rows: preview.hosts })` 與
  「受影響主機（N 台…）」也是全部渲染，**沒有分頁、沒有搜尋、沒有虛擬捲動**。
- **為什麼一定會遇到**：像 `DCOM 10016`、`Service Control Manager 7000` 這種問題在真實機房
  幾乎每台都有。2000 台環境下，admin 點一次「指派」或「統一標記」就會把 2000 列塞進 modal。
- **對照**：專案在別的地方都刻意處理過同一個規模問題——主機清單改伺服器端分頁、
  執行監控矩陣改每日彙總（「18 萬格 DOM」那條）、未回報主機改計數卡＋下鑽。
  這兩個 modal 是同一類風險的漏網之魚。
- **建議**：預覽端點加上限（例如 200 筆）＋回傳總數，modal 顯示「顯示前 200 台，共 N 台將受影響」；
  或加搜尋框與虛擬捲動。**統一標記尤其要小心**——它按下去是跨主機跨日的寫入，
  使用者更需要「我到底影響了多少」的正確感知，而不是一個捲不完的清單。
- **性質**：批次指派為既有（第四輪）、統一標記為**本輪（§6）引入**，兩者同一個成因。

### M11. AI 連線失敗是「已知事實」，卻沒有回饋到使用 AI 的入口

- **實測**：`/api/ai/status` 回 `available:true`（只代表「設定了位址」），
  但實際呼叫 `/api/ai/chat` 回 `data:null`（AI 服務 localhost:8080 拒絕連線）——
  而**排程作業頁的異常彙總早就記著這件事**（`ChatJsonAsync 最終失敗…目標電腦拒絕連線`）。
- **現況表現**：風險日詳情照常顯示完整的「詢問 AI」對話區塊，使用者輸入問題、等待，
  得到「AI 目前忙碌或無法回應，稍後再試。」——**失敗處理本身是正確的**（不會死當），
  但介面每次都重新邀請他再試一次。
- **問題**：系統其他地方已經知道 AI 連不上，這個資訊沒有傳到入口。使用者（尤其一般使用者）
  無從判斷是「這次剛好忙」還是「這功能根本沒通」。
- **建議**：`ai/status` 除了「有沒有設定」再帶一個「最近一次呼叫是否成功」
  （記憶體內的最後結果即可，不必新增儲存）；連續失敗時把對話區塊改成一行說明
  「AI 服務目前無法連線，請聯繫系統管理員」，而不是可輸入的對話框。
- **性質**：既有。

### M12. 「把某個人的工作全部轉移」沒有動線——離職／請假交接會很痛

- **現況**：改派是**逐案件**進行的（風險日詳情的日層級指派帶 `reassign`、
  依問題視角的批次指派逐列勾「改派」）。使用者詳細頁（本輪新增）雖然完整列出某人手上的
  N 件案件，卻**沒有任何「全部轉給某人」的操作**。
- **為什麼實務上一定會遇到**：人員離職、長假、輪班交接是內部維運的常態；
  一個人手上有 10~30 件案件時，逐案改派要開 10~30 次 modal。
- **建議**：使用者詳細頁的「處理中項目」加一顆「全部改派給…」（走既有
  `IssueCaseCoordinator.ReassignCase` 逐案執行，寫一筆彙總稽核）；
  或在停用使用者時偵測「他還有 N 件進行中案件」並提示先交接。
- **性質**：既有（功能缺口，非缺陷）；本輪新增的使用者詳細頁**讓這個缺口變得明顯**——
  畫面把問題攤開來了，卻沒給解決的按鈕。

### M13. 停用使用者時不會檢查他手上還有沒有工作

- **現況**：使用者頁的「停用」直接生效（`ActiveUserMiddleware` 即時擋登入）。
  但他名下的進行中案件**不會有任何提示或轉移**——案件仍掛在停用帳號上。
- **後果**：那些案件在「依問題」視角仍顯示「1 台處理中（某已停用者）」，
  其他人因為 §8 的協調保護**不能直接接手**（要管理者改派），而管理者不會知道要改派。
  工作就這樣卡住，直到有人發現。
- **佐證**：處理人工作頁已經考慮過停用者（名字後綴「（已停用）」），
  代表設計上知道會有這種狀態，但**沒有在停用當下攔截**。
- **建議**：停用前檢查該使用者的進行中案件數，>0 時在確認對話框顯示
  「此帳號仍有 N 件進行中案件，停用後需另行改派」，並提供直接跳到使用者詳細頁的連結。
- **性質**：既有。

## 四、驗證正確、不需改的部分（避免誤讀成全面有問題）

以下是這次實測**確認行為正確**的重點，記下來供日後回歸比對：

## 五、建議的處理順序（第二版：改以「業務痛感 × 修改成本」排序）

第一版是按技術嚴重度排的。實務上，對一個內網 5~10 人的維運團隊，
「權限盤點會誤判」「工作卡住沒人知道」的痛感高於無障礙缺陷；
而無障礙缺陷的修改成本又特別低（共用元件一次改完）。重排如下：

### 第 0 批：併回 master 之前該修掉的（都是本輪引入，範圍小）

| 項目 | 為什麼卡在這一批 | 預估成本 | 驗收方式 |
|---|---|---|---|
| **H2** 死按鈕 | 本輪 §7 引入，一行條件判斷 | 極小（2 檔各加一個 `hasCapability`） | 以 manager 開自己的工作頁，按鈕不出現 |
| **H3** 「無任何權限」說謊 | 本輪 §2b 引入，一句文案 | 極小 | 使用者清單看純負責人帳號，不再宣稱無權限 |
| **H4** 使用者詳細頁數字矛盾 | 本輪 §3 引入，會誤導部署第一天的 serverAdmin | 小～中（看採哪一案） | 以 `svc-lfadmin` 開任一使用者詳細頁，KPI 與歷程不再打架 |
| **M9** 授權矩陣沒提負責人路徑 | 本輪 §2b 引入，兩句說明 | 極小 | 群組頁與矩陣頁各看得到一句 |

### 第 1 批：一次改完全站受惠（共用元件，成本低、覆蓋廣）

| 項目 | 收斂在哪 | 預估成本 |
|---|---|---|
| **H5** 整列可點無鍵盤支援 | `core/ui.js` 的 `renderTable`（範本：`lf-card__header--clickable`） | 中（一處改、全站生效） |
| **H6** chip 無焦點指示＋**L9** 側欄收合鈕 | `site.css` 兩條 `:focus-visible` | 極小 |
| **M1** 404 顯示「請重新整理」 | `core/ui.js` 的 `guardLoad` | 小 |
| **M6** modal 焦點與 aria | `core/ui.js` 的 `showDetailModal` | 小 |
| **M4** disabled 上的 tooltip | 掛載點移到外層 | 極小 |

### 第 2 批：規模與交接——**上線前一定要處理**

| 項目 | 為什麼急 | 預估成本 |
|---|---|---|
| **M10** 批次 modal 無筆數上限 | 2000 台環境下按一次就塞爆瀏覽器；統一標記還是寫入操作 | 中（前後端各加上限與總數） |
| **M13** 停用使用者不檢查在辦案件 | 工作會靜默卡住，且因協調保護別人接不了手 | 小 |
| **M12** 無「整批轉移某人的工作」 | 離職／請假交接是常態，目前要逐案開 modal | 中 |

### 第 3 批：需要設計決策，建議併下一輪回饋一起談

**M2**（1024px 動作欄看不到）、**M3**（手機篩選列佔 80%）、**M7**（沒有「我手上有幾件」）、
**M11**（AI 連線失敗未回饋入口）、**M5**（圖表 aria）、**H1**（指派給無能力者的警告——

### 第 4 批：品質收尾

**M8** emoji 換 SVG、**L 系列**全部。**L11**（owners API 靜默清空）建議與其他後端健壯性一起做。

## 六、下一次體檢應該補的（比修完這批更重要）

這份報告最大的價值可能不是這 25 項，而是**它暴露的測試盲區**（第零節）。建議下一輪至少補三件：

1. **用 UI 走一次完整設定流程**（不要用 API 抄捷徑）：
   從空環境的 serverAdmin 登入 → 建 admin → 建部門群組 → 建主機群組 → 勾授權矩陣 →
   指定負責人 → 指派第一件案件。**記錄每一步點了幾下、卡在哪裡**。
   這條路徑是「第一次就能上手」的真正考題，這次完全沒走。
2. **造規模資料跑一次**（500~2000 台）：批次 modal、autocomplete、排行截斷、群組概況，
   這些全是為規模設計卻只在 N=1 驗過的功能。
3. **把時間相關的路徑補測**：逾期紅字、觀察到期、跨日案件掛接——
   需要改資料或跨日觀察，不能靠單次點擊驗證。

驗收建議：修完第 0、1 批之後，**以 `svc-lfadmin` 與一個純負責人帳號各走一次全站**——
這兩個角色是本次體檢中「最容易被忽略、卻最先接觸系統」的組合，
第一版報告漏掉的 H4 正是因為沒用它們看過畫面。

## 七、兩千台規模：程式碼薄弱點

> 以下全部來自**讀碼確認**（非推測），每項標出「什麼時候會炸」。
> 推算基準：2000 台主機 × 歷史保留 90 天；一台主機一天平均 5~20 個問題被標記或被案件同步。
>
> **先講結論**：分析紀錄（`lf_daily_records` / `lf_top_issues`）是**真正的 SQL 表且有下推過濾**，
> 這部分撐得住。撐不住的是**兩類東西**——(1) 每次查詢都把可見主機展開成 IN 參數；
> (2) 處理狀態／案件／主機／使用者這些「整份 JSON blob」的資料。

### S1【最高】可見範圍展開成 2000 個 IN 參數——全站每一次查詢都會經過

- **現況**：`RecordRepository.ApplyVisibility` 把**全部可見主機**塞進 `filter.Hosts`
  （ViewAll 就是全部主機＋墓碑列）；`EfAnalysisRecordStore.ApplyPushableFilters` 再轉成
  `WHERE r.HostId IN (@p0…@pN)`。
- **什麼時候炸**：
  - **SQL Server 單一命令參數上限 2100**——2000 台已經貼著上限，加上墓碑列（合併過的舊主機）
    就會**直接拋例外**，且是全站所有查詢一起壞（儀表板、問題查詢、報表、詳情頁）。
  - SQLite 舊版 `SQLITE_MAX_VARIABLE_NUMBER` 預設 **999**，2000 台當場失敗
    （新版提高到 32766，但測試環境版本要確認）。
- **另一個成本**：`VisibleHostKeys()` 每次都 `_hosts.GetAll()`（整份 blob 反序列化 2000 台）
  ＋建 HashSet ＋墓碑展開，且**沒有 per-request 快取**（`VisibilityService` 有快取，這一層沒有）。
- **建議**：ViewAll（不需要縮小範圍）時**不要下推 Hosts 條件**，改以「不加 WHERE」表達；
  受限使用者則改用「授權群組 → 主機」的 join／子查詢下推，而不是把 ID 清單搬進參數。
  這是本節唯一「不改就一定會壞」的項目。

### S2【最高】處理狀態與案件是「整份 JSON blob」——每標記一次就重寫整份

- **現況**：`IssueHandlingStore`／`IssueCaseStore`／`RecordHandlingStore`（快照）／
  `HostStore`／`UserStore`／`HostGroupStore`／`GroupAccessStore`／`NoiseMarkStore`
  全部繼承 `JsonBlobCollection<T>`——**整份陣列存在 DB 單一列**，
  `Read()` 反序列化整份、`Mutate()` 讀→改→**序列化整份寫回**（行程內鎖＋DB 交易）。
- **規模推算**（`issue_handling`）：一列約 200~300 bytes JSON。
  - 保守（每台每天 1 列）：2000 × 90 = **18 萬列 ≈ 40~55 MB**
  - 實際（每台每天 5~20 列，含案件同步逐日寫入）：**90 萬~360 萬列，數百 MB**
  - 每一次標記＝把這數十~數百 MB 讀出、反序列化成數十萬~數百萬個物件、改一筆、再全部序列化寫回。
- **什麼時候炸**：不是「某天突然壞」，是**隨資料累積線性變慢**，直到單次標記要數秒~數十秒；
  記憶體也會隨每次操作出現等同 blob 大小的尖峰（多人同時操作時疊加）。
- **建議**：`issue_handling`、`issue_cases`、`record_handling` 這三個**會隨主機數×天數成長**的
  集合改成真正的資料表（有索引的 `host_name + date + issue_key`）。
  `hosts`／`users`／`groups` 這類「隨組織規模成長」的維持 blob 沒問題（數千筆上限內）。
  這是架構級改動，建議獨立立案，不要夾在功能輪次裡做。

### S3【高】統一標記逐筆寫入，沒有用既有的 SaveMany 合併——**本輪引入**

- **現況**：`BulkCloseIssue` 的雙層迴圈對每一個（主機, 日期）呼叫一次 `ApplyIssueStatus`，
  而 `ApplyIssueStatus` 走 `_issueStore.Save(單筆)` → `SaveMany(1 筆)` → **一次整份 Mutate**。
- **規模推算**：對一個「1000 台主機、期間 30 天」的常見問題按下統一標記
  ＝ **30,000 次整份 blob 讀改寫**（每次都反序列化整份 issue_handling）。
  即使一次 100ms 也要 50 分鐘，而且全部在**單一同步 HTTP 請求**內完成——瀏覽器早就逾時，
  使用者不知道到底寫進去多少。
- **對照**：`IssueCaseCoordinator` 已經知道要避開這件事——它把跨日展開累積成 `toSave`
  最後 `SaveMany` 一次（程式碼註解寫得很清楚「避免逐日呼叫造成 N 次整份 blob 讀改寫」）。
  **統一標記沒有沿用這個模式**。
- **建議**：`BulkCloseIssue` 先把所有要寫的 `IssueHandling` 累積起來、`SaveMany` 一次；
  歷程（append-only，成本低）維持逐筆。同時搭配 M10 的筆數上限與非同步化（見 S7）。
- **性質**：**本輪（§6）引入**——這是我在規劃時只想著「走既有咽喉不開第二套狀態機」，
  沒注意到既有咽喉是「單筆」介面。

### S4【高】每晚批次的案件掛接，在迴圈內重寫整份案件 blob

- **現況**：`IssueCaseCoordinator.AttachNewDay` 每台主機：
  1 次 `GetOpenForHost`（整份 cases 讀）＋1 次 `GetForDay`（整份 handling 讀）
  ＋**迴圈內每個命中問題各一次 `_cases.Save(openCase)`（整份 cases 讀改寫）**
  ＋最後 1 次 `SaveMany`（已合併 ✅）。
- **規模推算**：2000 台 × 平均 2 個進行中案件命中 ≈ **每晚 4000 次整份 cases 讀改寫**
  ＋4000 次整份讀。案件 blob 在 2000 台環境可能有數千~數萬筆。
- **什麼時候炸**：這是**每晚必然發生**的，不是極端情境；會直接拉長夜間批次的執行時間，
  且與 Web 端的標記操作**搶同一把 blob 鎖**（`EfJsonBlobStore` 行程內 `lock`）。
- **建議**：`LastLinkedDate` 的推進累積成清單，迴圈外一次 `SaveMany`（案件 store 需補這個方法）。
  修法與 S3 同型，成本小、效益明確。

### S5【中】處理歷程的讀取是全表掃描，且站台啟動時全讀一次

- **現況**：歷程走 append-only 的 `EfJsonLogStore`（寫入 O(1) ✅ 設計正確），
  但 `GetLogs(hostName, date)` 是 `ReadAllLogs()` **讀回全部行再過濾**；
  且 `RecordHandlingStore` 建構式為了取 `_lastLogId` 也 `ReadAllLogs()` 一次。
- **規模推算**：2000 台 × 90 天 × 每天數次操作 ≈ **數百萬行**。
  - 每開一次風險日詳情的「處理歷程」＝ 全表讀取＋逐行 JSON 解析
  - 站台啟動＝一次全讀（幸好 store 是 Singleton，只發生一次，但啟動會明顯變慢＋記憶體尖峰）
- **建議**：`GetLogs` 下推 `host_name + date` 條件到 SQL（歷程表本來就是逐列儲存，加索引即可）；
  `_lastLogId` 改用 `MAX(seq)` 查詢，不要全讀。

### S6【中】儀表板／報表把整段期間的紀錄全部載入記憶體聚合

- **現況**：`DashboardService.GetSummary` 呼叫 `_repository.Query(new RecordQueryFilter { From })`
  取回**全部**紀錄（非分頁），再於記憶體做類別統計、主機排行、問題排行（本輪新增）、群組概況。
- **規模推算**：2000 台 × 7 天 = 14,000 筆紀錄，每筆含完整 `TopIssues`（20~50 個）
  → 一次反序列化 **數十萬個問題物件**；報表預設 30 天則是 60,000 筆紀錄、上百萬個問題物件，
  而且還要**再算一次前期對比**（等於雙倍）。
- **後果**：儀表板/報表每次載入都重算，無快取；多人同時開就是數 GB 級的瞬間配置與 GC 壓力。
- **建議**：把 KPI／排行／分布改成 SQL 端聚合（`GROUP BY`），只把 Top N 拉回應用層；
  或對「同一組參數」加短時快取（例如 60 秒），儀表板本來就不需要秒級即時。
  **本輪新增的問題排行（`BuildIssueRanking`）建在同一條全載入路徑上**，一併處理。

### S7【中】批次寫入是同步 HTTP，沒有進度也不能取消

- **現況**：統一標記／批次指派都是「按下去 → 同步等 → 回結果」。專案在別處已經有正確範本：
  排程「立即執行」是**觸發即回、背景執行、輪詢進度**（`POST run` 只等到取得 Mutex 就返回）。
- **規模後果**：2000 台規模的批次寫入必然超過瀏覽器/反向代理的逾時；
  逾時後使用者不知道寫進去多少，重按一次又是一輪。
- **建議**：批次寫入沿用排程那一套「觸發→背景→輪詢」的模式，或至少在後端限制單次規模
  （搭配 M10 的上限）並回報實際寫入筆數。

### S8【低】其餘隨規模線性劣化的點

| 位置 | 現況 | 影響 |
|---|---|---|
| `HostAdminService.GetHosts` | 「伺服器端分頁」實為**記憶體分頁**：`_hosts.GetAll()` 全讀 → LINQ 過濾排序 → `Skip/Take` | 2000 台每次請求反序列化整份（數十 ms，可接受）；但**規格 §9.8 的敘述會讓人以為已下推到資料層**，文件與實作有落差 |
| `JsonBlobCollection.NextId` | `Max(existingIds) + 1`，每次新增都掃全份 | 新增主機／使用者時多一次全掃，量級小可接受 |
| `HostLookup` / `HostIdentityResolver.Expand` | 每次查詢重建索引、展開墓碑 | 與 S1 同一條路徑，一併處理 |
| 主機 autocomplete | 伺服器端 `Take(20)`，**前端沒有「還有更多」的提示** | 2000 台輸入常見前綴只出現 20 筆，使用者誤以為只有這些（見 X4） |

### 規模結論（程式碼）

- **撐得住的**：分析紀錄的儲存與查詢（真 SQL 表＋下推）、歷程的寫入（append-only）、
  排程執行的背景化與進度回報、主機清單的傳輸量收斂。
- **撐不住的**：可見範圍的 IN 展開（S1，**會直接壞掉**）、
  處理狀態／案件的整份 blob（S2，**線性劣化到不可用**）、
  以及建在它們之上的批次寫入（S3／S4，本輪與既有各一）。
- **建議順序**：S1 →（S3、S4 這兩個小修）→ S6 →（S2 獨立立案）。
  S1 不修，2000 台當天就上不了線；S2 不修，上線後三個月內逐步變慢。

## 八、兩千台規模：UI/UX 管不管得動

> 前一節問「程式跑不跑得動」，這一節問「人管不管得動」。
> 判準：一個維運人員面對 2000 台、每天數百個問題時，**能不能在幾分鐘內知道今天要做什麼、
> 並把它做完**。

### 做對的地方（規模設計的既有成果）

這些都是明確為 2000 台想過的，實測與讀碼確認有效：

- **未回報主機改計數卡＋下鑽**（不逐台列出）
- **執行監控改每日彙總＋展開**（避免 2000×90 的 18 萬格 DOM）
- **主機清單伺服器端分頁＋搜尋＋chip 篩選**（傳輸量收斂）
- **依群組風險概況**（先看部門、再下鑽個別主機——2000 台的正確主動線）
- **主機篩選改 autocomplete**（不把 2000 台灌進 select）
- **主機排行 Top 10＋「其他 N 台」彙總**（尾端不隱形）
- **問題查詢四視角**（尤其「依問題」——2000 台時「哪些問題」比「哪些主機」更能收斂注意力）

### X1【高】「依問題」是對的方向，但問題本身也會有上千種

- **現況**：2000 台環境的相異問題簽章可能達**數百~數千**（本次 1 台就有 56 個）。
  「依問題」視角一列一個問題、預設每頁 10 筆 → **數十~數百頁**。
- **缺什麼**：沒有「問題層級的收斂手段」——沒有依分類分組摺疊、沒有「只看影響 >N 台的」、
  沒有「新出現的問題」與「長期存在的問題」之分。
  現有的篩選（風險層級、類型、Event ID、處理狀態）都是**條件**，不是**摘要**。
- **建議**：加「影響主機數」門檻篩選（例如「只看影響 ≥10 台」）與「本期新增問題」快捷；
  或在清單頂端加一行「共 N 個問題，其中 M 個影響 10 台以上」的分佈摘要。

### X2【高】授權矩陣在多部門×多主機群組時完全沒有規模設計

- **現況**：`groups.js` 的矩陣是完整二維渲染（`for hostGroup` × `for userGroup`），
  **沒有分頁、沒有搜尋、沒有凍結表頭、沒有虛擬捲動**。
- **規模推算**：2000 台的組織通常有 20~50 個部門群組 × 50~100 個主機群組
  ＝ **1,000~5,000 個 checkbox** 一次渲染在一張表裡，且橫向會遠超螢幕寬度。
- **後果**：這是系統管理者**設定權限的唯一畫面**。矩陣一旦超過一屏，
  「這個部門看得到哪些」就變成用手指在螢幕上比對——最容易出錯的操作卻沒有輔助。
- **建議**：矩陣加搜尋（部門／主機群組各一）、凍結首欄與表頭、
  並提供「以部門為主的清單檢視」（選一個部門 → 勾選它看得到的主機群組）當作大規模時的主要動線，
  矩陣退為總覽。

### X3【高】批次操作缺「以篩選條件全選」——要勾 500 台得翻 50 頁

- **現況**：主機頁的批次改群組支援跨頁保留勾選（`Map<hostId, hostDto>`）✅，
  但**只能逐筆勾**；沒有「全選符合目前篩選的所有主機」。
- **規模後果**：「把某個網段的 500 台加進新群組」＝翻 50 頁、勾 500 次。
  實務上使用者會放棄，改回去用 CSV——但 hosts.csv 已於本輪退役（§2a），**退路被拿掉了**。
- **建議**：批次工具列加「全選符合目前篩選的 N 台」（後端以篩選條件執行，不傳 ID 清單），
  並在套用前明確顯示「將影響 N 台」。這也回頭補上 §2a 退役 hosts.csv 造成的能力缺口。

### X4【中】搜尋結果被截斷到 20 筆，畫面卻不說

- **現況**：主機 autocomplete 伺服器端 `Take(20)`，**前端沒有任何截斷提示**。
- **規模後果**：2000 台輸入「SRV」可能有 500 台符合，只出現 20 筆。
  使用者合理地認為「只有這 20 台」——這與專案自己「涵蓋範圍要誠實顯示」的原則相牴觸
  （掃描結果、隱藏問題數都有誠實申報，唯獨這裡沒有）。
- **建議**：回傳總數，下拉底部顯示「顯示前 20 筆，共 N 筆符合，請再輸入以縮小範圍」。

### X5【中】「我的交辦」在大環境會變成第二個收件匣

- **現況**：2000 台環境下一個處理人手上可能有**數十~數百件**案件。
  工作頁的「進行中案件」表**沒有分頁、沒有搜尋、沒有排序切換**（固定逾期→最近出現）。
- **本輪的「依問題」視角有幫助**（把同一問題的多台收成一列），但問題種類多時仍是長清單。
- **建議**：加分頁或「只看逾期／只看本週到期」快捷；
  KPI 列的「逾期 N」做成可點的篩選（現在只是數字）。

### X6【中】沒有「批次操作的影響範圍預覽」以外的安全網

- **現況**：統一標記／批次指派都有預覽清單 ✅（本輪 §6 做得不錯），
  但**沒有「上一步／復原」**，也沒有「先試算不寫入」以外的分段執行。
- **規模後果**：一次影響 1000 台的寫入若判斷錯誤，只能逐台改回來（或再跑一次統一標記蓋掉）。
- **建議**：至少在結果 toast／結果 modal 提供「檢視這次影響的清單」連結
  （帶稽核 id 或問題＋期間的查詢連結），讓人能追回去確認；
  復原機制成本高，可先不做，但**要能查得到影響了哪些**。

### X7【低】儀表板「重點問題 Top 5」在大環境的資訊量會塌陷

- **現況**（本輪 §8-1 新增）：Top 5 依「最高嚴重度 → 主機數 → 總次數」排序。
- **規模後果**：2000 台環境常見問題（DCOM、SCM）幾乎每台都有，
  Top 5 可能全部顯示「1900+ 台」——彼此分不出輕重，且會長期固定不變（每天看到同樣 5 筆）。
- **建議**：加一個「本期新增／異常增加」的維度（例如與前期比較的增幅），
  讓這張卡回答「今天有什麼不一樣」而不是「哪些問題最普遍」。

### 規模結論（UI/UX）

- **收斂主機數的設計已經到位**（計數卡、彙總、分頁、群組概況、autocomplete、Top N＋其他）。
- **收斂問題數與設定規模的設計還沒有**：問題種類（X1）、授權矩陣（X2）、
  批次選取（X3）、搜尋截斷（X4）都是 2000 台才會浮現、目前無解的地方。
- **一句話**：目前的 UI 讓人**看得懂 2000 台的狀況**（監控面成熟），
  但**做不動 2000 台的維護**（設定面與批次面缺規模工具）。
  X2／X3 是其中最痛的兩項——它們是系統管理者每次擴編、改組織時必經的操作。

## 九、合起來看：真正的上線阻擋項

前面八節共 **44 項**（6 高／13 中／11 低／8 程式碼規模／7 UI 規模），
另有 §10 的規劃提案（不是缺陷，是改善方向）。
真正「不修就上不了 2000 台」的只有下面這幾項，其餘都是「會痛但走得下去」：

| 順位 | 項目 | 不修的後果 | 成本 |
|---|---|---|---|
| 1 | **S1** 可見範圍 IN 參數 | 上線當天全站查詢拋例外（SQL Server 2100／SQLite 999 上限） | 中 |
| 2 | **S3** 統一標記逐筆寫入（本輪引入） | admin 對常見問題按一次統一標記＝數萬次整份 blob 讀寫，請求逾時且不知寫入多少 | 小 |
| 3 | **S4** 每晚案件掛接迴圈內重寫 | 夜間批次時間隨案件數線性拉長，且與 Web 端搶同一把鎖 | 小 |
| 4 | **M10** 批次 modal 無筆數上限 | 同一個操作的前端側：2000 列塞進 modal | 中 |
| 5 | **X3** 批次選取無「以篩選全選」 | 擴編／改組織時實質無法操作（hosts.csv 退役後沒有退路） | 中 |
| 6 | **X2** 授權矩陣無規模設計 | 權限設定畫面超過一屏後靠肉眼比對，錯誤率高 | 中 |
| 7 | **S6** 儀表板／報表全量載入聚合 | 不會壞，但每次載入數十萬~上百萬物件，多人同時使用時 GC 壓力大 | 中 |

**S2（整份 blob 架構）刻意不列在上線阻擋項**——它是線性劣化而非立即失效，
且改動範圍等同一次儲存層重構。建議**獨立立案**，在上線後三個月內完成；
在那之前以 S3／S4 的批次合併與資料保留天數控制成長速度。

### 給下一輪的建議做法

1. **先做一次「造資料壓測」**：產生 2000 台 × 90 天的假紀錄與 5000 筆案件，
   跑一次儀表板／報表／統一標記／夜間批次，**用數字取代本節的推算**。
   這是驗證 S1／S2／S6 的唯一方法，也是第零節列的最大盲區。
2. **S1／S3／S4 可以在壓測前先修**——它們是讀碼就能確認的結構問題，不需要等數據。
3. **X2／X3 併入下一輪回饋討論**——需要設計決策（矩陣要不要改成以部門為主的清單）。

## 十、規劃提案：首頁與報表改以「問題的重要性」呈現，而不是數量

> 這一節是**設計提案**，不是體檢發現。起因是 X7／X1：
> 在 2000 台環境下用「數量」排序會讓**最普遍的**壓過**最重要的**，
> 首頁與報表因此失去「今天該先看哪一個」的能力。

### 10.1 為什麼數量排序一定會失效（先看實例）

以 2000 台環境的兩個真實問題對比（數字為典型量級）：

| 問題 | 主機數 | 出現天數 | 總次數 | 嚴重度 | 目前排序位置 | 實際該有的位置 |
|---|---|---|---|---|---|---|
| `DCOM 10016` | 1,900 | 90/90 天 | 380,000 | 低 | **恆在第 1** | 應該完全不出現（已知雜訊、每天都有、沒人要處理） |
| `Service Control Manager 7000` | 600 | 85/90 天 | 12,000 | 中 | 第 2~3 | 背景值，只在「異常增加」時才需要看 |
| `disk 153` | 3 | 2/90 天（**都在近 3 天**） | 4 | 高＋**重大** | 排在很後面 | **應該第 1**——硬碟故障前兆，且是新出現 |

三個維度同時在說話，但目前只有「數量」被聽見：

- **`disk 153` 的重要性來自「嚴重度 × 新出現 × 仍在發生」**，它的數量永遠贏不了 DCOM。
- **`DCOM 10016` 的數量永遠最大**，但它的資訊量是零——**每天都一樣**的東西不構成「今天的重點」。
- 現行的儀表板「重點問題 Top 5」與報表「問題排行」**都只排數量**（最高嚴重度→主機數→總次數），
  所以 2000 台環境下這兩張榜會**長期固定不動**，使用者看幾天就不再看了。

> **附帶指出本輪的一個設計失誤**：`RecordStatsBuilder.BuildIssueRanking`（本輪 §8 新增）
> **完全不看處理狀態**——我在 DTO 註解裡把這寫成「刻意不含處理狀態」，理由是
> 「排行卡回答哪個問題影響最大」。從 2000 台視角回頭看，這個「刻意」是錯的：
> 一個已經被全站標成「已知雜訊」的問題會**永遠霸佔首頁 Top 5 且無法移除**。

### 10.2 提案 A：重要性拆成四個維度，**不合成單一分數**

專案既有的哲學是「可解釋、不黑箱」——風險等級有 `RiskBasisText` 解釋為什麼是這個等級，
AI 產出一律標註來源。**問題重要性也必須遵守同一條**：不要做一個「重要性 87 分」的排序，
使用者無從判斷該不該相信它。改為四個各自可見、可排序、可篩選的維度：

| 維度 | 現況 | 缺什麼 |
|---|---|---|
| **1. 嚴重度** | ✅ 已有（規則定義的 High/Medium/Low ＋ `ElevatesDayRisk` 重大旗標） | 重大旗標沒有出現在排行清單上（只在詳情頁） |
| **2. 影響廣度** | ⚠️ 有主機數，但**沒有影響率** | 「600 台」在 2000 台環境是 30%、在 50 台環境是全滅——**絕對值無法跨環境解讀**，需要 `主機數 ÷ 可見主機總數` |
| **3. 時間形狀** | ❌ **完全沒有** | 見 10.3——這是目前最大的缺口，也是「今天有什麼不一樣」的唯一來源 |
| **4. 處理狀態** | ⚠️ 依問題視角有，**首頁與報表排行沒有** | 已有結論的問題應退出重點清單（見 10.6） |

### 10.3 提案 B：補上「時間形狀」——五個從既有資料就算得出來的訊號

這些**不需要新的儲存**，全部可由既有的 `DailyAnalysisRecord` ＋ `TopIssues` 推導：

| 訊號 | 定義 | 回答的問題 | 呈現建議 |
|---|---|---|---|
| **涵蓋日期範圍** | 首見 ~ 最近出現 | 這是老問題還是新問題？ | 清單欄位「2026-08-03 ~ 08-05」 |
| **出現密度** | 出現天數 ÷ 期間天數 | 天天都有（背景值）還是零星爆發？ | 「2/90 天」＋密度條 |
| **新出現** | 前一個等長期間的次數為 0 | **今天有什麼不一樣**？ | 醒目徽章「新」 |
| **變化幅度** | 本期 vs 前期的主機數／次數增減 % | 在惡化還是在收斂？ | ↑82%／↓30%（比照 KPI 卡既有做法） |
| **是否仍在發生** | 最近一次出現距今天數 | 還要不要處理？還是已經自己好了？ | 「今天／3 天前／已 21 天未再出現」 |

**為什麼「仍在發生」特別重要**：目前的排行把「90 天前爆發過、之後再也沒出現」與
「今天正在發生」視為同等——前者其實應該自動退場。

### 10.4 提案 C：首頁不要放「一張榜」，放**三個不同的問句**

一張排行榜只能回答一個問題。2000 台環境的維運人員每天早上實際要問的是三件事，
建議把首頁的「重點問題」卡改成三塊（或一塊三分頁）：

```
┌─ 今天有什麼不一樣 ─────────┬─ 什麼最急 ──────────────┬─ 什麼影響最廣 ──────────┐
│ 新出現／異常增加的問題      │ 高嚴重度＋未處理＋仍在發生 │ 影響率最高且尚無人處理   │
│ 排序：變化幅度              │ 排序：嚴重度→未處理主機數  │ 排序：影響率             │
│ （沒有新東西時明說「無」）  │ （這是「今天要動手的」）   │ （這是「該不該立規則」）  │
└──────────────────┴─────────────────┴────────────────┘
```

- **第一塊回答「變化」**——解決 X7「每天看到同樣 5 筆」的問題。
- **第二塊回答「行動」**——直接連到依問題視角的指派／統一標記。
- **第三塊回答「治本」**——影響率高又沒人處理的，通常該調規則或設抑制，
  這正好接上既有的「誤報 → 規則維護」動線。
- **三塊都空的時候要明說**（沿用既有「今日無風險訊號」的誠實原則），
  不要顯示空表格。

### 10.5 提案 D：每一列加「時間形狀」的視覺（sparkline）

清單只有數字時，「2/90 天」與「90/90 天」要靠讀字才分得出來。建議每列右側加一條
**近 14 天的迷你折線**（主機數或次數）：

- 一眼分辨：**持續**（平線）／**爆發**（尖峰）／**惡化**（上升）／**消退**（下降）
- 圖表準則（ui-ux-pro-max chart domain）：折線圖需要 **≥4 個資料點**才有意義 → 14 天足夠；
  無障礙等級 AA，且**必須有可切換的資料表**——專案的圖表工具列已經有「表格」切換的既有模式，沿用即可。
- 成本考量：sparkline 的資料是「逐日計數」，若對每個問題各查一次會踩到 S6。
  建議在既有的「一次撈回期間紀錄」流程中順便累加（見 10.7）。

### 10.6 提案 E：重點清單必須排除「已經有結論」的問題

- **規則**：某問題在**全部**受影響主機上都已被標成結案類（含已知雜訊、不處理、誤報）時，
  不進首頁重點清單；部分處理的則顯示「N 台未處理／M 台已處理」。
- **理由**：這正是把 `DCOM 10016` 從第 1 名移除的機制——它不是靠調權重，
  而是靠「有人已經對它下過結論」這個事實。
- **與既有機制的銜接**：`by-issue` 視角已經有 `GroupStatus` 三態（open／in_progress／resolved），
  排行只要沿用同一份推導即可，不必新增規則。
- **必須保留「看全部」的出口**：排除掉的要在卡片底部說明
  「另有 N 個問題已有結論（未列入）」並可一鍵展開——
  同「另有 18 項因嚴重度篩選未顯示」的既有誠實做法。

### 10.7 提案 F：報表加一張「影響 × 嚴重度」氣泡圖（取代／並列於問題排行）

問題排行的長條圖只能表達一個維度。2000 台環境的問題種類上千時，
**散佈／氣泡圖**才看得出群落與離群值：

| 視覺通道 | 對應維度 | 備註 |
|---|---|---|
| X 軸 | 影響率（主機數 ÷ 可見主機總數） | 用比率而非絕對數，跨期間可比 |
| Y 軸 | 嚴重度（High/Medium/Low ＋ 重大旗標加權） | 離散值需加抖動避免重疊 |
| 氣泡大小 | 期間總次數 | 準則：size 對應第三變數 |
| **形狀** | 處理狀態（未處理／處理中／已有結論） | **不可只用顏色**——準則明列色盲需要 shape 區分 |
| 顏色 | 時間形狀（新出現／惡化／持平／消退） | 需附圖例與數值 |

自然浮現的四象限，剛好對應四種處置：

```
嚴重度
  高 │  ① 個案深入        ②【最優先】廣且嚴重
     │   （少數主機、高嚴重）  （立刻指派／統一標記）
     │
  低 │  ④ 忽略             ③ 雜訊候選
     │                      （該調規則或設抑制）
     └──────────────────────→ 影響率
```

**必要條件**（依圖表準則）：
- 資料量 <500 點用 SVG、500~5000 用 Canvas 且 opacity 0.6~0.8、>5000 需先聚合——
  問題種類上千時要走 Canvas。
- **必須提供資料表替代**（無障礙等級 B）——沿用既有「表格」切換鈕。
- 點擊氣泡下鑽到依問題視角（帶 source＋eventId），與既有下鑽規則一致。

### 10.8 資料面需要補什麼（不需要新的儲存）

`IssueRankingDto`（本輪新增）需要擴充，全部可由既有資料推導：

| 新欄位 | 來源 | 用途 |
|---|---|---|
| `FirstSeen` | 期間內該問題最早的紀錄日期 | 涵蓋範圍、新出現判定 |
| `ActiveDays` / `PeriodDays` | 相異出現日數 ÷ 期間天數 | 出現密度 |
| `HostRatio` | `HostCount ÷ 可見主機總數` | 影響率（分母與儀表板 `TotalHosts` 同源） |
| `PreviousHostCount` / `PreviousTotalCount` | 前一個等長期間同一問題的聚合 | 變化幅度、新出現（前期為 0） |
| `DaysSinceLastSeen` | 今天 − `LastSeen` | 是否仍在發生 |
| `OpenHostCount` / `ResolvedHostCount` | 沿用 by-issue 的 `GroupStatus` 推導 | 排除已有結論、顯示處理概況 |
| `DailyCounts[]` | 逐日計數（近 14 天） | sparkline |
| `ElevatesDayRisk` | 期間內是否曾命中重大旗標 | 嚴重度加權、清單徽章 |

**效能前提（與 §7 直接相關）**：這些欄位若各自去查一次資料，會把 S6（全量載入聚合）
的成本再乘上好幾倍。正確做法是**在既有的單次期間查詢裡一併累加**——
`RecordStatsBuilder.BuildIssueRanking` 已經在遍歷所有紀錄的 `TopIssues`，
上述除了「前期對比」與「處理狀態」以外全部可以在同一趟迴圈算完；
前期對比則沿用報表既有的「查前一個等長期間」流程（報表已經在做，儀表板需比照）。
**建議與 S6 的 SQL 端聚合改造一起做**，不要先加欄位再回頭優化。

### 10.9 建議的落地順序

| 階段 | 內容 | 成本 | 立即效益 |
|---|---|---|---|
| **一** | 重點清單**排除已有結論**（10.6）＋加「涵蓋範圍」「出現密度」欄（10.3 前兩項） | 小 | 直接解決「DCOM 永遠第一」與「看不出新舊」 |
| **二** | 加「新出現」徽章與「變化幅度」（需前期對比，儀表板比照報表既有做法） | 中 | 首頁開始回答「今天有什麼不一樣」 |
| **三** | 首頁改三塊問句式卡片（10.4）＋ sparkline（10.5） | 中 | 三種每日決策各有出口 |
| **四** | 報表氣泡圖（10.7），與 S6 的聚合改造一起做 | 大 | 上千種問題時看得出群落與離群 |

**先做階段一**——它是唯一「不需要新資料、不需要新圖表、卻能立刻讓首頁有用」的一步；
其餘階段建議併入下一輪回饋，與 X1（問題數收斂）、X7 一起討論，
因為它們其實是同一個題目的不同切面：**在 2000 台環境裡，把注意力放對地方。**
