## 一、確定的缺陷（本輪引入）

### D1【最高】使用者詳細頁的 H4 修復**完全沒有生效**

- **實測**（以 `svc-lfadmin` 開 `/admin/users/5`）：KPI 仍顯示「處理中案件 **0**」，
  而不是規劃中設計的「—」＋說明；「處理中項目」區塊也仍是空表格，不是說明卡。
- **成因**：`user-detail.js` 的判斷寫成

  ```js
  function viewerHasNoBusinessScope() {
      return getCurrentUser()?.isServerAdmin === true;
  }
  ```

  但 `getCurrentUser()` 是 **`async`**（`core/api.js:87`），回傳的是 Promise。
  `Promise.isServerAdmin` 是 `undefined`，`undefined === true` **恆為 false**——
  這個函式永遠回 false，兩個分支都走不到。
- **影響**：H4 的核心情境（serverAdmin，正式部署第一天唯一能登入的帳號）
  看到的畫面與改版前**完全一樣**：上方「0」、下方歷程列出 2 筆處理中。
- **僅部分有效**：「以下項目以您的可見範圍顯示，可能不完整」那行說明**有**渲染，
  所以畫面至少不再毫無提示——但「0 vs —」這個關鍵區別沒有做到。
- **全站掃描結果**：`getCurrentUser()` 的其他 4 個呼叫點都在 `Promise.all(...)` 內、
  都有 await，**只有這一處**是錯的。

### D2【高】問題排行的「分類」欄變成空白

- **實測**：`GET api/dashboard/summary` 與 `GET api/reports/summary` 的問題排行，
  每一列 `category` 都是 `""`。儀表板重點問題卡與報表問題排行表的「分類」欄因此空白。
- **成因**：P4 把排行改走 `IssueRankingBuilder`，其中

  ```csharp
  Category = string.Empty,   // 由呼叫端自紀錄補（聚合表只存過濾用的 category 字串）
  ```

  註解說「由呼叫端補」，但**沒有任何呼叫端補**。
- **可修性**：`lf_top_issues` 本來就有 `category` 欄，`EfIssueAggregateQuery` 只要
  一併 `GROUP BY`／取眾數即可，不需要新欄位或回填。

### D3【高】並發衝突會回 500 而不是 409

- **規劃寫的**（§8.1 缺陷 3、P3 commit）：「衝突時回 409 並讓前端提示『這筆已被他人變更，請重新整理』」。
- **實際**：三張新表確實設了 `IsConcurrencyToken`，衝突會被資料庫偵測到並拋
  `DbUpdateConcurrencyException`；但**沒有任何地方攔它**——
  `ApiExceptionFilter` 只認 `DomainException`，其餘一律走「未預期例外」的 500 分支。
- **影響**：兩個人同時標記同一個問題時，後手看到的是一個沒有上下文的伺服器錯誤，
  不是可理解的「請重新整理」。體檢 §0 把併發衝突列為未驗證項目——
  現在偵測得到了，但**呈現是錯的**。
- **附帶**：`ApiErrorCodes.Conflict` → 409 的對應在 `ApiExceptionFilter:56` 已經存在，
  只差把 `DbUpdateConcurrencyException` 轉成 `DomainException.Conflict(...)`。

### D4【中】依問題視角的 CSV 匯出與畫面欄位不一致

- **實測**：畫面已有「涵蓋範圍」「出現密度」兩欄，但 `csvHeader()` 的 `issue` 分支仍是
  `['來源','Event ID','分類','嚴重度','主機數','風險日數','總次數','最近出現','處理概況','處理人']`
  ——沒有新欄位，且仍列著畫面上已經拿掉的「風險日數」。
- **影響**：「複製為 CSV」是公司管理者最可能真正使用的輸出方式之一（體檢 §0 已列為未驗證區域），
  複製出來的內容與螢幕上看到的對不起來。

### D5【中】歷程續號的健壯性比改版前差

- **改版前**：`_lastLogId = ReadAllLogs().LastOrDefault()?.LogId ?? 0`——整份讀（慢，這是 N4 要修的），
  但**壞掉的行會被 `JsonLogParser` 跳過**，仍能找到最後一筆有效的 LogId。
- **改版後**：只讀最後一行（快，N4 已解決）。但若**那一行剛好損毀**，
  `ReadLastLogId()` 回 0，續號從 1 重新開始 → 與既有歷程 **LogId 重號**，
  同一天的歷程排序（`ThenBy(l => l.LogId)`）會錯亂。
- **發生機率低**（要剛好最後一行壞），但退化方向不對：應該往回多讀幾行直到解析成功。

## 二、本輪造成的畫面不一致

### D6【高】報表選「未處理」時，KPI 與主機排行歸零，問題排行仍顯示全部

- **實測**（`from=2026-05-01&to=2026-08-06`）：

  | `handlingScope` | KPI 問題總數 | 主機排行 | **問題排行** |
  |---|---|---|---|
  | `all` | 605 | 1 台 | 55 種 |
  | `open` | **0** | **0 台** | **55 種** |

- **成因**：P4 把問題排行改走 `IssueRankingBuilder`，它直接查 `lf_top_issues`，
  **不吃 `FilterByScope` 的結果**。我在 commit 裡把這寫成「刻意的設計決策」，
  理由是「scope 是日層級過濾，問題聚合是跨日投影，套上去會答非所問」。
- **回看後的判斷：理由在抽象層次成立，但結論錯了。** 報表頁只有**一個** scope 選擇器在最上方，
  使用者的心智模型是「這個選擇器管整頁」。現在同一屏上「未處理的問題：0」與
  「問題排行：55 種」並列——**這正是體檢 H4 那一類「畫面說謊」**，而且是本輪自己造成的。
- **兩個可行方向**（需要決定，不是純技術問題）：
  1. 問題排行也套 scope——需要把處理狀態 join 進聚合（§10.6 的前提本來就要做這件事）；
  2. 維持不套，但**畫面必須說出來**：問題排行卡加一行「此排行不受上方『顯示範圍』影響，
     一律呈現期間內全部問題」。成本極小，且符合本專案「誠實申報」的既有原則。

### D7【中】側欄未結案徽章會對「動不了的人」顯示工作量

- **實測**：`mgr-wang`（只有 `ViewAll`，**沒有 `Handle`**）的側欄顯示徽章「1」。
- **這不是徽章的錯**——它忠實反映「他名下有 1 件進行中案件」，而那是體檢 **H1**
  （可以把問題指派給沒有處理能力的人，且完全沒有警告）造成的，H1 本輪**未修**。
- **但 M7 把 H1 的後果放大了**：改版前 manager 不點進去就不會知道；
  現在每一頁的側欄都提醒他「你有 1 件工作」，而他點進去之後**什麼都做不了**
  （H2 已修，按鈕不再出現——所以他看到的是一個沒有任何操作的清單）。
- **建議**：H1 與 M7 應該一起處理，否則等於把一個既有缺口變成每天都看得到的困惑。

### D8【低】報表 `handlingScope` 下，問題排行的「其他 N 個」彙總同樣不受影響

D6 的附帶效應：`IssueOthers`（其他 45 個問題）也一律以全量計算，與 KPI 不同基準。
處置隨 D6 一併決定即可。

## 三、與規劃不符 / 未落實

### G1【最高】blob 遷移仍在**啟動路徑**上——正是 §8.2 E3 要避免的事

- 規劃 §8.2 E3 明確指出：「回填一律背景執行，掛在啟動路徑上大 DB 會讓
  Windows 服務啟動逾時（預設 30 秒）」。P4 的 `TopIssueBackfiller` **有**照做（背景服務）。
- 但 **P3 的 `HandlingBlobMigrator` 是同步跑在 `StorageBackend` 建構式裡的**，
  而它處理的資料量比回填**更大**：
  - 它要把整份 `issue_handling` blob 讀成字串、反序列化、再逐列 INSERT；
  - 需要遷移的環境正是「blob 已經很大」的環境——2000 台約 108 萬列／350 MB；
  - 這一步既慢（分鐘級）又佔記憶體（近 GB），**而且正是我們要逃離的那個 OOM 路徑**。
- **本機實測沒抓到**：開發資料庫只有 56 列，0.3 秒完成，完全看不出問題。
- **建議**：遷移比照回填改為背景執行＋進度可查，且在遷移完成前
  **明確擋住處理狀態的寫入**（或以「資料搬移中」的唯讀模式呈現），
  不能讓使用者在搬到一半時寫入新表而造成新舊兩份資料並存。

### G2【高】「統計中」的畫面標示完全沒做

- 規劃 P4 與 `EfIssueAggregateQuery` 的註解都寫明：
  「回填未完成期間數字會偏低，由呼叫端誠實標示『統計中』」。
- **實際**：`/api/health/detail` 有 `backfillInProgress`／`backfillDone`／`backfillTotal`
  三個欄位，但**前端沒有任何地方讀它**（全站 grep 零命中）。
- **影響**：升級後回填完成前，儀表板與報表的問題排行數字**偏低但看起來完全正常**——
  這正是本專案最忌諱的「靜默給錯數字」，而且規劃自己寫了要防它。

### G3【中】`IssueRankingBuilder` 沒有單元測試

- P4 為 `IIssueAggregateQuery` 補了 9 條測試（聚合語意、授權語意、相異簽章），
  但**組出 DTO 的那一層沒有任何測試**——而 D2（Category 空白）與變化幅度／
  `IsNew`／`HostRatio` 的計算全在這一層。
- 一條「前期有資料 → `IsNew=false` 且 `PreviousHostCount` 正確」的測試就能擋下 D2 同類問題。

### G4【中】`handling_log` 從來不會被清理

- `AnalysisOrchestrator` 的清理段涵蓋 `lf_daily_records`／`batch_runs`／`import_logs`／
  `audit`／`lf_risky_events`／export 報告檔，**沒有 `handling_log`**。
- **這是既有缺口**（體檢也沒抓到），但本輪讓它更重要：
  P3 的 `GetLogs` 改成「以插入時間在 SQL 端窄化候選集」，
  這個最佳化的效果**隨表成長而遞減**——而這張表永遠不會縮小。
- 6000 台環境下 `handling_log` 是千萬列級且無上限成長。

## 四、既有問題被本輪放大

### W1【高】M2（1024px 動作欄看不到）明顯惡化

- **體檢原始量測**：依問題視角表格內容寬 1307px、可視寬 705px（溢出 **602px**）。
- **本輪實測**（同樣 1024×768）：欄數 10 → **11**，內容寬 **1512px**、可視寬 709px，
  溢出 **803px**——比體檢當時多了 200px。
- 「處理概況／處理人／動作（指派・統一標記・回覆處理狀態）」離畫面右緣更遠，
  而**捲動提示仍然沒有**（M2 未修）。
- **這是取捨的直接後果**：P5 為了回答「期間跨度」與「出現密度」加了兩欄，
  資訊密度提高了，但在最常見的遠端桌面解析度上更難用。
- **建議**：M2 從「第 3 批：需要設計決策」提前處理。最小成本作法是捲動容器加漸層陰影
  ＋「← 可左右捲動」提示；較完整的是窄視窗把動作欄改為列末固定（sticky last column）。

### W2【中】M3（手機篩選列佔 80% 畫面）未改善，表格更寬

- **實測**（375×812）：`.lf-toolbar` 高 **656px**（體檢當時 655px，未惡化），

- 頁面本身**無水平溢出**（✅ 維持正確），密度條在窄畫面仍佔 45px。

## 六、上帝視角：這批改動對整體的影響

### 6.1 沒有被破壞的邊界（確認過，可放心）

- **批次分析邏輯零修改**：P4 的新欄位在 `EfAnalysisRecordStore.Append` 寫入時填好，
  分析層看不到 `lf_top_issues`。`AnalysisOrchestrator` 只改了 store 的建構方式。
- **`IssueCaseCoordinator` 只有一個產品建構點**（`AnalysisOrchestrator`）＋DI，
  已全部指向新 store——不會出現「批次寫 blob、Web 讀真表」的分裂。
- **三層授權未動**：P1 只改「怎麼算得快」，`VisibilityService` 的規則一條沒改；
  四種角色實測的可見範圍與能力都與體檢當時一致。
- **NetIQ／Linux／AI 三條線未受影響**：都不經過本輪改動的路徑。

### 6.2 真正的系統級疏漏（規劃與角色動線都看不到）

**S-1：升級路徑整體沒有被當成一件事設計。**
P3 的遷移、P4 的 schema 升級與回填，三者各自都「冪等、可重跑」，
但**沒有人負責它們之間的順序與整體狀態**：
- 遷移在啟動路徑（同步、可能數分鐘），回填在背景（非同步）；
- 遷移進行中若使用者已經能操作 Web，寫入會進新表，而遷移仍在搬舊 blob 的資料——
  **兩者對同一鍵的先後順序沒有定義**（`AddRange` 對已存在的唯一鍵會直接違反約束）；
- 目前唯一的保護是「目標表非空即跳過」，但那是**全表**判斷，
  不是「這一列有沒有搬過」。第一次啟動若在遷移中途被中斷（服務逾時被 SCM 砍掉），
  下次啟動會看到「表非空」而**永遠跳過剩下的資料**。
→ 這是本次檢查找到的**最高風險項**：不是效能問題，是**可能靜默遺失資料**。

**S-2：`lf_blobs` 的三個舊 key 永遠留著，但沒有人說它們已經失效。**
遷移刻意不刪 blob（正確），但也沒有標記。日後若有人（或某個舊版本的執行檔）
再度以 blob 路徑寫入，就會產生兩份互不相通的處理狀態。
建議在遷移完成時於 blob 內容或另一個 key 寫下「已遷移至資料表，請勿再寫入」的標記。

**S-3：排程維持在 Web 行程內（本輪決策）的隔離措施尚未實作。**
規劃 §8.4 甲案含三項：orchestrator 獨立連線字串設 `Max Pool Size`、
每台主機之間讓出並限制 NetIQ 並行度、執行中畫面標示。
**目前一項都沒有做。** P3／P4 已讓單台分析的 DB 成本大幅下降，
但 6000 台的夜間分析仍與使用者請求共用同一個 thread pool、GC 堆與連線池。
`/api/health/detail` 已能看出「現在正在分析」（`analysisRunning`），
但那只是觀察，不是隔離。

**S-4：本輪新增了 4 個新的資料表與 1 個背景服務，但沒有納入既有的清理／備份敘事。**
`DB-SPEC` 的「資料量推估」與「清理策略」章節沒有更新——
三張處理狀態表隨主機數×天數成長，卻沒有對應的保留天數設定
（`lf_daily_records` 有 `RetentionDays`，處理狀態沒有）。
問題會在上線後三個月才浮現，與 S2 原本的症狀相同。

## 八、這次檢查本身的限制

1. **仍然只有 1 台主機的真實資料**。四角色動線驗得了「對不對」，驗不了「多不多」——
   D6 那種「55 種問題 vs 0」的矛盾是靠讀數字發現的，不是靠畫面感受。
   規模化的畫面問題（X1 上千種問題、X2 授權矩陣）依然沒有被眼睛看過。
2. **併發完全沒測**。D3 是讀碼推論，不是實測——兩個瀏覽器同時標記同一個問題會發生什麼，
   仍然是體檢 §0 列的未驗證項目。
3. **升級路徑沒有在「大 blob」上實測**。S-1 與 G1 都是推論；
   要證實需要造一份 100 萬列的舊格式 blob 再啟動一次。
4. **沒有實際列印**。P5 新增兩欄之後 `@media print` 的分頁切點沒有看過。
