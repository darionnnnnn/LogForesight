## 批次 D：帳號／來源值折行

### 現況與核對結果

- `keyDetailsBlock`（`record-detail.js:1833`）把「相關帳號／來源 IP」的值以 `lf-text-data` 輸出。
- `components.css:1365`「表格內 `lf-text-data` 不斷行」把它套成 `white-space: nowrap`。值一長就溢出格線欄，壓過「趨勢」「處理狀態」兩欄，也把表格撐出卡片。
- 截圖中的超長值是升級前（1.0.53.2）存下的錯誤擷取結果；現行擷取有邊界處理（`LogAggregator.EnumerateLabelValues`，單值上限 128 字）。但帳號數量多的主機日，正確資料同樣會超寬，所以這是樣式缺陷，不只是舊資料問題。
- `keyDetailsBlock`、`lf-key-details` 只有風險日詳情使用（已 grep 全前端與 View）。該檔其他 `lf-text-data` 只用在日期與計數。
- 超過 300 字的值由共用 `collapsibleText` 收合（`ui.js:1943`）。

### 定案

- 帳號／來源摘要的值一律可折行、可在任意位置斷，超長交給既有收合。
- 寫成不斷行規則的排除項（`:not()` 清單加一項），不事後覆寫。
- 舊資料的錯誤內容不修補；只保證不跑版。
- 同型普查只做「列清單與判定」，本輪只修會溢出的；不順手改其他樣式。

### 改動與驗收

| # | 改動 | 驗收 |
|---|---|---|
| D-1 | UI 資料集補兩筆問題：帳號 40 個的清單、單一 300 字無空白的值 | **測**：資料集產生測試斷言兩筆存在。**量**（改樣式前先跑）：`record.all-kinds` 的溢出量測在這兩筆上非 0，證明資料集抓得到這個缺陷 |
| D-2 | 帳號摘要值排除於不斷行規則，並允許任意斷行 | **量**：`record.all-kinds` 五個寬度六項為 0；`evalAssert` 斷言每列帳號值右緣不超過所在「問題」格右緣、且與同列「趨勢」「處理狀態」兩格的外框不相交。**變**：拿掉排除項，上述斷言轉紅 |
| D-3 | 邊界另一側：表格內短技術值維持不斷行 | **量**：`evalAssert` 斷言問題列的時段、清單頁日期欄高度為單行。**測**：既有設計系統守門照綠 |

## 批次 A：詳情頁滿版

### 現況與核對結果

- 七個頁面設 `ViewData["ContentWidth"] = "bounded"`：RecordDetail、HostDetail、WorkOrderDetail、HandlerDetail、UserDetail、Settings、Setup。
- `_Layout.cshtml:72` 依它加 `lf-content--bounded`；`layout.css:456` 把內容區限制在 `--lf-content-max`（120rem）且靠左。
- 規則出處 DESIGN-SYSTEM §8.4，理由是「避免單欄內容被拉到 2000px 以上」。1920 以下本來就滿版；2560 寬右側約空 370px。
- 五個詳情頁都是整寬卡片加表格，沒有單欄長表單（HostDetail 的表單在 modal 內）。成段文字另受 `--lf-measure: 40em` 限制。
- 側軌在 ≥ 1600px 已預設展開（`core/side-rail.js`），不需要新行為。
- 測試專案沒有斷言 `bounded` 的既有測試。

### 定案

- 五個詳情頁改滿版；設定、初始設定維持上限。`lf-content--bounded` 與 `--lf-content-max` 保留給這兩頁，不刪。
- 不提高上限（更寬的螢幕會再留白）、不置中（左側有固定導覽列，置中會多一條空帶）。
- 滿版後表格在 4K 會很寬，與清單頁現況一致，不另加欄寬上限。

### 改動與驗收

| # | 改動 | 驗收 |
|---|---|---|
| A-1 | 五個詳情頁的 View 移除 `ContentWidth = "bounded"` | **測**（新增守門）：`bounded` 只出現在 Settings 與 Setup。**變**：加回任一詳情頁轉紅；從 Settings 拿掉也轉紅（兩側都守） |
| A-2 | 五頁在寬螢幕用滿寬度 | **量**：`screens` 矩陣 2560 與 3840 下，`evalAssert` 斷言內容區右緣距視窗右緣等於版面留白（±2px）；設定頁在 2560 下仍受上限（邊界另一側） |
| A-3 | 五頁不因變寬而跑版 | **量**：五頁 `widths` 矩陣六項為 0；另抽 2560 字級「大」、375 字級「大」各一格 |

## 批次 E：來源觀測精簡

### 現況與核對結果

- `sourceEvidenceBlock`（`record-detail.js:1671`）每筆固定四行；主機與資源顯示內部鍵（`host-id:12`），「時間解讀」「原生參照」沒有值時每筆都印「未知」。只有風險日詳情使用。
- 上方摘要行已有「N 筆、N 筆有 UTC 時間、N 筆有原生參照」。
- DESIGN-SYSTEM §8.5 要求佐證層「內容一字不減」。
- 引用這些字串：`FrontendConsistencyUiTests`、`JsBehavior/record-detail-issue-cell.behavior.mjs`、`HelpContent/17-netiq.ai.md`、`docs/NETIQ-API-REFERENCE.md`。

### 定案

- 沒有值的「時間解讀」「原生參照」不逐筆印，由摘要行的計數承擔。任一筆沒有時間解讀時，摘要行加一句「N 筆無時間解讀，不能推定連續狀態」；原警語換位置、不消失，符合「一字不減」的用意。
- 主機鍵等於本頁主機時顯示主機名稱；資源鍵與主機鍵相同時不重複顯示。其他鍵原樣顯示（不猜別台主機的名稱）。
- 有值的行原樣保留。只改顯示，不動後端資料與報告全文。

## 批次 F：執行總表改以資料日為列

### 現況與核對結果

- 總表每列的日期是**執行日** D（`RunMonitorService.cs:124`），但各欄實際口徑不一：
  - NetIQ 主機狀態：讀帳本中資料日 D-1 的最新一筆回執（`NetiqStatus`，`:339`）。之後任何一趟補跑都會更新它，本質上已經是資料日口徑，只是掛在 D 的列上。
  - 本機主機狀態：D 當天開跑的趟；沒有的話看 D-1 的分析紀錄是否存在，存在標「已回補」（`LocalStatus`，`:375`）。
  - PRTG 欄：找逐日統計中日期等於 D 的那筆（`:138`～`:171`），與同列其他欄差一天，「今日」列永遠是「—」。
  - 執行時間：D 當天開跑的趟（`RunDayTimingBuilder`）。
- 所以回補時資料確實是補到「那個資料日」，但畫面把它標成隔天的日期，表頭又只寫「日期」。
- 可用的「哪一趟處理了哪個資料日」連結：NetIQ 回執帶 `RunId`（每個主機日只留最新一筆）；PRTG 逐日統計帶資料日。本機分析沒有這種連結，只有「已回補」狀態。
- `GetDaySummaries` 的消費端只有 `RunsController`（總表）與 `RunExportService`（匯出 `dailyHealth`，說明文字在 `:1439`）。展開列走 `GET /api/runs/day/{date}`（`RunsController.cs:74`），前端傳的是列的日期（`runs.js:322`），目前語意是執行日；前端沒有其他呼叫點。
- 執行詳情的「PRTG 逐日」表表頭也只寫「日期」，內容是資料日（`runs.js:756`）。
- 卡片說明小圖示（`Runs.cshtml:220`）、WEB-SPEC `:2968` 一帶、說明書 10（兩份）都以執行日描述這張表。
- 匯出 `schemaVersion` 沒有程式消費端。
- 今日 PRTG 實際有成功（匯出 `phases.prtg` 22 趟皆成功）。
- 未核對：會不會有「資料日＝執行當天」的紀錄（當天的趟處理當天的資料）。F-6 定義該情況並以測試鎖住，實作第一步先查事實。

### 定案

- **每列是一個資料日**（事件發生的那一天）。表頭寫「資料日」。一般情況下它由隔天凌晨的排程處理；之後補跑也歸在同一列。
- 各欄口徑統一為該資料日：
  - NetIQ、本機主機狀態：判定邏輯不變，只是列的日期改成它們本來就在核對的那一天。
  - PRTG 欄：取該資料日的逐日統計（現行取法，不再與其他欄差一天）。沒有逐日統計的舊紀錄取隔天開跑那一趟的趟次結果；有逐日統計但不含該資料日的趟不套舊規則（原保護不變）。
- **執行時間欄**表頭改「執行日與時間」，內容帶執行日：
  - 第一行是排程處理日（資料日的隔天）當天開跑的趟：「MM-DD HH:mm～HH:mm（耗時，共 N 趟）」，第二行各路耗時不變。
  - 該資料日的 NetIQ 最新回執或 PRTG 結果若來自其他日子開跑的趟，加一行「另於 MM-DD HH:mm 補跑」。多趟時列最新兩趟，其餘寫「等 N 趟」。
  - 補跑趟的耗時不併入第一行：一趟補跑通常同時處理多個資料日，耗時無法歸給單一資料日；要看細節到「執行紀錄」頁籤。
  - 排程處理日沒有任何趟時第一行顯示「—」，補跑行照常顯示。
- 原「今日」列改為日期照寫資料日，並標「今日處理」；還在跑時標「執行中」。出現條件不變（今天有取數趟才出現）。「尚未處理」的寫法與待補摘要留在這一列。
- 展開列的 API `GET /api/runs/day/{date}` 參數語意改為資料日（路由不變，權限快照不受影響）。
- 執行詳情「PRTG 逐日」表表頭改「資料日」。
- 日期換算集中在 `RunMonitorService` 一處；前端不做日期加減，執行日由後端給。
- 欄位名 `isToday` 保留、語意改為「今天處理的那一列」：改名會牽動 DTO、匯出與一批測試，沒有行為上的好處。
- 匯出 `dailyHealth`：`date` 改為資料日並新增執行日欄位，`guide` 文字改寫，`schemaVersion` 升為 2（`date` 本身換了意義，新舊檔案並排比對時要分得出來）。
- 找不到 PRTG 結果時仍顯示「—」，加滑鼠提示「這個資料日沒有 PRTG 處理紀錄」。
- 本條推翻「每列為執行日」與「總表 PRTG 徽章依資料日期、與其他欄不同天」的現行寫法，WEB-SPEC、說明書改寫為現況。
- 不做：把補跑趟的耗時拆分到各資料日、替本機分析補「哪一趟處理了哪天」的連結（沒有既有資料可用，要改執行紀錄的寫入端）。
