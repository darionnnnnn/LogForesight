## 3. 計法

沿用第 81 輪定案的計法，四個流程一致：

- 一步＝一次點擊，或一次輸入（在一個欄位打字或貼上算一次）。捲動、滑過不算。
- 定案要求的確認框與預覽不計入步數，但逐一列在紀錄裡。
- 起點是該角色登入後的落點頁，登入本身不算。
- 選填欄位不填。必填欄位（例如「不處理」的說明）照填並計一步。
- 每個流程走兩次：第一次照最短路徑，第二次確認不是巧合（換一個問題或一台主機）。兩次取大的。

## 4. 資料準備

第 81 輪在 D2 走不出這四個流程，原因是資料過期：D2 是固定的壓縮檔，畫面的期間以真實日期往前算，資料日離今天超過 7 天後，負責人名下就只剩 1 台 1 個問題。所以先重產資料，再確認形狀符合才開始計步。

| 步驟 | 做法 | 通過條件 |
|---|---|---|
| 1 | 以目前的 dev 重跑多日模擬產生新的 D2（2,000 台 × 14 天、產能 40，指令見 `CLAUDE.md` 測試慣例），打包上傳 VM 並部署 dev@21f9c675 的站台 | 站台登入頁回 200 |
| 2 | 以資料庫查詢確認 F10 的形狀：主機負責人帳號名下的主機，近 7 天有 2 個以上未處理問題、合計影響 20 台以上 | 查得到；記下帳號與問題名稱 |
| 3 | 確認 F05 的形狀：某位處理人名下，有一台主機同時在 3 張以上進行中的交辦單裡 | 查得到；記下主機名 |
| 4 | 確認 F16 的形狀：問題查詢有一個中低嚴重度、影響 50 台以上的問題 | 查得到 |
| 5 | 確認 F11 的形狀：儀表板「需要你處理」至少出現 3 類項目 | 畫面看得到 |

模擬資料走不出某個形狀時（例如沒有一台主機同時有 3 張單），改用 D1（UI 資料集加量體 500 台）補那一個流程，並在紀錄註明用了哪一份資料。兩份都走不出來就停下回報，不自行造資料。

## 5. 各流程的走法與達標線

每個流程記錄：每一步的畫面、動作、是否計步；最後的畫面結果（成功訊息與資料是否真的寫入）。

### F10 主機負責人（目標 4 步）
- 起點：負責人登入後的落點頁。
- 預期路徑：到問題查詢 → 問題列「統一標記」 → 選結論 → 套用。兩個問題各做一次，分開計，取大的。
- 另外確認三件事（不計步，只記是否成立）：落點頁有沒有告訴負責人「你負責的主機有未處理問題」；標記結果只落在自己負責的主機；非負責主機列為略過並說明原因。
- 達標：單一問題 4 步內。

### F05 一台主機 3 個問題（目標 3 步、同一頁）
- 起點：處理人已在該主機的詳情頁（找主機的步數另外記，不併入目標）。
- 預期路徑：在「這台的交辦」勾選問題（全選算 1 步）→ 選結論 → 送出。
- 達標：3 步內，且全程不離開主機詳情頁。
- 另記：從落點頁找到這台主機要幾步。

### F16 處理雜訊（目標 5 步）
- 起點：管理員在問題查詢、已看到那個問題的列。
- 做兩條路各一次：靜音、統一標記。各自從問題列算到套用完成。
- 達標：每條路 5 步內；且畫面上的比較表與選單說明足以選出做法——以截圖佐證，並記錄選擇時有沒有需要離開這一頁查說明。

### F11 管理員早上巡檢（目標 1 頁）
- 起點：管理員登入後的儀表板。
- 檢查清單（對照 F11 流程檔的六件事）：昨晚取數結果、有沒有上報、可派未派、派不出去、處理人停用或暫停仍有單、系統健康。每一件記「儀表板上看得到嗎」「到處理點要幾步」。
- 達標：六件事都不必換頁就看得到；每個異常 1 步到處理點。

## 6. 超標時的處置

- 任何流程超標：記下多出來的是哪一步、是不是定案要求的確認框，停下回報，由使用者決定「接受並改寫目標」或「排修正」。
- 走的過程發現功能缺陷（做不到、結果錯、訊息與實際不符）：同樣先回報，不順手修。
- 使用者決定要修時，另寫修正的契約與驗收補進本文件，再實作。

### 走的過程另外看到的三件事

1. **統一標記的結論預設選「已處理」。** 回覆彈窗刻意不預選結論（避免靜默誤回覆），統一標記的下拉卻有預設值，填了原因就能直接套用成已處理。
2. **靜音的原因欄沒有標「必填」。** 實際必填，直接送出才出現「請填寫靜音原因」；統一標記的同一欄有寫「原因（必填）」。
3. **F05 的 4 步。** 要到 3 步，得在勾選後不經按鈕直接出現結論區，屬於版面改動。
