## 現況與核對結果

- `PrtgProbeRunner.RunAsync(PrtgClient, IRunConsole)`（Core，靜態）只拿得到 PRTG 連線；測試呼叫點 **57 處**（`PrtgProbeRunnerTests.cs`）。
  由 `PrtgProbeService.TryStart`（`LogForesight.Web/Services/PrtgProbeService.cs:168`）在背景呼叫，服務目前只注入設定、探測狀態、回填狀態。
- 探測**不檢查 `PrtgEnabled`**（PRTG-SPEC §6）：它要能在啟用前跑。所以鏡像與主機對應**可能是空的**，站台對照必須把這當正常情況處理。
- 取數範圍的唯一出口 `PrtgScopeDevices.Compute(store, hostStore, guardSource, settings, sentinels, console, resolver)` 已存在；
  守門判定的唯一一份 `PrtgResourceGuardTargets.Resolve(source, …, ignoreOverride)`，來源有鏡像（`PrtgMirrorGuardSource`）與直接查 PRTG（`PrtgLiveGuardSource`，單發 `count=50000` 取 devices 與 sensors 各一次）。
- 9d-5 的樣本裝置是從全站感測器清單挑的（底下有非 Up 感測器者優先），**不一定是取數範圍內的裝置**——
  它驗的是「這台 PRTG 的 `id=<裝置>` 查詢成不成立」，答不了「我的主機那幾台查起來多久、有沒有訊息」。
- 第一趟同步會清掉多少感測器，目前只能等同步跑完看執行輸出；守門找不找得到 PRTG 主機，只能到設定頁按預覽。

## 批次A：站台對照——取數範圍試算

### 定案

1. **不改 `PrtgProbeRunner.RunAsync` 的簽章**。站台對照寫成 Core 的另一個靜態入口（暫名 `PrtgProbeSiteCheck.RunAsync`），
   由 `PrtgProbeService` 在 `RunAsync` 結束後接著呼叫、輸出接在同一份探測輸出後面，自己一個段落標題「══════════ 站台對照 ══════════」。
   - 不選「`RunAsync` 加參數」：57 個測試呼叫點全要跟著改，而環境步驟（只需 PRTG 連線）與站台步驟（需鏡像與主機主檔）本來就是兩種相依。
   - 不選「可選參數」：本專案紅線（漏注入時保護靜默消失）。
   - 環境探測失敗（連線或認證）時不跑站台對照。站台對照自己失敗只印原因，**不改變探測的成功／失敗結果**。
2. **取數範圍試算**（純讀本機資料，不打 PRTG）：
   - 以 `PrtgScopeDevices.Compute`（鏡像來源，即夜間同步實際會用的那份）算範圍，印
     `範圍 N 台（對應 a、衝突 b、人工 c、守門 d）`。
   - 印鏡像現況：裝置 D 台、感測器 M 顆、其中範圍外 K 顆——`K > 0` 時加一句「下次結構同步成功後會清除」。
   - 鏡像沒有任何裝置：印「鏡像尚未同步，無法試算；請先執行『同步結構與對應』」並略過本批其餘輸出（B 照跑，它不靠鏡像）。
   - 範圍為 0 台：印原因指路（尚無主機對應），略過實測。
   - `對應 = 0` 但範圍非空：提示「下次同步不會清除感測器鏡像」（第 48 輪的保護），避免管理者以為清除壞了。
3. **範圍內裝置實測**（打 PRTG，唯讀）：從範圍內挑最多 3 台（鏡像中底下有非 Up 感測器者優先，其次 objid 小到大；挑法與 9d-5 同一個函式，不另寫一份——
   把 `PrtgProbeRunner` 的挑樣本邏輯改成可被兩邊呼叫，或本段直接重用其輸入型別，執行端擇一並說明）。每台：
   - `content=sensors&id=<裝置>`：耗時、回傳顆數，對照鏡像中該裝置的顆數（不同只印差異，不判錯——鏡像可能是舊的）；
   - `content=messages&id=<裝置>&filter_drel=7days&count=50`：耗時、列數、是否含下層感測器訊息（判定文字與 9d-5 (b) 相同，**共用同一個判定函式**）。
   - 結論兩行：「範圍內裝置逐台查詢 ✓／✗／無法判定」；以平均每台耗時 × N ÷ `PrtgFetchConcurrency` 估
     「感測器階段約 x 秒、狀態變更階段約 y 秒（回望 7 天級距；30 天級距的資料量更大，實際會更久）」。
   - 成本：最多 6 次 `table.json`，寫進段落開頭的成本說明行。
4. **互斥與取消**：沿用探測既有的互斥（探測執行中其他 PRTG 作業不啟動）；站台對照在同一個背景工作內，不另開狀態。

### 改動

1. 新增 Core `PrtgProbeSiteCheck`（暫名）＋測試檔。
2. `PrtgProbeRunner`：挑樣本與 (b) 判定兩個函式開放給同組件共用（internal），行為不變。
3. `PrtgProbeService`：建構子新增**必填**相依（`StorageBackend`、`IHostStore`、`ISentinelStore`），`RunAsync` 成功後呼叫站台對照。
   DI 為自動解析，三者皆已註冊；測試的建構點（2 處）跟進。

### 測試／驗收

- 範圍試算：種 ok／unmatched 裝置與感測器 → 輸出的 N、四項組成、M、K 為精確數字（突變：K 改算全部感測器 → 紅）。
- 鏡像空、範圍空、對應 0 三個分支各一條，且都**不發任何 PRTG 請求**。
- 實測：替身對範圍內裝置回下層感測器訊息 → 結論 ✓ 且估算行的數字＝平均耗時 × 台數 ÷ 併發（以注入的時鐘或只斷言格式，執行端擇一並說明）；回裝置自身 → ✗。
- 請求只打範圍內的裝置 id（替身記錄 URL，比對 `id=` 整段，避免 `id=1` 誤中 `id=10`）。
- 環境探測回 false 時站台對照不執行；站台對照擲例外時探測結果仍為成功且輸出含原因。
- `PrtgProbeRunnerTests` 既有 57 處呼叫與斷言零改動；全套綠。

## 批次B：站台對照——守門目標偵測

### 定案

1. 以**直接查 PRTG** 的來源（`PrtgLiveGuardSource`）跑一次 `PrtgResourceGuardTargets.Resolve(..., ignoreOverride: true)`——判定邏輯不複製。
   成本：devices 與 sensors 各一次單發 `count=50000`（實機感測器那次約 50 秒），寫進成本說明行。
   - 不重用環境探測步驟 3／6 已抓的清單：那要改 `RunAsync` 的回傳型別並讓兩份資料形狀對齊，省一次查詢不值得多一條耦合。（暫定；執行端若發現重用很便宜可提出。）
2. 輸出：
   - Sentinel 與 PRTG 主機各自命中的裝置（名稱與 objid）、各分類感測器數（cpu／memory／corehealth）；
   - PRTG 主機是**位址命中**還是走 **corehealth fallback**（`Resolve` 目前不回傳這個區別——從它的輸出警告判讀不可靠，
     需要讓抽出的守門裝置偵測（第 48 輪的 `DetectGuardDevices`）多回一個旗標；只加欄位、不改判定）；
   - **對照取數範圍**：命中的裝置逐台標「在範圍內／不在」。不在＝夜間讀鏡像會偵測不到 → 印處置：
     「到設定頁『自動偵測並填入』存入覆寫清單，快照服務下一輪會把這些感測器補進鏡像」。
   - 覆寫清單有值時另印：清單中有幾顆已在鏡像、幾顆不在（不在的會由範圍補抓處理）。
3. 守門未啟用也照跑（探測的用途就是啟用前先看）；沒有設定任何 Sentinel 且 PRTG 位址解析不出 host 時印一行說明並略過。
4. 即時來源回應被截斷（少於 treesize）時沿用它既有的警告，並在結論標「結果可能不完整」。

### 測試／驗收

- 位址命中、fallback 命中、都沒命中三種各一條，輸出文字可分辨（突變：旗標恆為位址命中 → fallback 那條紅）。
- 命中裝置不在範圍 → 輸出含處置文字；在範圍 → 不含。
- 覆寫清單的「在鏡像／不在鏡像」計數精確。
- `PrtgResourceGuardTargetsTests` 既有斷言零改動。

## 明確不做（本輪定案）

- **探測結果落地／歷史比較**：維持只存記憶體（PRTG-SPEC §6 現行設計）。
- **把「主機清單未回報提示」放進探測**：它是畫面行為，探測只能印同一份資料的另一種呈現，沒有新資訊。
- **依探測結果自動切換逐裝置／逐感測器取法**：取法是程式常數（`StateChangeQueryObjects`），探測只回報、不改行為。
- **站台對照獨立成另一顆按鈕**：同一次探測一次看完；成本（多約一分鐘）寫在輸出開頭。

## 使用者定案

- 守門目標偵測照做（多付約 50 秒的全站查詢）：探測越完整，後續越知道怎麼處理。
- 站台對照放在探測輸出的最後，不改 `RunAsync` 簽章。

## 規劃完成後複檢

- **與既有設計衝突**：探測「只需位址與認證、啟用前可跑」（PRTG-SPEC §6）——站台對照多了對鏡像與主機主檔的相依，但兩者為空時只印說明，不破壞這條；
  探測「結果不影響其他功能」——站台對照唯讀、不寫任何表（`Compute` 與 `Resolve` 皆無副作用，已核對）。
- **批次間**：B 用 A 算好的範圍，不重算。
- **四個坑**：什麼算一個——K 的分母是鏡像全部感測器、分子是 `DeviceObjid` 不在範圍者；分母為零（鏡像空）已寫分支。破壞性操作——無。單向閘門——無。移除類——無。
- **待驗證的技術事實**：`PrtgLiveGuardSource` 在探測的背景工作內使用是否有執行緒／取消上的限制（它原本跑在請求執行緒上）——執行端先讀再用，有問題回報。
- 複檢完成，無其他新增事項。
