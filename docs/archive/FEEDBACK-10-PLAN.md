## §1 側欄品牌（圖示／名稱／文字）可自訂＋預設文字去「Windows」

### 現況

- `_Layout.cshtml:22-30` 寫死：speedometer2 圖示＋「LogForesight」＋`<small>Windows 事件日誌預警</small>`。
- `Login.cshtml:18` 另有一句寫死的「Windows 事件日誌預警系統」。
- 系統已支援 Linux 主機（docs/LINUX-RULES.md），「Windows」字樣名不符實。

### 方案

1. **`SystemSettings` 新增三欄**（遵守「新增設定必須有消費端」紅線，消費端見第 3 點）：
   - `BrandName`（預設 `LogForesight`）
   - `BrandSubtitle`（預設 **`事件日誌預警`**——即使使用者從不自訂，預設值也要把「Windows」拿掉）
   - `BrandIconDataUri`（預設空字串＝沿用內建 speedometer2 圖示）
2. **設定頁新增「外觀」區塊**（放「層級與顯示」分頁內，或獨立分頁——傾向放「層級與顯示」
   分頁頂端，避免分頁數量再膨脹）：名稱、副標文字框＋圖示上傳。
   - 圖示上傳限 **PNG／JPG**、上限 **64KB**（側欄顯示尺寸僅約 36px，64KB 綽綽有餘；
     SystemSettings 是整包 blob，塞大圖會拖慢每次設定讀寫）。前端讀檔轉 data URI 送出，
     後端驗證前綴（`data:image/png;base64,`／`data:image/jpeg;base64,`）與解碼後大小。
   - **刻意不收 SVG**：SVG 可內嵌 script，即使以 `<img>` 載入安全，仍不值得為此開驗證面。
   - 提供「還原預設」小按鈕（清空三欄回預設值）。
3. **消費端＝`_Layout.cshtml` 伺服器端渲染**：注入 `ISystemSettingsService` 直接輸出品牌三元素
   （圖示有自訂值時輸出 `<img>`，否則維持現有 `<svg>`）。不走前端 fetch——側欄品牌是每頁第一眼，
   等 API 回來才換會閃動。`ViewData["Title"] - LogForesight` 的 `<title>` 一併改用 `BrandName`。
4. **登入頁一併套用（Q7 已定案：要）**：`Login.cshtml` 的標題與副標同樣伺服器端渲染
   `BrandName`／`BrandSubtitle`（副標原句「Windows 事件日誌預警系統」直接以 `BrandSubtitle`
   取代，不再自行加「系統」字尾——自訂文字該長什麼樣由使用者全權決定）；
   自訂圖示存在時登入卡的 logo 一併替換。

### 影響與測試

`SystemSettings`／`SettingsDtos`／`SystemSettingsService`（驗證）／`Settings.cshtml`／`settings.js`／
`_Layout.cshtml`（改為需要注入的動態殼，仍不含資料查詢）。測試：設定驗證（格式、大小上限）、
預設值、還原。WEB-SPEC §9.9b 補述。

## §4 「系統管理 > 主機」沒有資料時一直顯示載入動畫（Q1 已定案：`/admin/hosts`）

### 現況與探勘結果

`hosts.js` 的 `render()` **有**空狀態分支（「尚無主機」），後端三支 API
（host-groups／users／netiq/overview）對空資料庫的回傳路徑靜態檢查也都安全
（`GetOverview` 空清單、`GetServerNames` 空集合皆不拋例外）——
所以骨架列停住的成因是 `load()` → `search()` 流程中**某一步拋出未被接住**：
全站共通缺口是各頁 `load()`／`init()` 頂層沒有 catch，`renderLoading()` 畫出骨架列後，
中途任何 API 失敗或前端例外（例如空資料下某個 DOM 假設不成立）都會讓骨架列永遠停留
（`api.js` 的錯誤 toast 消失後，留下的就是「一直載入」的觀感）。

### 方案

1. **空 DB 實測重現定位根因**：以全新 Sqlite 資料庫啟動 dev server，開 `/admin/hosts`
   逐步追出實際拋出的那一步（console／Network 雙看），修掉該邏輯洞——這是本項的驗收核心，
   不能只靠通用防護把症狀蓋掉。
2. **`ui.js` 新增 `guardLoad(container, fn)` 共用守則**：包住各頁的載入流程，失敗時
   `renderEmpty(container, { title: '載入失敗', hint: '請重新整理頁面後再試。', icon: 'exclamation-triangle' })`，
   骨架列不再無限停留。
3. **逐頁套用**：`renderLoading`／`renderSpinner` 的全部呼叫點體檢一輪（hosts／dashboard／groups／
   handler-detail／handling-panel／host-detail／imports／netiq／permission-changes／record-detail／
   records／audit／runs），確保每條路徑都有「成功渲染／空狀態／失敗狀態」三收斂之一。

### 測試

`guardLoad` 行為測試（JS 無測試基建——以後端不變、前端手測清單代替，列入體檢腳本）。

## §5 報表仍出現捲軸，無法一屏看完

### 現況

第九輪已做過一頁化（`.lf-chart` 280→230px、主機排行半寬＋三顆占比小圖並列），但同輪 §5 又加了
「顯示範圍」chips 一列（`Reports.cshtml:36-44`），加上頁底「簽章查詢併入問題查詢」的說明段落
（`:136-139`），垂直空間又被吃回去。KPI 卡、卡片 header、`.row` 間距（`g-3`＋`mt-1`）也各有壓縮餘地。

### 方案（Q2 已定案：**隨螢幕自動縮放**，不押定固定解析度）

固定像素高度（第九輪的 230px 一刀）永遠追不上「瀏覽器邊框＋工具列＋左側選單吃掉多少」的
變數——改成**視窗高度驅動的版面**，讓圖表區高度由實際可用空間決定：

1. **版面骨架改 viewport-bounded**：報表主內容改為「高度＝視窗高扣掉 topbar 與期間列」的
   flex／grid 容器（`100dvh` 基準），KPI 列固定內容高、兩列圖表區各分配剩餘高度的固定比例
   （fr 單位）。圖表 wrapper 高度來自容器而非寫死 px——`charts.js` 已是
   `responsive: true` + `maintainAspectRatio: false`（core/charts.js:65-66），canvas 天然跟著
   容器長高縮矮，不需動圖表層。占比小圖三顆在右半直向均分同一份高度。
2. **回收固定高度佔用**：期間列與「顯示範圍」chips 併成同一列（省一列）；頁底「要查同一事件
   簽章…」導引段落收進期間列的 `lf-help` popover（§8.6a 收斂原則的延續）。
3. **可讀性下限**：圖表容器設 `min-height`（暫定 160px／小圖 120px，實測調整）——視窗矮到
   連下限都塞不下時**允許出現捲軸**（極端矮窗下硬塞會讓字小到不可讀，捲動是較誠實的退路）；
   一般桌機（1920×1080 含瀏覽器邊框）與筆電（1536×864）都應在下限之上、一屏呈現。
4. 字級「大」同樣受益（版面隨內容可用高自動讓位）；列印版面（`@media print`）不受影響，
   維持既有卡片不裁切規則；「自訂圖表」關掉部分圖時，留下的圖自動分得更多高度（fr 天然行為）。

### 測試

無後端改動；以 browser preview 於 1920×1080／1536×864／1366×768 三檔實測截圖驗收
（前兩檔須無捲軸，第三檔允許觸發 min-height 捲軸但不得版面破碎）。

## §7 被指派者無主機權限：只開放「該主機該問題」＋指派當下告知

### 現況

- 指派下拉（`handling-panel.js`）與批次指派 modal 列**全部**使用者（`/api/admin/users`），
  不檢查被指派者可見範圍。
- 被指派者若無該主機權限：「我的交辦」工作頁以**檢視者自己的可見範圍**過濾（WEB-SPEC §9.4a）
  → 案件整個看不到；直連風險日詳情 → `EnsureVisible` 404。**指派了等於白指派，而且沒人知道。**

### 方案：案件授與可見性（case-scoped visibility grant）

**核心規則**：使用者是某進行中案件的處理人（`IssueCase.HandlerId`）時，對該案件的
（主機, IssueKey）獲得**範圍限定**的檢視權——僅那台主機、僅那個問題。

1. **`IVisibilityService` 擴充** `GetCaseGrants()`：回傳目前使用者為處理人的進行中案件
   `(hostId, issueKey)` 集合（含 `EnsureVisible` 放行邏輯——經案件授與可見的主機不再 404，
   但要能區分「完整可見」與「僅案件授與」兩種等級，供下游裁剪）。
2. **風險日詳情對「僅案件授與」的存取裁剪**（`RecordDetailQueryService`）：
   - 重點問題只留該 issueKey（其餘問題連同關聯訊號、類型分布一併裁掉）；
   - **報告全文卡隱藏**（全文含整台主機當日所有問題，洩漏範圍外資訊）；
   - AI 白話總覽四段隱藏（同理，總覽是整日敘事）；「詢問 AI」下拉僅列該問題（context 端
     `GetDetail` 授權路徑同源，自然收斂）；
   - header 顯示提示：「您以案件處理人身分檢視此頁，僅顯示被指派的問題」。
3. **「我的交辦」工作頁**：`GetWorkload` 的過濾改「檢視者可見範圍 ∪ 自己的案件授與」——
   被指派者的進行中案件表／被指派風險日表因此看得到這些主機（僅這些日子）。
   問題查詢／儀表板／報表**不納入**案件授與（統計語意不變，動線一律走「我的交辦」與直連）。
4. **指派當下告知指派人員（Q3a 已定案：告知執行指派的 admin）**：日層級 `Assign`、批次指派、
   群組指派（§12）送出前，後端檢查被指派者對目標主機的可見性，**回應帶 `assigneeNoAccessHosts`
   清單**；前端在確認框／結果 toast 明示：「○○○(帳號) 無主機 XXX 的檢視權限，將僅能檢視
   被指派的問題」。批次指派 modal 的預覽 API 一併帶出，送出前就看得到。
5. **授與的生命週期（Q3b 已定案：處理過的保留）**：授與條件＝「**現在或曾經**是該案件的
   處理人」——案件結案後可見性**不收回**，處理人隨時可回顧自己處理過的問題（「我的交辦」的
   已結案切換點進詳情不再 404）；被改派（§9）後原處理人對該案件仍保留回顧權（他確實處理過）。
   授與隨案件資料被保留天數清理而自然到期，不需要額外的回收機制。

### 影響（本輪最大的一項）

`VisibilityService`（新概念）、`RecordDetailQueryService`（裁剪）、`HandlingHistoryQueryService`
（工作頁聯集）、`DayHandlingCommandService`／`IssueHandlingCommandService`（告知清單）、
`AiController` chat 授權、前端詳情頁／handling-panel／指派 modal。`EnsureVisible` 全部呼叫點
逐一清點決定「放行＋裁剪」或「維持 404」。WEB-SPEC §7.1 需增補第 3 層的例外描述。測試量大
（授權邊界必須逐條測：僅案件授與者查詳情／查別的日子／查別的問題／案件結案後）。

**日層級指派的邊界（Q3c，使用者未反對，依建議定案）**：日層級指派給無權限者時，授與範圍
同樣只到**建案成功的那些問題**（`BuildCasesForDay` 本來就逐問題建案），日層級處理面板對
僅案件授與者隱藏——「只能查看該主機該問題」的語意在兩條指派路徑上一致。

## §8 詳情頁重點問題的「顯示範圍」選單（預設隱藏他人處理中＋已完成的顯示控制）

### 現況

重點問題不分案件歸屬全部列出；嚴重度篩選鈕（`detail-severity-filter`）只依嚴重度過濾；
已結案類問題目前收合在分節底部的「已處理／已有結論 N 項」可展開列。已由他人案件涵蓋的問題
照樣可勾選、可改狀態（後端 `SyncStatus` 也不限制操作者）。

### 方案（Q4 已定案：他人處理中對所有人——含 admin——預設隱藏；顯示邏輯設計如下）

先把每個問題劃入四個互斥桶（前端以既有 DTO 欄位推導，不需新 API）：

| 桶 | 定義 |
|---|---|
| **U 未處理** | 無結案標記、無進行中案件（含明確 `open`） |
| **M 我處理中** | 進行中案件的處理人＝自己，或無案件但自己標了 `in_progress`/`observing` |
| **O 他人處理中** | 進行中案件的處理人≠自己 |
| **D 已完成** | 結案類（resolved／wont_fix／false_positive／known_noise）＋預設不處理＋自動雜訊 |

`detail-severity-filter` 旁加一顆**單選「顯示」下拉**（嚴重度鈕群 `present.length<=1` 時
不渲染，此下拉獨立恆在），與嚴重度篩選 AND 疊加；狀態不持久化（每次進頁回預設，
同已結案收合的誠實預設原則）：

| 選項 | 顯示內容 | 對應需求 |
|---|---|---|
| **待處理（預設）** | U＋M；O 隱藏；D 維持收合列 | 「預設不顯示已被指派別人處理的問題」 |
| **顯示所有問題** | U＋M＋O（O 不可勾選）；D 維持收合列 | 「加上顯示所有問題」 |
| **隱藏已完成** | U＋M＋O；D 整個隱藏（連收合列都不出現） | 「隱藏已處理完成項目」 |
| **僅已完成** | 只顯示 D，**直接平鋪列出**（不收合——這個視角就是要看結論）；U/M/O 隱藏 | 「只顯示已處理完成」 |

配套：

1. **選項附數量**：下拉各選項標當前桶數（「待處理」「顯示所有問題（含他人處理中 N 項）」…），
   使用者切之前就知道會多／少幾列。
2. **O 桶不可點選**：checkbox `disabled`＋灰階樣式，批次套用全選跳過；單列狀態操作區隱藏。
   **後端同步擋**（防繞過）：`ApplyIssueStatus` 路徑檢查該問題進行中案件的處理人非本人時拒絕
   （`validation_failed`：「此問題由○○○(帳號)的案件處理中」）——**admin 換人走 §9／§11 的
   改派流程**，不從狀態標記側繞。
3. **計數器與進度**：三段計數（已處理／處理中／未處理）**維持全量**（與後端統計一致，
   顯示範圍只是顯示層）；隱藏發生時在計數器旁補「另有 N 項已依顯示範圍隱藏」，數字才對得上。
4. **與其他機制的交集**：「詢問 AI」問題下拉沿用「目前可見問題」既有連動（`visibleTopIssues()`
   擴充為嚴重度×顯示範圍的交集）；§7 僅案件授與的檢視者本來就只看得到自己的問題，
   下拉對其只剩「待處理／隱藏已完成／僅已完成」的實質差異，行為自然收斂；
   類型分布頁內導航計數維持全量（它是當日事實，不隨顯示範圍變動）。

### 測試

四桶劃分規則（自己／他人／無案件×各狀態）、後端拒絕非處理人標記、全選跳過 disabled 列。

## §9 admin 對「已指派問題」再指派時：提醒並確認變更

### 現況

`IssueCaseCoordinator.BuildCase` 對已有進行中案件的問題一律**跳過不搶走**（Q2 定案），
事後 toast 回報略過清單。admin 想換人只能請原處理人清狀態，沒有正規改派路徑。

### 方案：二段式確認＋案件改派

1. **Coordinator 新增 `ReassignCase`**：轉移進行中案件的 `HandlerId`（**不結案重開**——
   案件是「這個問題這一輪處理」的連續紀錄，換人不該斷歷程），寫 `case_reassign` 歷程
   （note 記「處理人由○○○變更為×××」）＋稽核；案件涵蓋各日的 `IssueHandling` 列不動
   （狀態沿續），`UpdatedAt` 推進。
2. **日層級 `Assign`**：偵測到勾中的問題有他人進行中案件時，若請求未帶 `reassign=true`，
   回 `conflict` 信封＋衝突明細（問題×既有處理人）；前端 `confirmAction`：
   「N 個問題已指派給○○○(帳號)，是否改派給×××(帳號)？」確認後帶旗標重送——
   確認改派的走 `ReassignCase`，其餘照舊建案。**不帶旗標的舊行為（跳過）保留為預設**，
   批次排程等非互動呼叫端零改動。
3. **依問題批次指派 modal**（既有）：預覽已顯示既有處理人——各列加「改派」checkbox
   （預設不勾＝維持既有跳過語意），送出帶 `reassignHostIds`。
4. 與 §8 呼應：勾選「顯示所有問題」看到他人案件問題後，admin 的指派入口即會觸發此確認流。

### 測試

Reassign 歷程／稽核、conflict 信封、旗標重送、批次 modal 選擇性改派、原處理人工作頁案件消失。

## §10 角色與群組定義是否重複——全盤檢查結論

### 檢查結果：**不重複，是刻意的單一機制雙用途，但呈現層確實容易造成混淆**

模型現況（`WebIdentity.cs`／`RoleCapabilityMap`／`GroupAdminService`）：

- **角色（UserRole）掛在群組上，不掛在使用者上**——使用者透過「加入群組」取得角色，
  多群組時能力取**聯集**（dev 與 manager 不構成直線階層，聯集才是對的模型；`WebIdentity.cs:4-8`
  的設計註解明確記載）。
- 群組同時承擔兩件事：
  1. **角色容器**：builtin 的 admin／manager／dev 群組（鎖刪除、鎖 Role）；
  2. **可見範圍單位**：Role=User 的群組（部門）才進授權矩陣（`GetAccessMatrix` 只列 User 角色
     群組，ViewAll 角色刻意不列——「放進矩陣只會讓人以為那些勾選有意義」）。
- 「使用者頁的角色篩選」選項來自現有群組去重——角色在 UI 上看起來像使用者屬性，實際是群組屬性。

**為什麼不算重複**：角色回答「能做什麼功能」（能力，第 2 層授權），群組回答「是誰的集合＋
能看哪些主機」（範圍，第 3 層授權）。拆掉任何一邊都表達不了現有語意。把角色改掛使用者
（方案 B）會產生新問題：部門群組與角色脫鉤後，「這個部門的人都是一般使用者」要逐人維護，
授權矩陣的列也失去「角色群組不進矩陣」的清晰邊界——重構成本高、換到的只是另一種形狀的複雜度。

### 方案（建議 A：模型不動，呈現澄清）

1. **群組頁「使用者群組」頁籤視覺分組**：builtin 角色群組（admin／manager／dev）與
   一般部門群組（Role=User）分兩段呈現，段標題各附一句定位說明
   （「角色群組：決定成員能使用哪些功能」／「部門群組：決定成員能看見哪些主機（見授權矩陣）」）。
2. **新增／編輯群組 modal 的「角色」欄位加 help popover**：說明「角色掛在群組上；
   一人多群組時能力取聯集」——這是目前唯一沒被 UI 說出來的模型事實。
3. **使用者頁「角色」篩選 chip 補 tooltip**：「角色來自所屬群組」。
4. WEB-SPEC §7.1 補一段「角色與群組的分工」小結，供日後回查。

（方案 B＝角色拆離群組改掛使用者：不採，理由如上；Q8 已定案採 A。）

## §11 依問題視角：同問題多主機一次性回覆處理狀態

### 現況

案件同步（`IssueCaseCoordinator.SyncStatus`）只涵蓋**同主機**跨日；同一問題被指派到 N 台主機
＝N 個獨立案件，處理人要逐台進詳情頁標 N 次一樣的狀態；admin 在依問題視角只看得到
「處理概況」計數（N 台處理中／M 台未處理），要看說明得逐台點進去。

### 方案

1. **新 API `POST api/handling/issue-cases/bulk-status`**（能力 `Handle`）：
   `{source, eventId, status, note, dueDate}` → 伺服器找**目前使用者為處理人**的該問題全部
   進行中案件（跨主機），逐案走既有 `SyncStatus`（觸發日＝各案件 `LastLinkedDate`；
   同一批共用同一 `occurredAt`，timeline 分組規則沿用）。狀態值域同問題層級六態＋observing；
   結案類→各案件結案。單筆彙總稽核（「批次回覆『Source EventId』跨 N 台主機標為…」）。
2. **前端（依問題視角）**：該問題的 `handlers` 含目前使用者時，列尾動作區顯示「回覆處理狀態」
   鈕→ modal（狀態 chip＋說明＋預計完成日，重用詳情頁的狀態選擇語彙與必填規則——
   不處理→說明必填）。成功後就地更新處理概況欄。
3. **admin 在依問題直接看到回覆結果**：
   - 處理概況欄維持三態計數（已是聚合事實）；
   - **展開列**（受影響主機×日期）已有「處理狀態」「處理人」欄——補「處理說明」欄
     （該日該問題的 note，超長 truncate＋tooltip），admin 不必進詳情頁就看得到各台的說明。
   - 各主機詳情頁的逐問題說明本來就由案件同步逐日落盤，「各自主機進入時看到每個問題的處理說明」
     既有行為已滿足。
4. **admin 不做代回覆，做「批次變更處理人」（Q5 已定案）**：admin 的需求是讓**真正處理的人
   掛名**，不是替人回覆狀態——依問題視角的既有「批次指派」modal 升級為同時涵蓋改派：
   預覽列出各主機的既有處理人（現有 `ExistingHandlerName`），勾選「改派」的主機走 §9 的
   `ReassignCase`（案件與歷程連續、掛名換人），未勾選維持既有跳過語意。改派後被移走的
   原處理人依 §7 Q3b 保留回顧權。**不新增獨立入口**——「指派」與「變更處理人」是同一個
   modal 的同一張預覽表，差別只在該列有沒有既有處理人。

### 測試

跨主機批次同步、非處理人案件不受影響、結案類批次結案、稽核彙總、必填驗證、
批次改派掛名與歷程連續性。

## §12 指派整個群組：主機平均分攤給群組成員

### 現況

依問題批次指派 modal 只能選單一處理人（`BulkAssignIssueCaseRequest.HandlerId`）。
硬體類問題橫跨數十台時，admin 要手動分批指派多次。

### 方案

1. **modal 指派對象二擇一**：使用者（現況）／**使用者群組**。選群組時列出群組內
   **啟用中成員**（含人數），並即時預覽分攤結果。
2. **分攤規則二模式，admin 送出時選擇（Q6 已定案：兩種都做）**：後端單點定義
   （`IssueCaseCoordinator` 旁的純函數，可獨立測試），modal 內單選：
   - **平均輪流（預設）**：受指派主機依名稱排序、成員依帳號排序，round-robin 逐台分配；
   - **依現有負載**：成員以「目前進行中案件數」升冪排序，逐台指給當下累計負載
     （既有案件數＋本次已分到的台數）最低者，同值時帳號序決勝。
   兩者皆**確定性**（同輸入同結果，預覽與實際落盤一致）；切換模式即重算預覽。
3. **預覽可調整**：modal 預覽表每列（主機→成員）提供成員下拉可個別改指派，送出時帶
   最終的 `hostId→handlerId` 明細（API 形狀因此從單一 `HandlerId` 擴充為
   `assignments: [{hostId, handlerId}]`，單人模式＝全部同一 handlerId，一支 API 兩用）。
4. **既有語意沿用**：已有他人進行中案件的主機照 §9——預設跳過、可勾「改派」；
   成員無主機權限照 §7——授與案件範圍可見性＋預覽標示告知。
5. **稽核**：單筆彙總（「批次指派『Source EventId』給群組○○（N 名成員分攤 M 台）…」），
   detail 帶完整分攤明細。

### 測試

輪流分配確定性、單人／群組同 API 相容、預覽調整落盤、停用成員排除、與 §7／§9 的交互。
