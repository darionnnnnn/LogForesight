## 目標、範圍與成功定義

1. 能逐站台、逐主機、逐 sensor 說明：是否納入監看、資料是否新鮮且完整、量測語意是否可信、哪條規則使用該資料、finding 是否進入使用者可處理的入口。`0 finding`、`沒有資料`、`規則未啟用`、`取數失敗`不可混成「正常」。
2. PRTG 的狀態型與值型訊號，在各自資料條件成立時，能走到風險、問題、案件／交辦、通知與白話說明；外部取數失敗仍與 NetIQ 分路隔離，並在執行及健康畫面明確顯示。
3. PRTG＋NetIQ 的新增結論須有可檢查的主機、時間、資源身分及證據品質；只具同日同主機證據時不宣稱「雙重確認」或「不是誤報」。用真實案例比較單來源與合併後的提前量、可處理性及誤報。
4. 初次啟用、日常檢查、告警處置三條操作動線都能讓使用者看出目前狀態、阻塞原因與下一步，不必自行在多個頁籤拼湊前提。
5. 尚未有真實站台證據的預警規則維持停用或標成待驗，不以程式測試、模擬資料或六日匯出宣稱實機校準完成。

本文「未校準規則停用」指不得投入正式派工／通知；允許在經驗證無正式副作用的隔離試算中評估，詳第三次複查 T06。

本輪涵蓋 Core 取數／對應／規則／關聯／追加、持久層、Web 設定與查詢、排程與健康、使用者畫面、測試及現況文件。`docs/archive/` 不作例行搜尋或讀取。

## 批次總覽（建議順序）

| 批次 | 交付主題 | 規模 | 相依／驗收界線 |
|---|---|---|---|
| A | 初次啟用與監看範圍的可操作性 | 中 | 契約定案並獲實作指示後可獨立修正；實際取數仍須 B 驗證 |
| B | PRTG 取數、資料品質與狀態延續的正確性 | 大 | A 的設定行為；正式站台探測與資料樣本決定取數分支 |
| C | finding 到風險、交辦及歷史一致性 | 大 | B 的可信 finding；PRTG 獨立建案已定案，資料模型與所有讀取端須一起驗收 |
| D | NetIQ＋PRTG 證據分級與提前預警效果 | 大 | B、C；真實案例與 sensor 類型決定可啟用模式 |
| E | 管理者與處理人的端到端操作、成效驗收 | 中 | A–D 的狀態與證據輸出；需走真實 Web 動線 |

各批次可再拆成可獨立驗收的階段，但不得先把尚未定案的產品選項實作成既定行為。跨批次共同驗收是「資料取得 → 可用性判定 → finding → 主機／使用者入口 → 處置結果」以同一組樣本追蹤到底。

**相依修正**：A–E 是交付分類，不是機械式依序開工。先共同定義 B 的來源／時間／品質、C 的識別與處置、D 的證據欄位，再實作持久層；否則做到 D 才發現 C 沒保存必要證據。E 的使用者情境從各批設計時就驗收。以下「建議」「驗收」均為待實作規格，不表示已修改或已通過。

## 批次 B：取數與判定資料的可信度

### 現況與核對結果

- 取數範圍依主機對應與資源守門決定，device 鏡像全站，sensor／messages／快照僅限範圍（`docs/PRTG-SPEC.md:248-306`）。PRTG 現場是否以裝置查詢取到子 sensor 的 messages，需看環境探測 9d-5；結論為「只有裝置自身」時，現路徑會少資料（`docs/BACKLOG.md:384-403`）。
- `PrtgDailyPipeline` 每日只讀 `day-1` 到 `day+1` 的變更（`LogForesight.Core/Service/PrtgDailyPipeline.cs:307-312`）；`PrtgRuleEvaluator` 只遍歷有變更的 sensor（`LogForesight.Core/Service/PrtgRuleEvaluator.cs:153-160`）。更早進入 Down／Warning、之後數日沒有新訊息的 sensor 可能不再產生 finding，並破壞跨日升級及長期 Down。現有前一日無變更測試不足以抓這個情境。
- 保守快照與激進歷史值的品質、coverage 不同；磁碟趨勢只認 28 日逐 sensor 有效資料與有效語意證據（`LogForesight.Core/Service/PrtgValueReadiness.cs:39-84`、`docs/PRTG-SPEC.md:933-964`）。正式站台先前僅約六日可用值且 `Unit=null`，28 日效果待驗。
- 快照部分批次提交後重試可能將已寫入樣本的 coverage 再加一次（`docs/BACKLOG.md:413-417`）；這會影響可用小時與磁碟 readiness，不宜只當效能問題。

### 建議契約與待確認假設

- 持續狀態的判定要有可追溯的「當日零時之前最後可信狀態」；不能以缺少新訊息推論 Up，也不能無期限沿用過期鏡像。狀態起點、資料缺口、sensor 暫停／刪除及重新對應須分別處理。具體持久格式與取數方式在實機訊息語意核對後選定。
- 狀態變更取數若需逐 sensor，先以探測量測範圍、請求數、耗時及 PRTG 負載，再確定可支援的收斂策略；不得回退為全站 `id=0` 查詢。
- 快照重試以同一批已提交資料不重複加權為契約；`ok` 與 `sampled` 優先序不變。時區／小時邊界需在 PRTG 與站台實機核對。

### 階段與驗收

1. **正式站台取數探測**：保留 9d-5 結論、代表性 device／sensor 原始回應與時間戳、鏡像對應、缺漏／截斷、單台耗時及快照 coverage。沒有現場證據時此階段標「待實機」，不可宣稱完成。
2. **狀態延續修正**：先建立可重現的失敗案例：兩天前 Down／Warning 後連續無訊息、期間恢復、確認／暫停、查詢失敗、重新對應；修後驗 finding、跨日升級、長期 Down、誤報反例及重跑冪等。資料不可信時呈現未知，不產生確定性結論。
3. **數值可靠度**：驗部分寫入後重試的 coverage 不重複、快照與真平均覆蓋優先序、28 日逐顆缺口、語意證據失效、資料保留足夠與真實磁碟頻道方向。未通過前磁碟規則維持停用；局部補值不回溯建立舊 finding／交辦。

## 批次 C：finding 的業務落點與一致性

### 現況與核對結果

- finding 只追加到**已有分析紀錄**的主機日，以免偽造 NetIQ 覆蓋率（`docs/PRTG-SPEC.md:812-837`）；沒有該日紀錄時，PRTG 無法獨立觸發既有案件／交辦。這是目前契約，不是資料庫漏寫。
- 記憶體就地追加及資料庫補追加共用登錄簿；新 finding 進風險、案件與 AI（`LogForesight.Core/Service/HostDayPostProcessor.cs:144-217`、`LogForesight.Core/Service/PrtgDailyPipeline.cs:507-545`）。已存在的 finding 不回寫，也不重算佐證（`docs/PRTG-SPEC.md:812-933`）。
- **更正前稿併發敘述**：目前 `EfAnalysisRecordStore` 已有程序內 `HostDayLocks`，Append、AttachPrtgFindings、AI／週體檢回寫有鎖，主列與子列寫入有交易（`:57-61,100-105,210,246,324-330,421-422`）。不能僅憑 BACKLOG 就判定一般追加必然不一致。仍須重現驗證 DeleteDays 未持同鎖的刪除／重建空窗（`:430,537`）、先算後寫的舊資料覆蓋，以及若部署允許多程序時的鎖邊界；資料列版本是否必要，依重現結果與支援部署方式決定。

### 舊 C1 決策紀錄（2026-09-30 已撤回，不再實作）

- PRTG finding 即使沒有 NetIQ 日誌日紀錄，也要能形成獨立、可指派的監控問題；其來源、取數品質、日期與責任歸屬須清楚，不能偽造「NetIQ 當日已分析」紀錄或提升日誌涵蓋率。沿用既有案件／交辦與通知能力，但其入口與查詢須認得 PRTG-only 事實，不在 Core 複製 Web 權限規則。
- **實作前核對的資料邊界**：`lf_top_issues.record_id` 非空且參照 `lf_daily_records`；`AttachPrtgFindings` 找不到 NetIQ 主機日就返回 false；案件合格日、問題彙總、郵件批次均以分析紀錄為入口。單純插入假 `DailyAnalysisRecord` 會使 `HasRecord`、`ReadRecent`、重跑選日、趨勢基準及涵蓋統計誤認 NetIQ 已分析。需讓 PRTG-only 觀察具有明確來源識別，並逐一核對上述讀取端、NetIQ 真紀錄晚到時的合併、保留期與刪除、主機改名／合併、重跑冪等；不可只讓案件表有一列卻在清單與通知消失。
- **擬採持久邊界**：PRTG 觀察另存以站台、主機 PK、日期、sensor／規則穩定鍵識別的事實及資料品質，與 NetIQ 的 `DailyAnalysisRecord` 分離；問題、案件、交辦與通知查詢在服務層合併兩種來源，同日顯示同一主機的兩種證據。NetIQ 晚到只增加日誌分析事實，不刪 PRTG 觀察；重跑以穩定鍵 upsert 並保留人工處置。寫入時要有明確「成功、部分成功、未知、已停用」狀態，不能把沒有觀察列一概解讀為正常。上線前須核對 SQLite 與 SQL Server 是否共用這個契約、觀察列的保留／清理及版本遷移，再落 schema；其間不以假日誌紀錄作捷徑。

### 階段與驗收

1. **落點契約**：以四種主機日矩陣驗收：兩來源皆有、只有 NetIQ、只有 PRTG、兩者皆無；含未對應、衝突、停用主機、抑制／靜音、使用者可見範圍。Dashboard、主機詳情、問題查詢、交辦、郵件與 AI 的計數和下鑽對齊，NetIQ 覆蓋統計保持真實。
2. **一致性與重跑**：同一主機日的追加、重跑、AI 回寫、案件掛接在受控排程下交錯驗證；主列 JSON、子列、日風險、處理狀態一致。失敗可重試且不重複 finding／交辦；舊資料的回溯規則明確，不能讓只有重跑模式才偶然修復。

## 批次 D：跨來源證據與真正的提前量

### 現況與核對結果

- 三個模式均只查同主機、同日的已判定 finding：儲存 I/O＋hardware warning/down、`srv 2013`＋disk warning、非預期關機＋availability down/flapping（`LogForesight.Core/Analysis/PrtgCorroboration.cs:43-111`）。目前沒有時間接近度或同磁碟／磁碟區比對；`PrtgFindingMapper.ToSignature` 把 `FirstSeen/LastSeen` 設為整天（`LogForesight.Core/Service/PrtgFindingMapper.cs:67-96`）。
- 儲存模式依賴 hardware 類 sensor；目前實機已知硬體類型主要掛在網路設備，站台若沒有伺服器硬體健康 sensor，該模式自然零命中（`docs/BACKLOG.md:421-423`）。值型趨勢＋NetIQ 的合適關聯尚未實作（同檔 `:441-443`）。
- 目前「使用效果」只有各自分母不同的計數，含已抑制佐證的主機日也計入「有 PRTG 佐證」；無單來源對照、提前量、查證結果或假陽性分母（`LogForesight.Web/Services/PrtgEffectivenessService.cs:22-109`）。

### 已定案產品契約 D1

- **證據分級**：只有同主機同日的資料，稱「同日兩來源訊號」，屬弱佐證且不因配對上調風險。各模式分別定義必要身分：儲存／容量須對到磁碟或磁碟區，連通性須證明相同主機及適當探測範圍，不強迫所有模式都有磁碟識別。有可核對的時間關係及所需身分才考慮稱「雙重確認」，但仍不等於證明根因；缺必要維度時不可補猜。既有歷史紀錄可能保留舊的強佐證文字與風險依據；須另定預覽、遷移或讀取端降級策略，不能只修新寫入。
- 「更早發現」的優先候選是經實機驗證的磁碟可用空間趨勢及真正有伺服器硬體語意的 sensor。CPU／記憶體、Linux 或新關聯模式須有明確可用的資料與處理動作才加入，不為湊模式數量新增規則。

### 階段與驗收

1. **來源證據**：對三種現有配對及候選值型配對，列輸入欄位、時間精度、主機／磁碟身分、品質、失敗及不可判定情境；以真實變體建立應命中與不應命中的樣本。必要欄位若目前未保存，先決定最小持久契約與既有資料的降級顯示。
2. **關聯與文案**：相同主機但不同時間、不同磁碟、被抑制、不明 sensor 分類、跨日接近事件、NetIQ 缺日，均有明確結果。較弱證據不得出現「證實」「不是誤報」；風險只按定案的證據等級變動。需核對規則、詳情、AI prompt、週體檢、郵件與歷史紀錄。
3. **效果評估**：以同期間、同監看範圍對照 NetIQ 單獨、LogForesight 的 PRTG 單獨、合併後，另納入 **PRTG 原生告警**作實務基準。以事故為單位去重，記錄首次可取得、判定、可見及通知時間、確認有用／誤報／無法判定數、調查步驟與處置結果。重播只能使用當時已取得的資料、設定及語意證據，不能偷用後續補值或事後標記。提前量以相同事故的可行動通知比較；僅事件時間較早不算提前。分母、觀察期間、未審查及無資料語意寫清；不足以計算時顯示未知，不虛構提升率。

## 實用程度判定：目前缺什麼、如何補齊

### 目前能下的結論與不能下的結論

目前已有 PRTG 取數、狀態／磁碟判定、與 NetIQ 配對及追加到既有分析紀錄的程式路徑，可作為監控背景與分析輔助。**尚未證明「在指定站台與監看範圍內，能持續可靠地協助使用者提早發現並處理問題」**。此結論限於本輪 PRTG 整合與原始目標，不表示整個 LogForesight 或既有 NetIQ 功能都沒有實用價值。

不足有三種，處理方式不同：

1. **已定位的程式／契約缺口**：初次保守啟用受阻、較早開始且無新訊息的持續故障可能不再形成 finding、白名單語意不一致；須修正並驗收。已知問題不能只靠延長觀察期解決。
2. **產品行為未定案**：無 NetIQ 當日紀錄的 PRTG 問題落點、跨來源證據分級、長期 Down 政策、試點範圍與可接受通知延遲；須先決策，再實作與驗收。
3. **證據不足**：正式站台是否完整取回訊息、磁碟歷史身分／語意是否連續可信、實際告警與操作效益、長時間負載及故障恢復；須取得現場與使用者驗收紀錄。缺證據標「未驗」，不直接推論功能一定失敗。

先前 69 項測試通過僅來自既有編譯產物，既不能排除上述未覆蓋情境，也不能回答「比原生 PRTG 更早多少、是否少花時間、會不會漏掉真正的問題」。原稿的缺點是列了很多驗收項目，卻未集中列出實用程度的判定門檻；本節補齊這個缺口。

### 補充評估方法：避免只檢查「系統自己找到的問題」

- **獨立事故清單**：以既有工單、原生 PRTG 告警與維護紀錄建立候選事故，不能只從 LogForesight 命中列表挑樣本。由處理人確認哪些在宣告範圍內、當時是否有足夠可觀測資料；無法判定者另列。
- **漏報與涵蓋分開**：已知、可觀測且屬支援情境的事故未被發現，列規則／管線漏報；缺 sensor、錯誤對應或資料中斷列涵蓋／採集缺口。兩者都影響實用性，不能藉排除資料不足事故美化成效。
- **指標分母固定**：有效告警比例＝已確認有用告警事故／已完成查證告警事故，另列未查證量；漏報比例＝未發現的可觀測支援事故／獨立清單中已查證的可觀測支援事故。沒有完整事故清單時不得宣稱全站召回率；各指標列原始件數及觀察範圍。
- **分開計算預警與查證效益**：提前通知未改善但有減少查證時間，可列輔助調查價值，不能用來通過 P04。記錄中位數、最差案例及樣本數，不能只挑改善最大的案例。跨來源佐證增加風險時另驗是否造成更多無效交辦。
- **試點期間與樣本**：建議先在實際生產來源資料上影子評估（不新增正式派工／通知），再由定案範圍受控啟用。候選觀察期為資料就緒後連續 14 天，磁碟規則另需先滿足可信 28 日視窗；兩者不是自動等同固定 42 天。期間須涵蓋正常、異常、恢復與失敗重試；無真實異常則補歷史無未來資訊重播，仍不足就延長／縮小結論。觀察期及每類最低樣本數由 F4 定案，14 天本身不保證效果成立。
- **證據紀錄欄位**：每個 P01–P07 留軟體版本、設定／規則版本、站台與監看範圍、起訖時間、樣本數、預期／實際結果、去識別證據位置、缺陷與重驗結果、負責人、驗收日期。真實憑證與敏感原始資料不放 repo。

### 整體回查後的必要修正

- **通知時間的可信度**：P04 的「通知到達」須註明證據層級。應用程式提交郵件、SMTP 接受、信箱收到、使用者讀取是不同時間；只能取得前兩者時不得當作實際收到。實機端到端案例需由測試收件人確認，其餘標可取得的代理指標。
- **晚到資料與結論修訂**：B／C／D 補驗同一事故 NetIQ 先到／PRTG 先到、跨午夜與時鐘偏移、補值晚到、抑制或語意失效發生於寄送後。定案哪些允許改寫目前結論，哪些只追加歷史修訂；保留當時通知內容與判定版本，避免舊郵件與新頁面互相矛盾卻無說明。是否發修訂通知納入 N1，不能無聲重寄。
- **驗證與正式作用分離**：影子評估的儲存、問題建立、案件掛接、AI／週體檢、郵件及成效統計皆須檢查副作用；優先選既有隔離試算能力，若不足再規劃最小補強，不先重建一套分析架構。真實來源讀取仍受資源守門。
- **PRTG 故障不可遮住既有 NetIQ 結果**：以相同 NetIQ 輸入對照 PRTG 關閉、正常、超時、失敗、積壓五種情境，核對既有問題、日誌涵蓋、案件及通知無非預期遺失；允許的風險增益須可解釋。共用 DB／排程／資源競爭造成的延遲也納入 P06，不能只驗例外被 catch。
- **限制測試與修改範圍**：新增 T01–T06 對應 A–E 既有階段，不另開通用 UI、郵件或權限重構。測試覆蓋新契約與實際受影響的呼叫端；問題未重現前先核對，不因反覆審查就持續增添無證據功能。必要案例未通過不得宣告相應範圍完成。

本次複查結論：規劃仍有通知承諾、設定生效、試算一致性、責任交付、預防成效歸因與階段門檻的缺口，已補入。既有證據不足項目依 P01–P07 執行，不能用抽象清單替代實機證據；C1／D1／D2／N1／N2 已依使用者回覆定案。
