## NetIQ 主體修訂（本輪有效開發契約）

**主體與邊界**：本輪 PRTG 功能只補充已由 NetIQ 分析的主機日。主機必須在既有 NetIQ 納管及可見範圍內，且該日有可辨識的 NetIQ 分析紀錄；單有主機主檔、PRTG 對應或本機日誌紀錄不等於滿足此條件。NetIQ 取數失敗／缺日／分析尚未完成時，顯示日誌待完成與 PRTG 資料現況，保存必要原始證據等待補充；不生成 PRTG 獨立問題／交辦／通知。NetIQ 正常分析但事件數為零仍是有效分析紀錄，允許 PRTG 提供問題證據。重跑失敗不能拿舊成功紀錄冒稱本次成功；保留版本與最新嘗試狀態。

PRTG 可以在有效 NetIQ 主機日內提供新增風險訊號，即使 NetIQ 本身沒有命中同類事件；介面清楚表示「NetIQ 分析完成，PRTG 命中」，不能冒稱兩來源都證實故障。原有非 PRTG 的本機日誌功能不因本輪重寫或移除。

### 必須補齊的實作與驗收

1. **來源資格單點判定**：查實 `DailyAnalysisRecord` 的來源／執行 provenance 如何辨識 NetIQ，不能只用 HasRecord、HostId 或 Sentinel 對應猜測。正式與重跑、補追加、AI、通知均用同一資格判定。舊資料無法辨識時顯示待確認，不能自動當成合格。既有程式可能對任何日誌紀錄追加 PRTG，須納入本輪核對。
2. **兩路完成順序與晚到**：NetIQ 先完成、PRTG 先完成、PRTG 失敗、NetIQ 失敗後隔日補跑，最終同一份 NetIQ 日紀錄都能得到唯一且版本正確的補充判定。不能只靠單趟記憶體登錄簿；重啟後補跑仍有路徑。資料完整性與來源身分不足時保留未知，不能為補齊結果回填猜測。
3. **補充後真的進處置**：已有日紀錄追加高風險 PRTG finding 後，SQL 子列、JSON、有效日風險、儀表板／清單／詳情、案件合格日、交辦與 AI 輸入一致；晚到風險不得被「該主機日已寄信」遮住。依既有 WorkOrderCoordinator 建單，無責任人保持未指派並可見，不能留下散案。
4. **重評與人工狀態**：五次重跑、改規則、舊佐證降級、AI 回寫交錯不重複 finding／成員，不覆蓋人工回覆；原始與有效風險分開。刪除／重建 NetIQ 日紀錄時，正式問題入口及待送意圖重新核對父紀錄版本，既有交辦保留最小證據與刪除原因，不留下無法理解的失效連結。
5. **跨日 PRTG 與缺日 NetIQ 分開**：sensor 連續 Down 可由可信 PRTG 區間證明，NetIQ 缺日不等於 sensor 恢復；缺日不建立正式問題日。NetIQ 補齊後依歷史修訂契約補證據，過期歷史不自動寄即時告警；目前仍成立的問題按 Q2 重評通知。
6. **真正的合併效益**：比較「NetIQ 原有分析」與「同一批 NetIQ 主機日加入 PRTG」，另以原生 PRTG 告警作外部基準。不再要求開發 LogForesight PRTG-only 正式模式；研究對照若需 PRTG 單來源訊號，只能以隔離重播／原生輸出評估。量測合併後的可行動提前量、查證時間、誤報與額外成本；同日共現仍是弱佐證。

**替代 G2／固定矩陣**：H1 有 NetIQ 一個問題且無 PRTG finding；H2 無 NetIQ 日紀錄但有 PRTG finding；H3 有 NetIQ 一個問題及 PRTG 一個不同問題；H4 兩者皆無。初始正式問題為 3 個來源問題、2 個問題主機日、2 個 NetIQ 分析主機日，H2 零交辦／通知且呈待日誌。H2 的 NetIQ 成功分析晚到且無原生日誌問題後，PRTG 補充生效，成為 4 個來源問題、3 個問題主機日、3 個 NetIQ 分析主機日；五次重跑仍只有一份 PRTG finding／交辦成員。另驗 NetIQ 成功零事件、NetIQ 失敗、本機日誌-only、僅主機對應及受限角色只見 H2 的前後結果。

**修訂開發順序**：先完成 NetIQ 來源資格與 S1 可信 PRTG 判定 → 補追加／晚到／重跑的一致性與 G2 垂直操作 → 通知意圖及歷史有效風險 → 權限／瀏覽器／遷移相容與維運 → 指定站台提前預警及合併效益。下一個主要交付改為「NetIQ 主機日補充 PRTG 的完整處置鏈」。本輪仍需 G1、替代 G2、G3–G8 通過才結案，取消 PRTG-only 不等於資料流探測通過即可宣稱實用。

#### 重新核對後的必要補強

1. **時間預算與使用情境相容**：正式判定仍按日跑，分鐘級快照不等於分鐘級告警。先列資料取得→判定→問題可見→SMTP→實收的最大容許延遲，與目標事故可介入時間比較。若每日排程不滿足，列明受影響情境並在規劃討論中決定判定頻率／工作量；不能宣稱支援該情境。僅當實際選定情境可容忍此延遲時，才能沿用日判定通過 G7。
2. **支援能力清單必須對到站台實際資源**：目前硬體類主要為 Cisco 健康訊號，不能推論已能預警 Windows/Linux 伺服器硬體故障或入侵。每條正式啟用規則列主機／sensor、頻道、單位、方向、規則、預期動作、排除條件及驗證狀態。CPU／memory／traffic 有值只列資料能力；磁碟數量多也不代表每個磁碟被主頻道覆蓋。
3. **有限樣本不可解鎖全站**：目前取數 20 devices，含 2 個對應衝突；鏡像差額推得範圍內 126 sensors，仍須用實際清單確認。初次正式開啟使用明確、後端強制的主機／sensor 試點清單；衝突不參與歸戶。守門資源可取數但不能因加入守門而自動成為業務派工對象。
4. **從收到資料到處置的失敗必須補得回來**：每個實際副作用都留持久身分、採用設定版本、最後成功階段及重試狀態；修復後以失敗處續跑。排程健康要包含判定／下游派工及通知積壓，取數成功不能遮蔽後段失敗。重評結果改變時留修訂並使全部查詢快取失效。
5. **驗收版本可追溯**：環境探測目前只印 `1.0.0.0` 與 `legacy`，不足以鎖定這次試點。證據包需可辨識的 build/commit、設定修訂與去識別範圍清單、規則／語意版本、執行 ID、時間與時區。不得匯出帳密/token；未知版本明列未知，不能事後補猜。這是 S6 的交付項，尚未完成。
6. **暖機不能用回填偽裝通過**：28 日值、歷史主機對應與頻道語意都必須可信。先完成程式及驗收工具，真實累積期間照實保留待驗；若已有可信歷史，可匯入／重播但不能使用當時尚未知資料計算提前量。觀察期無足夠事故時 G7/G8 為證據不足，仍未結案。
7. **遷移與回退需能保住人工成果**：共同查詢切換前驗舊／新 PRTG 去重、歷史風險、可見性與計數；舊問題及信件連結保持可讀。回退不刪新觀察、處理紀錄或交辦單；先停新副作用再回退相容版本，提供實際可操作的步驟。PRTG 資料搬運 v1 不含影子表，需完成新版本與相容處理後才算 G6 通過。

#### 本輪開發與驗收順序

1. **共用契約與 S1**：來源／資源身分、觀察時間／涵蓋、持久區間及逐日評估接線。收到的 9d-5 已支持逐裝置查詢可用，但不免除逐 sensor 完整性驗證；不必等待更多站台資料才開始固定樣本實作。
2. **S2–S3 垂直流程優先**：完成一個真實 PRTG-only 問題從落庫→共用查詢→證據詳情→既有 WorkOrderCoordinator→受限處理人回覆，再擴及所有彙總／AI／匯出讀取端。這是下一個主要交付；不得繼續只增加影子統計而把 C1 留到最後。
3. **S4–S5 整合**：事故／通知意圖、重試／取消、責任收件範圍、恢復再發，以及歷史有效風險在所有讀取端一致。G2–G4 的故障及競爭反例一次串接驗證。
4. **S6 上線就緒**：遷移／搬運／保留、實際 DB provider、瀏覽器角色與全鏈操作、守門與效能。同步 HelpContent／現況 SPEC；逐項 PLAN↔程式入口↔測試／實機證據回查，不能用測試數作完成比例。
5. **S7 真實效益**：固定版本與範圍後量測 F2–F4；結果未達標就回到對應開發階段，不只補文件。使用者手動測站台已獲授權，代理完成可本機驗的開發，不把缺現場存取當作 S2–S6 未實作理由。

結案表每個 G 項都填「程式位置、可重現案例、測試版本、站台／本機、實際結果、缺陷及重驗結果」。G1–G6 全過才是可運作的 PRTG 處置能力；G7 通過才支持指定情境的提前預警實用性；G8 另支持雙來源增益。使用者本輪要求涵蓋三者，因此不可只完成 G1–G6 就宣布全部規劃完成。F2–F4 的實際門檻與負責驗收者須在試點前填妥，開發工作可先行，不反覆詢問已定案的產品政策。

## 共用資料與身分契約

1. **觀察與判定分開**：PRTG 觀察保存站台來源世代、主機 PK、device／sensor 識別、資源識別與精度、來源時間及時區、取得時間、判定日與時間、品質原因、規則 ID／版本、語意版本、證據引用。未知欄位不可用整日時間或今天對應補成精確事實。
2. **穩定鍵**：日別判定鍵為來源世代＋主機 PK＋資源種類／objid／資源世代＋規則語意代碼＋判定日；規則 ID／版本屬可追溯的判定版本，重建相同語意規則不新增事故。原始觀察另依其來源事件或採樣鍵去重，不混用日別判定鍵。保留既有 EventKey 作相容對照，但新處置識別必須涵蓋來源與資源世代；不能只在觀察表加世代，案件、靜音和跨日查詢卻仍拿舊 EventKey 合併。來源換 Core、sensor 重建或 objid 重用須結束舊身分區間。無證據判別時標身分待確認並阻斷跨區間續算，不宣稱 objid 可永久唯一。
3. **問題與事故**：保留既有 Source／EventId 的問題分類及完整簽章處置鍵，另存資源觀察與事故關係。同類多顆 sensor 可在同一問題顯示，但證據與持續時間不能混算；不同來源同日共現不能自動合併成同一根因事故。事故持續期間不以換日新建。可信恢復結束故障區間；人工結案、靜音、失去資料各自保存，不代表 sensor 已恢復。
4. **四來源矩陣**：兩來源都有時呈現同主機日的兩份證據；只有 PRTG 時有問題與 PRTG 風險，但 NetIQ 分析狀態仍缺資料；只有 NetIQ 時維持其結果；兩者皆無時呈現未知／未監看，不造正常紀錄。綜合風險由有效且未抑制的獨立證據計算，不因弱配對再加權。
5. **品質不等於風險**：取數成功、部分成功、失敗、停用、取消為作業狀態；正常／故障／未知是資源判定。不同維度分欄。部分失敗可以保留其餘可信 finding，但不得聲稱整台或整站正常。
6. **持久與投影**：獨立 PRTG 觀察不依附 DailyAnalysisRecord；服務層提供共同問題／主機日讀取契約，SQL 端先篩選與聚合，避免撈全期間 JSON 再合併。NetIQ 日誌統計、重跑選日及日誌趨勢基線繼續只認真實日誌紀錄。SQLite 與 SQL Server 均須遵守相同唯一鍵、交易、字串長度與遷移契約。

## S1：持續狀態、資料缺口與值型語意

- 每顆納管 sensor 建立「目標日開始前最後可信狀態＋當日變更＋查詢覆蓋區間」。前導狀態來自帶時間的歷史事件或先前已保存的可信狀態檢查點；當前鏡像只能證明採集當時，不倒填過去。必要時在既有保留範圍內有界補查，不發全站 messages 查詢。
- 延續必須同時滿足來源身分／對應不變，以及前導事件到目標區間的訊息涵蓋可信。分頁收斂、零筆、transport 成功都不能單獨滿足 sensor 涵蓋證明；9d-5 顯示 device 不含子 sensor 時，改採範圍內逐 sensor 查詢並先估 API 預算。
- 已知 Down 後跨三日無變更且覆蓋可信，三日都可產生日別故障觀察；當日恢復、Warning→Down、暫停／確認、亂序重複、午夜與時鐘偏移均以實際區間判斷。缺口阻斷連續故障日數，但不把未解問題標恢復；下次可信觀察只證明其可支持的區間。
- 數值型規則沿用 28 日逐 sensor readiness；歷史對應與語意必須涵蓋使用的區間。以規則要求的頻道、單位、方向重新 probe；每次正式評估檢查該輪可取得的現況證據，重驗失敗或偵測漂移即未知，不靠任意猜測的有效天數延長信任。歷史語意區間缺證據就等待累積，不將今日 probe 追認 28 日。
- 驗收：固定三日 Down／Warning、恢復再發、查詢空值／截斷／失敗、對應改變、objid 重用、語意漂移、28 日缺一天；明確斷言命中日期、duration、品質及未知原因。失敗不清除可信歷史；現場來源證明與本機演算法測試各自記錄。

## S2–S3：PRTG-only 到可處置問題

- 新增獨立觀察持久契約及每次評估結果；有效結果 upsert 與下游待處理意圖須可重試。來源暫時失敗不覆蓋上次可信觀察，也不生成恢復。重跑修訂保留原始證據及人工狀態；NetIQ 晚到不移除 PRTG 觀察。
- 舊日紀錄內 PRTG finding 採可重跑的遷移／相容對照；新觀察與舊副本共存時只呈現一次。同一份舊資料沒有足夠來源身分則標 legacy／未知，不猜站台或歷史資源；先輸出遷移預覽、重複鍵與缺欄位統計再切換讀取。切換有版本就緒門檻，避免一半查舊一半查新。
- 案件資格與逐日同步接共同問題查詢，建單仍經 WorkOrderCoordinator。沒有合格責任人時保留「未指派」，不產生無單進行中案件；取消或已結案單沿用既有流程，不默默重開。可信恢復後的新事故保留與舊案的關係，再依既有派工政策建立新處置。
- 刪除 NetIQ 分析日不能級聯刪獨立 PRTG 觀察。主機改名使用 PK，合併使用既有存活主機映射；觀察保留原始來源身分。原始取數遵守 PrtgRetentionDays，案件保存最低必要的判定／來源／品質快照及原始證據是否已過期；案件仍存在時不能因清原始資料而失去處置依據。

## S4：通知、取消與故障恢復

- 通知意圖以事故／問題＋有效通知版本識別，記收件範圍及送出結果；不再以主機日已寄遮住晚到高風險。使用案件識別作連結，尚未指派者使用穩定問題識別。
- 每個合格收件人保存待送、SMTP 接受、失敗或結果不明；無合格收件人顯示待處理，不用其他信成功標記。重試可重寄已成功者，但不換案件、不重複派工；實際信箱收到與 SMTP 接受分開記。Q2 定案後套用即時通知條件。
- 停用／縮小範圍儲存後推進設定／範圍版本。新工作讀目前版本；執行中在每個請求批次開始、下一頁、下一日期、判定提交前及通知送出前核對。縮小只保留新範圍交集，擴大留待新工作；主機對應改變不得把舊回應寫給新主機。使用相同取消 token 解除 HTTP 與守門等待。
- 已進入原子 DB 提交的批次允許完成並記錄採用版本，其後停止；取消前已取得且待補寫的原始樣本可用原身分補寫，不因此生成範圍外新判定／通知。已進 SMTP 的信無法收回，保存結果；尚未送者重查權限與範圍。畫面顯示停止中／已取消與最後完成階段。
- 待寫樣本採有界、可恢復的本地待寫紀錄並保持既有穩定批次 ID，DB 恢復後重送；容量耗盡須停採並顯示缺口，不靜默丟棄。序列化只含必要樣本，不含憑證；清除已確認提交批次必須可重試。強制重啟驗證已接收並記錄的批次可恢復，不能承諾 HTTP 尚未完成資料不丟失。

## S5：歷史弱佐證、強佐證與試算一致性

- Q1 建議方案下保留原始判定；建立可供 SQL 篩選的有效風險與修訂版本。只有能從保存證據重算時才移除舊配對加權，不能直接把所有高風險降成中。無法還原獨立風險依據者標「歷史風險待重評」，不得冒充已精確重算，也不因遷移重新寄舊告警。
- 詳情、清單、統計、AI prompt／已存摘要、週體檢、待寄郵件、成效服務共用有效證據等級；原始文字放可辨識的歷史區域。預覽列影響筆數與不能重算原因；正式遷移分批、可重試、有回復步驟，不在通用 Deserialize 中偷偷改寫資料。
- 強佐證需逐模式的時間窗口及資源對應樣本，尚未校準時維持弱佐證。容量必須同磁碟／磁碟區，連通性需相同主機與探測對象。未知分類、不同資源、被抑制、時鐘不明一律不得升級；沒有實證的硬體／安全新模式不啟用。
- 試算輸入標明規則 ID／版本、是否啟用、設定版本、資料截至時間、語意版本及是否使用草稿；正式與試算在相同輸入下相同結果。資料或設定變更後顯示需重算。採集時間與判定時間分列，補值不自動回溯寄舊通知；下一次評估時間由現行排程推導，不承諾分鐘級。
- R07 另驗 28 日 readiness 與可調趨勢視窗／最少有效天數的合法組合，缺日／缺小時、低位平坦、快速下降及短暫暴跌。未命中趨勢不顯示資源健康；不以修改門檻或新增未定案規則硬使案例命中。

### 全專案回查：資料、生命週期與切換

1. **來源世代不能只靠 URL 推導**：憑證輪替、DNS／位址搬遷不必然換 Core。新連線先核對可取得的來源識別；無法證明相同時要求管理者確認延續或新來源，顯示影響的對應、未結問題與暖機範圍。這是具體來源變更操作的資料確認，日常儲存不重複詢問。sensor 世代同樣保存判別依據，現有 API 不足時明示無法連續追溯。
2. **日別紀錄不足以描述同日恢復再發**：事故由可信狀態區間辨識，日別判定引用可多個事故的證據清單。驗上午 Down→恢復→下午 Down，同日觀察可彙總但有兩個事故；若中間只是資料缺口，不能當兩次復發。跨日升級先按證據可用的日期順序計算，再按畫面排序輸出；現行 pipeline 接受近到遠日期，不能讓一次補三日與分三次跑的結果不同。
3. **規則沒有命中不等於恢復**：停用規則、門檻變更、資料不足、缺 sensor 不能結束既有事故；只有符合已定義恢復條件的可信資料才標恢復。日別重新評估撤銷 finding 時記判定修訂，不刪人工交辦；規則調整後仍須保存當時門檻及新結果差異。容量趨勢的恢復判定必須由其規則契約定義，不能直接沿用 Down→Up。
4. **觀察→案件→通知需跨步驟可重試**：有效觀察及下游意圖在可控交易內提交；worker 以固定身分處理，記待掛接／已掛接／待送／結果不明。不把 SMTP 包進 DB 長交易。驗觀察已寫但建單失敗、建單成功但意圖確認失敗、SMTP 接受後落庫失敗；三者均可恢復且不重複派工。管理者能看到下游未完成，而非顯示整趟成功。
5. **快取與彙總版本一致**：PRTG-only 寫入、修訂、取消、人工處置及歷史有效投影都推進對應資料版本；儀表板／清單／詳情使用相同就緒版本。驗新增 PRTG-only 後重新整理及下鑽數字一致；NetIQ 與本機真實日誌涵蓋均不受污染，不能把全專案所有日誌都誤標成 NetIQ。
6. **遷移切換與回復需有可觀察界線**：先新增結構→預覽及回填→驗唯一鍵／對照／總數→將同一組讀取端切到已就緒版本；回填未完時明示準備中，不能只讓部分入口讀新數據。保留切換前資料與備份，驗重啟續跑、兩個升級程序互斥及新舊版程式相容範圍。回退時停止新功能副作用，保留新觀察與處置，不能刪新表冒充回復成功。
7. **本地待寫佇列與 DB 帳本必須共同保留**：S4 暫存仍是待實作設計，不是現況。持久保存成功才稱樣本已接收；驗部分檔案、checksum 錯誤、磁碟滿、程序強制終止及雙程序重放。批次 ID／來源世代／目標資料庫身分隨批次保存；DB 還原或切換來源後不盲目重放到另一站。冪等帳本不得早於可重放批次被清除，否則舊批次會再加 coverage；過期批次列明丟棄／隔離原因與資料缺口，不靜默補錯。
8. **保留期與搬運包含衍生資料**：原始觀察、身分區間、判定版本、案件證據、通知意圖及影子結果各自列清理條件；有引用者保留必要快照。匯出／匯入帶來源及格式版本，匯入不自動派工／通知，重複匯入冪等；錯站台、錯主機或未支援版本先拒絕／隔離。變更既有 PrtgDataTransfer v1 前列出舊包相容路徑及錯誤回應。
