## 批次 A：版號規則與守門

### 現況與核對結果

- `Directory.Build.props:8` 的 `<Version>` 自第 53 輪後沒動過。側欄底部顯示的就是這個數字（`_Layout.cshtml:48`）。
- 診斷匯出的「依版本看問題」因此只有一列。本次評估有三條訊號事後查 git 才知道 11/04～11/05 已修，版號有變的話匯出檔自己就看得出來。
- `BuildVersion.Current.Label`（版號＋短 sha）仍是判斷「部署了哪個 commit」的依據，這條不變。
- 寫死舊版號的測試：`NetiqEvidenceMetadataProbeTests.cs:46`。`BuildVersionTests` 的字面值是解析樣本，不受影響。文件與說明書沒有寫死版號（已 grep）。
- `docs/archive/` 的規劃檔名都是 `FEEDBACK-N-PLAN.md`，目前最大 69。

### 定案

1. 版號格式 `1.0.<輪次>.<修訂>`：
   - **輪次**＝該輪 `FEEDBACK-N-PLAN` 的 N。開輪第一個提交就改，修訂歸 0。
   - **修訂**＝同一輪內「會交給使用者實測」的後續修正批次：實作方自查修正、換模型體檢修正、併 dev 後依實測回饋的補修，各加 1。同一批修正多個 commit 只加一次。
   - 不屬於任何一輪的零星修補：修訂加 1，輪次不動。
   - 前兩碼 `1.0` 保留給產品里程碑，由使用者決定何時動。
2. 守門測試：版號第三碼必須等於 `docs/` 與 `docs/archive/` 內 `FEEDBACK-N-PLAN.md` 的最大 N。第四碼無法機器判定，靠慣例與收尾檢查。
3. 規則寫在三處：`Directory.Build.props` 註解、專案 `CLAUDE.md`「慣例」新增「版號」一條、`CLAUDE.md`「不要做」原本那條改寫成現況。
4. 不做：每個 commit 自動遞增（沒有 git 的建置環境會得到不同版號，且與 Label 的 sha 功能重複）；畫面上的更新紀錄頁（本輪沒有需求）。

## 批次 B：空資料待複查在同窗口內複查

### 現況與核對結果

使用者看到的「兩台失敗、沒重試、下個時段也沒補跑」，對照診斷匯出與程式後判定為「空資料待複查」而非失敗（11/10、11/11 的排程趟都是成功、失敗 0，但 11/10 只分析了 10／12 台）。**此判定為假設**，使用者尚未確認當時畫面的狀態字樣；若是紅色「失敗」，本批次仍成立，但要另開一條追查。

- `NetiqPipelineService.cs:799`：排程趟、沒有舊紀錄、回 0 筆且未截斷時不寫紀錄，帳本記 `empty-once`；下一趟再回 0 筆才寫成功（一筆 0 事件的紀錄）。
- 數量只寫在里程碑文字（`AnalysisOrchestrator.cs:1323`），沒有存進執行紀錄。`RunResume.Of` 看不到它，`ScheduleCalculator.RunToContinue` 不會為它續跑。
- 畫面說明寫「空資料，下一窗口複查一次」（`RunMonitorService.cs:308`）；只設一個窗口的站台等於隔天。
- 執行紀錄以 JSON 行儲存，新增可空欄位不需要 schema 升級。
- 帳本摘要 `AttemptHistory` 沒有最後嘗試時間。
- 續跑只算 `Trigger == schedule` 且屬於目前窗口實例的趟；自動補跑趟沒有窗口實例。

### 3000 台規模下的評估

| 面向 | 結論 |
|---|---|
| 會有多少台 | 安靜的主機每晚都回 0 筆，3000 台時是常態，設計以「每晚發生」為前提。 |
| 排程輪詢成本 | 判斷只讀執行紀錄上的一個整數，不逐主機掃帳本。 |
| 複查查詢成本 | Sentinel 查詢 50 台一批，500 台待複查是 10 個批次查詢。 |
| 複查趟的計畫階段 | 一般續跑會重掃全部主機的缺漏日，每晚多掃一次的耗時未量測。B-5 先量再決定。 |
| 第一趟跑很久 | 間隔從上一趟開跑起算，3000 台第一趟跑 3 小時，結束後下一次輪詢就複查。 |
| 第一趟被窗口結束停掉 | 不續跑（既有規則），由下一個窗口依帳本接手，回望 7 天內補得回來。 |
| 太快複查 | 同晚又有失敗時，10 分鐘後的失敗續跑不查未滿間隔的待複查主機日（定案 3）。 |

### 定案

1. **待複查算「還有事沒做」**：執行紀錄新增可空欄位，記**這趟結束時仍為待複查的主機日數**——本趟新記的，加上因未滿間隔而略過的（否則失敗續跑那一趟的數字會是 0，第三趟永遠不會發生）。`RunResume` 納入並在摘要寫出。null（舊紀錄）視為 0。
2. **複查間隔 60 分（暫定）**，從上一趟開跑起算；常數只定義一處（Core），排程判定與取數管線共用。只留待複查、沒有失敗時用這個間隔；留有失敗時維持現行 10 分。
3. **未滿間隔的不查**：排程趟遇到帳本狀態是待複查、最後一次嘗試距今未滿複查間隔的主機日，本趟不送查詢、狀態不動、不計入重查次數。`AttemptHistory` 因此帶最後嘗試時間；時間來源可注入，測試不靠真時鐘。
4. **趟數上限**：失敗續跑上限不變（同一窗口實例 2 趟）。只為待複查而跑的那一趟可以是第 3 趟，同一實例至多一次；複查趟自己又留下失敗，不再續跑。
5. **單一判定點**：「下一次複查是什麼時候」只有一個函式，排程觸發與畫面說明都呼叫它。畫面三種文字：
   - 窗口內排得進：「空資料，約 02:00 複查」。
   - 排不進（窗口太短、已用完趟數、非今日的格子）：「空資料，下一窗口複查」。
   - 排程未啟用：「空資料，排程未啟用，不會自動複查」。
6. **沒留紀錄就離開的出口**：
   - 窗口到點前排不進複查、手動停止、異常中斷、自動補跑趟留下的：下一窗口依帳本接手（既有）。
   - 站台重啟：趟數與待複查數都從執行紀錄讀，不歸零。
   - 帳本讀不到：該趟第一次回 0 筆就定案（既有降級，不變）。
   - 當日自動重查用完：畫面寫「今天的自動重查已用完，明天會再試」（既有）。
7. 手動趟維持現況：回 0 筆立即定案。
8. 診斷匯出的異常趟次多帶這個欄位，匯出說明補一句，日後看得出某晚留了多少待複查。
9. 不做：把待複查計入失敗數（會讓趟次變失敗並觸發 10 分鐘續跑）；依主機歷史跳過複查（把「來源暫時沒資料」與「真的沒事」又混在一起）；把間隔做成設定。

## 批次 C：排程趟「天天警告」的來源

### 現況與核對結果

診斷匯出裡排程取數 14 趟只有 4 趟是「成功」，跟隨取數的 AI 15 趟只有 3 趟。

警告數的排除目前只認一個 logger 名稱（`BatchRunRecorder.IsWarnCountExemptLogger`，慢 SQL 用）。

### 定案

1. **C-1 強制格式的啟用狀態跨呼叫記住**：
   - 以「端點＋模型＋回覆型別」為鍵。換模型或換端點自然是另一個鍵，不需要重置邏輯。
   - 連續 3 次（暫定）「帶強制格式的第一次嘗試回空」後，同一鍵的後續呼叫第一次就不帶強制格式。
   - 每 20 次呼叫（暫定）試一次帶強制格式，回得來就恢復預設。
   - 不帶強制格式的第一次嘗試若解析失敗，立刻恢復預設（計數歸零），避免對這個模型反而更糟。
   - 一次 `ChatJson` 呼叫算一次，不論內部重試幾次；互動與背景共用；狀態物件全站一個、執行緒安全。
   - 從未觀察到空回覆時，行為與現況完全相同。

3. **風險趨勢**：逐日堆疊長條（高、中），不用平滑曲線。長期間不另做彙總，由座標軸自動略過刻度；保留「表格」切換。
4. **處理進度**：一條橫向堆疊條（已處理、處理中、未處理）＋三個數字；其下一條風險層級條（高、中）＋兩個數字。三顆甜甜圈整組移除。顯示範圍不是「全部」時，處理進度卡沿用現行隱藏規則，趨勢卡補滿該列。
5. **主機排行**：有顯示名時標籤為「顯示名（IP）」，沒有時只顯示名稱；「主機｜問題」切換保留。`DashboardHostDto` 新增顯示名；控制器宣告型別與實際型別一致。儀表板畫面本輪不改。
6. **風險類型分布**：圖不變；卡片副標顯示問題總數並可下鑽（取代原本第一張 KPI）。
7. **工具列一列**：左側是目前條件的文字（期間、日期、比較基準；顯示範圍不是「全部」時也寫出來），右側是快捷期間、「更多條件」（自訂日期、比較模式、顯示範圍；有套用時標數量，沿用 `filterDisclosure`）、大螢幕、列印。
   - 移除「查同一問題的其他主機」按鈕與說明圖示（側欄已有「問題查詢」）。
   - 移除「自訂圖表」：固定編排的一屏版面，逐圖開關會留下空洞。既有的 localStorage 鍵不再讀取，也不主動清除。**本條推翻 WEB-SPEC §9.6 的自訂圖表設計。**
8. **一屏**：1280×800 與 1920×1080（中字級）都不需捲動。矮到觸發圖表下限時內容區仍可捲（既有行為）。

**大螢幕模式**

9. **進入與離開**：工具列「大螢幕」鈕，或網址帶參數（暫定 `display=wall`）。進入後隱藏側欄、頁首、所有橫幅、工具列控制項、「表格」切換；數字與圖表不可點。版面殼的隱藏由伺服器端依參數決定，進頁不閃現側欄。
   - 按鈕進入時同時要求瀏覽器全螢幕，被拒絕不影響模式本身。
   - 離開：按 Esc；滑鼠移動時右上角出現的離開鈕；由按鈕進入的瀏覽器全螢幕被使用者退出時也一併離開。離開後網址參數移除、回到一般模式。
   - 視窗寬度不足 992 時不提供：按鈕不顯示、參數忽略。
10. **標頭列**：產品名、目前條件的文字、最後更新時刻。這是大螢幕上唯一的說明文字。
11. **字級**：隨螢幕高度等比放大，圖表文字跟著放大；不受使用者的小／中／大字級偏好影響。目標：1080 高時第一排數字不小於 64px、2160 高時不小於 128px（暫定，以量測定）。
12. **自動更新**：
    - 上一次取數**完成後** 15 分鐘（暫定）才排下一次——不是固定間隔，重算再久也不會疊請求。資料主要在夜間排程後才變，15 分鐘足夠；3000 台時這是相對於「每次都重算」唯一需要的保護。
    - 快捷期間是滾動的（跨過午夜自動變成新的期間）；自訂日期則固定。
    - 分頁不可見時不取，回到可見時若已超過間隔就立刻取一次。
    - 更新時數字與圖表不做進場動畫；畫面不閃爍、不出現載入骨架（首次載入除外）。
13. **更新失敗**：保留畫面上的資料，標頭列以警示寫「更新失敗，目前是 HH:mm 的資料」，下一輪照常再試，成功後訊息消失。首次載入就失敗時顯示全頁錯誤並在下一輪重試。
14. **登入到期**：沿用現行行為（導回登入頁，登入後回到大螢幕網址）。本輪不做長效登入或展示專用帳號；需要整天不中斷時，站台可調高 `Jwt:ExpireHours`（全站生效）。
15. **配色**：沿用淺色。深色主題記入 BACKLOG。
16. 列印：不受大螢幕模式影響。

### 程式面

- 失敗續跑略過未滿間隔的待複查後，那一趟的待複查數若只算「本趟新記的」會是 0，第三趟不會發生。修訂 B 定案 1。
- 警告排除機制現況只認 logger 名稱。C-2 改為「嘗試層級一律不計」，不需要知道最後成敗，也不另造機制。
- 複查間隔常數原本可能在排程與管線各寫一份，明定只在一處。
- `SummaryCache` 存活上限 30 秒，大螢幕定時更新每次都會重算。改為「完成後才排下一次」＋15 分鐘間隔，不動快取。
- 強制格式狀態以端點＋模型為鍵，省掉重置邏輯；補上「不帶反而失敗就恢復」的對稱規則。
- 體檢與本機分析的執行條件不一致是 C-3 的根因方向，略過條件收在既有的單一判定函式。
- 頁首在側軌之外，視窗寬度就是它的寬度，不需要容器查詢。

### 管理者角度

- 排程狀態會更常是「成功」：C-2、C-3 之後，沒出事的晚上不再是黃燈；真正的失敗與降級照舊是紅或黃。被排除的警告在執行詳情與匯出仍看得到。
- 取數整晚失敗時，報表第一排的資料完整度會變色，戰情中心看得到；這補上了「沒告警不等於沒問題」在主管視角的缺口。
- 每晚可能多一趟複查取數（輕量：只查待複查的主機，PRTG 沿用同日結果）。排程頁的趟數會從 1 變 2，交付說明要提。
- 版號每輪都會變，匯出檔的「依版本」統計開始有意義；升級前後對不對得上一看就知道。
- 大螢幕帳號沒有特殊權限：看到的範圍就是該帳號的可見主機。
