## 批次 A：穩定性

### 定案與契約
- **A0 排程觸發判定的現存 bug（先修，A2 建在它上面）**〔親核〕：排程器判斷「這個窗口跑過沒」時只篩觸發來源為排程、**沒排除 AI 工作類型**，而 AI 排程自動觸發的來源也是排程——窗口重疊時 AI 那筆會讓取數被判成「跑過了」而靜默不觸發（`SchedulerHostedService.cs:139,170`、`AiAnalysisHostedService.cs:202,247`）。修法：「取數排程的觸發紀錄」抽成單一查詢點（排除 AI 工作類型），排程器兩處與 A2 補跑都只用它。另：執行紀錄建立得太晚，在它之前失敗＝該窗口無紀錄、每 60 秒重觸發一次——紀錄要在觸發當下就建立。
- **A1 寄信有上限**：單封寄送有總時限（暫定 30 秒），逾時視為該封失敗、走既有熔斷；排程輪詢呼叫通知時帶站台停止權杖。**輪詢迴圈任何一段都不得無上限等待外部系統**——通知整段另有總時限（暫定 5 分鐘），逾時寫 Warn 後繼續往下做排程判斷。
- **A2 補跑**：判定為「最近一個已結束的窗口實例沒有任何排程觸發紀錄，且距該窗口結束未超過一個週期（暫定 24 小時）→ 補跑一次」。補跑寫里程碑「補跑：上一個窗口（起～訖）未執行」。**觸發來源字面維持排程**（既有 5 處行為判定都以它為準，換字面會讓補跑不算跑過而重複補、或被誤判成手動佔用）；「這趟是補跑」用獨立欄位標示，執行總表據此顯示。需新增「上一個已結束窗口的起訖」計算與「依區間查取數排程觸發紀錄」查詢（現況都沒有）。
  - 什麼算「跑過」：該窗口實例區間內有排程觸發紀錄（不論成敗）；手動執行是否佔用沿用既有唯一判定點。
  - 一個窗口都沒設、排程未啟用：不補跑。全新安裝（沒有任何歷史紀錄）：不補跑（沒有「上一個」）。
  - 單向閘門的繞過：每個窗口實例只補一次；補跑本身失敗不再補（避免啟動迴圈），由 A3 的健康訊號接手；使用者永遠可以手動立即執行。
  - 補跑會落在上班時間：自動補跑只在「距窗口結束未滿 N 小時（暫定 4）」時進行且受資源守門約束；超過則不自動跑，改在健康告示上提供「立即補跑」按鈕由人決定。排程設定新增開關「錯過窗口時自動補跑」（預設開；消費端＝本判定）。
  - 連續停機數日：補跑的回望天數自動放大到涵蓋缺口（上限沿用既有回望上限），里程碑寫明涵蓋哪幾天。
  - 時鐘回撥／日光節約：判定只用窗口實例起訖與紀錄時間比較，同一實例不因時鐘回撥補兩次（表格式測試加一列）。
  - 修正 `ShouldTriggerNow` 的註解（現況宣稱涵蓋漏跑補償，不實）。
- **A3 健康訊號**：新增「排程新鮮度」判定——排程已啟用且距上次**成功**的取數排程執行超過門檻（暫定兩個週期）→ `degraded`。「成功」的定義現況只存在於執行監控的私有推導（6 個狀態值、警告不算成功、須排除 AI 工作類型）——抽成共用的唯一判定，健康、補跑、總表同一口徑；**本判定把「成功」與「有警告但完成」都算已更新**（資料確實更新了）。上次成功時間從執行紀錄（持久）讀。消費端三處：站台告示列（`Maintain` 與 `DevMonitor` 可見）、儀表板（所有人可見一行「資料更新至 yyyy-MM-dd」，過期時標警示色）、每日摘要信開頭。排程未啟用時不算 degraded，但儀表板同樣顯示資料日期。
  - 無管理能力者看到過期警示時，下一步是「請聯絡系統管理員」並列出管理員名單（不指向他進不去的頁）。
  - 不變成噪音：健康訊號可由管理者「確認並靜音到某日」（寫稽核）；摘要信只在狀態**轉變當天**帶警示段，之後每週提醒一次；刻意停用的模組（PRTG 關閉、排程關閉）不產生訊號。
- **A4 系統健康頁籤**：設定頁新增「系統健康」頁籤，收納：排程新鮮度、各背景服務最近一次活動時間、慢查詢清單（自資料保留面板搬來）、PRTG 批次寫入耗時埋點（數值寫入／取樣合併／清除三項進慢查詢統計）、快照待寫列數與捨棄數（1-8 的靜默捨棄改為看得見）。
- **A5 SQLite**：連線開啟時設 WAL 與 busy_timeout（暫定 5 秒）；提供啟動設定可關回原模式（第一晚出事能退）。SQL Server 分支不受影響。`HandlingBlobMigrator` 的單一大交易改分批提交（冪等、可續跑）。
- **A6 外部呼叫上限**：LDAP 繫結與搜尋設逾時（暫定 10 秒）並限制逐 DC 重試總時長；AI 逾時設定值夾在上限內（暫定不超過 600 秒）且**逾時不重試**（只重試連線類錯誤）；`PrtgTriggeredValueFetcher` 的輪詢加總時限；快照服務重用 `HttpClient`（設定變更時才重建）；PRTG 單發大查詢改串流解析或設回應大小上限，超過時出聲。
- **A7 保留清除獨立**：保留清除不再只依附分析執行——排程輪詢每日至少觸發一次（分析有跑就沿用，沒跑就單獨跑）。`lf_issue_first_seen` 隨問題最後出現日超過保留期清除；**未結案**交辦單與案件本身不清（那是進行中的工作），其事件「超過保留期且不在該單最近 200 筆內」者清除。
  - 破壞性判準反例：建單事件永不清（詳情頁要顯示誰何時建的）；仍被靜音／負責人設定引用的問題，其首見日不清。
  - B1 新增的執行輸出明細納入既有執行紀錄保留期。
- **A8 升級啟動的總指揮**：一次性工作分兩類——**啟動閘門內同步完成**（schema 變更含 J2／J4／K 的加欄與索引、H1 金鑰產生與重加密；全部在既有具名互斥內，早於任何背景工作）與**背景回填**（G1、K 回填與既有各支回填／遷移服務）。背景回填共用一個全域節流閘：同時最多一支在寫、取數排程執行中讓路。Windows 服務的啟動逾時不得被閘門內工作拖過（重加密資料量小；schema 變更沿用既有模式）。
- **A9 README 的 IIS 應用程式集區設定與 WAL 備份說明跟本批同時出**（不等批次 L）：補跑預設開＋IIS 閒置回收＝每天早上第一個開站的人觸發全量取數，文件必須同步到位。

### 驗收
- 寄信替身永不返回時：輪詢在時限內繼續、排程照常觸發、log 有 Warn（替身自驗，不用壓力測試）。
- A0：同一窗口內先有一筆 AI 排程紀錄→取數仍觸發；突變「查詢點拿掉工作類型排除」必紅。
- 補跑：表格式測試涵蓋「啟動於窗口內／窗口外當日未滿 N 小時／超過 N 小時（不自動、出按鈕）／隔兩天（回望放大）／無歷史／未啟用／補跑失敗後再啟動／開關關閉／時鐘回撥」九列；補跑那趟本身算「跑過」（不重複補）；突變「移除一個週期上限」必紅。
- A8：兩個行程同時首次啟動→閘門內工作只做一次；背景回填同時寫入數不超過 1（由節流閘自己斷言，不用壓力測試）。
- 健康：上次成功為三天前→degraded 且告示、儀表板、信件三處都出現；站台重啟後判定不變（持久來源）。
- SQLite：`PRAGMA journal_mode` 回 wal 的斷言；兩個 context 交錯寫入不擲 locked。
- LDAP／AI／PRTG 各一條「替身卡住→在時限內返回且錯誤訊息可讀」。
- 保留清除：分析未執行的日子清除仍發生；反例兩條不被清。

## 批次 B：執行紀錄說實話

### 定案與契約
- **B1 執行輸出進紀錄**：**不是放寬 log 層級**（那會把函式庫的 Info 全寫進資料庫，而且 PRTG 那幾支執行輸出實作根本不寫 log）——改為執行紀錄提供明確的「訊息」寫入入口，全部執行輸出實作（正式碼 10 個，規格前列清單；刻意靜默的要註明理由）統一走它。執行詳情預設摺疊顯示、可展開。每趟上限（暫定 2000 行），超過保留頭尾並標示略過行數。前端與 PRTG-SPEC §3a「原因見執行詳情」從此為真。
  - 取數與 AI 兩個 recorder 並行時各收各的（沿用逐實例識別，CLAUDE.md 紅線）。
- **B2 PRTG 產出數字**：執行總表 PRTG 徽章後帶「sensor N／finding M」；新增 outcome「無產出」——階段全成功但**該評估的東西一個都沒評估**（無啟用規則、範圍為空、鏡像為空）時用它，徽章為警示色並附一句原因。保守策略下 sensor 0 屬正常，不算無產出，改顯示「數值由快照供應」。
  - 什麼算「無產出」：規則評估數為 0 或範圍裝置數為 0；finding 為 0 但規則有評估＝正常。
  - outcome 是字串常數、沒有編譯期窮舉：前端對照表漏登錄會靜默顯示空白——本條自帶「後端全部 outcome 值都在前端對照表」的守門測試（現況不存在）。
- **B3 致命原因**：整趟致命例外的訊息必須出現在該趟執行紀錄。
- **B4 規則未套用**：偵測到「內建 PRTG 規則有新版未套用」或「無任何啟用中的 PRTG 規則」時，除 B2 的無產出外，PRTG 維護頁與系統健康頁籤各有一則提示並連到規則維護頁。
- **B5 PRTG 卡輪詢**：/runs 的 PRTG 卡與取數／AI 卡同一套輪詢；別處啟動的同步／回填在這頁看得到進度與停止鈕。**只做進度與停止**——啟動鈕在 E3 會搬走，本條不碰啟動鈕與其測試，避免同一段改兩次。
- **B6 逐日明細**：執行詳情加 PRTG 逐日表（日期、finding、歸戶主機、有無對應、目標／失敗 sensor），消費 `BatchRun.PrtgDays`；舊紀錄為 null 時整塊不顯示。回填與探測狀態顯示已執行時長（消費 `StartedAt`）。
- **B7 freshness 記錄**：每個 PRTG 資料類別（裝置／感測器／狀態變更／快照／數值）記「最後一次成功同步時間」與「最後一次取得筆數」，鏡像狀態頁與系統健康頁籤顯示；連續成功但 0 筆達 N 次（暫定 3）→提示，前提是該類別**歷史上曾有非 0**（從來沒有狀態變更的小站台不亮）。儀表板的 PRTG 失聯台數在結構同步寫入後推進資料版本戳。

### 驗收
- 以「PRTG 未啟用」「保守策略回望 3 天」「無啟用規則」三個情境跑 pipeline，執行紀錄各含對應白話訊息；突變「某個執行輸出實作不走訊息入口」由實作清單的反射守門抓到。
- 並行兩個 recorder 的既有隔離測試維持綠，並新增「訊息層級也隔離」。
- outcome 表格式測試：正常／保守 0 sensor／無規則／範圍空／階段失敗 五列。
- 致命例外測試：丟例外後讀回該趟紀錄含例外訊息。
- 前端：PRTG 卡輪詢的結構斷言（與另外兩卡共用同一個輪詢註冊點，不是第三份拷貝）。

## 批次 G：效能

### 定案與契約
- **G1** 清單分頁的舊列探測改為「套用本次篩選之後」才判斷（主線）。**這類列不是只有舊資料**：主機主檔更新失敗時分析照寫、`HostId` 為 0，今天仍會產生——寫入端對此出聲（Warn＋健康頁籤計數）。附帶提供冪等背景工作：能唯一對到主機的補上 `HostId`。
  - 破壞性判準：只補 `HostId`、不刪列；名稱對到多台主機時不補（列入對不到）。
- **G2** `UserStore` 開啟版本探測式快取（四個寫入路徑已確認都走原子更新）。兩個配套：①單筆查詢回傳的是共用參考，規格前 grep 消費端有無就地修改；②每次登入更新最後登入時間會推進版本、讓快取在尖峰反覆重載——最後登入時間搬出使用者清單（獨立存放）。每請求的啟用檢查因此不再每次反序列化整份清單。
- **G3** 五個跨請求快取滿了改逐筆淘汰（最久未用），上限放寬（暫定 256）；鍵的授權維度不變。五檔各改即可（共用元件收益不大）；淘汰行為由同一組測試案例套五個快取。
- **G4** 稽核與匯入 store 的啟動讀取改反向讀最後一筆（沿用既有反向讀取）；稽核查詢沒有日期範圍時後端自動補預設下界（暫定 90 天）並在回應標示「已套用預設範圍」，前端顯示。
- **G5** 主機清單的 PRTG 提示改依本頁 host_id 查詢；PRTG 衝突清單後端真分頁。

### 驗收
- G1：有一列無關舊列時，篩選不含它的查詢走 SQL 分頁（可觀測旗標或查詢計數替身斷言）；契約測試兩條路徑結果一致維持綠。
- G2：改使用者後下一次讀取立即看到新值；200 列清單頁對使用者 blob 的完整讀取次數為常數。
- G3：塞滿後最近使用的鍵仍命中；突變「淘汰改回整批清空」必紅。
- G4：啟動不呼叫整表讀取（替身計數）；無日期查詢回應帶預設範圍標示。

## 批次 H：安全

### 定案與契約
- **H1 金鑰檔**：金鑰來源優先序＝環境變數 → 金鑰檔 → 首次啟動自動產生金鑰檔。金鑰檔位置暫定 `DataRoot/keys/`，**不得與資料庫檔同目錄**（備份 DB 時不會順手帶走），產生時限縮檔案權限（只留站台執行身分與 Administrators；限縮失敗只 Warn）。啟動時一次性把既有內嵌金鑰時代的密文重新加密（冪等）。密文共 6 欄、全部在系統設定與 Sentinel 的整份型資料裡——重加密必須走各自 store 的原子讀改寫，不是 SQL 更新。解密保留「現用金鑰失敗→退回內嵌金鑰」過渡。
  - **多行程競態**：金鑰產生＋重加密在既有具名互斥內（A8）；兩個行程同時首啟只產一把。
  - **金鑰指紋**：金鑰檔帶識別碼，資料庫存一份指紋；啟動比對不符時明確報「金鑰檔與資料庫不相符」（還原配錯、多站台共用同一個資料庫各自 DataRoot 都會走到這裡），不讓它退化成下面的「視為未設定」。
  - **現用解密的靜默亂碼**：現行以「解密擲例外」判斷金鑰不對，錯金鑰約有 1/256 機率填充碰巧合法而回傳亂碼——金鑰輪替常態化後會被踩到。新密文改用帶驗證的格式（新前綴版本），舊格式仍可讀。
  - 未設環境變數的警告現況是每次加解密都印（註解宣稱一次），改為真的一次。
  - **降版不可逆**：重加密後舊版程式解不開（舊版只認環境變數與內嵌金鑰）。見〈升級與回滾〉。
  - 金鑰檔遺失＝密文全部解不開：所有解密點失敗時不得讓頁面 500 或讓排程整趟失敗，視為「未設定」，並在系統健康頁籤與設定頁對應欄位顯示「無法解密，請重新輸入」。
  - README 明寫：金鑰檔要另外備份、還原 DB 到新主機要一併搬金鑰檔或重新輸入密碼；IIS 集區身分／服務帳號需對金鑰目錄有寫入權；啟動 log 印出金鑰來源與目錄的有效權限摘要。（資料搬運匯出檔不含密文，不受影響。）
- **H2 登入節流**：帳號與來源 IP 兩個維度各自計數（暫定：帳號 5 分鐘 10 次、IP 5 分鐘 50 次→暫停 5 分鐘；IP 門檻較寬是因為反向代理或 NAT 後方多人共用 IP，避免一人打錯鎖全公司）；回覆不區分帳號存在與否；**節流命中時不呼叫 AD**（避免替攻擊者鎖網域帳號）；同來源同帳號的連續失敗稽核合併計數而非逐筆寫。救援帳號**不受 IP 維度節流**（AD 掛掉時它是唯一入口），只受自己既有的鎖定。IP 維度只在取得到可信來源 IP 時啟用——站台現況沒有處理轉送標頭，本條一併加入（信任的代理清單為啟動設定；未設定時 IP 維度對代理位址停用）。節流狀態在系統健康頁籤看得到並可手動解除。
- **H3 環境欄杆**：已知 JWT 金鑰、已知救援密碼雜湊、Stub 驗證三項改為「只有 Development 放行」，其餘環境值一律拒絕啟動；免密碼 demo-admin 只在 Development 建立。未設環境變數時預設就是 Production、現況已擋，本條實際影響的是「刻意設成 Staging／Test」與「用 Stub 做內網展示」的站台——拒絕訊息要印出目前環境值、是哪一項、以及 Windows 服務與 IIS 各自怎麼設環境變數。
- **H4** PRTG／NetIQ／AI／SMTP 的 URL 類設定在進稽核、回前端、進例外訊息前一律過遮罩；儲存時若 URL 的查詢字串含機敏參數直接拒絕並提示改填專用欄位。
- **H5 降權即時**：每請求的使用者檢查除「啟用中」外一併比對權限版本。能力來源有三條——群組與角色、主機負責人、問題負責人——三條的寫入點都要推進版本（群組 8 處、另兩條規格前列清單），漏一條就是「移出群組即時、拔掉負責人不生效」；不符時要求重新登入。登出後的 token 在到期前列入行程內撤銷清單（重啟清空可接受，註解明講）。
- **H6** innerHTML 守門擴及 `wwwroot/js/core`；`core/ui.js` 現有 4 處插值指派同批改為 DOM 組裝（守門一擴就會紅，必須同批）。I1 的錯誤態元件也住同一檔——本批只動這 4 處。登入回跳網址的安全檢查補上反斜線變形（現況只擋雙斜線）。分析 prompt 的 log 原文加資料界線標記（照既有洞察 prompt 的寫法）。

### 驗收
- H1：無環境變數無金鑰檔啟動→產生金鑰檔、既有密文重加密後以新金鑰可解、再啟動不重複加密；刪金鑰檔後各設定頁不 500 且顯示重新輸入提示、排程照跑（對應來源略過並出聲）；密文欄位清單以反射守門（新增密文欄位沒進重加密清單→紅）。
- H2：超過門檻回節流且 AD 替身未被呼叫；稽核列數不隨失敗次數線性成長；不同帳號同 IP 未達 IP 門檻時互不影響。
- H3：環境值 `Staging`＋出廠設定→啟動失敗且訊息指出哪一項。
- H4：含 `passhash=` 的 URL 存檔被拒；測試連線失敗的稽核明細不含機敏字串。
- H5：移出 admin 群組後下一個請求即被要求重新登入。
- H6：守門測試掃到 core 目錄；突變（在 core 放一處插值 innerHTML）必紅。

## 批次 C：處理說明

### 定案與契約
- **C0 回覆彈窗不丟字**：交辦單回覆是彈窗——有未送出內容時按 Esc、點遮罩、點關閉都要先確認；工作階段逾時被導去登入再回來，內容仍在（靠 C2 草稿）。
- **C1** 風險日詳情的處理表單：勾選變動只更新「套用對象」區，不重建輸入欄位；說明、到期日、狀態選擇在任何重繪後保留使用者輸入。併發衝突重建面板時同樣保留使用者剛打的字。
- **C2 草稿**：範圍縮為兩處——風險日詳情的處理表單與交辦單回覆彈窗（其餘輸入處短、C1 修好後收益低）。瀏覽器端暫存未送出的文字（鍵含使用者、頁面與對象；送出成功或使用者清除後刪除；**使用者主動登出**時清除本人全部草稿，**逾時被登出不清**；儲存不可用時功能照常）。帶入類動作（草稿還原、沿用上次、常用語、AI 整理）在文字框非空時一律先確認取代或附加；草稿只記使用者最後看到的文字框內容。
- **C3 長度三層把關**：上限 1000（D4a）。前端即時字數計數並在超過時擋送出；全部請求 DTO 有長度驗證（補上交辦單回覆）；寫入前依欄位上限截斷——協調層串接狀態與台數**之後**再截，截斷時使用者文字優先、附加資訊可省略。同一份說明會寫進三個地方（交辦單事件有上限、處理狀態與案件的說明欄無上限）→三處口徑一致，不得出現「成員列完整、時間軸殘缺」。管理者代為結案的理由同型一併把關。順手修：回覆不填說明時時間軸顯示英文狀態碼（前端只認全形冒號）。
- **C4 必填在後端**：`wont_fix` 與 `escalated` 說明必填、`observing` 到期日必填，由後端唯一驗證點把關（日層級與問題層級共用）；「確認不處理」走同一個輸入流程。必填未填時欄位下方有文字訊息並 focus；移除與原生驗證重複的那一套；失敗只跳一個 toast。
- **C5 批次回覆的一致性**（複檢後重定）：現況三個協調層都不持有資料庫連線、寫入散在二十多個各自提交的方法，包成單一交易等於改寫整層 store 介面——列入明確不做。改為：①送出前全部驗證（含已結案、權限、長度、必填）任何一張不過＝零寫入；②驗證通過後逐張寫，**每張成功即寫稽核與通知**（現況部分失敗時稽核與通知一行都不寫，這比原子性更急）；③中途失敗時回應列出「已完成哪幾張、失敗哪一張與原因、未處理哪幾張」，前端據此只保留未完成的勾選讓使用者直接重送。靜音選「代為結案」同一模式。已結案的單在列層不可勾選（比照成員層）。
- **C6 AI 整理**：
  - 入口：處理說明輸入處旁的「AI 整理」按鈕；AI 未設定時整個按鈕不出現（沿用狀態探測）。AI 服務提供者不是地端時，按鈕旁標示「內容會送至外部 AI 服務」。
  - 行為：把文字框目前內容送後端→回傳四段條列（問題／原因／處理／結果與後續；原文沒提到的段落省略，**不得編造**）→填回文字框，原文以「復原」一鍵還原；整理中顯示進行狀態、可放棄等待（後端呼叫沒有取消權杖，放棄＝前端不再採用回應）；失敗或逾時顯示可讀訊息、文字框不變。「復原」還原到**最近一次整理前**的內容，復原後或送出後按鈕消失；整理後使用者手改再按整理＝以手改後的內容為新原文。
  - 後端：新端點需 `Handle`；輸入上限 4000 字、空白直接回提示不呼叫 AI；過短（暫定少於 20 字）時提示明講用途「整理你已經寫下的內容，不會補你沒提到的事」並直接打開常用語；輸出超過 1000 字時要求模型精簡一次，仍超過則截斷並標示；每使用者節流（暫定每分鐘 6 次）；提示注入圍欄照既有寫法（輸入視為資料）；輸出走既有清洗與簡繁轉換；帶入問題脈絡（問題名稱、主機數）讓四段對得上；一次回覆多張不同問題的單時不帶脈絡、只整理文字。
  - 夜間 AI 排程執行中：現況沒有可讀的忙碌訊號——以 AI 排程的執行狀態為訊號，按鈕旁提示「AI 分析排程執行中，可能較慢」；逾時沿用 chat 設定。
  - 稽核：記「誰、何時、對哪個對象、輸入字數、成功與否」，不存原文與輸出。計量：進既有 AI 用量統計（現況沒有類別維度，加類別要改計量介面與存放結構——不做；整理次數由稽核統計即可）。
  - 此輸出**只可作為文字框內容**，不得被任何自動判定消費。
- **C7 沿用與常用語**：文字框上方「沿用此問題上次的說明」（取檢視者可見範圍內、同一問題最近一筆非空說明，顯示來源主機與日期，點了才帶入）；常用語為每使用者自訂清單（上限暫定 20 條），管理者可設全站預設。現況全站沒有每使用者偏好的存放處——新建獨立的使用者偏好存放（不塞進使用者清單，避免放大登入成本）。沿用說明的查詢需要「依問題查最近一筆」的索引與查詢方法（問題層級的說明是真欄位、可下推）。

### 驗收
- C1：JS 測試——填說明→勾選／取消／全選→值仍在；突變「重繪時重建輸入欄位」必紅。
- C3：1001 字請求在每個端點皆 400；使用者文字 1000 字時協調層寫入值不超過欄位上限（長度斷言）。
- C4：直接打 API 送 `wont_fix` 無說明→400（日層級與問題層級各一）。
- C0：彈窗有內容時三種關閉方式都先確認（JS 測試）。
- C5：混入一張已結案→零寫入；第三張寫入丟例外→回應含「已完成 2／失敗 1／未處理 N」、前兩張各有稽核。
- C6：AI 替身回四段→端點回傳；替身逾時→可讀錯誤；未設定→狀態端點回不可用；超過節流→429；稽核不含原文；缺 `Handle`→403；注入字串仍被包在資料界線內（prompt 組裝的快照測試）。
- C7：不可見主機的說明不會被帶入（授權維度測試）。

## 批次 D：處理人動線

### 定案與契約
- **D1 我的交辦**：處理人（有 `Handle`、無管理能力）登入後落地頁為自己的工作頁；導覽沿用既有名稱「我的交辦」（已有徽章）並移到第一項，儀表板為第二項——**全案用詞統一為「我的交辦」**，說明書新章節同名。管理角色落地頁不變。登入前原本要去的網址（通知信連結）優先於落地頁。
- **D2 頁面結構**：主清單以交辦單為單位，預設只列進行中、依優先序排序；每列直接顯示問題白話名稱、台數、最近發生、期限。列上的動作＝「回覆」（清單列內的重複動作樣式降階，不算頁面主要按鈕；I3 守門同口徑）。
  - **回覆的預設對象**：單一主機的單→直接回覆；多台的單→回覆面板先列出成員並**預設全不選**，提供「全選」與依主機群組快速選取——不得一鍵把 96 台一起結掉。
  - 期限可在列上就地修改（只改到期日、不動狀態與說明、記歷程）。
  - 空狀態分流：可見主機為 0→「尚未被授權任何主機，請聯絡管理員」（F6 同句）；有授權但名下沒單→「目前沒有被指派的工作」與前往儀表板的連結。「依主機」「被指派的風險日」收進「進階檢視」折疊區，預設收合。
- **D3 就地回覆**：回覆成功後只更新該列（結案的列以完成樣式淡出），不重打整頁、不丟勾選與展開、捲軸不動；回覆面板有「儲存並下一筆」，依目前排序移到下一張未結單；全部結完顯示完成狀態。下一筆的表單：狀態沿用、說明清空並提供「帶入上一筆的說明」；必填沒過時停在原單不跳。
- **D4 跨頁勾選**：換頁保留勾選並顯示「已選 N 張（含其他頁 M 張）」；**改變篩選或排序條件時清除全部勾選並提示**（不得回覆到看不見的單）；已結案列不可勾。
- **D5 入口改導**：儀表板未處理卡、問題查詢「去處理」、工作頁列連結——該出現點屬於**檢視者名下**某張進行中的單時，導向該單的回覆（工作頁定位到該列並展開）；否則維持導向風險日詳情。風險日詳情頁頂部若該主機該問題屬於檢視者的單，顯示「此問題屬於交辦單 #N，共 M 台——一次回覆全部」。
- **D6 詳情頁回覆入口**：交辦單詳情頁對處理人本人顯示回覆入口（消費 `viewerIsHandler`）；通知信連結落地後可直接回覆。單已被改派時顯示「這張單已改派給〈姓名〉」與回到我的交辦的連結（不是空白或拒絕存取）。
- **D7 概念收斂**：處理人視角的畫面用詞只出現「交辦單／主機／狀態」三個概念；「案件」一詞只留在管理視角與進階檢視。三種不處理機制在處理人畫面只露出「不處理（需說明）」，靜音與抑制屬管理動作不在此露出。
- **D8 說明書開放**：`/help/manual` 與提問端點改為登入即可；章節清單現況沒有任何能力中繼資料——每章新增「所需能力」欄（未標＝所有人可見），章節依能力過濾（維護類章節對無 `Maintain` 者隱藏，AI 提問的檢索範圍同樣過濾）；新增處理人章節「我的交辦：三分鐘上手」。導覽的說明書入口對所有人顯示。
- **D9 畫面沒接的欄位**：問題檔案顯示靜音歷程（最近 10 筆）；使用者詳細頁的被指派歷程含「已被改派走」（由處理歷程的改派紀錄反查，**不新增第二事實來源**，只在顯示層合併）；日層級指派與立即派工建單時寄建單通知（沿用既有建單信與熔斷；同一次操作多張單合併一封）。

### 驗收
- 落地頁：只有 `Handle` 的使用者登入後導向工作頁；管理者不變；帶回跳網址時以回跳為準。
- D3：回覆後的 API 呼叫不含整頁三支；勾選狀態保留的 JS 測試。
- D5：出現點屬於名下單→連結指向工作頁定位參數；不屬於→風險日詳情。兩條都要測，避免全部改導把管理者帶錯頁。名下進行中的單每個請求只查一次（不逐列查）；儀表板回應現況沒有處理人資訊，需補欄位。
- D2：多台的單打開回覆面板時選取數為 0；期限就地修改只產生一筆到期日歷程。
- D7：處理人頁面文案守門（工作頁相關檔不含「案件」字樣，進階區除外）。
- D8：無 `Maintain` 者取章節清單不含維護章節、直接打維護章節 id 被拒；提問不會引用被過濾章節。
- D9：改派歷程測試；建單信在兩條路徑各寄且受熔斷保護。

## 批次 E：排程與 PRTG 合一

### 定案與契約
- **E1 立即執行串回填**：立即執行的確認框在「PRTG 已啟用、保守策略、回望 N>1」時出現預設勾選的「一併補 PRTG 數值 N 天」與估算（感測器數×天數、預估耗時）；勾選則取數結束後**由同一趟接續回填**（天數＝回望天數，不讀設定的回填天數），執行紀錄同一列呈現兩段。回望 1 天或激進策略不出現此選項（激進本來就取）。指定主機範圍時回填也只做該範圍。
  - 回填是附掛尾段：分析結果發佈、AI 就緒訊號、派工與通知都不等它。
  - **現況回填會被「取數執行中」擋下，而該狀態要到整趟回傳後才釋放**——同一趟接續會被自己擋住。契約：回填演算法本來就在 Core 且範圍／天數是傳入參數，由分析主流程透過介面直接呼叫（比照既有結構同步閘門的介面先例）；互斥定義為「取數與其尾段回填是同一趟的兩段、彼此不互斥，對外仍佔用回填的執行權」（PRTG 維護頁的回填狀態卡看得到這段進度、可停止）。回填既有的「近 N 天有無對應」閘門改讀本趟天數，不再讀設定的回填天數。
  - 請求新增欄位自帶 JSON 綁定守門測試（站台預設忽略未知欄位，既有綁定測試不會擋）。
  - 互斥沿用既有四向互斥；接續回填被擋（探測中）時寫里程碑說明、不算整趟失敗。
  - 夜間排程不自動回填（只有使用者手動回望才有「過去日」需求）。
- **E2 回填自癒**：回填啟動時鏡像為空或近 N 天無對應→自動先跑結構同步再回填（進度顯示「先同步結構」）；同步失敗才擋並給正確指路。擋門訊息全面校對，不再叫人等夜間排程。
- **E3 按鈕收斂**：/runs 的 PRTG 卡只顯示狀態（啟用與否、策略、監看裝置數、上次同步、快照狀態、進行中工作的進度與停止鈕）與一個「前往 PRTG 維護」連結；啟動類按鈕（同步結構、回填）只在 PRTG 維護頁。卡上明講「結構同步會在每次執行時自動進行」。
- **E4 範圍殘留**：守門關閉→守門裝置不入範圍；人工對應的目標主機停用或不存在→不入範圍且在對應清單標示「目標主機已停用」；指定主機更新→PRTG 只處理該主機對應的裝置（範圍參數必填，CLAUDE.md 紅線）；感測器鏡像的範圍外清除**沿用既有那一套**（「本趟沒刷新到就清」），不另立第二套（兩套會與快照補抓形成「補抓→清除→再補抓」來回）；本條只新增**數值與狀態變更**依範圍口徑的清除，並明訂與既有保留天數清除的先後。
  - **兩個「範圍」改名**（同頁兩個意思，使用者無從判斷會被清的是哪一種）：由主機對應算出的裝置集合稱「**監看裝置**」；數值取數的主機範圍設定稱「**數值取數對象**」。清除說明指名用的是「監看裝置」。全站用詞表、說明書、PRTG-SPEC 同步。
  - 破壞性判準反例：
    - 範圍**計算失敗、回空、或裝置鏡像本趟未成功更新**→不清。
    - **縮圈趟一律不清**〔親核既有保險只有「對應成功數為 0」，單台時為 1 擋不住〕：指定主機更新這種「本趟範圍不是全量」的執行，任何清除都不得發生——否則單台更新會把其餘裝置的感測器鏡像當成「沒刷新到」清掉。
    - **範圍異常縮小不清**：監看裝置數較上次成功清除時的基準縮小超過門檻（暫定 30% 或 50 台取大者；DNS 大批失敗、誤停用一批主機、人工對應被清都會走到這裡）→不清、出警示，由管理者在維護頁看過「本次會清除哪些裝置、幾列」的預覽後確認。首次套用（無基準）同樣走預覽確認。
    - **守門關閉的雞生蛋**：守門裝置是從感測器鏡像反推的——守門一關就清掉它們的感測器，日後重開守門時自動偵測無物可認。守門關閉時這些裝置不取數值，但其感測器鏡像保留。
    - 主機暫時停用又啟用的，清了就是清了（可由回填補回）——在停用主機的確認框明講。
  - 範圍超過 500 台改全站分頁、快照超過 2000 顆單發全站：維持（效能取捨），但在維護頁「估算規模」明示目前走哪條路徑。
- **E5 取數範圍說實話**：保守策略下「取數範圍」下拉顯示「保守策略下不適用（數值由快照供應，快照涵蓋全部已對應裝置）」且停用；/runs 卡同步。策略與範圍兩個設定在畫面上相鄰並有一句話講清楚關係。設定值本身保留（切回激進時沿用）。
- **E6 新主機當晚生效**：快照服務已有「範圍內缺感測器的裝置補抓」且受互斥保護——本條補的是三件事：主機新增或改 IP 時**立即喚醒**它（不等下一輪）、一併補近期狀態變更、主機詳情在補抓完成前顯示「PRTG 資料準備中」而非「無資料」。
- **E7 探測可停止**：環境探測加停止鈕與取消端點（沿用回填的取消模型）。

### 驗收
- E1：保守＋回望 3 天＋勾選→同一趟紀錄含回填段、回填天數＝3；未勾選→不回填；激進→選項不存在；指定主機→回填目標只含該主機裝置；AI 就緒訊號早於回填段開始。
- E2：空鏡像啟動回填→先同步再回填；同步失敗→錯誤訊息含「同步結構」指路。
- E4：表格式測試（守門開／關 × 對應目標啟用／停用／不存在）；範圍計算擲例外、回空、鏡像未更新、縮圈趟、縮小超過門檻→零刪除（五列各自獨立）；守門關閉後其裝置的感測器鏡像仍在；突變「移除任一道保護」必紅。單台更新的 PRTG 查詢目標數＝該台裝置數，且其餘裝置的感測器鏡像列數不變。
- E5：保守策略下設定端點回傳「不適用」旗標，前端兩處一致。
- E6：新增有 IP 的主機→補抓被排入；互斥中→延後不丟。

## 批次 F：初期設定

### 定案與契約
- **F1 常駐引導列**：未達就緒時，`Maintain` 使用者每頁頂部顯示「初始設定 X／Y 完成——下一步：〈步驟名〉」連到該步；可暫時收合（本次工作階段）、可關閉；全部就緒自動消失。
  - 關閉是**每位管理者各自**的選擇（前任關掉不影響新接手的人），且任何時候可從「設定 > 系統健康」的初始設定區重新打開——現況隱藏開關只在全部就緒後才看得到，做到一半關掉就再也叫不回來。
  - **頁頂告示區總量**：現況已有「分析執行中」「案件逐日同步」兩條，加上精靈返回、引導、健康共五條。規則：最多同時顯示兩條，優先序＝健康 > 執行中 > 引導 > 其餘；超過收成一行「另有 N 則提醒」。精靈返回列與引導列合併為同一元件。
- **F2 精靈步驟**：順序改為 儲存體 → **AD 驗證** → 管理員帳號 → **部門群組** → NetIQ → 主機群組與授權 → **PRTG（可跳過）** → 郵件（可跳過）→ AI（可跳過）→ 排程。AD 在使用 AD 驗證模式時不可跳過（規格前核對驗證模式的判定點）。步驟定義現況散在三處（漏改合法清單的症狀是「按跳過沒反應也沒錯誤」）——收斂為單一定義。「可否跳過」現況是寫死的常數且就緒服務沒有注入驗證相依，需注入驗證模式判定。
  - **升級站台**：升級當下若舊狀態已是全部就緒或已隱藏，一次性把新增步驟記為已跳過——引導列只對全新安裝與本來就沒設完的站台出現；已運作一年的站台不會突然每頁跳提示。

## 批次 K：來源名稱大小寫正規化

- **根因**：來源名稱在寫入時沒有正規化，SQL 端用 `UPPER()`（無法走索引、SQLite 只轉 ASCII）、C# 端多處區分大小寫，同一問題大小寫不同時處理標記不互通。
- **這不是新機制**：交辦單已有唯一的來源正規化規則，案件表與首見日表也已有 `source_key` 欄，資料層註解早已定案「存正規化欄位優於 `UPPER()`」——K 照抄這套，不另立第二種正規化。
- **契約**：`lf_top_issues` 加寫入時以**既有那一條正規化規則**計算的 `source_key`＋索引；全部 SQL 比對與分組改用它；問題鍵的比對全專案改為單一比較器（量級：正式碼約 236 行／46 檔）。
  - **最大斷點**：問題簽章鍵有「字串一字不變、可反解回顯示用原字」的不變式——正規化**不能做在鍵的產生處**，只能做在比較器。
  - 三處最危險、各自要有反例測試：可見範圍服務的授權快取鍵（放寬比對＝放寬可見範圍）、每日紀錄寫入的去重（放寬會靜默少寫 finding）、兩個自訂比較器的相等與雜湊必須同時改。
  - 現況已有三處不分大小寫、其餘區分——K 要一次收齊，否則只是換個方向分岔。
  - 既有處理狀態／案件／交辦單／靜音／問題負責人的鍵在讀取時以同一比較器比對（**不改寫既有鍵的字面**，避免不可逆）。「最近一次發生」的來源過濾下推到 SQL。
- **回填**：背景分批補 `source_key`（冪等、可續跑、進度在系統健康頁籤）；回填完成前查詢走舊路徑（以完成旗標切換），完成後才切新路徑——任何時刻結果一致。
- **合併效應要先量**：正規化後原本被當成兩個問題的會合併，KPI 與排行會變。回填前先產出「會被合併的問題組」預覽列在系統健康頁籤；為 0 組就是純效能改動。
- **驗收**：契約測試新舊路徑結果逐位一致（大小寫無差異的資料集）；大小寫混雜資料集——處理標記互通、計數合併；回填中斷續跑；規模壓測比較前後耗時。
- 獨立 commit。任何一條驗收不過＝本批不併入，其餘批次照常收尾。
