### 依據（調查結論，細節見討論紀錄）

以下來源的關鍵數值，主代理都已抽查原始碼或原文：

- **根字級不改**：Bootstrap 5.3 的 `$font-size-root: null`、Tabler 的 `$font-size-root: null`。15 個後台樣板與元件庫裡，沒有一個用 vw 或 clamp 當根字級；只有 Grafana 把根字級固定在 14px。
- **WCAG F94**：用視窗單位調整的文字，無法透過縮放或調整字級放大。
- **字階是挑選的固定級距**：Tailwind 是 12／14／16／18／20／24／30／36。只有標題可以隨視窗流動。
- **按鈕字級不大於內文**：Bootstrap 的 `$btn-font-size` 和 `$input-font-size` 都等於 `$font-size-base`；shadcn 的 sm／default／lg 三種按鈕都是 `text-sm`，只差高度。
- **密度只調間距與列高**：大螢幕靠內容最大寬度與欄數處理，放大交給作業系統縮放。
- **圖表要自己同步字級**：Chart.js 預設 12px，不會自動跟 CSS 走，要從 token 換算，並在字級改變時重畫。

### 全批次共同契約（每一段的規格與驗收都要逐條抄入）

1. **頁面與元件只引用文字角色或字階 token**，不寫字級數值。例外只有大螢幕模式既有的 `64px × 倍率`、`18px × 倍率` 兩處。
2. **不改類別名稱、不刪既有類別、不改標記的巢狀結構**。真的需要時只新增修飾類別，並在回報列出。
3. **不新增沒有消費端的 token**。每個 token 至少要有一處使用。
4. **用 Bootstrap 既有的 CSS 變數接上**（`--bs-body-font-size`、`--bs-btn-font-size` 等）。站台用的是預先編譯好的 `bootstrap.min.css`，所以不另做一套平行的字級機制。
5. **點擊區下限不變**：全站 24×24；處理人會用的三個頁面（我的交辦、交辦單詳情、風險日處理面板）36px 高。**小、中、大三檔都要成立。**
6. **對比與焦點**：`AccessibilityUiTests`、`DesignSystemGuardUiTests` 維持綠。
7. **不寫 `style=` 屬性與不帶 nonce 的 inline script**：`CspPolicyGuardTests`、`InlineStyleUiTests` 維持綠。
8. **既有 104 個量測情境全數通過**，包括大螢幕一屏、輪詢穩定、列印、互動情境。情境裡的期望值不得為了通過而修改；確實因為字級改變而必須調整的，逐條列進執行紀錄（舊值、新值、理由），由主代理核可。
9. **每批完成後產生前後對照**，主代理親看之後才提交。
10. **不新增 JS 模組、設定項、互動與文字角色類別**。字級來源只有 `base.css` 的字階 token 一處；圖表透過一個函式讀取，不在 JS 重寫換算規則。
11. **批次 B～D 的中間狀態不能單獨上線**。合併到 dev 的單位是整輪。
12. **畫面量測在這台 Mac 的 Chrome 執行**。每批推送後確認 CI（Windows 與 Linux）的測試結果。

## 批次 B：基準與字階

### 現況與核對結果

- 根字級在 `base.css` 的 `html { font-size: calc(clamp(15px, 0.5vw + 13px, 20px) * var(--lf-font-scale, 1)); }`。小／大兩檔由 `:root[data-font-scale]` 設定倍率 .9／1.15。偏好由 `layout.js` 的 `initFontScale` 讀 `localStorage` 的 `lf.fontScale`。
- 字階 token 在 `base.css:121-127`：xs .78／sm .86／base .95／lg 1／xl 1.2／2xl 1.45／stat 1.95。
- `--lf-control-font-size-sm: 1rem`（`base.css:133`）被 `.btn-sm`（`base.css:324`）使用，`--lf-control-height-sm`（`base.css:134`）也由它推導，共 2 處。
- `.btn` 沒有覆寫字級，沿用 Bootstrap 預設的 1rem。
- `.form-control`／`.form-select` 寫死 `font-size: 1rem`（`base.css:440-450`）。註解寫明這是使用者在回饋二十七輪 P9 指定保留的大小。新系統下內文本身就是 1rem，兩者相等，**不推翻 P9**。
- 所有 `@media` 都用 px，根字級改變不會讓中斷點位移。
- 側欄寬 `15.25rem`、`brand-align.js` 讀實際字級，兩者都會跟著縮放，不需要另外處理。
- 本輪推翻第十四輪 UI-1 的決定（`base.css:245-248` 註解：「舊版 16px 在 2K/4K 偏小，改 clamp」）。理由是 F94 的風險，加上業界做法；大螢幕的需求改由使用者偏好、瀏覽器縮放與第 73 輪的版面格線滿足。

### 定案

- `html` 的字級 = 瀏覽器預設 × 偏好倍率：小 .875／中 1／大 1.125。不含 vw、vh、clamp，也不寫死 px。
- 偏好機制不重做：`data-font-scale`、`--lf-font-scale`、`localStorage` 的鍵與值、`lf:font-scale` 事件全部沿用。這樣大螢幕模式的 `:root.lf-wall` 規則仍然優先，大螢幕不受偏好影響的既有行為不變。
- xs 設下限 12px（任何檔位、任何瀏覽器字級下都不小於 12px）。小檔的 .75rem 只有 10.5px，中文看不清楚。
- `.form-control-sm`／`.form-select-sm`（全站約 100 處）維持等於 base。同一列的 `.btn-sm` 是 sm，兩者字級不同是刻意的：輸入框沿用 P9 的指定，而且 iOS Safari 遇到小於 16px 的輸入框會自動放大整頁。
- Bootstrap 的浮層與元件（下拉選單、提示框、popover、toast、分頁、頁籤、modal、alert）都用 rem，會跟著根字級變化；本批要確認它們的計算字級都落在字階內。
- 字階數值換成「字級系統」一節的那組數值；不新增 token。
- `body` 用 base；`--bs-body-font-size` 同步。
- `.btn`、`.form-control`、`.form-select`、分段控制 = base；`.btn-sm` = sm。
- 移除 `--lf-control-font-size-sm`（與 sm 重複）。`--lf-control-height-sm` 改由 sm 推導，並維持「篩選列的輸入框、下拉選單、按鈕、膠囊同高」這條既有行為。
- 守門（C#，CI 會跑）：
  - `html` 的字級規則不含 vw／vh／clamp。
  - 字階 token 的值等於上述清單，且相鄰比值 ≥ 1.11。
  - 按鈕與輸入框的字級來源不大於 base。

## 批次 C：文字角色對應與點擊區

### 現況與核對結果

- 文字角色類別在 `components.css:74-78`（`lf-text-title`／`-meta`／`-label`／`-data`／`-alert`）。

## 批次 D：圖表字級

### 現況與核對結果

- `core/charts.js:60-73`：字型寫死成 `"Segoe UI", "Microsoft JhengHei"`；`fontSize(base)` 把 11／12／13px 乘上模組變數 `fontScale`。
- `setFontScale` 只有 `reports.js:1048` 在大螢幕模式呼叫，倍率是 `scale × WALL_CHART_FONT_BOOST`（1.4，定義在 `reports.js:436`）。`charts.js:152` 在倍率不等於 1 時另外覆寫座標字級。
- `reports-wall.behavior.mjs:542-577` 有 4 個案例在測 `setFontScale`。
- 字級偏好切換時，`layout.js:372` 會發出 `lf:font-scale` 事件；`reveal.js:108` 已在監聽。圖表目前沒有監聽。

### 定案

- 圖表字級從字階取得計算後的 px：座標與圖例用 xs，提示框用 sm。做法是讀取套用該 token 的元素的計算字級，這樣偏好、瀏覽器字級與 12px 下限都由 CSS 算好，JS 不重寫換算規則。讀取集中在 `charts.js` 的一個函式，行為測試可以用替身取代；`charts.js` 不得再出現字級數字常數。
- 大螢幕模式的倍率改變（視窗大小改變、進入、離開）時，圖表要用新的字級重畫。
- 字型改讀 CSS 的 `--lf-font-family`。
- 收到 `lf:font-scale` 時，現有的圖表要更新字級並重畫，不需要重新載入頁面。已銷毀的圖表不得殘留監聽。
- 移除 `setFontScale` 與 `WALL_CHART_FONT_BOOST`。依賴方與處理方式：
  - `reports.js:1048`：改成不呼叫；大螢幕模式靠自己的根字級自動放大。
  - `charts.js:152` 的覆寫分支：一併刪除。
  - `reports-wall.behavior.mjs` 的 4 個案例：改成驗證「圖表字級與根字級成正比」，並同步 C# 的 `InlineData`。
- 大螢幕模式下，1080 高時圖表座標字不得小於改版前（11px × 1.4 ≈ 15px）。用 xs 達不到時，大螢幕模式可以改用 sm。這個數值暫定，執行端可以依實測推翻，但要回報理由。

## 我無法驗證、需要你實機確認的部分

- **4K 螢幕在 100% 縮放下的觀感**：本輪不再隨視窗放大字，4K 用 100% 縮放時字會偏小。這是刻意的取捨，靠作業系統縮放、瀏覽器縮放、「大」字級，以及第 73 輪的版面格線處理。請在實際 4K 螢幕上看一次，判斷能不能接受。
- **中文在 12～14px 的清晰度**：我量得到計算字級，量不到 Windows ClearType 在實際螢幕上的渲染效果，特別是「小」字級的 12.25px。
- **既有使用者的感受**：「中」會從約 19～20px 變成 16px。
- **Windows 上的換行與溢出**。量測在這台 Mac 的 Chrome 執行，中文用的是蘋方；正式環境是 Windows 的微軟正黑體，字寬不同，換行位置可能不一樣。CI 會在 Windows 跑守門測試，但不跑畫面量測。請在 Windows 上開幾個主要頁面看一次。
- **原本選「大」的人**（定案 6）：改版後最大只有 18px，需要更大要用瀏覽器縮放。
- Mac、行動裝置實機，以及正式站台的資料量。

## 站台側待辦（不是程式改動）

- 交付說明寫明：「字級整體調整為業界標準大小；想維持原本大小，請在右上角改選『大』」。
- `presentations/` 下的簡報如果含畫面截圖，需要重新截圖。

## 明確不做（本輪定案）

- **版面格線**：「建議處置」區塊、上下分欄對不齊、孤立在右下的元素、寬度沒填滿、卡片外的說明文字、內容最大寬度、寬螢幕分欄，都留給第 73 輪。
- 表格密度切換（緊湊／寬鬆）的使用者介面。
- 流動的 KPI 數字或標題字級：本輪全部固定。之後若要做，限定標題與 KPI 數字，且最大值不超過最小值的 2.5 倍。
- 圖表配色（`charts.js` 的寫死色碼）：維持 BACKLOG。
- 深色模式。

- 中斷點維持 px。rem 中斷點能讓放大字級的人拿到較寬鬆的版面（Comeau 的建議），但會讓中斷點隨偏好位移，現有的 `lf-kpi-strip` 等寬度規則都要重驗，價值不足以在本輪一起做。
