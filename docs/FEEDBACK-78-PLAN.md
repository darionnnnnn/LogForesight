## 使用者定案的原則

1. **不改運作邏輯**：目前的做法可以。本輪只做「在目前邏輯下達到最佳效能」——同樣的輸入，改動前後的結果、順序、寫進資料庫的內容、畫面顯示都相同，只是用更少的查詢、更少的讀回列數、更少的記憶體配置、更短的持鎖時間做到。
2. **本輪依序把待辦項目處理完**：不等環境探測；八個批次依序做完。
3. **AI 待補繼續排隊**：不放棄、不改順序。

## 這個原則怎麼落到每一項

每一項都要同時通過兩種驗收，缺一不做：

| 驗收 | 內容 | 做不到時 |
|---|---|---|
| 等價 | 改動前先把結果記錄成測試（對帳），改動後逐項相同 | 無法證明等價的改法不做，改提別的做法或列入「不在本輪」 |
| 成本下降 | 以與機器快慢無關的計數證明：指令數、讀回列數、配置量、持鎖期間的資料庫或外部呼叫數。兩個小級距下不再隨主機數或天數成長，或成長倍數明顯降低 | 階段 0 量不到成長（讀碼推估的機制不成立）就取消該項並記錄數字 |

不寫毫秒門檻、不在開發機模擬 3000 台、不以開發機耗時下結論。

## 作業總覽

- **委派模型**：實作一律 Sonnet 5.5（內建 Agent，背景執行）；純機械替換可用 Haiku 5.5。同一 checkout 一次只派一個會改檔的 subagent。

- **commit**：每段驗收通過才 commit 並 push 到 `feature/feedback-78`，指令寫成「測試通過才 commit」的條件式。
- **全量測試**：各段只跑定向；改到共用查詢出口或共用寫入路徑的批次（I、J、P）各在完成時跑一次全量；收官再跑一次。

## 批次 L：通知流程

### 現況（已讀碼）

`MailNotificationService.NotifyAfterRunAsync` 每次執行：

- 以每頁 500 筆讀出回望 14 天內所有主機日，每個主機日讀一次工作流狀態（`CaptureDeliveryVersion`）。
- 收尾的 `ClosePlans` 對同一批主機日再各讀一次狀態，並各寫一到三次（兩個通道的 `ReplaceMailPlan` 與 `CloseMailPlan`），即使寫進去的內容與已存的完全相同。
- `ClosePlans` 內以 `summaryRecords.Any(...)`、`urgentRecords.Any(...)` 逐主機日線性比對，每次比對都組字串；`SendRunSummaryAsync` 內另有同型的 `qualifying.Any`。
- `RetryPendingUrgentAsync` 由每 60 秒的輪詢呼叫：即時通知的待送清單只要有一筆非終態，就整個重跑 `NotifyAfterRunAsync`。

以算術表示：3000 台 × 14 天＝42,000 個主機日，每趟至少 84,000 次狀態讀取與 42,000 次以上的寫入；待送清單卡著一筆時每分鐘重來一次。

### 定案

- **L-1 集合查找**：三處逐筆 `Any` 改成以主機日為鍵的集合查找。
- **L-2 內容相同不寫**：要寫入的郵件計畫與結案內容和已存的狀態完全相同時不發出寫入。判斷放在工作流服務內單一處。版本檢查（寄送期間狀態被改就放棄）不動。
- **L-3 重入不重做已完成的部分**：白天重入時，資料與設定自上一趟以來都沒有變動的主機日不重新讀取與規劃。等價的前提是「重跑一次與不重跑，該主機日的狀態與寄出的信相同」；階段 0 先以對帳測試確認這個前提，確認不了就只做 L-1、L-2。

### 驗收

| # | 驗收 | 確認方式 |
|---|---|---|
| L-A0 | 基線：同一份資料連跑兩趟，記錄每趟的狀態讀取數、寫入數、規劃結果（主機日、通道、意圖）與寄出的信 | 階段 0，於未修改的建置確認 |
| L-A1 | 規劃結果與寄出的信和基線逐項相同：摘要與即時兩個通道、有收件人與無合格收件人、郵件停用各一組 | 對帳測試 |
| L-A2 | 第二趟（資料沒變）寫入數為 0 | 計數斷言；突變：拿掉「內容相同不寫」轉紅 |
| L-A3 | 兩趟之間其中一個主機日的父紀錄版本變了：只有那一個被重寫，結果與基線做法相同 | 新測試 |
| L-A4 | 待送清單有一筆待重試、回望期內另有 20 個已結案主機日：重入後的狀態與寄信和整套重跑相同，讀寫數不隨那 20 個成長 | 對帳＋計數；突變轉紅 |

## 批次 I：問題聚合查詢

### 現況（已讀碼）

## 批次 J：報表與問題清單的整期載入

### 現況（已讀碼）

- `ReportCategoryTrendService` 與 `ReportEffectivenessService` 以不帶風險條件的 `QueryLightweight` 載入整期所有主機日（處理成效另往後延伸觀察期），每筆連帶全部問題子列，再於記憶體分組。
- `RecordListQueryService.FindHandling` 對每筆紀錄線性比對全部處理列，每次比對做主機名查找與字串比較。
