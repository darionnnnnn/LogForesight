## 批次 K：AI 待補的順序、中止與可見性

### 現況與核對結果（主代理已讀碼）

- `AiAnalysisHostedService.SelectNextBatch`：近日層（今天往前 2 天）日期新到舊、積壓層七日一塊；`EfAnalysisRecordStore.QueryPendingAi` 的排序是日期 → 主機編號 → 紀錄編號，**風險等級不參與**。同一天的中風險小編號主機排在高風險大編號主機之前。
- 一批 50 筆逐筆做完才判斷：只有「整批沒有任何一筆有進度」且待補總數沒變才結束該輪。AI 伺服器不回應時，每筆都等滿逾時（設定預設 1200 秒）才換下一筆。
- 失敗者留在本輪的已嘗試集合，下一批查詢量放大為「50＋已嘗試數」，上限 1,000 筆輕量投影。
- `EfAnalysisRecordStore.PruneDetails` 在詳情保留期到時把 `ai_pending` 一併清為 false。理由成立（詳情清掉後 AI 輸入無法重建），但**清掉幾筆沒有任何紀錄**；從未完成 AI 的主機日就此沒有白話摘要。
- `RecordBackoffOutcome`：一輪只要有一筆完成或降級就算有進度、解除退避。

### 根因

排序鍵沒有反映「哪一筆比較要緊」；中止條件以整批為單位，沒有以「AI 服務現在是否可用」為單位；清除待補是正確行為但缺少可見性。

### 定案

- **K-1 排序**：同一日期內依風險等級高 → 中 → 其餘，再依既有順序（主機編號、紀錄編號）。近日層與積壓層都適用。日期順序、層的優先序、積壓層「同主機舊到新」都不變。
- **K-2 連續失敗中止**：一輪內連續失敗達門檻（暫定 5 筆）就中止該輪。
  - 什麼算一次失敗：該筆最終沒有寫回結果（AI 呼叫未成功、或擲出取消與記憶體不足以外的例外）。降級寫回算有進度，不算失敗。
  - 計數歸零：任何一筆完成或降級。
  - 並行分片共用同一個計數，以「結果回來的先後」為序。
  - 中止的那一輪在退避判定上**視為無進度**（即使本輪稍早有成功），沿用既有退避；手動觸發照既有規則不進入退避。
  - 一筆都沒嘗試（沒有待補）時不適用。
- **K-3 清除待補留紀錄**：`PruneDetails` 回報「本次清掉的列中原本仍待補的筆數」；大於 0 時寫入資料保留那一趟的執行輸出與記錄檔，0 筆不出聲。消費端是執行紀錄的輸出內容。
- 不做：積壓放棄策略（D2）、主機輪替（D3）、`CountPendingAi` 的實查頻率（丙類，要正式站台的耗時）。

### 改動

1. `QueryPendingAi` 的排序加入風險等級（雙後端都要能翻譯；風險等級在資料庫是字串，排序對應要與 `RiskLevels.Rank` 同一份順序，不另寫一份對照）。
2. `SelectNextBatch` 的說明註解與 WEB-SPEC §9.10 的排序描述同步。
3. 處理迴圈加入連續失敗計數與中止；退避判定接上「本輪因連續失敗中止」。
4. `PruneDetails` 回傳或輸出被清掉的待補數；資料保留的呼叫端寫入執行輸出。
5. 現行文件：WEB-SPEC §9.10（AI 待補順序與中止）、DB-SPEC（保留清除與待補旗標）。

## 批次 L：通知流程

### 現況與核對結果（主代理已讀碼）

`MailNotificationService.NotifyAfterRunAsync` 每次執行：

- 以每頁 500 筆讀出回望 14 天內**所有**主機日，每個主機日讀一次工作流狀態（`CaptureDeliveryVersion`）。
- 收尾的 `ClosePlans` 對同一批主機日再各讀一次狀態，並各寫一到三次（兩個通道的 `ReplaceMailPlan` 與 `CloseMailPlan`），不論該主機日上一趟是否已結案。
- `ClosePlans` 內以 `summaryRecords.Any(...)`、`urgentRecords.Any(...)` 逐主機日線性比對，每次比對都組字串；`SendRunSummaryAsync` 內另有一處同型（`qualifying.Any`）。
- 設定停用郵件時仍走完整個 `ClosePlans`。
- `RetryPendingUrgentAsync` 由每 60 秒的輪詢呼叫：即時通知的待送清單只要有一筆非終態，就整個重跑 `NotifyAfterRunAsync`。

以算術表示：3000 台 × 14 天＝42,000 個主機日，每趟至少 84,000 次狀態讀取與 42,000 次以上的寫入；待送清單卡著一筆時每分鐘重來一次。這個數量與機器快慢無關。

### 根因

流程以「回望期內全部主機日」為處理單位，而不是「這一趟有變動或尚未結案的主機日」；重試入口沒有區分「重送一筆」與「重新規劃全部」。

### 定案

- **L-1 集合查找**：三處逐筆 `Any` 改成以主機日為鍵的集合查找。純等價替換，規劃結果不變。
- **L-2 已結案不重寫**：主機日的郵件計畫已結案，且父紀錄版本、應走通道與結案原因都與本趟算出的相同時，本趟對它零寫入。版本檢查（寄送期間狀態被改就放棄）維持不變。
- **L-3 重入只送待送**：`RetryPendingUrgentAsync` 只處理待送清單裡非終態的項目，不重新掃描回望期、不重新規劃。待送項目所屬主機日的版本已變更時，該項目照既有規則作廢。
- 「零讀取」不列為本輪目標：是否結案存在工作流狀態內，讀一次是必要的；L-2 之後讀取上限是每主機日每趟兩次。要再降需要把結案旗標抽成可查詢欄位，屬資料表變更，本輪不做（列順延）。

### 改動

1. 三處線性比對改集合查找。
2. `ClosePlans` 的寫入加上「內容相同就不寫」的判斷；判斷放在工作流服務內單一處，不在通知服務手寫比較。
3. 重試入口拆出「只送待送項目」的路徑；`NotifyAfterRunAsync` 的序列化 gate 兩條路徑共用。
4. 現行文件：WEB-SPEC 郵件通知一節補「重試只處理待送項目」。

|---|---|---|

## 批次 N1：PRTG 補齊估算計入配額

### 現況與核對結果（主代理已讀碼）

- `PrtgScopeEstimateController` 的補齊時間估算＝查詢數 × 1.5 秒 ÷ 併發 ÷ 60，沒有計入 historicdata「任一 60 秒最多 5 次」的配額。
- 配額下界已有單一實作：`PrtgFullBackfillPlan.QuotaLowerBoundSeconds`（完整回填預覽在用）。
- 以算術表示：併發 8 時估算是每次查詢 0.19 秒，配額下界是每次 12 秒，相差約 64 倍。使用者在設定頁看到的預估時間因此嚴重偏低。

### 定案

- **N1-1**：估算時間取「依併發算出的時間」與「配額下界」兩者較大者，配額下界呼叫既有的單一實作。
- **N1-2**：回應標明這個估算受哪一個因素限制（配額或併發），畫面顯示對應說明。這是既有估算區塊的文字，不新增元件。

## 批次 O1：執行輸出不吃掉失敗訊息

### 現況與核對結果（主代理已讀碼）

- `BatchRunRecorder.Message` 保留執行輸出的前 1,500 行與最後 500 行，中間以「已略過 N 行」表示。3000 台每晚約 3,000 行，逐主機日的成功行就會把配額用完。
- 執行輸出的入口是 `IRunConsole.WriteLine(string)`，**沒有類別**；正式碼約 427 個呼叫點，其中約 100 個的文字含失敗、錯誤、略過、逾時等字樣。
- Warn 以上的記錄事件走另一條路（NLog target）寫進執行紀錄，不受這個行數上限影響。
- 所以會被略過區段吃掉的，是「只寫在執行輸出、沒有另外記成 Warn 事件」的失敗訊息。有多少個這種呼叫點，要盤點才知道。

### 階段 0（主代理做，結果回填本節）

盤點含失敗語意的 `WriteLine` 呼叫點，分成「同一處另有 Warn 以上記錄」與「只有執行輸出」兩類。第二類為 0 時本批只做 O1-4，其餘取消並記錄盤點結果。

### 定案（階段 0 有第二類才做 O1-1～O1-3）

- **O1-1**：執行輸出增加「需保留行」的入口；`IRunConsole` 以預設實作擴充，既有呼叫點不必改。只有階段 0 列出的第二類呼叫點改用新入口。
- **O1-2**：需保留行不受中段略過影響；它自己有上限（暫定 500 行），超過時寫出「另有 N 行未列出」，不得靜默。
- **O1-3**：是否保留以呼叫端使用哪個入口為準，不以文字內容比對關鍵字。需保留行落在略過區段時，緊接在「已略過」標示之後依發生順序列出。
- **O1-4**：「已略過 N 行」的標示補一句說明：警告與錯誤另列於該趟的警告清單，不在略過範圍內。

## 批次 I：問題聚合查詢

### 現況與核對結果（主代理已讀碼）

- `EfIssueAggregateQuery.LatestOccurrences`（經 `IssueRows`）在資料庫端只以 `event_id` 粗篩，把期間內**每一天的每一列**拉回記憶體，再比對來源、解析合併主機、依出現點分組取最近一次。它要的結果是「每個出現點一筆」，讀回的卻是「每個出現點 × 出現天數」筆。
- 呼叫端七處：`IssueRankingBuilder`、`IssueHandlingRollupQuery`、`RecordListQueryService`（兩處）、`WorkOrderBoardService`、`WorkOrderCommandService`、`MailIssueDigest`。`RecordListQueryService` 的依問題視角在分頁之前對篩選後的全部問題呼叫。

### 根因

兩個無法下推的理由（來源鍵可能未回填、合併主機的別名解析）都只影響少數情況，卻讓所有請求走最貴的路徑。

### 階段 0（主代理做，結果回填本節）

- 讀回列數的成長形狀（隨主機數、隨天數各是幾倍）。
