## 根因

1. **PRTG 路徑的日期是單值參數**：登錄簿、規則評估、對應重算、觸發式取數全部只認一天，回望天數沒有通道進來。
2. **階段 3 的取法是「取整個相對窗、丟掉非當日」**：messages 依時間排序（探測步驟 8 有判定），分頁迴圈沒利用這點。
3. **回填的前提（host map）沒有閘門**，進度沒接，「什麼都沒抓」與「正在抓」在畫面上一樣。

## 定案（使用者採納「以找異常為先、速度其次」）

### 1. 狀態變更一次取完、依日分桶、不少抓一筆（批次 A）

- `FetchStateChangesAsync` 改收**日期區間** `[from, to]`（含），用涵蓋整段的最小級距發**一次**查詢；每列依 `changedAt.Date` 分桶，區間內的列全部寫入（`AppendStateChanges` 依 `(sensor, changed_at)` 冪等）。
- **區間一律往兩端各放寬一天**：規則評估看的是 `day-1 ～ day+1`，所以取 `[最早目標日-1, 今天]`。今天的部分列會寫入（明天再補齊，冪等），跨午夜的 down 持續時間從此算得準——這是完整性上的改善，不是副作用。
- **提早停止（只省查詢、不省資料）**：翻頁時每頁自驗 datetime 是否**單調遞減**；成立、且整頁最新一筆都早於 `from - 1 天`（再多一天緩衝）時才停。頁內不單調、或任一筆時間解析失敗，**退回翻到底**。停止與否都寫執行輸出（「依時間排序，於第 N 頁提早結束」／「順序不單調，翻到底」）。不依賴探測結果，執行期自己判。
- 回傳改為**每日寫入筆數**；執行輸出印讀取頁數、讀取筆數、各日寫入數、是否提早停止。畫面「狀態變更 N 筆」仍是新增數（冪等重跑顯示 0 是正常，文案註明「新增」）。
- **探測 9d-4 補判定**：`filter_drel=today` 的第一頁與最後一頁（`start=treesize-5`）各取 datetime，印三態：「參數生效（末頁仍在今天）」／「參數被忽略（末頁早於今天）」／「treesize 封頂（末頁取不到）」。這是給管理者看的診斷，不影響取法。

### 2. 立即執行的回望天數連動 PRTG（批次 B）

- `PrtgDailyPipeline.RunAsync` 改收**日期清單**（由近到遠）。`BackfillOverride=N` 時為昨天往前 N 天（與本機／NetIQ 同一個回望值，並受同一個保留期上限夾制）；未指定時只有昨天。**夜間排程行為不變**。
- 結構同步只做一次；狀態變更用批次 A 一次取完；**主機對應重算、規則評估、finding 發佈與補追加逐日進行**，登錄簿改為按日期鍵、可同時持有多天。
- 就緒訊號（`prtg-findings-ready`）在**全部日期發佈後**才發：AI 排程等的是「當日已到齊」，多天時不能只到齊一天就放行。
- **觸發式數值取數依策略、逐日做**：激進策略下每個回望日都對該日觸發主機逐顆查歷史值（與夜間同一套選法、同一個資源守門）；保守策略維持跳過並印「其餘 N 天的 PRTG 數值請用歷史回填」。理由：回望重跑的正是「出過問題的日子」，激進策略已明示接受逐顆查詢的代價，為了速度只做昨天會讓那些日子的值型訊號缺一角；保守策略不變是尊重使用者的策略選擇，不是省事。
- 規則庫沒有啟用中 PRTG 規則時的提示保留，改為整趟印一次。
- 執行輸出每日一段摘要；排程頁 PRTG 軌顯示「第 i／N 天」。
- **過去日的主機對應不硬造**（與 §5「回填不做主機對應」同一條線）：對應重算只對最新一天（昨天）做；其餘日期取**該日或該日之前最近一日**的既有對應。該日之前沒有任何對應（鏡像部署晚於那一天）時，那一天的 finding **不歸戶、不追加**，執行輸出寫明「YYYY-MM-DD 無主機對應可用，PRTG finding 未歸戶」。用今天的對應去套 30 天前的資料會把裝置掛到錯的主機上，而且看起來與真的一模一樣。
- **沉默 device 規則（`silent`）只評估最新一天**：它的依據是 sensor **現況**（目前狀態全 Unknown），不是狀態變更表；對過去日評估等於把今天的沉默套到 30 天前，是假訊號。其餘三條（down／flapping／warning）依該日的狀態變更逐日評估。
- **AI 分析的完整性閘門要涵蓋本趟全部日期**：現行閘門在取數執行中只擋「昨天」，其餘待補日照跑——回望重跑的 29 天會在 PRTG finding 到齊之前就被 AI 判讀，敘述缺 PRTG 訊號。`SchedulerRunState` 改記本趟 PRTG 處理的日期範圍，就緒前這些日期一律不合格；就緒後全部放行。
- **回望上限與本機／NetIQ 同一個**：`backfillDays` 已被 `ValidateBackfillDays`／`effectiveLimit` 夾在保留期內，PRTG 沿用同一個值，不另設。
- **立即執行的確認訊息**：回望 > 1 天且策略為激進時，執行前提示「PRTG 將對 N 天的觸發主機逐顆查詢歷史值，可能耗時數小時；可先切保守或縮小天數」。回望 > 1 天且策略為保守時提示「PRTG 只補狀態變更與規則，過去日數值請用歷史回填」。
- **執行紀錄的 PRTG 欄位**：`BatchRun` 的 PRTG 結構化欄位改為本趟**合計**（涵蓋日數另存一欄），執行詳情逐日各一行；執行總表按日期列的 PRTG 欄依**資料日期**取逐日統計（待決 2 定案：做）；舊紀錄沒有逐日統計時對應開始日的前一天（一趟取數處理的是前一天）。

### 3. 歷史回填修正（批次 C）

- 啟動閘門加三道：**host map 為空**（近 31 天內沒有任何 `ok` 對應）→ 拒絕並指路「同步結構與對應」；**取數執行中** → 拒絕；**結構同步執行中** → 拒絕。與現有互斥矩陣對齊（探測、快照服務已互斥）。
- 回填的狀態變更改用批次 A：整趟只翻一次 messages（區間＝回填天數兩端各放寬一天），再逐日做對應查詢與數值。
- 傳 progress：翻頁期間顯示「狀態變更 已讀 N 筆／約 T 筆」，之後才是「第 i／N 天：sensor a／b」。
- 接上 `CancellationToken`，加 `POST prtg-backfill/cancel` 與排程頁停止鈕（形式同結構同步的停止鈕：只在執行中出現）。停止後的結果摘要寫明「已停止，完成 X／N 天」。
- 成功判定改嚴：某日目標 sensor 為 0 且該日沒有任何對應 → 計「略過」而非成功，摘要印「略過 N 天（無主機對應）」。
- 取消端點與停止鈕需 `Maintain`（與 start 同），寫稽核；`DevMonitor` 看不到停止鈕（與結構同步停止鈕同一套 d-none 規則，輪詢不得把它翻出來）。
- 拒絕啟動的訊息要說出「等多久」：取數執行中 → 「取數執行中（已 X 分鐘），請等它結束或按停止執行」；結構同步中同理。

### 4. 結構同步狀態合併（批次 D）

- 夜間結構同步（`FetchDayAsync(syncStructure:true)`）成功時也寫 `prtg_sync_status`（來源欄標「夜間擷取」）；失敗不寫。排程頁與維護頁顯示「上次同步：時間（夜間擷取／手動）」。既有「從未執行」判定不變。

- 不動保守策略的語意：保守下回望多天仍不逐顆查歷史值。
- 不把回填天數改成跟隨排程頁回望值：兩者用途不同（回填是離峰補值，回望是重跑分析），畫面各自標明來源。

## 規劃完成後複檢（四角度）

**整體專案**
- §5「回填不做主機對應（歷史對應無法重建）」與「回望多天逐日重算對應」衝突 → 已改為只重算最新一天、其餘取既有最近對應、沒有就不歸戶（定案 2）。
- `silent` 規則依 sensor 現況評估，對過去日是假訊號 → 只評估最新一天（定案 2）。
- AI 排程的完整性閘門只擋昨天，回望重跑的舊日會在 PRTG finding 到齊前被判讀 → 閘門改涵蓋本趟日期範圍（定案 2）。這條不補，「連動 PRTG」對 AI 敘述就沒有效果。
- 快照服務在夜間取數的 `prtg-` 階段暫停；激進策略回望多天時暫停時間會拉長到數小時，那段時間 `sampled` 列 coverage 會低。可接受（激進策略已接受逐顆查詢），執行輸出印暫停時長讓人看得到。
- 觸發式取數逐日做時沿用既有「輪詢分析結果、分析結束再掃一次」的機制，每一天各自跑一輪；資源守門同一個實例。
- 今天的部分狀態變更從此會寫入：`lf_prtg_state_changes` 每天多一次「今天的一半」再被明天冪等補齊，表不會重複成長。
- §3a「狀態變更一律帶 filter_drel 最小級距」仍成立（改為涵蓋整段）；§9「登錄簿只登錄當日」被本輪推翻，改按日期鍵。

**程式面**
- `PrtgTablePager` 需要一個「整頁讀完後決定停不停」的掛鉤（拿到本頁已轉換的列），提早停止的判定放在 messages 呼叫端而不是分頁器（分頁器不懂時間）。停止時同樣算收斂，不擲未收斂例外。
- A 先定下「每日寫入數」的回傳型別，B 與 C 消費；`FetchDayAsync` 對外簽章保留（單日＝長度 1 的區間），夜間排程路徑零改動。
- `PrtgFindingsRegistry` 改按日期鍵後，`AttachExclusive`／`WasAttached` 的鍵本來就含日期，不用改；`IsReady` 改為「本趟全部日期已發佈」。
- `SchedulerRunState` 新增本趟 PRTG 日期範圍（開始時設定、`EndRun` 清除），`IsWaitingForFindings` 改回傳範圍；AI 服務以範圍判合格。
- 會被迫改的測試：`PrtgDailyPipelineTests` 九支（簽章）、`PrtgBackfillRunnerTests` 的逐日與進度測試、`PrtgFetchServiceTests` 的級距 InlineData、`PrtgTablePagerTests` messages 查詢字串、`AiAnalysisHostedServiceTests` 閘門、`RunsPageUiTests`／`PrtgAdminPageUiTests` 的「尚未同步」文案。規格白名單要涵蓋。

**使用者（尖銳但有理）**

- 「提早停止會不會漏？」→ 執行輸出印出停止依據（第幾頁、該頁最新時間、門檻日期），不單調就印「翻到底」。
- 「回填被拒絕，但夜間跑八小時」→ 拒絕訊息帶已執行時長並指路停止鈕。

**管理者**
- PRTG 負載：messages 從每日一次全窗掃描變成每趟一次；激進策略回望多天的逐顆查詢受觸發範圍與資源守門節制，並在執行前提示。
- 稽核：回填取消寫稽核；閘門拒絕不寫稽核（沒有發生動作）。
- 權限：cancel 端點 `Maintain`；停止鈕對 `DevMonitor` 隱藏。
- 升級注意：零 schema 變更；立即執行回望多天時 PRTG 行為改變（激進策略耗時變長）；回填在沒有主機對應時會被拒絕（過去是靜默成功）；今天的部分狀態變更會開始寫入。
- 可觀測：執行詳情逐日一段；結構同步狀態多一個「來源」欄。

**拆分原則四問**
- 分母為零：回望 N 天但沒有任何一天有狀態變更 → 各日 finding 為空、照發佈；回填 N 天全部略過 → 整趟「略過」不是成功；某日無對應 → finding 不歸戶並印出。
- 單向閘門：回填「host map 為空就拒絕」的繞過路徑＝先按「同步結構與對應」，訊息直接指路。
- 破壞性判準：提早停止是唯一可能少抓的點，條件「單調遞減＋整頁最新一筆早於 from-1 天」，反例（頁內不單調、任一筆解析失敗、頁內有一筆晚於門檻）都退回翻到底，全部列進驗收。
- 移除類：無。
