## 目的與成功定義

PRTG 在本系統是 Windows／Linux 日誌的獨立佐證及早期資源訊號，不另造一套監控系統。成功不是抓到多少列，而是：受監看主機有可信資料；異常能說出哪台、哪顆 sensor、哪個時段、何種證據；適當地提高風險或形成既有案件／交辦；處理人能辨別需要處置、已在 PRTG 確認、資料不足三種情況；管理者看得見訊號的實際採納與雜訊量。

本輪保留 `PrtgScopeDevices` 縮圈、現有狀態型規則、`PrtgFindingMapper` 的穩定簽章、案件與交辦鏈、風險只上調、抑制／靜音，以及 `ok` 優先於 `sampled` 的寫入順序。任何新增數值判斷先過資料品質門，不能靠 AI 猜原始數值含義。

## 決策與交付邊界

**本輪實作與實機驗證分開交付**：A～F 的服務、資料契約、管理畫面、規則試算、既有處置鏈和自動化測試均列入完整實作，不因目前僅有約六天可用歷史而省略。未取得真實 28 天基線及磁碟頻道語意確認前，實機驗收只能標「待資料／待人工驗證」，不得把規則描述為已校準；同時環境探測頁必須持續顯示累積進度與可執行的驗證步驟。完成程式實作與測試不等於值型規則已可投入正式派工。

1. 低 coverage 先診斷、出聲、提供受控的指定主機／日期回填；**不自動大量呼叫** `historicdata`。回填可停止、可預估請求數，沿用現有互斥與稽核。理由：PRTG 當下若忙或故障，自動補洞會加重負載。
2. 第一個值型情境限於「磁碟可用空間持續下降，依可信歷史預測將於處理期間內耗盡」。只對量測語意已驗證、該 sensor 自己有足夠可用歷史的目標啟用；不以其他 sensor 或四項全域校準代替。
3. 新值型規則**完整實作但預設停用且不發 finding／交辦**；管理者可在資料累積期間反覆預覽，真實資料及語意驗證後，才透過既有規則維護流程明確啟用。預覽不寫 finding、風險、案件或交辦；啟用後才按規則的嚴重度與既有派工閘門運作。資料品質不足的 sensor 即使規則已啟用也逐顆跳過。既有狀態型規則與已開單者不受影響。狀態型 finding 的 `PrtgFindingsReady` 時點不後移；首版值型規則只讀評估開始前已落盤的完整日資料。
4. 歷史回填只補資料與基線，不自動替過去日新開案件／交辦；最新已完成資料日的重算另走冪等、可追溯入口。否則一次 30 天回填可能突然派出大量過期工作。
5. 「資料不足」是第三種明確結果，不等於正常，也不產生風險提升。規則因資料品質跳過時，管理者可查原因；處理人只在與該問題相關時看到簡短資料品質註記。

## 作業 A：快照可信度與原因定位

### 現況與契約

`PrtgSnapshotHostedService.GetStatus` 仍包含行程記憶體狀態；校準的 `SnapshotCoverage24h` 是 sampled 列平均，不能回答哪個完整小時缺了幾次。診斷由最小必要的持久化快照嘗試／寫入統計，及沿用 `PeriodStart` 索引對最近 24 個完整小時已落盤列所做的 SQL quality／coverage 聚合共同組成，不依賴重啟前記憶體。`ok` 會覆蓋 sampled；聚合可區分 coverage 25% 不足、被 `ok` 覆蓋後的數值可用與寫入失敗，但仍無逐 sensor identity 證明，不能宣稱每顆成功或 100% coverage。讀取最近完整小時，區分：PRTG 未啟用、沒有快照目標、取樣未形成整點列、取樣列 coverage 不足、已被 `ok` 覆蓋、正常可用、擷取暫停／退避、資料庫待寫。分母為零時顯示「無目標／無資料」，不可算 100% 健康；今日未結束的小時不參與健康判定。剛啟用或重啟所跨到的第一個部分小時要標為「啟動中／部分時段」，不能與完整小時等同計算連續異常。

持久診斷只留按小時聚合的嘗試／成功／跳過／寫入失敗計數與原因類別，受現有保留期約束，不逐次、逐顆 sensor 寫日誌。尚在記憶體待寫的列只可標「目前待寫」；重啟後若沒有可還原的佇列，歷史只能標曾寫入失敗或無法判定，不能假稱知道當時還欠哪幾筆。

同一個 sensor 在一小時只算一個目標；`ok` 覆蓋 `sampled` 時視為該小時**數值可用**，但快照執行健康另以持久統計判斷，不能因此聲稱快照成功，也不能因 sampled 列不見而誤報數值不可用。管理者在 PRTG 維護頁與現有系統健康頁看到「近幾個完整小時是否可用、原因、檢查或回填入口」。提示只在連續異常後出現，待定門檻先以兩個完整小時作評估起點；停用 PRTG、無目標、已確認維護與正常夜間互斥需分流顯示，不每天寄重複警報。無 Maintain 者不指向無權限的管理頁。

### 驗收

- 用四次取樣、一次取樣、`ok` 覆蓋、無目標、行程重啟、夜間互斥和寫入失敗的替身逐一證明診斷不同；25% 不得顯示為「正常」。
- 管理頁在窄螢幕與鍵盤操作下能查原因與下一步；API 只對原有授權者暴露維運細節。
- 只新增讀取與提示，不改 PRTG 發請求頻率及舊資料品質規則。

## 作業 B：校準就緒與感測器語意

### 現況與契約

保留四項校準資料作各自的報告，不再要求它們全部達標才開任何一種值型功能。值型 readiness 要逐顆確認：在已對應且啟用中的主機、未暫停的 sensor；類型、主頻道與量測方向可靠；歷史窗口內有足量**可用**小時與天數；近期資料新鮮；資料點缺口不被當成 0；同一顆 sensor 被改對應、改裝或重新建置時不能沿用舊主機的基線。基線所需天數／每日小時門檻沿用或標明推翻 `CalibrationConstants` 的既有值，避免 UI 與評估器兩套定義。

`Unit=null` 及不同類型量級不能被同一個 P90/P99 自動解釋。磁碟候選先對照實機探測的 `SNMP Disk Free` 第一頻道、PRTG 顯示單位、historicdata 與快照同日數值及「剩餘百分比越低越危險」的方向；無法可靠判定的磁碟 sensor 列為不適用，而不是硬套規則。**資料量就緒與數值語意驗證是兩個獨立條件**：有 28 天不等於知道百分比是哪個頻道，也不能因站台沒有其他九台主機的基線就擋住這一顆。逐顆判定與後述 F 工作台使用同一服務／同一品質閘門。流量、記憶體、CPU 只作資料語意核對，不在此階段直接產生新 finding。管理頁須把「全站鏡像顆數」、「目前監看裝置」與「快照目標」分開標示；鏡像尚未依取數範圍完成成功同步時，不把未對應顆數當作待抓取工作量。

### 驗收

- 四項全域校準都不足但一顆磁碟 sensor 真正就緒時，該 sensor 可進預覽；帳密殘留和 Down=0 不得擋它。其他不足的 sensor 仍不得進預覽。
- 一台主機 A 顆 sensor 有 28 天、B 顆只有 6 天時，B 不可借用 A 的 readiness；歷史對應有變或單位／方向不確定時不就緒。
- UI 清楚區分「需要等幾天」、「缺多少可用小時」、「資料新鮮度不足」與「量測語意未確認」。

## 作業 C：局部、受控的歷史修補

### 現況與契約

現有 `POST prtg-backfill/start` 不收主機或日期。新局部入口或擴充契約須以已儲存主機與日期區間為輸入，先預覽裝置、sensor、天數、估算 API 請求量與覆寫 `sampled` 的筆數，再由管理者確認；後端自己計算實際範圍，不信任前端給的 sensor id。只有有效的歷史主機對應才能歸戶，不能用今天映射補舊日。空選取、零可抓、超出保留期、與排程／同步／探測互斥時應有可操作訊息。執行沿用現有取消、節流、併發上限、逐 sensor 失敗隔離、`ok` 優先序與稽核。重跑同一區間冪等；不新增自動背景補洞排程。

### 驗收

- 指定一台一天時僅該歷史範圍發請求；沒歷史對應不寫錯主機；拒絕範圍外主機與不存在的日期。
- 預覽數與實際請求量有可解釋差異；取消與部分失敗不報為全成功；成功 `ok` 不被後續 sampled 蓋回去。
- 回填不替過去日新開案件／交辦；管理者能看見補值後的 readiness 變化。

## 作業 D：磁碟可用空間趨勢的第一個值型訊號

### 現況與契約

只對 B 已確認的磁碟百分比 sensor 運作，不以 type 全體分位數直接設全域門檻。完整實作所需的逐顆品質判定、趨勢計算、規則模型、只讀預覽與正式 finding 路徑；其中低水位、下降穩定度、預估耗盡時距及最低支持資料量標「暫定」，待真實 28 天資料與後續實機驗證校準。現有匯出只有約 6 天可用 `ok` 基線。自動化測試已完成，但不代表真實環境已校準或適合啟用正式派工。條件必須同時滿足：近期可用資料、下降趨勢足夠穩定、當前可用空間真的接近處理門檻；短暫尖峰、資料缺口、單日突變或某磁碟永遠停在固定值不能形成預警。沒有可信單位／頻道時不評估。

產出沿用 PRTG 問題簽章與規則庫的嚴重度／抑制／靜音語意，顯示「哪台、哪個磁碟 sensor、目前剩餘、歷史窗口與可用小時、預測時距、資料截至何時」。首版預設停用，只提供無副作用預覽；正式啟用後才可依既有派工閘門建單。處理人能在原交辦動線看到證據與 PRTG 開啟方向，不需先理解校準四項。`Down (Acknowledged)` 既有降級語意**只屬狀態型 Down**；磁碟數值規則沒有對應的 PRTG 確認語意，不得硬套。同主機同 sensor 若已有活動 Warning 工單，會避免另開第二張趨勢工單；Warning 工單頁從已發布的 `TopIssue` 顯示最近 30 日趨勢證據。同趟先後兩種順序已有修正與測試。正式站台與真實 PRTG 驗證仍待完成。跨行程關單的極窄競態尚未完全原子化，列入後續風險。

### 規則套用的完整契約

- **唯一規則來源**：首個值型代碼加入既有 `platform=prtg` 規則庫，不另建一套「磁碟告警開關／嚴重度」設定。`PrtgRuleCatalog` 只給種子預設值；執行期的啟用、分類、嚴重度、重大旗標、說明與知識庫依命中規則決定。新代碼必須從 `RuleValidator`、規則 DTO／編輯頁、匯入差異與覆寫、執行輸出、顯示名稱一路打通，不能只放進選單。新規則預設停用，既有部署不被升級自動開啟；種子版本遞增，管理者套用內建規則後仍要自行啟用，已修改的內建規則及既有 Enabled 值按現有匯入契約保留。
- **適用範圍**：首版只接受已驗證為「可用空間百分比」的 disk sensor；PRTG 的 `disk` 大分類本身不足以證明單位。沿用目前主機／device 對應與數值白名單，但預覽要列出「不在白名單、無對應、暫停、語意不明、資料不足」的個數，不能讓一條看似啟用的規則實際套用零顆卻顯示正常。規則若支援分類覆寫，磁碟值型代碼固定只接受 disk，不可退回不限分類規則誤套 CPU／流量。
- **門檻型別**：現有 `PrtgThreshold` 的分鐘／次數語意不得借給百分比、斜率或預測天數；值型條件用明確、有上下限且可說明單位的欄位或結構，和狀態型欄位互斥驗證。若擴充 `KnownIssueRule`，其 DTO、儲存相容、種子覆寫複製、匯入差異、反射守門與舊規則回讀一併覆蓋；不可改變四種舊代碼的欄位意義。畫面直接解釋「何時成立、資料不足時會怎樣」，並顯示當前規則實際適用 sensor 數與最近完整日的命中、排除、抑制數。若資料不足 28 天，保留預覽與不適用原因，不得假稱此輪已完成實機門檻校準。
- **預覽與啟用**：管理者可對尚未儲存的候選條件執行有範圍／日期上限的唯讀預覽，回每顆 sensor 的適用性、資料品質、計算依據與預期命中；預覽即使規則目前 Enabled=false 也可跑，且不寫 `lf_top_issues`、案件、交辦、稽核業務事件或通知。正式啟用要顯示最近期間的預估命中主機／交辦量及上次預覽時間，讓「啟用」是可理解的決定；儲存與啟用沿用 Maintain、規則異動稽核及現有匯入入口。預覽資料可能在啟用前變動，故啟用後第一趟仍按最新資料與品質重新判定，不承諾預覽筆數必等於派工筆數。
- **規則挑選與故障**：同代碼／分類的重複規則，沿用現有「分類優先、相同候選取 Id 最小且警告」或在 UI 阻擋歧義，不准另有一套隱形優先序。沒有可用規則、規則停用、值型查詢失敗及品質不足都各自記入執行輸出／管理頁；值型出錯不得讓狀態型規則跳過。正式評估只針對當趟最新的已完成資料日建立新 finding；多日回望只供預覽／基線，不追溯派工。首次啟用後既有歷史日不自動追溯開單；停用後停止新增 finding，不刪既有案件與處理說明。
- **簽章、抑制與跨日**：新 finding 使用穩定的 `Source=PRTG:{代碼}`、`EventKey=prtg:{代碼}:{sensorObjid}` 與命中的 `RuleId`，不得含 `|`；狀態型四代碼不改名。規則型／簽章型抑制及靜音沿既有鏈運作，但 `RuleMayHit` 與規則頁的抑制影響預覽目前只按代碼粗估，值型規則必須標明或修正其適用分類、sensor 與資料品質，不能把「同代碼全部分類」冒充精確影響數。`PrtgCrossDay` 現有連續三日自動升級面向狀態告警；值型趨勢首版不得因每日同一預測重複升級或重開單，須以明確驗收證明排除或另定值型跨日語意。`PrtgCorroboration` 現有三模式只認狀態型代碼，新代碼不會自動成為儲存容量的跨來源佐證；要納入時需另驗證 `srv 2013` 的匹配與抑制，不得只改 Source 名稱即宣稱生效。

**時序邊界**：值型評估與狀態型規則在同一趟 PRTG finding 就緒訊號之前結束，但**只讀評估開始前已落盤的完整日數值**；不得為等當趟激進模式 `historicdata` 而延後狀態 finding 發佈或 AI 開跑。資料尚未就緒就明確跳過該 sensor，本趟後段新取得的精確值供之後基線與明確重跑使用，不能偷偷在 AI 就緒後再追加一張單。整點小時未收束不可被當正常。當趟重算須冪等，已發佈、已處理及已靜音的同一簽章不可重複建單。歷史回填預設只補基線，不自動追溯派工。若當日尚未有有效主機對應，不歸戶、不派工。

### 驗收

- 相同讀值在 `ok` 與 coverage≥75 的 sampled 可用；coverage=25、null、過期、跨主機錯配、單位不確定及反向上升值均不出 finding。
- 一次命中後重跑不重複建案件或交辦；靜音、抑制、狀態型 Down 的 PRTG 已確認、使用者已回覆／結案各有明確結果；數值趨勢不得繼承 Down 的確認語意。
- 規則端到端：無 seed／seed 未套用／停用／啟用／草稿預覽／分類與單位不符／重複代碼／規則型抑制／修改門檻／再次匯入各有測試；尤其要證明停用規則的預覽可算但不寫業務資料，既有四條狀態規則不受新代碼影響。
- 規則頁的候選量、實際可套用量、預覽命中量與正式 finding／交辦量各有口徑；預覽不掃全站 4 萬顆鏡像、不回傳無權限主機。
- 執行順序測試：歷史值後到、快照整點晚到、手動排程重跑、回填多日都不會偷偷變成過期派工；狀態 finding 與 AI 的既有就緒時點不後移。
- 規則關閉時零新告警，仍保留狀態型 finding 與既有交辦內容。

## 作業 F：環境探測頁保留後續實機驗證機制

### 現況與契約

`/admin/prtg#probe` 現有「驗證小範圍資料流」只試一台、一顆、昨天一天並寫入讀回；「完整環境探測」會量全站 API，輸出留在行程記憶體；四張校準卡在同頁的「進階校準」折疊區，按「重新計算」才做重查詢，且匯出仍以四項共同達標為條件。這些都**不能**直接證明某顆磁碟的值型規則就緒。新增一張在環境探測頁預設可見的「磁碟值型規則驗證」卡，並明確保留原有兩顆探測按鈕與進階校準匯出用途；新卡不從探測文字輸出解析結果，不依賴行程記憶體，也不要求四張卡全綠。進階匯出的四項共同門檻若仍保留，只限匯出用途，畫面要說明它**不是**值型規則啟用門檻。

F1. **到站就能看累積進度**：載入探測頁時從已落地資料取得輕量、可重算的逐顆就緒摘要，不觸發 PRTG API、不強制執行現有四項重查詢。查詢先限已對應且啟用主機的 disk 候選 sensor 與保留期內的必要日期，聚合／分頁取數，不把全站 4 萬顆鏡像與所有 hourly 列送到瀏覽器。顯示候選 sensor、已對應且未暫停者、白名單內者、達到每日有效小時門檻者、達到 28 個有效日者、語意已驗證者、可供預覽者及各類排除數；每顆可展開「有效日 X／28、最近資料截至何時、缺哪些小時、品質、主機／device／sensor 對應、單位或頻道是否已確認」與下一步。28 天只是本規則的暫定門檻，必須和 D 評估器共用定義。沒有候選時明示檢查白名單／主機對應；零筆不是 100% 就緒。頁面保留明確的「重新檢查」動作；資料增加後下次開頁可自動看到新狀態，不需重跑全站探測或重新部署。

F2. **可重跑的實機驗證**：資料未足時仍可做原有的一顆一天資料流驗證，卡片標記其結果只證明 API→解析→寫入→讀回。資料達門檻後，顯示「驗證磁碟感測器與規則」入口：可選一顆，或用有上限的分批方式驗證多顆已就緒 sensor；先對指定的已對應主機／sensor 做有明確請求數與日期上限的唯讀 PRTG 語意抽查，對照主頻道名稱／單位、原始值與資料庫同時段值；再用相同 sensor 的已落地 28 天資料跑 D 的**唯讀規則試算**，回報品質、趨勢、門檻、預期命中與例外原因。能由資料明確證明語意者自動標記，不要求管理者逐顆確認；`Unit=null` 或 PRTG 回應不足以確證百分比時回「語意待人工核實」，不得只憑 type 名稱給綠燈。若需要人對照 PRTG 畫面確認頻道／單位，提供附證據摘要的明確確認與稽核，不接受沒有候選 sensor 或無資料時的空白確認。真正量測值缺口、固定值或尚無下降案例時只能說「計算路徑已驗證／真實命中尚待觀察」，不能宣稱預警準確率已通過。

F3. **驗證狀態與失效**：顯示「未設定、資料累積中、資料就緒但語意未確認、可試算、已驗證、驗證失敗／已失效」等互斥狀態及上次檢查時間。逐顆語意確認只保存最小證據（主機／device／sensor、頻道與單位、確認方式與人、時間、解析語意版本），不存整包原始 PRTG 回應或憑證；重啟後仍能讀到。主機對應、sensor type／主頻道或解析語意改變時舊確認失效並指出原因；白名單移除只讓該顆暫時不適用、再加入時可重用仍有效的語意證據；單純修改預警門檻只使舊**試算**過期，不清除頻道／單位確認。新一天資料進來只重算品質與預覽，不把已確認的相同頻道每日清零。管理者可再次驗證，失敗、取消、PRTG 逾時和停止各有不同結果。F 的驗證與現有探測／回填／同步／取數互斥與取消一致，絕不為等 PRTG 卡住夜間分析。

F4. **啟用邊界與操作**：卡片區分「程式與測試已備妥」「這顆 sensor 資料就緒」「實機語意已確認」「真實預警效果已觀察」「規則已啟用」五種不同事實，不以單一綠色徽章混為一談。從卡片可直達規則頁預覽與受控回填；預覽無副作用，驗證成功也**不自動啟用**規則或重算歷史交辦。只需 Maintain 的管理者可見個別 sensor 與操作，其他人不暴露 PRTG 連線資訊。卡片在窄螢幕、鍵盤、載入失敗與空資料時均有可辨識且能重試的狀態。規則是全站的一條 Enabled 設定，**啟用後仍逐顆套 B 的品質／語意閘門**：至少一顆已就緒且實機語意已確認才允許首次啟用，其餘未驗證 sensor 不會跟著派工；不要求全站或舊四項校準都可用。真實趨勢命中若尚未發生，只標「效果待觀察」，不能虛構正例，也不因此讓一條已通過資料與語意驗證的規則永久無法啟用。若管理者決定啟用，規則頁再次顯示驗證時間、資料截至時間和預估影響，沒有任何仍有效的合格 sensor 時擋下並指回探測頁；不得只靠前端 disabled，後端同樣驗證。

F 的 Web 契約至少有三種清楚分離的操作：只讀的逐顆 readiness 分頁／摘要查詢、明確啟動／查狀態／取消的有限 PRTG 語意驗證、以及不發 PRTG 請求的規則試算。沿用 `Maintain`、現有探測互斥及統一 API 錯誤慣例；同一個啟動請求不可因重試而排出兩趟作業。需要人工確認語意時才另設有稽核的確認操作。讀取 readiness 不修改任何值、規則或上次驗證證據；試算也不修改業務資料。驗證結果不以 `PrtgProbeStatusDto.Output` 文字作唯一來源，否則行程重啟會失去證據且無法可靠給 UI 使用。

### 驗收

- 以時鐘／資料替身從 6 日→27 日→28 日、有效小時不足、`sampled` coverage 25%、`ok` 補齊、無候選、對應變更及資料保留截斷逐一測：狀態與欠缺數正確；28 日達成後開頁呈現就緒，不呼叫完整探測或四項校準重查詢。
- 一顆一天資料流通過但 28 日不足，只顯示「資料流已通、規則待資料」；28 日已足但單位未知，只顯示「資料已足、語意待確認」；語意確認且試算完成仍不自動開規則／派工。零下降樣本不偽稱預測效果通過。
- 替身驗證抽查只向被選 sensor 發有限請求；取消／逾時／PRTG 失敗不更新成功證據；sensor 改對應、type／頻道或解析語意變更時不沿用舊確認。修改規則門檻僅讓舊試算失效，不能洗掉正確的語意確認。SQLite 與 SQL Server 回讀、重啟、保留期及稽核均覆蓋。
- 探測頁新卡、規則頁預覽與 D 正式評估對同一份數據回相同品質／命中結果；唯讀預覽不寫業務資料，原有完整探測、小範圍資料流、進階匯出不退化。

## 作業 E：使用效益、實機與文件驗收

### 現況與契約

管理者需要回答「這個訊號有沒有幫忙」而不只看資料筆數。優先從現有 finding、案件、交辦、回覆與抑制資料做唯讀聚合，顯示 PRTG 單獨發現、跨來源佐證、進交辦、已回覆、已靜音及品質不足數；不同口徑不硬湊成一個採納率。只在確實有可重算定義的欄位上展示，無法從現有資料得知「真的修好了」就不要偽稱解決率。資料範圍／日期與授權遵循現有管理頁慣例。

現況文件在程式實作完成後按**已交付程式行為**更新：`PRTG-SPEC.md`、`WEB-SPEC.md`、`BACKLOG.md`、必要的使用說明與測試基線；同時把真實環境尚未驗證的條目明列為待驗，不因版本合併就寫「已在實機通過」。本 PLAN 完工後歸檔。未來實機驗收至少涵蓋一台磁碟有穩定歷史、一台缺資料、一台 PRTG 已確認、一台主機對應衝突，以及資源守門裝置不在主機清單的情況；可透過 F 工作台逐步補齊，真實環境尚未具備時不阻擋程式與替身測試交付，也不能只靠單元測試聲稱站台已驗證。

### 驗收

- 從一筆實際 PRTG 訊號循主機日→問題→案件／交辦→處理說明追蹤，核對名稱、日期、感測器、證據與權限。
- 管理者看到「有資料但沒命中」與「根本缺資料」兩種不同結果；處理人不被校準術語或資料品質表格淹沒。
- SQLite 與 SQL Server 的查詢翻譯、批次成本、索引及資料保留期均驗證；前端窄螢幕、鍵盤、空／錯誤狀態檢查；程式測試結果進執行紀錄，未來的實機輸出及通過／失敗／待驗狀態在 F 工作台與驗收紀錄追蹤。

## 第一線與管理者情境複檢

| 角色／尖銳問題 | 走查後的契約 |
|---|---|
| 處理人：「又給我一張看不懂的 PRTG 告警？」 | 單內直接寫磁碟、目前剩餘、多久可能耗盡及證據截至時間；同根因不重複開單；能在原交辦頁回覆，不導去校準頁。 |
| 處理人：「PRTG 已經確認了，為何還被當成新的重大事件？」 | 狀態型 Down 的已確認語意沿用；值型沒有等價的 PRTG 確認旗標，須和同感測器既有 Warning 同組顯示／去重，不把狀態確認誤當「空間已修好」。 |
| 一般使用者：「無數值是不是正常？」 | 缺資料明示為未知；不顯示安全綠燈，也不因此自動拉高風險。需要維運操作時只給可到達的聯絡或說明。 |
| 新管理員：「告訴我抓了 100 顆，卻 100 顆都不能用？」 | 顯示完整小時的實際 coverage 與停頓原因，並有受控補值入口；預覽先算負載，避免按完才知道要打幾千個 API。 |
| 新管理員：「今天只有 6 天，等到 28 天要不要請工程師改版？」 | 探測頁平時顯示逐顆 X／28 和缺口；資料一達標就顯示可驗證的 sensor 與動作，無須重跑完整環境探測或重新部署。驗證成功不會替他打開派工開關。 |
| 尖銳管理員：「四張校準卡三張黃，磁碟規則是不是永遠不能用？」 | 進階校準與單顆磁碟 readiness 分離；只要一顆確有足夠可用歷史且語意確證，就能試算，其他卡的不足不阻擋；正式啟用仍須明確決策。 |
| 維運者：「IIS 一直回收，警示會不會每天吵？」 | 診斷讀持久資料，區分服務未執行與 PRTG 回傳失敗；連續異常才告警、相同異常不重複洗通知；不靠記憶體最後成功時間假裝健康。 |
| 主管：「PRTG 買了，究竟幫我們少漏掉什麼？」 | 顯示訊號從 finding 到交辦／回覆的可證實計數及雜訊，不宣稱無資料可支持的節省工時或修復率。 |

## 上帝視角複檢：跨系統影響與反例

1. **資料流先後**：PRTG 狀態型 finding 與 `PrtgFindingsReady` 既有時點不可被 D 搬壞；值型評估只讀評估前已落盤且完成的日期。觸發式回填、手動補值和夜間分析三條路要同一品質定義，回填不偷開舊單。不能因值型缺資料而阻塞狀態型 finding。
2. **主機與權限**：歷史對應不能用今天的映射；只有成功對應能歸戶。主機可見範圍、Handle／Maintain 權限、內網 PRTG 名稱與外部連結都沿用既有守門。
3. **現有狀態維護**：新簽章的 EventKey 必須穩定，抑制、靜音、案件、交辦與回覆不能因重算而失聯；停用新規則不刪舊處理歷程。不得讓已結案單因回填重開。
3a. **規則庫影響面**：新代碼進入 `KnownIssueRule` 後，驗證、序列化、種子匯入、草稿預覽、規則型抑制預覽、白話說明、問題排行與通知都要按同一規則代碼識別；不能讓維護頁顯示「已啟用」但取數白名單／單位／品質使有效母體為零。值型預覽是只讀試算，正式派工仍受啟用狀態及現有案件閘門約束。
4. **品質優先序**：`ok` 覆蓋 sampled；低 coverage 不作 0；同一小時跨重啟合併、批次部分失敗和重試不能虛增 coverage。此輪若觸及 `MergeSampledValues`，需把已知部分提交後重試重複合併納入驗收。
5. **成本與故障邊界**：目前 100 顆只要兩批快照；擴大到 >2000 顆會改全站查詢，本輪不自動改範圍。PRTG 不可用不得拖垮 NetIQ／本機分析；查詢、分頁、取消與資源守門互斥沿用現有機制。
6. **資料保留及升級**：逐顆基線只取現有保留期內資料；規則不足時不新增虛假歷史。schema／索引若需調整，同步考慮 SQLite、SQL Server 與升級前既有 4 萬顆鏡像，不在啟動時全表重建。
7. **文件語意**：現況文件不能在 D 尚未上線時宣稱「已有值型預警」。本 PLAN 與已存在的 `PRTG-SPEC.md` §11、`BACKLOG.md`「四項共同閘門」衝突處，只有實作完成後才改現況文件，並於收尾逐條對照。
8. **探測與規則的一致性**：F 的逐顆就緒、D 的預覽與正式派工使用同一品質及語意判定；小範圍資料流只證明一顆一天的資料路徑，不能升格為 28 天趨勢驗證。A 的快照健康也不等於該 sensor 的有效歷史。資料達標、語意確認、試算命中、真實效果及規則啟用各有獨立證據與失效時機。
9. **後續實機驗收不拖欠程式交付**：資料與單位尚未具備時，A～F 仍可用替身、兩種 DB 後端及 UI 操作完整驗收；真實 PRTG 的單位、低 coverage 根因、28 天門檻與誤報率維持「待驗」，在 F 工作台就緒後由管理者進行。升級時規則預設停用，不因等待實機而偷偷改掉舊狀態規則。

## 明確不做（規劃假設）

- 不把 43,421 顆全站 sensor 逐顆呼叫 `historicdata`，不因校準不足就切激進策略；不讓 AI 直接由原始數值決定風險。
- 不同時推出 CPU／記憶體／流量的通用數值告警：匯出單位與方向尚未可靠，尤其流量只有主頻道且不同型別量級不同。
- 不自行修改 PRTG 的監控設定、認領／確認狀態或訊息推送設定；本系統仍只讀 PRTG API。
- 不新增另一套案件、交辦或獨立監控通知；新訊號必須走既有處置與稽核架構。
