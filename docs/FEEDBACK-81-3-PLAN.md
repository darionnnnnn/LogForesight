## 3. 原則

- BACKLOG 是現行文件：只寫現況、為什麼不做、觸發條件。不寫「原本／後來／已改成／第 N 輪」。
- 移除只限有程式證據的「已解決」，而且在移除當下重查一次證據；信心不足的不移除。
- 改寫只修正事實（數字、檔名、已消失的前提），不改變該條「做或不做」的結論。
- 小修不加設定、不動資料表、不碰派工與交辦的判定邏輯。
- 不過度設計：不為這七個小修新增抽象、介面或共用模組；能用既有出口就用既有出口（見第 7 節）。
- 每個小修先寫在未修正時會紅的測試、確認紅，再修；修完主代理另做一次突變。
- 每一項的驗收都要是在本機或測試 VM 上可以執行並看到結果的；需要正式站台才知道的不列為驗收。

### B1 儀表板「24 小時登入失敗」點進去看不到大部分紀錄
- **現況（已查證）**：卡片數字是 24 小時內 `login_failed` 動作的筆數（`DashboardService`）；下鑽網址是 `/audit?result=Denied`（`dashboard.js:430`）。登入失敗有四種寫入：密碼錯誤、AD 驗證失敗、帳號不存在是結果 `Failed`，只有帳號已停用是 `Denied`（`IdentityService`）。所以點進去只看得到帳號停用那一種，而且會混進其他動作的被拒紀錄。
- **定案**：下鑽改為 `actions=login_failed`、不帶 `result`，並帶 `from`＝24 小時前那一天、`to`＝今天。稽核頁已支援這三個參數，且選項載入後才套用（`audit.js`）。
- **口徑差要講清楚**：稽核頁只能依日期篩選，卡片依小時。修完後清單會**包含**卡片計入的每一筆，另外多出「昨天、但超過 24 小時」的紀錄，所以清單筆數大於等於卡片數字，不保證相等。這是刻意接受的落差（不擴充稽核頁，見第 2 節）；卡片的說明文字補一句「明細含昨天全日」。
- **驗收**：
  - 行為測試：卡片連結含 `actions=login_failed`、含 `from`（＝本地日期的昨天）與 `to`（＝今天）、不含 `result=`；用固定時鐘，不依賴真實今天。
  - 行為測試：稽核頁以這組參數開啟時，動作下拉選到「登入失敗」、結果下拉是「全部」、起迄日是帶入的兩天。
  - 服務測試：同一批資料（24 小時內 3 筆 `Failed`、1 筆 `Denied`、25 小時前 1 筆、其他動作的 `Denied` 1 筆）——卡片數字 4；以下鑽參數查詢得到 5 筆，且包含卡片計入的 4 筆、不含其他動作那一筆。
  - 突變：下鑽改回 `result=Denied` 時，前兩個測試紅。
  - 量測：儀表板相關情境五寬度六項為 0（卡片多了一句說明）。

### B2 PRTG 診斷資料匯入沒有寫稽核

- **定案**：
  - 完成驗證成功時寫一筆 `prtg_data_import`：摘要寫「匯入 PRTG 診斷資料（隔離儲存，未寫入正式資料）」，明細放搬運編號、宣告位元組數、分塊數、封包雜湊前 12 碼。
  - 放棄時寫一筆同動作，摘要寫「放棄匯入」。
  - 建立不寫（之後不一定有資料進來）。對已完成的搬運再呼叫完成（直接回傳現況）不重複寫。驗證失敗不寫成功紀錄。
  - 寫在控制器，與其他控制器的做法一致；不為此新增服務。
- **不得外洩**：明細不放檔案內容、連線位址或例外原文。
- **驗收**：
  - 控制器測試四例：完成成功＝稽核 1 筆且動作、摘要、明細欄位如上；同一搬運再呼叫完成＝仍是 1 筆；放棄＝1 筆且摘要含「放棄」；雜湊不符導致驗證失敗＝0 筆。
  - 動作標籤維持「匯入 PRTG 鏡像資料」（與匯出的標籤成對，不改）；「隔離儲存」寫在每筆的摘要。以既有的動作標籤測試確認對照表有這個動作。
  - `Authorization|ControllerRouteSnapshot` 綠（端點與權限沒變，快照不得有差異）。
  - 突變：拿掉完成時的寫入，第一例紅；拿掉「已完成不重複寫」的判斷，第二例紅。

### B3 前端行為測試輸出讀不完時靜默回空
- **現況（已查證）**：`NodeRuntime.RunCore` 在程序結束後最多等 5 秒讀完 stdout／stderr，沒讀完就把輸出當成空字串回傳；呼叫端拿空輸出去比對，失敗訊息看不出是管線問題。
- **定案**：`NodeRunResult` 加一個旗標表示輸出不完整；`RunOrFail` 看到它就以「node 輸出管線逾時」失敗並附已讀到的內容。等待秒數不變（要解的是靜默，不是時間）。不加重試。
- **驗收**：
  - `NodeRuntimeTests` 新增一例：執行一支會啟動孫程序抓住管線後自己結束的腳本（或以同等方式讓管線在 5 秒內讀不完），斷言 `RunOrFail` 的失敗訊息含「輸出管線逾時」。
  - 既有 `NodeRuntimeTests` 與全部 `*BehaviorTests` 綠（正常路徑旗標為 false、行為不變）。
  - 突變：把旗標固定成 false，新測試紅。
  - 這個測試本身要在 10 秒內結束，不拖慢全量。

### B6 掃描匯入精靈列出密碼解不開的 Sentinel
- **現況（已查證）**：`netiq-import-wizard.js` 的下拉只篩 `active && canDiscover`；`canDiscover` 只看欄位非空，密碼解不開（`credentialState === 'undecryptable'`）的也會列出，選了必定失敗。同頁「探測」下拉是把它列出並標「密碼無法解密」，兩處處理不同。
- **定案**：匯入精靈下拉排除 `undecryptable`。因此沒有可選項時，提示依原因分兩句：有解不開的寫「有 Sentinel 的密碼無法解密，請至『設定』分頁重新輸入密碼」；其餘沿用既有的「補上探索帳密」。判斷直接寫在篩選條件裡，不另抽共用函式（兩處的處理方式本來就不同）。
- **驗收**：
  - 行為測試三例：一個正常加一個解不開＝下拉只有正常那個；全部解不開＝顯示「密碼無法解密」那句；全部是帳密未設定＝顯示既有那句。
  - 突變：拿掉 `undecryptable` 條件，第一例紅。
  - 量測：NetIQ 維護頁相關情境五寬度六項為 0。

### B7 權限異動清單依主機名排序，兩種資料庫順序不同
- **現況（已查證）**：`PermissionChangeStore` 依 `HostName` 排序。SQLite 區分大小寫（大寫排在小寫前），SQL Server 預設不區分，兩個後端順序不同。資料表有正規化的 `HostNameKey`，而且已有 `(HostNameKey, DetectedAt)` 索引。次序鍵含唯一編號，不會漏列或重複。
- **定案**：主機名排序改用 `HostNameKey`，其後的次序鍵不變。順帶讓這個排序用得到既有索引。
- **同型普查**：問題查詢「依主機」排序（`EfAnalysisRecordStore` 的 `OrderBy(r => r.HostName)`）是同一型。該表若有對應的正規化鍵欄就一併改並補同款測試；沒有就不加欄位，記進 BACKLOG。
- **驗收**：
  - store 測試（SQLite）：`srv-b`、`SRV-A`、`srv-c` 升冪得到 A、B、C，降冪反之；同主機名多筆時依偵測時間新到舊。
  - SQL Server 翻譯測試（`ToQueryString`）：產生的 SQL 以 `host_name_key` 排序。
  - 分頁測試：三頁各取一筆，合起來不重複、不漏。
  - 突變：改回 `HostName`，第一個測試紅。
  - 同型普查的結果（改了或記 BACKLOG）寫進執行紀錄並附 `git grep` 輸出。
