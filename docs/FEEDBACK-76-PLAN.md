## 使用者定案（2026-11-16）

1. **沒有真實資料**：評估全部使用合成資料，報告須標明「合成情境只能驗證規則照設計運作，不代表正式環境的誤報率」。
2. **不建立假的 PRTG／NetIQ 伺服器站台**：NetIQ 已確認可正確取數，只跑既有回歸；PRTG 要確認能正確取得資料（含第 75 輪處理過的快照停擺），以程序內替身與官方 API 文件驗證。
3. **其餘照主代理建議**：在測試程式內直接餵事件給分析流程；模擬工具留成永久回歸資產；「應有嚴重度」由主代理依官方文件與領域知識標註並附依據，標完先提交再跑對照；已確認的缺口記進依據、第二階段一起修；上一輪留下的項目第一階段不做。
4. **本輪是總體檢**：從取數、分析、派工、通知、授權、API 到畫面與說明書，每一層都要有檢查紀錄。

## 第一階段原則

- **只取依據，不修正式碼**：第一階段的改動限於測試專案、量測工具與文件。發現的問題一律記進評估記錄，第二階段再依整體角度決定修法；唯一例外是「資料會遺失或授權外洩」等級的問題，發現時立刻停下來與使用者討論。
- **先標預期再看結果**：嚴重度與串接情境的「應有行為」先寫好、先提交，之後才執行；避免看了結果回頭調整預期。
- **每條發現都可重現**：記錄要附重現方式（情境名稱、測試名稱、資料集情境 ID 或檔案:行號），不接受「看起來怪怪的」。
- **照現況斷言**：E3、E4 的回歸測試斷言目前的行為，與預期不同的格子列進「已知差異」清單並對應記錄編號。清單外出現新差異會轉紅；清單內的項目若已與預期一致也會轉紅（逼第二階段修好時一併移除），避免測試變成只會綠的擺設。

## 評估記錄格式

記錄寫在 `docs/drafts/FEEDBACK-76-EVIDENCE.md`（不放 `docs/` 主目錄：那裡只放現行事實，`DocNarrativeGuardTests` 也會掃；收尾時與本檔一起歸檔）。每條一列：

| 欄位 | 內容 |
|---|---|
| 編號 | `E{批次}-{序號}`，如 `E3-07` |
| 層面 | 取數／分析／AI／派工／通知／授權／API／畫面／說明書／維運 |
| 角色與情境 | 誰、在做什麼 |
| 現象 | 實際看到的行為（附重現方式） |
| 預期 | 應有的行為與依據（規格 § 編號、官方文件、說明書句子） |
| 影響等級 | **阻斷**（做不完或做錯）／**誤導**（結果或文字會讓人判斷錯）／**困擾**（多步驟、要猜、要來回）／**瑕疵**（不影響判斷） |
| 同型 | 同一模式在別處有沒有（同型普查的結果） |

截圖不進版控：每張都可由 `ui-scenarios.json` 的情境 ID 重拍，記錄只寫情境 ID 與量測結果。

## 批次 E0：模擬工具

### 現況與核對結果
- UI 資料集（`LogForesight.Tests/UiFixture/UiFixtureDataSet*.cs`）直接寫入分析結果、處理狀態、交辦單，是 28 天的靜態快照，不經分析流程，也沒有逐日推進。帳號有 `ui-admin`、`ui-manager`、`ui-handler`、`ui-viewer`、`ui-handler-long`、`ui-same-a/b`。
- 量測工具 `ui-shots.mjs` 有 `click`、`clickIf`、`waitFor`、`key`、`evalAssert`、`patchApi`、`faultApi` 等步驟，**沒有輸入與送出**；寫入流程只能用 `evalAssert` 自己呼叫 API，走不到真的表單驗證與畫面回饋。
- 管線層測試用記憶體替身組裝（`NetiqPipelineBaselineTests`、`PrtgDailyPipelineTests`），沒有「事件 → 分析 → 夜間派工 → 處理人回覆 → 管理者覆核」整條、跨多天的驅動。
- 整合式 HTTP 測試只有授權矩陣（`Authorization/AuthorizationHttpFixture.cs`，`WebApplicationFactory` 多角色登入）。

### 定案
- **E0-a 逐日情境驅動器**（測試專案內，暫定放 `LogForesight.Tests/Scenarios/`）：
  - 輸入：一份情境描述——主機清單（平台、群組、負責人）、使用者與角色、逐日的合成事件（Windows 事件或 Linux syslog，含時間、來源、事件編號、訊息主體）、PRTG 替身資料（可選）、每日要執行的人為動作（處理人回覆、管理者交辦／改派／退回／代為結案／靜音、停用使用者、改主機群組等）。
  - 執行：以可控時鐘逐日推進，每天依序跑真實的分析（規則、趨勢、關聯、主機日風險）、夜間派工、該日的人為動作；人為動作一律經 Web 服務層（與控制器同一條路徑），不直接改資料表。
  - 輸出：每一天的主機日風險與判定依據、問題清單、派工決策與略過原因、交辦單狀態、通知佇列內容、稽核紀錄；可以輸出成 markdown 表格供評估記錄引用。
  - AI 用既有替身；需要檢查 AI 輸入時讀替身收到的 prompt，不呼叫真實模型。
  - 情境描述用 C# 建構（型別安全、可重用片段，如「磁碟逐步故障七日」），不另造檔案格式。
- **E0-b 量測工具補兩種步驟**：`type`（對選擇器輸入文字，觸發 `input`／`change`）與 `select`（下拉選值）；送出沿用 `click`。找不到元素一律失敗，不做條件式版本。`DESIGN-SYSTEM.md` §8.7 補說明。
- **E0-c 角色帳號補齊**：UI 資料集補三種目前沒有的身分——Dev 角色、只因「主機負責人」而隱含處理能力的使用者、`serverAdmin` 救援帳號的登入情境；既有情境不受影響。

### 驗收
- 驅動器自身的測試：一份兩台主機、三天的最小情境，第 1 天磁碟錯誤 → 第 2 天夜間派工建單 → 第 3 天處理人回覆「已處理」，斷言每天的風險、建單、回覆後的交辦單狀態與通知佇列；把「人為動作經服務層」改成直接寫表時，至少一條斷言（稽核或通知）要轉紅（主代理突變）。
- 時鐘：同一份情境跑兩次輸出逐位元相同（確定性）。
- `type`／`select`：一個新的量測情境在設定頁輸入值並送出，斷言畫面出現已儲存的回饋；選擇器打錯時情境失敗（反例）。
- E0-c：新增帳號後既有 184 個情境的量測結果不變（跑 `quick` 矩陣比對）。
- E0 結束跑一次全量測試，結果寫進執行紀錄。

## 批次 E1：說明書與畫面文字逐句核對

### 範圍
- 說明書 24 章（`LogForesight.Web/HelpContent/*.md`）、對應的 AI 參考指引（`*.ai.md`）、`manifest.json`（標題、關鍵字、權限、相關章節）。
- 畫面上的說明文字：頁面內的提示與說明、空狀態文字、確認對話、錯誤訊息（`ApiErrorCodes` 對應的訊息）、通知信範本、匯出檔的欄位說明。

### 方法
- 逐句抽出**可查證的主張**：按鈕與欄位名稱、導覽路徑、網址、權限與角色、數字（門檻、天數、筆數）、步驟順序、「會發生什麼」的描述。
- 每條主張對照實際來源：導覽名稱對 `layout.js` 與 View 的顯示文字；權限對 `RoleCapabilityMap` 與控制器屬性；數字對程式常數或 `SystemSettings` 預設值；行為描述對服務層程式。
- 結果分類：**正確**／**錯誤**（與程式不符）／**過時**（功能已改）／**含糊**（使用者照做會卡住或誤會）／**缺漏**（畫面有、說明沒寫，或常見情境沒寫）。
- 另外以 `HELP-WRITING-GUIDE.md` 的讀者設定（非 IT 人員）檢查：術語是否解釋、句子是否能照著操作。
- 使用者版與 AI 參考指引要互相一致；不一致本身就是一條發現。

### 執行
- 24 章分四組交給唯讀代理並行（Haiku 做抽取與比對，判斷含糊與缺漏的部分交 Sonnet）；代理只回報，不改檔。
- 主代理每組抽驗至少五條「正確」與全部「錯誤／過時」，抽驗不符的那組整組重做。

### 驗收
- 每章至少一列記錄（沒發現也寫「已核對，N 條主張皆正確」並列出抽驗的幾條）。
- 主張總數、各分類數量寫進評估記錄的摘要表。

## 批次 E3：管理者與處理人串接情境矩陣

### 已確認（開輪核對時讀過程式碼）
1. **靜音的「代為結案」會讓問題永遠不再派工**：靜音選代為結案時以 `wont_fix` 結案（`IssueOwnerAdminService.cs:306`）；派工的「不再打擾」只看該主機該問題最近一件案件是否以不處理類狀態結案（`DispatchContext.cs:236`），沒有過期條件。靜音到期後，續掛、問題負責人、自動派工三條路徑全被擋住。
2. **代為結案不通知處理人**：`WorkOrderCommandService.AdminClose`（`:393`）只寫稽核；通知種類只有建立、追加、轉出、取消、退回五種，靜音暫停與恢復同樣不通知。
3. **續掛不檢查處理人狀態**：`WorkOrderDispatcher` 的續掛（`:83`）只看單是否可續掛、範圍是否涵蓋；處理人已停用、暫停接單、離開派工池或看不到該主機時，新主機照樣掛進去。

| S14 | 處理人沒有 email、管理者群組都沒有 email | 通知去哪裡 |

| S16 | 問題負責人路徑與自動派工同時適用 | 優先序是否如 WEB-SPEC §9.4b |
| S17 | Manager／Dev 打開「我的交辦」 | 他們沒有處理能力時畫面怎麼說 |

### 驗收
- 18 個情境全部以 E0 驅動器實作成測試，斷言現況；與預期不同者列入「已知差異」並對應 `E3-xx` 記錄。

## 批次 E4：規則嚴重度情境庫

### 現況與核對結果
- 規則唯一種子 `KnownIssueSeed.cs`（Version 11），約 104 條：Windows 64、Linux 28、PRTG 12；會拉高主機日風險的「重大」規則 18 條，次數門檻全是 1。
- 主機日風險（`LogAnalysisService.ComputeRuleBasedRisk`）：未被抑制的重大問題或重大關聯 → 高；有趨勢告警、任何關聯、或未被抑制的 High 問題 → 中；其餘低。AI 只能往上調。
- 已核對：`builtin-hardware-whea-error` 比對所有事件編號、沒有次數門檻、帶重大旗標；`builtin-hardware-kernel-power-41` 同樣單次即重大。
- 次數門檻是單日總數，不看時間分布；頻率上升判定在歷史中位數很低時 5 次即成立，High 規則因此直接變成重大（`TrendAnalyzer`）；部分關聯（帳號異動＋新服務、儲存連鎖）只要求同一天各一筆。
- 沒有任何以事件序列、依情境斷言最終風險的測試；校準匯出只涵蓋 PRTG。

### 預期等級的標註
- 由主代理依官方文件（Microsoft 事件說明、Linux 核心與發行版文件、PRTG 手冊）與實務常識標註，每個情境寫明**應有的主機日風險**、**應出現的問題與關聯**、**依據來源**（網址或文件章節）。
- 標註以「維運人員第二天早上看到這個等級，會不會做出正確的動作」為準：
  - **高**：今天就要有人處理，不處理可能停機、資料損毀或已被入侵。
  - **中**：這週要看，單獨出現不急，但不能忽略。
  - **低**：記錄即可。
- 標註完先提交，之後才執行對照。

### 情境清單（約 24 個，硬體／入侵／雜訊三類各約三分之一）
- **可能高估**：計畫性重開（Kernel-Power 41＋6008 在維護窗口）、patch 日（服務重啟、NTFS 修復訊息）、單次已修正的 WHEA、單次藍屏後穩定、Defender 單次處置失敗、IT 日常新建帳號又安裝服務、Linux USB／光碟的 I/O error、SAN 多路徑切換、歷史基準為 1 時某天出現 5 次的 High 事件。
- **可能低估**：Medium 規則連續多日出現、磁碟錯誤逐日增加但每天都未達門檻、Linux 儲存三連（I/O error＋唯讀重掛＋陣列降級）同一天、低速密碼噴灑（每天少量、跨很多帳號）、登入失敗集中在一小時內 vs 分散全天、事件日誌磁碟錯誤與 PRTG 磁碟 down 同一天。
- **應該正確**（對照組）：磁碟逐步故障七日、暴力破解後成功登入、清除稽核紀錄、正常營運日（應為低）。
- Windows 與 Linux 各自覆蓋；PRTG 相關情境只用程序內替身資料。

### 驗收
- 每個情境的預期、實際、差異方向（高估／低估／一致）與牽涉的規則或門檻寫進評估記錄的對照表。
- 情境進回歸測試，差異列入「已知差異」清單。
- 對照表附摘要：高估幾個、低估幾個、牽涉哪些規則、哪些是單一門檻造成、哪些是機制造成（例如只看單日總數）。
- 主代理突變：把任一重大規則的旗標拿掉，至少一個「應該正確」情境要轉紅。

## 批次 E5：PRTG 取數驗證

### 現況與核對結果
- 第 75 輪批次 G-4 已找到快照停擺的根因：快照待寫檔記著資料庫識別，資料庫被換掉或重建後識別對不上，每一輪都直接返回；診斷卡因此誤寫「無目標」，健康頁與啟用準備也沒有反映。第 75 輪已加上「安全時自動封存並重新開始」、維護頁的手動出口、診斷新狀態與健康頁警示，並以兩個 SQLite 檔的整合測試重現。**使用者那台開發站台升級後是否恢復，第 75 輪列為交接確認事項，尚未確認。**
- PRTG 相關測試約 120 個類別，多數是單元或單一服務層；沒有從「PRTG 回應」一路到「主機日風險」的整條檢查。
- 鏡像的感測器單位全為空（BACKLOG「PRTG 鏡像沒有感測器單位」）；數值語意只依感測器類型判定（`PrtgValueAssessment.cs`），PRTG 介面語系不是英文時對照會全部對不上（BACKLOG）。

### 方法
1. **API 契約對照官方文件**：逐一列出程式呼叫的 PRTG API（裝置、感測器、頻道、歷史值、訊息、狀態），對照 Paessler 官方 API 文件確認參數、欄位意義、分頁與 `treesize` 截斷行為、狀態代碼、時間格式與時區、數值的原始值與顯示值。每條記「程式的假設／官方說法／一致與否」。
2. **整條鏈程序內驗證**：用 `HttpListener` 替身回應依官方格式構造的 JSON，依序跑結構同步 → 主機對應 → 取數範圍 → 快照 → 夜間每日流程 → PRTG 發現 → 主機日風險與畫面資料，斷言每一層拿到的數字與上一層一致。
3. **邊界**：分頁截斷（回傳筆數少於 `treesize`）、單次請求逾時、空回應、權限縮小造成的範圍縮小（不得清除）、感測器類型名稱非英文、時區跨日、同一 sensor 一天多筆訊息（不得以 `objid` 去重）。
4. **快照停擺修正的回歸**：G-4 的七種情況重跑一次並確認測試仍在全量裡；另檢查「快照停止 → 健康頁警示 → 管理者照畫面指示能否自行恢復」整段在畫面上講得通（與 E2 管理者旅程合併操作）。
5. **NetIQ**：只跑既有回歸（`Netiq` 相關測試類別），不新增。

### 驗收
- 契約對照表每條都有官方文件出處；與官方不一致者為一條發現。
- 整條鏈測試全綠，每一層的數字可對帳；把「回傳筆數少於 treesize 時出聲」拿掉，截斷案例要轉紅（主代理突變）。
- 交接事項：請使用者在開發站台確認快照已恢復（鏡像狀態頁有本次啟動後的成功取樣），結果記進評估記錄；不作為本批完成的條件。
