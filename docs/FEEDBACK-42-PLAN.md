## 批次A：結構同步分頁收斂保險絲

### 現況與核對結果

- `FetchTablePagedAsync` 只有兩道停止：回應不是陣列、本頁筆數少於 500。offset 累加後無上限，每頁受單次逾時 60 秒約束、整段無上限。
- 三個呼叫端（devices／sensors／messages）都丟棄它的回傳值，各自在 onBatch 累加寫入數。
- messages 階段的回應順序不穩定（探測事實），分頁重疊時同一筆會出現兩次；目前靠 upsert 唯一鍵吸收，讀取數會偏高但不出錯。
- 階段失敗只 `failures++`，寫入數停在 0；Runner 以「Failures>0 且 Devices==0」判定整趟失敗、不做對應。

### 定案

1. **分頁迴圈抽成 `PrtgTablePager`**（Core，internal，可獨立測試），`FetchTablePagedAsync` 改為呼叫它。單一實作，之後任何新的分頁需求都走這裡。
2. **停止條件三道**，任一成立即停：(a) 回應不是陣列或空頁；(b) 本頁筆數少於頁大小；(c) **本頁沒有任何新 objid**（以 objid 集合去重；objid 缺失或無法解析的列不計入「新」）。(c) 正是探測看到的「夾到末頁」情況的收斂條件。
3. **頁數上限**＝max(⌈treesize ÷ 頁大小⌉ + 2, 400)（兩個數字皆暫定）。treesize 在帶 `filter_drel` 的 messages 查詢下是「過濾後」還是「全表」筆數**未驗證**，因此它只能把上限放大、不能縮小；真正的收斂靠條件 (c)，上限是最後一道保險絲。到達上限仍未收斂時擲出可辨識例外（訊息含 content、已翻頁數、已讀筆數），**不靜默**。
4. **去重後才交給 mapper**：同一 objid 第二次出現的列直接丟棄，不進 onBatch。讀取數（進度分子）仍算原始列數，另回報「重複列數」。去重集合以 HashSet<long> 存 objid，messages 階段最壞數十萬筆、記憶體數 MB，不違反 §3 記憶體原則。
4a. **查詢加 `sortby=objid`**（暫定）：探測看到 messages 同頁內 objid 不遞增，順序不穩定的來源分頁會漏列，這是 PRTG 端的性質、去重救不了。PRTG table.json 文件有 `sortby` 參數；加上去對不支援的版本無害。批次 0 追加：探測步驟 8 改帶 `sortby=objid` 並印出「頁內是否遞增」，讓下次探測直接驗證。
4b. **同步摘要加每階段耗時與重複列數**：現行只有整趟耗時，管理者無從判斷哪個階段值得優化（BACKLOG 三項的觸發條件需要這個數字）。
5. **N3 失敗語意**：保險絲例外由呼叫端當作該階段失敗（failures++），但**已寫入的筆數照樣回報**（Devices／Sensors 不歸零），Runner 現行規則「有失敗但拿到裝置時對應照做、整體不報成功」自然接得上；錯誤訊息要說得出「分頁未收斂，已寫入 N 筆」。
6. 不加整段逾時（維持 PRTG-SPEC §3 原理由）；批次 C 的取消鈕與本批次的保險絲合起來取代它。
7. 分頁器讀 objid 的欄位名固定為 `objid`，三個 content 都有。

### 改動

1. 新增 `PrtgTablePager`（Core/Service），承接現行迴圈、進度回呼、每 50 頁一行執行輸出。
2. `PrtgFetchService` 三個呼叫端改走分頁器；階段 catch 內把已寫入數保留到結果。
3. `PrtgFetchResult` 不加欄位；錯誤文字進執行輸出與 `ErrorMessage`。

### 測試／驗收

- 替身「每頁回滿 500 筆且 objid 集合固定」：迴圈在第 2 頁停止（條件 c），寫入 500 筆，不擲例外。
- 替身「每頁回滿 500 筆且 objid 每頁都新」、treesize=1000：第 4 頁到上限擲例外，例外訊息含頁數與筆數；上層階段記失敗、已寫入的 1500 筆回報在結果。
- 替身「treesize 缺失、永遠回滿頁且 objid 每頁都新」：第 400 頁停止並擲例外（用可注入的上限常數把 400 縮小跑，避免測試慢）。
- 替身「總筆數剛好 1000、超出範圍夾到末頁」（模擬探測事實）：讀 3 頁、寫入 1000 筆、重複列數 500、不擲例外。
- 既有「伺服器忽略 start」測試改成每頁回滿 500 筆同一批 objid，斷言請求數 ≤ 2 且寫入 500。
- 既有分頁測試（503 筆、treesize 缺失）維持綠。
- 同步摘要含每階段耗時與重複列數（執行輸出斷言）。
- 全套 `dotnet test` 綠。

## 批次B：資源守門即時來源改單次大 count

### 現況與核對結果

- `PrtgLiveGuardSource.FetchAll` 分頁 50 頁上限，超過直接回傳已讀部分、無任何訊號；跑在 HTTP 請求執行緒上，同步阻塞。
- 正式環境 42864 個感測器需 86 頁，現行必然截斷在 25000 筆；偵測結果對落在後段的感測器一律「未偵測到」。
- preview 回應 DTO 已有 `Warnings` 清單與前端渲染，加警告不必動 DTO 與前端。
- 探測已證明 `count=50000` 單次抓完 42864 筆。

### 定案

1. 即時來源**改為兩段單發**：先 `count=1` 取 treesize，再以 `count=treesize`（treesize 缺失時 50000）一次取完；不再分頁。
   〔實作結果：改為**單次一發**——treesize 隨同一份回應回來，先探一次是多餘的往返。見〈與規劃的落差〉3。〕理由：它在請求執行緒上，翻 86 頁的逾時風險比記憶體實際；探測與同步已各有一套取法，守門跟探測同型。
2. **截斷不靜默**：實際筆數少於 treesize、或 treesize 缺失且筆數等於 50000 時，把「取樣不完整 N／M 筆，偵測結果可能漏掉部分感測器」加進 Warnings，**並附處置**：「請改用覆寫清單指定 objid」（PRTG 單次回應上限約 5 萬筆，超過就不是分頁能解的）。結果照常回傳（讓使用者仍看得到已偵測到的部分）。
2a. **部署注意（寫進 PLAN 體檢交接與 PRTG-SPEC §7）**：本輪之前用「自動偵測並填入」產生的覆寫清單是從截斷後的 25000 筆偵測的，**可能不完整**；部署後要重按一次自動偵測並重新儲存。
3. Warnings 的輸送管道沿用現有 `ResourceGuardWarningConsole`（來源要能寫入警告，介面暫定加一個可選的警告回呼；不改 DTO）。
4. 移除 `MaxPages`／`PageSize` 常數與對應註解。

### 改動

1. `PrtgResourceGuardSource.cs`：`PrtgLiveGuardSource` 取法改寫，加警告回呼。
2. `SettingsController.PreviewPrtgResourceGuard` 把警告接到既有 Warnings。

### 測試／驗收

- `PrtgLiveGuardSourceTests`：刪除「靠上限停止」測試；新增「treesize 42864、大 count 回 42864 筆 → 全數回傳、無警告、恰好兩次請求」；「treesize 42864、回 25000 筆 → 回傳 25000 筆且警告含 25000／42864」；「treesize 缺失、回 50000 筆 → 警告」。
- `PrtgResourceGuardPreviewEndpointTests`：即時來源截斷時回應 `Warnings` 含該字句、`Source` 仍為 live。
- 全套綠。

## 批次C：結構同步可取消

### 現況與核對結果

- `PrtgStructureSyncService.Cancel()` 已存在且取消時已會落地「同步已被取消」狀態，只缺對外端點與按鈕。
- `IPrtgStructureSyncGate.WaitUntilIdleAsync` 回 true＝結束，取數路徑據此跳過自己的結構同步；同步被取消或失敗時鏡像不完整，取數卻不補爬。
- 兩個前端入口：維護頁鏡像頁籤（`prtg-admin.js`）、排程作業頁 PRTG 卡（`runs.js`），各有一顆「同步結構與對應」按鈕。

### 定案

1. 新增 `POST prtg-structure-sync/cancel`（權限與 start 相同）。未執行中時回 409 與說明；執行中時觸發 `Cancel()` 並回成功（實作為 200，理由見定案 6）。
2. 兩處入口各加一顆「停止同步」按鈕，只在 status 回報執行中時**出現**（實作採隱藏／顯示而非灰掉——沒有東西可停時按鈕根本不該在畫面上）；按下後輪詢到結束為止。既有「三卡按鈕互斥」規則（R41）不變：停止鈕不算啟動動作。
3. **閘門契約收緊**：`WaitUntilIdleAsync` 回 true 的條件改為「**這次等待的那趟同步**結束且成功」；被取消、失敗、逾時等待都回 false，取數路徑照常自行同步結構。介面註解同步改寫。範圍限定在「等待的那趟」：取數路徑只在同步執行中才呼叫閘門（`PrtgDailyPipeline` 已核對），不會拿幾天前的成功結果放行。
4. 取消後的狀態卡文字維持「同步已被取消」，並加一句「鏡像可能不完整，夜間取數會重新同步」。
5. **稽核**：取消寫一筆 `AuditActions.PrtgStructureSyncCancel`（與 start 的 `PrtgStructureSyncRun` 同型），管理者要查得到誰在什麼時候中止了同步。
6. 取消與啟動的競態：端點先看 IsRunning 再呼叫 Cancel；在 TryStart 之後、`_cts` 指派之前的極短窗口取消會落空，回應仍為成功，下一次輪詢會看到還在執行，使用者再按一次即可。不加鎖。（實作回 200 而非 202：本專案的 API 信封沒有用 202 的先例，不為這一支破例。）

### 改動

1. `SettingsController`：cancel 端點。
2. `PrtgStructureSyncService`：閘門判定改看等待的那趟結果；`Cancel()` 對外。
3. `prtg-admin.js`、`runs.js`、對應 cshtml：停止鈕與狀態聯動。
4. UI 測試補停止鈕存在與 disabled 規則。

### 測試／驗收

- 端點測試：未執行中 → 409；執行中 → 202 且服務的 Cancel 被呼叫。
- 閘門測試：等待中的那趟結果 Success=false 時 `WaitUntilIdleAsync` 回 false；成功時回 true。
- 稽核測試：取消端點寫入 `PrtgStructureSyncCancel`。
- `PrtgDailyPipeline` 既有「等待同步後跳過結構同步」測試補反例：閘門回 false 時照做結構同步。
- `PrtgAdminPageUiTests`／runs 頁測試：停止鈕存在、未執行時 disabled。
- 全套綠。

## 明確不做（本輪定案）

- **整段逾時**：有取消鈕與收斂保險絲後不需要，原理由（大型環境會誤殺）仍成立。
- **感測器階段只抓有對應裝置的感測器**、**規則評估先過濾未對應感測器**、**探測與同步取法統一**：效能與一致性，進 BACKLOG，觸發條件「結構同步實測耗時超過可接受範圍」。
- **結構同步改單次大 count**：探測證明 start 被遵守，分頁加保險絲即可；單次 5 萬筆進記憶體違反 §3 的記憶體原則。
- **分頁器回傳值被呼叫端丟棄**：不影響行為，順手清但不列驗收。

## 部署前後的操作注意（給管理者）

- 部署前：正式環境若有跑不完的同步，仍只能重啟站台停掉；每晚取數會先等它 90 分鐘才自行同步，這段期間夜間批次晚 90 分鐘完成。
- 部署後：① 重按「自動偵測並填入」並儲存（舊清單可能不完整，見批次 B 2a）；② 手動跑一次「同步結構與對應」看每階段耗時，決定 BACKLOG 三項要不要提前。
- 無 schema 變更，可直接回退分支。

## 規劃完成後複檢（四角度）

- **整體專案**：分頁只剩一個實作（批次 A）；守門與探測同用單次大 count（批次 B）；三份規格互相引用的段落已列在批次 D。treesize 語意未驗證的部分只當放大器不當縮小器。
- **程式面**：閘門只在同步執行中才被查詢，收緊契約不會被舊結果污染；鏡像只 upsert 不刪舊列，半套同步不會誤刪（舊裝置永不移除是既有行為，本輪不動）；保險絲例外與取消例外走不同型別。
- **使用者**：截斷警告附處置、取消後說明鏡像狀態、同步摘要給每階段耗時；舊覆寫清單可能不完整要主動告知，不能等使用者自己發現「怎麼還是少」。
- **管理者**：取消有稽核、權限同 start、無 schema 變更可回退。
- 批次 A 的「本頁無新 objid 即停」與 messages 階段的當日過濾不衝突：去重在 mapper 之前，過濾在 mapper 內。

### 與規劃的落差

1. **頁數上限公式在規劃階段就從「treesize 已知時用推算值」改成「max(推算值, 400)」**
   （規劃複檢時改的，正文第 3 條已是改後版本）。理由：treesize 小的環境會推算出很小的上限
   （例如 1000 筆＝4 頁），若 PRTG 回報的 treesize 是過濾後筆數而實際資料更多，
   合法同步會被誤判成未收斂。改成只放大不縮小。
   測試「treesize已知時上限跟著放大而不是被縮小」鎖住這個語意。
2. **`RunPagedStageAsync` 把未收斂例外轉成階段結果**而非讓它往外擲到 FetchDayAsync 的泛用 catch。
   理由：泛用 catch 會讓該階段的寫入數歸零，畫面顯示「沒有取得任何裝置」與事實不符（定案 5 的要求）。
3. **B 的取數改為單次一發，不是本文批次 B 定案 1 寫的「兩段單發」**（該條仍是規劃當下的版本，未回頭改寫）。
   理由：treesize 隨每次回應一起回來，先探一次是多餘的往返。單次 `count=50000` 後直接比對
   回應內的 treesize 即可判斷截斷。
4. **preview 端點層沒有新增「live 截斷時 Warnings 含警告」的測試**。
   原因：該端點用 `PrtgClientFactory.Create(settings)` 建 client，測試無法注入 HttpMessageHandler，
   做不出「live 成功但截斷」的情境。覆蓋改為兩段：來源端警告由 `PrtgLiveGuardSourceTests` 驗證，
   console→Warnings 的管道由既有 `mirror-fallback` 測試驗證。**殘留風險**：
   SettingsController 傳 console 進 `PrtgLiveGuardSource` 這一行若被改掉，沒有測試會紅。
5. **C 的「閘門只看等待的那趟」以行程內 volatile 旗標實作**，初值 false。
   影響：站台重啟後、還沒跑過成功的手動同步之前，取數一律自己同步結構（安全方向）。

### 測試守門力的已知缺口

- **閘門回 true 的分支沒有單元測試**：要造出「一趟成功的同步」必須注入 PRTG 替身，
  而 client 由 `PrtgClientFactory` 從設定建立，測試無法插手。不為此在正式碼開測試後門。
  現有測試涵蓋「跑完但未成功 → 回 false」與「被取消 → 回 false」兩條真實路徑，
  且都同時斷言 `GetStatus().LastSuccess`（來自持久化狀態，不是恆真的旗標初值）。
  一度寫過的「啟動失敗後不沿用上一趟成功」測試因為旗標初值就是 false、寫死也會綠，已移除。
- **preview 端點層沒有「live 截斷 → Warnings」測試**，原因同上（無法注入替身）。

### 測試穩定性

全套跑過三次，第二次出現 1 個偶發失敗但輸出未保留失敗名稱，之後四次重跑全綠。
已為新測試中會啟動背景同步的兩個案例加上「等 IsRunning 轉 false」的收尾等待
（不等的話 Dispose 會在背景工作仍在寫 SQLite 時刪掉暫存目錄，紅在別的測試上）。
