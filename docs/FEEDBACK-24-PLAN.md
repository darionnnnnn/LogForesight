# 回饋第二十四輪規劃（FEEDBACK-24）：權限異動解析修正與例行同步合併

## 0. 背景與範圍

輸入：二十三輪實測回饋——列表第一層仍看不出重點（解析失效）、單日 9.2 萬則對稱異動的處置。

**已定案決策**（2026-08-20 與使用者討論定案）：
- **解析失效的根因是兩個獨立缺陷**：①NetIQ `msg` 攤平成單行，Extractor 逐行解析（區段偵測
  失效＋取值切到行尾）②群組名在真實訊息是「群組: … 帳戶名稱:」，`Section.Group` 無消費點，
  多行也抓不到。修法：後端移植前端已驗證的「行內多對＋區段感知」規則。
- **欄位辨識只用公認的 Windows／LDAP 標準欄位名**（中英官方欄名：Subject／主體、Member／成員、
  Group／群組、Account Name／帳戶名稱、Security ID／安全性識別碼、Group Name／群組名稱、
  Object Name／物件名稱…）。**測試資料不得引入公司內部自訂欄位假設**。不同公司若有自訂
  欄位名，由**欄位對應設定**解決：使用者把自訂 key 名對應到語意角色，不改程式。
- **超大量對稱異動維持合併**：同主機日「同成員＋同群組」的成員新增與成員移除**成對**出現、
  且成對數達門檻時，這些成對異動合併為一筆「例行同步彙總」列，說明文字明示推測原因
  （「可能是 AD 自動化程序（例如每天以先清空再重建方式同步群組成員的腳本）產生」）。
  **只合併這種情況**：未成對的異動、特權群組的異動（即使成對）一律逐則，避免夾帶誤判。
- 存量髒資料（舊版寫入的整段尾巴 TargetAccount、空 Target）：以新解析器從 `AlertText`
  重剖回填；`AlertText` 只有前 500 字，接受「盡力回填、剖不出維持降級句」；截斷上限維持 500。
- 彙總列 EventId 顯示「0」→ 顯示「—」。
- 批次確認 500 上限：合併機制落地後量會降，遞延 BACKLOG。

**明確不做**：AlertText 截斷上限加大；操作者白名單自動確認（丙案，另有需求再議）；
批次確認上限放寬。

## 3. 作業明細

### 作業 A-階段 1：解析器重寫（agy）
- **背景**：NetIQ 把 Windows 事件訊息攤平成單行 key: value 串；現行逐行解析在單行下失效，
  且群組區段內的帳戶名稱（真實群組名所在）沒有消費點。前端已有一套驗證過的通用解析規則。
- **契約**：
  1. `ParseMessage` 改為「行內多對」解析：每行拆成若干 (key, value) 對——key 出現在行首或
     空白之後、長度 2～20 字元、至少含一個字母或中日韓文字、不含冒號，後接半形或全形冒號；
     value＝冒號後到「下一個 key 起點」或行尾（去頭尾空白）；冒號後為空（緊接下一個 key
     或行尾）＝**區段標題**。單行與多行輸入都必須正確。
  2. **區段感知**：主體／成員／群組／物件等區段（中英官方名）內的「帳戶名稱／Account Name」
     「安全性識別碼／Security ID」依區段分派語意——**群組區段內的帳戶名稱＝群組名**（現缺的
     消費點）。既有欄位名清單（群組名稱:/Group Name:/物件名稱: 等）保留，從子字串命中改為
     key 精確比對（Subcategory 誤命中 Category 的守衛由精確比對天然取代）。
  3. 欄位名**只用 Windows 事件的官方中英欄名**；不得為任何公司特定值或格式寫死判斷。
  4. `Extract` 的對外行為契約不變：剖不出對象時 Target 為空字串；操作者優先取事件自帶值。
  5. 值內含冒號的路徑（`C:\share`）不得被誤切（key 長度下限 2 已擋 `C:`，維持）。
- **範圍**：`LogForesight.Core/Service/PermissionChangeExtractor.cs`＋對應測試檔。
  不准動 Web、docs/、HostDayPostProcessor（介面不變就不需動）。
- **驗收**：build 警告 ≤1；test 全綠、既有一支不少（基準 2433 總／略過 6），新增至少 8 支。
  **真實樣本必測**（逐例回報各欄位實際值）：
  - 單行 4756（使用者實測原文形狀）：`已新增成員到已啟用安全性的萬用群組。 主體: 安全性識別碼: S-1-5-21-x-17749 帳戶名稱: OP_ACCT 帳戶網域: DOM1 登入識別碼: 0x1FC9071B 成員: 安全性識別碼: S-1-5-21-x-278464 帳戶名稱: CN=User One,OU=Dept,DC=example,DC=com 群組: 安全性識別碼: S-1-5-21-x-40793 帳戶名稱: GROUP_A 帳戶網域: DOM1 其他資訊: 特殊權限: -`
    → 操作者=OP_ACCT、成員=CN=User One,…、群組=GROUP_A
  - 單行 4670（物件名稱: - 之後接控制代碼識別碼等）→ Target=`-` 經 CleanValue 後為空，不吞尾巴
  - 多行「群組:\n 帳戶名稱: X」（區段感知）→ 群組=X
  - 既有多行樣本全部維持等價（特別是 4719 的 `Object Access - File System：Success removed`
    逐字斷言與「Subject 帳號不得洩漏進 Member」兩支）
- **回報**：檔案清單、測試數字、逐樣本欄位值、偏離與理由。

### 作業 B-階段 1：欄位對應設定（agy）
- **背景**：不同公司的 NetIQ／事件來源可能用非標準欄位名。與其在程式裡累積各公司特例，
  提供設定讓使用者把自訂 key 名對應到語意角色。
- **契約**：
  1. `SystemSettings` 新增權限異動欄位對應：四個語意角色（操作者帳號／成員帳號／群組名稱／
     物件名稱），每個角色可設多個自訂 key 名（字串清單）。預設**全空**＝只用內建標準欄名。
  2. 解析時自訂 key 名**併入**該角色的判定（與標準欄名同權重、同解析規則）；自訂名同樣走
     key 精確比對。設定即時生效（沿用 SystemSettings 既有讀取模式）。
  3. 設定 UI：設定頁新增區塊，沿用既有設定頁的表單模式（不新做元件）；每個角色一個輸入
     （一行一個 key 名），含簡短說明「事件訊息用了非標準欄位名時才需要設定」。
  4. 消費端必須存在（專案紅線：有設定無行為是禁區）——Extractor 讀取對應表的路徑要接通
     並有測試證明「設了自訂名就解析得到」。
- **範圍**：`LogForesight.Core`（SystemSettings、Extractor 注入點）、`LogForesight.Web`
  （設定 DTO、設定頁、settings.js）＋測試。不准動 docs/。
- **驗收**：build 警告 ≤1；test 全綠既有不少，新增至少 5 支（自訂名命中／未設定時零影響／
  角色分派正確／設定往返序列化／UI 綁定的 DTO 形狀）。grep：Extractor 不得寫死任何非標準欄名。
- **回報**：同 A。

### 作業 C-階段 1：例行同步成對合併（agy）
- **背景**：AD 自動化（先清空再重建式同步）每天產生數萬則對稱的成員新增＋移除，逐則入庫
  會淹沒真正可疑的異動。使用者定案：只對這種情況合併，附說明文字。
- **契約**：
  1. **成對定義**（什麼算一對）：同一主機日內，(成員帳號, 群組名) 完全相同的「成員新增」與
     「成員移除」各一則配成一對；一則只能配一次；成員或群組剖不出（空）的不參與配對。
  2. **合併條件**：該主機日成對數 ≥ 門檻（暫定 50 對）才觸發合併；未達門檻全部照常逐則。
     **特權群組（IsPrivilegedTarget 命中）的異動即使成對也不合併**，照常逐則——安全訊號
     不得被自動化噪音機制吞掉。
  3. 觸發合併時：成對的異動不逐則寫，改寫**一筆**「例行同步彙總」列（ChangeType 暫定
     「例行同步（彙總）」、Category 沿用 `summary`），AlertText 說明格式暫定：
     「本日偵測到 {N} 對「成員新增＋成員移除」的對稱異動（涉及 {M} 個群組、{K} 個帳號），
     未逐則列出。此模式可能是 AD 自動化程序（例如每天以先清空再重建方式同步群組成員的
     腳本）產生；未成對的異動仍逐則列出。」
  4. **冪等**：彙總列去重鍵不得含筆數（筆數變動時更新既有列而非新增第二筆——上上輪的
     去重鍵教訓）；重跑同主機日結果一致。
  5. 顯示端：`GenerateSummaryText` 對此列輸出 AlertText 原文（沿用 summary 分支即可，驗證
     不需改就不改）；類別標籤沿用「權限異動彙總」。
- **範圍**：`LogForesight.Core`（HostDayPostProcessor、必要的模型常數）＋測試；Web 端若
  summary 分支已涵蓋則不動。不准動 docs/。
- **驗收**：build 警告 ≤1；test 全綠既有不少，新增至少 7 支：達門檻合併＋未成對仍逐則／
  未達門檻全逐則／特權群組成對不合併／一則只配一次（新增 2 移除 1 只成 1 對）／重跑冪等
  不產生第二筆彙總／筆數變動更新既有列／彙總列欄位形狀（EventId null、Before/After 空）。
- **回報**：同 A。

### 作業 D-階段 1：存量重剖回填（agy）
- **背景**：舊版解析缺陷寫進 DB 的髒值（TargetAccount 是整段尾巴、Target 空），修好解析器
  後要把既有 NetIQ 列盡力修回。
- **契約**：
  1. 對 `Source = NetIQ` 的既有列，以新解析器從 `AlertText` 重剖，更新 Target／TargetAccount／
     InitiatorAccount／Before／After（重剖結果非空才覆蓋；剖不出的欄位維持原值或空，
     顯示端既有降級句兜底）。彙總列（category=summary）跳過。
  2. 執行形狀沿用專案既有樣板：啟動時毫秒級判定＋背景服務執行（比照 `PermissionChangeMigrator`
     ／`HandlingBlobMigrator`），不掛啟動路徑；冪等（重跑不重複處理，完成後寫狀態不再掃）。
  3. `IsPrivilegedTarget` 隨重剖後的 Target 重算（群組名修好後特權判定才會生效）。
- **範圍**：`LogForesight.Core`（新遷移器＋註冊）＋`LogForesight.Web`（背景服務註冊若需要）
  ＋測試。不准動 docs/。
- **驗收**：build 警告 ≤1；test 全綠既有不少，新增至少 5 支：髒值列重剖後欄位正確／剖不出
  維持原狀／彙總列跳過／冪等（跑兩次結果相同）／IsPrivilegedTarget 重算。
- **回報**：同 A。
