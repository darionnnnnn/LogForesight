# 回饋第 78 輪規劃（草案）

> 狀態：草案——批次已劃分、現況已核對；**定案與驗收大多標「待量測」**：指以第 77 輪批次 0 的測試方法在開發機取得計數、比值與配置量後才定，不是等正式站台數字。
> 量測原則（同第 77 輪批次 0）：開發機效能不佳，**不模擬 3000 台、數字不當成正式主機的結果**；瓶頸以與機器效能無關的測試方法確認：沿用第 77 輪批次 0 的 T1（指令計數）、T2（查詢計畫）、T4（配置量）、T5（留存量）、T6（可回收性）、T7（上限）、T8（注入時鐘）；本輪若需要「持鎖中做了什麼」的盤點（批次 P），屆時再加，不預先建。正式主機的實測由使用者另開一輪以環境探測處理，本輪不以它為前提。
> 記憶體：每一批都含洩漏與膨脹檢查（見「記憶體檢查」一節）。
> 基準：第 77 輪完成後的 dev（開輪時填 sha 與測試數）
> 來源：第 77 輪的 3000 台規模盤點中排到第二輪的三類——聚合把原始列拉回記憶體、背景工作吞吐、只能靠量測回答的項目。
> 開輪時先做：讀第 77 輪「量測紀錄」→ 依數字刪掉不成立的項目、排定順序 → 把本檔搬到 `docs/FEEDBACK-78-PLAN.md` 再補定案。

## 核對程度標示

- **［親核］**：主代理讀過該段程式碼，機制成立。
- **［回報］**：掃描代理回報、主代理尚未複核；開輪時先讀碼確認再寫定案。

## 批次 I：問題聚合查詢

### 現況與核對結果
- ［親核］`EfIssueAggregateQuery.LatestOccurrences`（`:438`）以 `event_id IN` 粗篩後把逐列資料拉回，再於記憶體比對與分組；呼叫端傳入的是期間內全部問題，不是當頁。
- ［親核］`Aggregate`（`:168-180`）除主查詢外再補四趟；`SurvivingHostCounts`（`:2023`）先 `DISTINCT` 再 `ToList()` 拉回，原因是合併主機（墓碑）的別名解析無法在查詢端表達。
- ［回報］`SurvivingHostDayCounts`（`:2044`）的去重列數接近期間內原始列數；`DailyHostCounts`（`:514`）基準窗口 30 天。
- ［回報］呼叫端：`IssueRankingBuilder`（儀表板、報表排行）、`IssueHandlingRollupQuery`、`RecordListQueryService`（依問題視角，分頁之前就對全部問題做完）、`WorkOrderBoardService`（待派試跑）。
- ［回報］`AggregateByHost`（`:1721`）最新一天用相關子查詢。
- ［回報］儀表板 `SummaryCache`：鍵含 3000 個主機 id 的排序串接、同鍵並發未命中各算一次、任何寫入都推進同一版本戳。
- 既有實測：無 3000 台數字。BACKLOG 記「依問題視角的日風險子查詢重複四次」。

### 根因
別名合併只影響少數墓碑主機，卻讓整個去重無法下推；以及「取處理狀態」需要逐出現點資料，但被套用在全部問題而不是當頁。

### 定案（待量測）
- 方向一：沒有墓碑主機時走全下推路徑，有墓碑時只對牽涉到的主機補算。
- 方向二：逐出現點資料只對當頁問題取。
- 兩者是否都做、順序，由量測決定；快取的鍵與單飛一併處理。

### 驗收方向
- 同一份資料下，儀表板卡片數字、依問題視角筆數、報表排行、待派頁四個入口的數字一致（改前改後對帳）。
- 有墓碑與無墓碑兩組資料各一；可見範圍受限的使用者一組。
- 查詢回傳列數不隨主機數線性成長（以兩個小級距的結構性計數斷言，不寫毫秒門檻、不建 3000 台資料）。
- 驗收篩選涵蓋全部呼叫端的測試類。

## 批次 K：AI 待補的順序、放棄與失敗放大

### 現況與核對結果
- ［親核］`AiAnalysisHostedService.SelectNextBatch`（`:430`）：近日層（今天往前數天）優先、其餘為積壓塊；風險等級不參與排序，同日內由小主機編號先做。
- ［親核］`EfAnalysisRecordStore.PruneDetails`（`:1055-1064`）在詳情保留期到時把 `AiPending` 清為 false；程式註解的理由是詳情清掉後 AI 輸入無法重建。從未完成 AI 的主機日就此沒有白話摘要，畫面沒有提示。
- ［親核］一輪以 `batchSuccessCount == 0` 判定無進度（`:689`）；AI 逾時預設 1200 秒（`AppSettings.cs:52`、`SystemSettings.cs:101`）。
- ［回報］一批 50 筆逐筆做完，沒有「連續失敗就中止」；拒絕連線時每筆退避約 70 秒，不回應時每筆等滿逾時。
- ［回報］`CountPendingAi` 註解記實機 7～15 秒，跟隨取數期間每次輪詢都實查。
- ［回報］版本升級後存量回填未完成前 AI 不自動開跑。
- 容量算式：每日可做筆數＝窗口秒數 ÷ 單筆秒數 × 並行數。全天窗口、併發 1、單筆 20 秒約 4,320 筆；需求＝主機數 × 非低風險比例。比例未知。

### 定案（待量測與討論）
- 排序加入風險等級：同一層內高風險日先做。是否同時加主機輪替避免小編號永遠優先，待議。
- 積壓超過每日容量時的策略要使用者決定：全部排隊、只保證近 N 天、或低優先的主機日標「不產生白話」。
- 保留期清掉待補時要有可見的紀錄（數量進執行紀錄或健康頁），不再靜默。
- 一輪內連續失敗達門檻就中止該輪（門檻暫定，須寫明「什麼算一次失敗」：最終失敗，不含已重試成功）。

### 驗收方向
- 排序：同日高風險先於中風險（邊界：同風險時維持既有順序）；近日層優先於積壓不變。
- 連續失敗：門檻兩側各一例；中間夾一筆成功時計數歸零。
- 保留期清除：被清掉待補的筆數有紀錄；0 筆時不出聲。
- `AiRequestGateTests` 與 AI 待補順序單一判定的守門測試維持綠。

## 批次 L：通知流程

### 現況與核對結果
- ［親核］`MailNotificationService.NotifyAfterRunAsync` 每次分頁讀回望期內所有主機日（每頁 500）、再載入達門檻的整份紀錄；`:252-262` 對每個主機日以 `Any(RecordKey == key)` 比對兩份清單，是主機日數 × 紀錄數的迴圈，每次比對都組字串。
- ［回報］每個主機日一次 `CaptureDeliveryVersion`（blob 讀）。
- ［回報］第二個觸發點：每 60 秒的摘要檢查會先呼叫即時通知重試，outbox 有非終態時整套重跑，發生在白天。
- BACKLOG 已知：夜間掛接逐主機日寫入（另一件事）。

### 定案（待量測）
- 兩份清單改成以主機日為鍵的集合查找。
- 回望期內已結案（郵件計畫已關閉）的主機日不再重掃：只處理本趟寫過的與仍未結案的。
- 重入：outbox 重試只重送待送項目，不重跑整套規劃。

### 驗收方向
- 同一份資料下規劃結果（哪些主機日、哪些通道）與改動前相同。
- 已結案的主機日不被重讀（查詢計數斷言）。
- outbox 有一筆失敗待重試時，重試只觸及那一筆。
- 「沒留下紀錄就離開」的出口逐一列出：SMTP 失敗、設定停用、收件人為空、版本不符，各自的主機日之後是否還會被處理。

## 批次 M：NetIQ 取數在窗口放不下時

### 現況與核對結果
- ［親核］常數：每批 50 台（`NetiqPipelineService.cs:32`）、單 job 上限 10 萬筆（`NetiqOptions.cs:28`）、續跑回看 7 天（`AnalysisOrchestrator.cs:929`）。
- ［回報］計畫順序是日期由舊到新、同日依主機編號；窗口到點後下一窗口續做，最新一天排最後；超過 7 天未補的不再掃描。
- ［回報］截斷時把批次切半重查，遞迴到單台；單台仍截斷時對整份主機清單讀改寫一次。
- ［回報］Sentinel job 輪詢逾時固定 120 秒，逾時整批失敗且不切批，下次同樣組成。
- ［回報］計畫階段逐主機讀取並反序列化；既有實測 3000 台回望 14 天約 3 分鐘（`EmptyRecheckPlanBenchmarks`）。
- ［回報］回報時間只在每台 Sentinel 跑完才寫回，異常中斷時整台的回報時間遺失。
- 既有實測：穩態 3000 主機日／小時（SQLite）。六小時窗口約 18,000 主機日，單日 3000 台餘裕約 6 倍；停擺 7 天後的補洗超過一個窗口。

### 定案（待討論）
- 做不完時的優先序：最新一天先做或維持由舊到新，要使用者決定（影響「今天看不看得到昨天」）。
- 超過續跑回看天數的缺口要可見。
- 逾時與截斷一致處理（逾時也切批）：以注入時鐘與假的 Sentinel 回應（T8）驗證最壞等待與重查次數後定；Sentinel 的實際延遲留給環境探測輪。

### 驗收方向
- 「沒留下紀錄就離開」的出口逐條列出並各有回執。
- 讀與寫的範圍一致（寫幾天就讀幾天）。
- 批次組成改變後失敗主機日的重查計數仍正確。

## 批次 N：PRTG 背景吞吐與估算

### 現況與核對結果

### 定案（待量測）
- 估算公式與完整回填預覽共用同一個配額下界（這一項不需量測，可先做）。
- 近期狀態補抓：是否需要每日重置全部、切片預算是否隨範圍大小調整。

### 驗收方向

- 取數範圍必填的守門維持（新查詢路徑不得退回全站）。

## 批次 P：平行度、鎖、連線池與 SQL Server

### 現況與核對結果
- ［回報］全域鎖：夜間派工 Gate、`WorkOrderCoordinator` 的 static 鎖（與 Web 的回覆、取消共用）、NetIQ 帳本 static 寫入鎖加 Serializable 交易、執行紀錄每行一把鎖、64 條主機日條帶鎖。

### 定案
- 本批以序列化點盤點（T9）確認「哪一段在持鎖中做資料庫或外部呼叫」，據此決定要不要縮小鎖的範圍；鎖與連線池在正式規模下的實際爭用留給環境探測輪，本輪不調整平行度的預設值。SQL Server 若是正式環境的資料庫，需要一個能實連的測試環境；沒有的話本批只做 SQLite 部分並明寫「SQL Server 未驗證」。
- 不變式（鎖、狀態機）的驗收不用壓力測試，改用在被保護對象上斷言前置條件的替身。
