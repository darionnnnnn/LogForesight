# 環境探測輪規劃（草案）

> 狀態：草案——只列出要回答的問題、現有可用的量測管道與待決事項；**定案、批次與驗收都還沒寫**，開輪時與使用者討論後補。
> 目的：在**正式站台**（或資料量接近正式的站台）取得開發機給不出來的數字——實際耗時、吞吐、記憶體走勢、外部系統的真實行為——用來決定第 78 輪哪些項目真的要做、上限與預算要設多少。
> 基準：dev（1.0.77.3）。目前無法在正式站台執行，開輪時間未定；第 78 輪（`docs/FEEDBACK-78-PLAN.md`）的「順延」一節列出各項目在等本輪的哪個數字。
> 與第 78 輪的關係：互不相依。第 78 輪以與機器快慢無關的方法（指令計數、查詢計畫、留存量）確認瓶頸；本輪提供正式站台的實際數字。本輪的數字用來決定第 78 輪順延的項目哪些要做、哪些不必做。
> 開輪時先做：與使用者確認「待決事項」→ 逐項讀碼核對「現有管道」是否真的給得出該數字 → 把本檔搬到 `docs/` 並依專案慣例命名，再補定案與驗收。

## 設計約束（沿用使用者已定的原則）

- **不在開發機模擬 3000 台，開發機的耗時不當成正式主機的結果。** 本輪的數字只來自正式站台或使用者指定的站台。
- **能放進探測或診斷匯出的就放進去**：唯讀、可在啟用功能前執行、輸出可整段複製或下載；不要靠翻夜間執行紀錄或等隔天看結果。
- 探測不得改資料、不得對外部系統造成額外負擔（沿用 PRTG 請求預算與逾時、可停止）。
- 輸出可能含主機名與 IP：沿用診斷匯出既有的去識別做法，分享前可遮蔽。
- 不新增沒有消費端的設定與欄位；新增的量測欄位要有畫面或匯出讀它。
- 每條驗收都要是主代理在開發機可確認的（探測或匯出的**輸出格式、欄位、邊界**以測試驗；數字本身由使用者在正式站台跑出來後回填）。

## 要回答的問題

來源：第 77 輪規劃「留給環境探測輪」與「非本輪驗收」、BACKLOG 各條的觸發時機。「現有管道」一欄**尚未逐項讀碼核對**，開輪時要先確認。

### A. 查詢與頁面

| 要知道的事 | 為什麼需要 | 現有管道（待核對） |
|---|---|---|
| 各頁主要查詢在實際資料量下的耗時與讀回列數（儀表板、問題查詢三個視角、報表三支、交辦總覽、待派頁、執行總表展開某日、問題查詢展開） | 第 78 輪批次 I、J 是否要做、先做哪個 | 健康頁慢查詢清單與診斷匯出（`SqlPerformanceMonitor` 保留最慢前十支）；沒有「讀回列數」 |
| 每主機日的問題數分布、未派出的出現點數 | 待派 20,000 與統一標記 5000 兩個上限是否日常就會碰到 | 無現成管道；可由唯讀聚合查詢算出 |
| 全站型問題（例如 DCOM 10016）在 90 天內的主機日數 | 問題查詢展開每次換頁重讀是否需要快取 | 無現成管道 |
| 六個跨請求快取的條目數、命中率、逐出數、「單筆過大被拒」次數 | 快取上限與 TTL 是否合適；結果進不了快取時是否常發生 | 健康頁記憶體詳情（`ICacheStatistics`） |

### C. 記憶體

| 要知道的事 | 為什麼需要 | 現有管道（待核對） |
|---|---|---|
| 連續多日每趟開始與結束時的工作集、.NET 堆，是否逐日上升 | 有沒有慢速洩漏；硬上限（目前 60%）是否合適 | 健康頁記憶體卡、診斷匯出 `runMemory` |

### F. 第 77 輪上線後的確認項

第 77 輪改動中只有正式站台能確認的事，做進探測或診斷匯出比事後翻紀錄可靠：

| 確認項 | 預期 | 不符時 |
|---|---|---|
| 升級後執行總表過去日期「PRTG 待補」的主機日數 | 新跑的日子不再出現；升級前已卡住的過去主機日不會自動回復 | 數量大時做一次性對帳（BACKLOG「已卡在 PRTG 待補的過去主機日」） |
| 低風險日的工作流在 AI 排程與復原服務讀過之後是否穩定（版本不再推進） | 升級前以完整內容算指紋的低風險列重設一次後收斂；中風險以上不重設 | 持續推進代表還有紀錄內容在寫入後變形，回頭查父指紋 |
| 低風險日詳情頁的「已抑制的告警」 | 升級後新寫入的低風險日有內容；升級前寫入的沒有（無法回補） | — |
| PRTG 監看範圍在主機數超過 3,000 時的頁面與儲存 | 上限 10,000，可正常選取與儲存 | 查 `ScaleLimits` 的引用點 |
| 探測／回填／結構同步輸出超過 2,000 行時 | 中間標「已略過」，頭 1,500 與尾 500 行都在 | — |
| 使用者升級後沒有重新整理的舊分頁 | 重新整理即恢復（多個端點回應改為分頁物件、`hosts/all` 已移除） | — |

## 做法方向（未定案）

- **擴充既有管道，不另建一套**：站台層的數字優先加進診斷匯出與健康頁；PRTG 相關的加進既有環境探測；需要主動執行的唯讀量測（各頁查詢的耗時與讀回列數、問題數分布）做成一個可停止的「站台探測」，輸出可複製。是否真的需要新的站台探測，取決於開輪時核對現有管道後還缺什麼。
- **連續多日的觀察**靠每趟自動記錄（記憶體標記、階段耗時），不是靠人每天去按；探測只負責把它們整理成一份可讀的摘要。
- 探測的查詢本身不得成為負擔：有逾時、有列數上限、可取消；在取數執行中是否允許執行要定案。

## 待決事項（開輪時問使用者）

1. 正式環境的資料庫類型；是否有可實連的 SQL Server 測試環境。
2. 探測在哪個站台跑、由誰跑、多久回報一次；數字要回填到哪裡（規劃文件的量測紀錄、或另存）。
3. 本輪與第 78 輪的先後。
4. 記憶體連續觀察要幾天才算足夠（目前想法：至少涵蓋一個完整的週檢週期）。
5. 輸出去識別的程度：是否需要連主機數量級都遮蔽。
6. BACKLOG「下一輪預定」既有群組是否與本輪合併。

## 明確不做（草案）

- 在開發機模擬正式規模、以開發機耗時下結論。
- 依探測結果直接調整上限、GC 參數、平行度或硬上限——那是拿到數字之後另一輪的定案。
- 會寫入資料或對 PRTG／Sentinel／AI 伺服器造成額外負擔的量測。
- 第 78 輪的範圍（聚合改寫、背景吞吐）。
