## E3 串接情境

### 預期行為（執行前先提交；依據為 WEB-SPEC §9.4b 與「使用者第二天打開系統時該知道什麼」）
判斷原則：（1）每個狀態變化，受影響的人都要在某個地方知道（通知、徽章或清單篩選至少一種）；（2）系統動作不得在使用者不知情下永久改變後續行為；（3）規格刻意的取捨照規格判定，不算差異。

| # | 情境 | 預期 |
|---|---|---|
| S1 | 夜間派工 → 處理人回覆已處理 | 自動派工建單給派工池內看得到主機的處理人，處理人有建立通知；回覆後成員結案、單推導為已結案；稽核有回覆紀錄；管理者總覽看得到結案 |
| S2 | 處理人回「無法處理」→ 管理者退回／改派／代為結案 | 回「無法處理」必填原因、單為上報中、管理者收到上報信；退回：成員回處理中、處理人收到退回通知；改派：新處理人收到建立、原處理人收到轉出；代為結案：處理人收到結案通知 |
| S3 | 「無法處理」後管理者 7 天未處理 | 上報中的單可在總覽篩出；超過數天（暫定 3 天）仍未處理時管理者收到提醒（摘要信或徽章） |
| S4 | 處理人被停用 | 停用當下提醒管理者此人有 N 張進行中單；既有單可由「只看處理人已停用」找到；之後的夜間派工不再把新主機續掛到該人的單，新問題改派給其他候選人 |
| S5 | 處理人暫停接單 | 不再收到新派工，也不被續掛新主機；既有單照常可回覆 |
| S6 | 處理人的主機授權被移除 | 處理人仍看得到被交辦的問題（案件授與）；之後不再續掛他看不到的主機；管理者在單上看得到「處理人看不到 N 台」 |
| S7 | 主機停用、改群組、換主機負責人 | 停用主機上的進行中成員不再算處理人的待辦，管理者看得到原因；改群組後可見範圍隨之更新；換負責人後新問題走新負責人 |
| S8 | 問題結案後再出現（已處理／不處理／誤報／已知雜訊） | 已處理後再出現：重新派工、標「復發」、優先派給上次處理的人；其餘三種：依規格不再派工，但管理者在待派或問題頁看得到「因先前結案為 X 而不派工」並可恢復 |
| S9 | 靜音（暫停）→ 解除 | 靜音期間單推導為暫停、處理人清單預設排除；暫停與恢復時處理人都知道；解除後「只看自靜音恢復」找得到 |
| S10 | 靜音（代為結案）→ 解除 → 問題再出現 | 解除後問題再出現時照常派工（靜音造成的結案不等同處理人判定的「不處理」） |
| S11 | 夜間派工找不到人（無派工池、全部暫停、都看不到主機） | 待派頁籤列出並帶原因；管理者被主動告知（徽章或信件）；隔天問題仍在時再試一次 |
| S12 | 兩位管理者幾乎同時改同一張單 | 後到者得到明確的衝突或「已結案」訊息（4xx），不是一般錯誤（5xx） |
| S13 | 觀察中到期 | 到期後列入逾期篩選，處理人與管理者看得到 |
| S14 | 處理人沒有 email、管理者都沒有 email | 站內徽章照常提示；交辦時提示對方收不到信；上報時有地方記錄「沒有人收到」並讓管理者在站內看得到 |
| S15 | 同一問題多台、部分處理 | 有任一成員未結案時單為進行中；看板、清單、處理人頁的台數一致 |
| S16 | 問題負責人與自動派工同時適用 | 問題負責人優先（規格 ④⑤⑥ 順序） |
| S17 | Manager／Dev 打開「我的交辦」 | 沒有處理能力的角色不顯示該導覽，或頁面明說「你的角色沒有處理能力」 |
| S18 | 改派時目標已有同問題的單 | 併入目標單、原單標轉出並唯讀可開；雙方都收到通知 |

S3、S13 依真實時間（建單、期限、到期由正式碼的 `DateTime.Now` 決定），驅動器的逐日推進無法讓真實時間前進；能以 API 把期限設在過去就照做，做不到時記為「無法以情境模擬」並改以程式碼核對判定。

## E5 PRTG 取數

### 整條鏈程序內驗證（`PrtgEndToEndChainTests`，13 個案例）
假 PRTG 以真實 HTTP（`TestDoubles/FakePrtgServer.cs`）回應官方格式（含 `*_raw` 欄位、historicdata 實機列形狀）。3 台主機、PRTG 5 台裝置（3 台對得上）。逐層斷言皆通過：
1. 結構同步：裝置 5、範圍內感測器 10、狀態變更 5 筆逐筆一致；devices 單發、sensors／messages 逐台查且 messages 帶 `filter_drel`。
2. 主機對應：3 ok、2 unmatched，經 `GetHostMapForDay` 讀回一致。
3. 取數範圍：只含 3 台；全程沒有任何對整台 PRTG 或範圍外的請求。
4. 快照：10 顆數值等於 `lastvalue_raw`；網卡流量依 `×3600÷interval` 換算。
5. 每日管線：只產生 Ping Down 與磁碟 Warning 兩個發現；PRTG 獨立主機日風險為高、判定依據含 `prtg:down`；觸發式取數只查該主機。
6. 主機詳情服務讀回的感測器與數值評估與前兩層一致；別台主機看不到。
邊界：截斷不清除、逾時約 1 秒結束、空回應不清除、權限縮小一半以上不清除、跨日歸本地日、同 sensor 同日 6 筆全留、5003 台分頁與剛好 5000 台的末頁夾回皆正確。
主代理突變：拿掉「讀到筆數少於 treesize 就出聲」→ 截斷案例轉紅；messages 列鍵改成只用 objid → 4 案例轉紅；皆以備份還原並 `cmp` 確認。
未涵蓋：範圍外數值與狀態變更清除（需成功同步的父作業識別，測試組裝限制）、每日管線的逾時重試（會真等 15＋60 秒，由既有 pager 測試負責）、探測路徑。

**結論：在程序內替身與官方格式下，PRTG 取數從回應到畫面每一層數字一致，範圍與保護規則照規格運作。** 未涵蓋真實 PRTG 的語系、版本差異與網路行為；使用者開發站台的快照恢復仍待確認（見交接確認事項）。
