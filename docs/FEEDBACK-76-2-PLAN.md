## 批次 A：1102 規則來源名

### 現況與核對結果
- 種子規則 `builtin-security-audit-log-cleared-1102` 的來源樣式是 `Security-Auditing`（`KnownIssueSeed.cs:306-307`）。
- 規則比對是「事件來源包含規則樣式」、不分大小寫（`KnownIssueCatalog.cs:389`），一條規則只有一個樣式。
- Windows 的 1102 由 `Microsoft-Windows-Eventlog` 發出。實測環境：103 的 Windows 11 26300（ARM64）VM；實測資料性質：提供者中繼資料（不是真的清除記錄產生的事件）。
- **未實測**：NetIQ 回傳的來源欄是否保留原始提供者名稱。
- 滅跡關聯的錨點是 1102／4719（`CorrelationAnalyzer.cs:51-52`）；規則沒命中時錨點跟著失效。
- 種子版本目前是 11；既有站台靠「規則維護」頁的升級橫幅由管理者手動套用（`RuleBootstrapper.cs:97`）。

### 根因
規則的來源樣式照「同類稽核事件」的來源寫，沒有對照 1102 真實的發出者。

### 定案
- 真實來源（`Microsoft-Windows-Eventlog`）與現行樣式（`Security-Auditing`）**兩種都要命中**：NetIQ 的行為未實測，不能把現行樣式直接換掉。做法暫定為保留現有規則、另加一條同內容的規則比對 `Eventlog`；兩條的分類、嚴重度、重大旗標與說明一致。
- 種子版本加 1。既有站台要到「規則維護」頁套用升級橫幅才生效——列入交接確認事項與說明書。
- 不選「把樣式改成更短的共同子字串」：兩個來源名沒有可用的共同子字串。

### 改動
1. 種子規則與版本。
2. `SeverityScenarioTests` 的 I5 情境從已知差異清單移除。
3. `docs/DETECTION-SPEC.md`、`docs/RULES-SPEC.md` 的對應清單同步。

### 驗收
- I5（真實格式的 1102）判定日為高、命中規則為重大、滅跡關聯成立。
- 邊界兩側：來源 `Microsoft-Windows-Eventlog` 的 1102 命中；來源 `Microsoft-Windows-Security-Auditing` 的 1102 也命中；來源 `Microsoft-Windows-Eventlog` 的 104 不被新規則吃掉（仍由 104 規則命中）；同一筆事件不會被兩條規則重複計數。
- 主代理突變：新規則的事件編號改掉 → I5 轉紅。
- `dotnet test --filter "FullyQualifiedName~SeverityScenarioTests|FullyQualifiedName~KnownIssue|FullyQualifiedName~Correlation|FullyQualifiedName~RuleBootstrap|FullyQualifiedName~RuleImport"`

## 批次 T：可替換時鐘

### 現況與核對結果
- Core 與 Web 共 476 處直接讀真實時鐘（150 個檔）。交辦、靜音、觀察中相關的約 90 處，分布在 `EfWorkOrderStore`、`EfIssueCaseStore`、`WorkOrder*Service`、`IssueOwnerAdminService`、`IssueHandlingCommandService`、`DayHandlingCommandService`、`HandlingHistoryQueryService`、`DispatchContext`、`MailNotificationService`、`WorkOrderOutboxStore` 等（清單暫定，實作時以 grep 為準）。
- 專案已有 `TimeProvider` 的用法（`PrtgClient`、`PrtgAddressResolver`）。
- 第一階段有三個情境因此無法模擬：S3（上報後沒人管）、S9（靜音恢復紀錄）、S13（觀察中到期）。

### 根因
到期、逾期、起算日都由正式碼自己讀真實時鐘，測試沒有介入點。

### 定案
- 交辦、靜音、觀察中三條路徑的「現在」與「今天」一律取自注入的 `TimeProvider`；正式站台註冊系統時鐘，行為不變。
- 範圍只到這三條路徑會經過的類別。其餘約 380 處不動（列入明確不做）。
- 情境驅動器把假時鐘接到「第 N 天」：逐日推進時假時鐘跟著前進。

### 改動
1. 上述類別改由建構式取得時鐘（沿用既有 DI 註冊方式）。
2. 情境驅動器接上假時鐘；S3、S9、S13 拿掉略過，改成真的執行。
3. 守門測試：列入範圍的檔案不得再出現直接讀真實時鐘的寫法。

### 驗收
- S3、S9、S13 三個情境實際執行（S3、S13 的預期差異若仍存在，留在已知差異清單給 C 批清）。
- 守門測試先拿一個「該命中」的反例確認判準比得到，再套用到範圍檔案。
- 邊界兩側：觀察中期限「今天」不算到期、「昨天」算到期；靜音迄日當天仍算靜音、隔天解除。
- 主代理突變：其中一個服務改回讀真實時鐘 → 守門轉紅。

## 批次 B：「不再打擾」

### 現況與核對結果
- 判定只有一份：`DispatchContext.DismissedKeys`（`:236`）——每台主機每個問題取建立最晚的案件，狀態是不處理、誤報或已知雜訊就擋。沒有過期，也沒有解除。
- 消費端兩處：夜間派工的閘門 4（`WorkOrderDispatcher.cs:77`，續掛、問題負責人、自動派工都擋）與日層級處理（`DayHandlingCommandService.cs:365`）。
- 會寫入不處理類狀態的系統動作兩條：靜音代為結案固定寫「不處理」（`IssueOwnerAdminService.cs:306`）；管理者代為結案可選四種結案狀態（`WorkOrderCommandService.cs:393`）。兩條都經 `WorkOrderCoordinator.AdminClose`。
- `IssueCase` 沒有欄位記錄「誰決定結案」；只有 `Cancelled` 標記取消。
- 待派頁對這個閘門只顯示排除台數（E3-08）。
- 代為結案對話框沒有後果說明、預設「已處理」（E2-03、E1-41）。
- 案件授與只看「是否曾是處理人」，不看狀態（`EfIssueCaseStore.HasCaseOnHost`，消費端 `VisibilityService.cs:300`）；取消的案件仍讓原處理人看得到主機（E6-11）。

### 根因
系統動作與處理人判定寫進同一個狀態欄，閘門分不出來；閘門是單向的，沒有繞過路徑，也沒有畫面說明它存在。

### 定案
1. **案件記錄結案來源**（暫定三種：處理人回覆、管理者代為結案、靜音代為結案）。升級前的既有結案案件沒有來源，視為「處理人回覆」——閘門對舊資料的行為不變，靠恢復入口處理。不依說明文字回推來源：有合法說明長得像系統產生的文字，回推錯了會讓已決定不處理的問題重新派工。
2. **閘門規則**（仍只有 `DismissedKeys` 一份）：最近一件案件以不處理類結案，**而且**（來源是處理人回覆，或管理者結案時明確勾選了「之後不再自動派工」），**而且**結案之後沒有被恢復，才擋。
3. **靜音代為結案一律不觸發**：靜音自己有期間，到期後恢復正常派工。
4. **管理者代為結案改成明確選擇**：選不處理類時出現「這台主機的這個問題之後不再自動派工」勾選框，預設不勾。不勾就不觸發閘門，問題再出現會照常派工；對話框寫明這一點，並提示不想再收到可改用靜音。
5. **恢復入口**：待派頁列出被閘門擋住的（主機、問題、先前結案狀態、誰結的、哪一天），可單筆或多選恢復；恢復寫稽核。恢復後下一趟夜間派工照常判斷。
6. **代為結案對話框**：加後果說明（處理人會收到通知、可否復原）；不預設結案狀態；確認鈕文字寫出動作（不用「確定」）。通知本身在 C 批做，文字先寫好、C 批完成前不合併到 dev。
7. **取消收回授與**：`Cancelled` 的案件不算案件授與；結案的案件照舊保留。改派出去的案件處理人已換人，核對確認原處理人不再有授與（若不是，一併修正）。

### 單向閘門的繞過路徑（規劃時逐條列）
- 處理人誤判為不處理 → 管理者在待派頁恢復。
- 管理者勾了不再派工後反悔 → 同一個恢復入口。
- 升級前被靜音代為結案卡住的舊資料 → 恢復入口看得到（來源顯示為處理人回覆，狀態與日期照實）。
- 恢復之後處理人又回不處理 → 新案件、新判定，閘門重新生效（恢復只對那一件案件有效）。

### 改動
1. 案件模型、兩個後端的資料表與升級（`docs/DB-SPEC.md` §A 同步）。
2. `WorkOrderCoordinator.AdminClose` 帶入結案來源與是否不再派工；靜音與管理者兩個呼叫端各自傳值。
3. `DismissedKeys` 規則；兩個消費端不必改呼叫方式。
4. 待派頁的清單與恢復動作（新端點要有授權屬性，`ControllerRouteSnapshotTests` 基準重產並逐列檢查）。
5. 代為結案對話框。
6. 案件授與查詢排除取消的案件（`HasCaseOnHost` 與同檔的 `IssueKeysOnHost`）。
7. `docs/WEB-SPEC.md` §9.4b 的閘門段落、授權段落同步。

### 驗收
- S10（靜音代為結案 → 解除 → 再出現）會派工；S8 的待派頁列得出主機與先前狀態並可恢復。對應已知差異鍵 `E3-01`、`E3-S10-*`、`E3-S8-*` 移除。
- 邊界兩側：處理人回不處理 → 擋；管理者代為結案選不處理且不勾 → 不擋；勾 → 擋；勾了之後恢復 → 不擋；恢復後處理人再回不處理 → 擋。
- 四種結案狀態各一例：已處理從不觸發閘門（與來源無關）。
- 舊資料：沒有結案來源的不處理類案件 → 擋（行為不變）且恢復入口列得出。
- 日層級處理路徑與夜間派工對同一筆資料的判定相同（同一份規則的兩個消費端各一條斷言）。
- 取消的案件：原處理人看不到該主機；結案的案件：仍看得到自己的處理紀錄。
- 畫面：待派頁與代為結案對話框在五個寬度六項量測為 0；恢復入口 0 筆時顯示說明文字；先 grep 測試專案與前端 `querySelector`／`closest` 用到的舊類別名。
- 主代理突變：閘門拿掉「未被恢復」條件、拿掉來源條件，各自轉紅。
- `dotnet test --filter "FullyQualifiedName~HandoffScenarioTests|FullyQualifiedName~WorkOrder|FullyQualifiedName~Dispatch|FullyQualifiedName~IssueMute|FullyQualifiedName~Visibility|FullyQualifiedName~DayHandling|FullyQualifiedName~ControllerRouteSnapshot|FullyQualifiedName~UiTests|FullyQualifiedName~JsModuleImport|FullyQualifiedName~BehaviorTests|FullyQualifiedName~ApiTimeout"`

## 批次 D：派工資格

### 現況與核對結果
- 候選人池只收「啟用中且具處理能力」的使用者；可見主機只替「在派工池且未暫停」的人計算（`DispatchCandidate.cs`）。
- 三條路徑各自判斷（`WorkOrderDispatcher.cs`）：
  - 續掛：只看單可續掛、範圍涵蓋，**完全不看處理人**。
  - 問題負責人：要在池內快照、未暫停；刻意不要求在派工池、不檢查可見主機。
  - 自動派工：在派工池、未暫停、看得到這台主機。
- 自動派工的「看得到」包含案件授與，原處理人因此成為該主機新問題的候選人（E3-15，評估時標「待確認」）。
- 主機停用後，進行中成員仍算進徽章與負載看板（E3-07）。
- 停用處理人時沒有進行中單的提醒（E3-05）；處理人授權被移除後單上沒有標示（E3-06）。

### 根因
「這個人現在能不能接這台主機的這個問題」沒有單一判定，三條路徑各寫一份；案件授與是為了讓人打開自己的處理紀錄，卻被當成一般的主機可見。

### 定案
1. **單一資格判定**放在 Core 的派工決策內，三條路徑都呼叫它：
   - 續掛：處理人要啟用中、具處理能力、未暫停、看得到這台主機。不符合就不續掛，往下走問題負責人與自動派工。
   - 問題負責人：啟用中、具處理能力、未暫停；不檢查可見主機維持現狀（負責人靠案件授與取得存取，是刻意設計，寫進規格的資格對照表）。
   - 自動派工：照現況。
2. **派工用的可見主機不含案件授與**：只算群組授權與主機負責人。可見範圍規則仍只在 Web（由 `IDispatchCandidateSource` 算好交給 Core），不在 Core 複製。
3. 候選人快照要替「有可續掛單的處理人」也算可見主機，不只派工池成員。
4. **續掛被擋要看得到**：交辦單詳情與交辦總覽標示「續掛已停止」與原因（處理人已停用／暫停接單／看不到新主機）。
5. **停用主機**：其進行中成員不算進處理人徽章、負載看板與 KPI 的台數，成員列標「主機已停用」。先普查報表與儀表板是否同樣計入，同型一起改。
6. **停用或暫停處理人時**：回應帶進行中單數，畫面提示並連到已篩選的交辦總覽。
7. **交辦單詳情**顯示「處理人目前看不到 N 台」（每次讀取時計算）。

### 改動
1. 資格判定與三條路徑。
2. Web 的候選人快照。
3. 徽章、看板、KPI 的計數與成員標記。
4. 使用者停用與暫停接單的回應與畫面提示。
5. `docs/WEB-SPEC.md` §9.4b 加三條路徑的資格對照表。

### 驗收

## 批次 C：通知與出聲
