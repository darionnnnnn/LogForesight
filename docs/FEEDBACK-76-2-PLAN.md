## 原則

- **修根因**：每批先寫根因，主修法對到根因。
- **擴充既有機制，不另立平行機制**：
  - 通知沿用既有通知佇列與「每位收件人一封摘要」的寄送方式。
  - 管理者提醒沿用同一套摘要，不新增排程。
  - 系統層警示沿用導覽既有的健康告示（`layout.js` 的 `loadHealthBanner`）。
  - 時鐘沿用專案已在用的 `TimeProvider`。
  - 錯誤訊息沿用 `ApiExceptionFilter`。
- **一個判定只有一份**：不再打擾（`DismissedKeys`）、派工資格、健康整體狀態、信件連結、PRTG 失敗說明各只有一個出口。
- **不加用不到的彈性**：不建例外階層、不建通知偏好系統、不建通用的閘門框架。
- **驗收只寫主代理做得到的**：全部以程序內測試、情境驅動器、量測工具或 grep 判定；需要正式環境才能確認的事列在「交接確認事項」，不算驗收。
- **已知差異清單是驗收的一部分**：`HandoffScenarioTests`、`SeverityScenarioTests` 的已知差異鍵在對應批次修好時移除（清單內的項目若已一致會轉紅）。
- 契約裡標「暫定」的數值與名稱，執行端可依實作事實調整，但要在執行紀錄寫理由。

## 批次 A：1102 規則來源名

### 現況與核對結果
- 種子規則 `builtin-security-audit-log-cleared-1102` 的來源樣式是 `Security-Auditing`（`KnownIssueSeed.cs:306-307`）。
- 規則比對是「事件來源包含規則樣式」、不分大小寫（`KnownIssueCatalog.cs:389`）；一條規則只有一個樣式，沒有頻道欄位。
- Windows 的 1102 由 `Microsoft-Windows-Eventlog` 發出。實測環境：103 的 Windows 11 26300（ARM64）VM；實測資料性質：提供者中繼資料，不是真的清除記錄產生的事件。
- NetIQ 的來源欄 `obssvcname` 存的是提供者名稱（`docs/NETIQ-API-REFERENCE.md` 第 212 列，值例 `Microsoft-Windows-Security-Auditing`）。依此推論 NetIQ 回傳的 1102 來源是 `Microsoft-Windows-Eventlog`。**未實測**：沒有正式環境的 1102 樣本。
- 滅跡關聯的錨點是 1102／4719（`CorrelationAnalyzer.cs:51-52`）。
- 種子版本目前是 11；既有站台靠「規則維護」頁的升級橫幅由管理者手動套用（`RuleBootstrapper.cs:97`）。

### 根因
規則的來源樣式照同類稽核事件的來源寫，沒有對照 1102 真實的發出者。

### 定案
1. 真實來源與現行樣式**兩種都要命中**。做法：保留現有規則，另加一條內容相同、樣式為 `Eventlog` 的規則。
   - 不選「直接改現有規則的樣式」：若有站台的收集器把來源標成現行樣式，改掉就是讓原本抓得到的入侵跡象變成抓不到。兩條規則的代價是規則維護頁多一列。
   - 不選「共同子字串」：兩個來源只共有 `Microsoft-Windows-`，會把別的提供者的 1102 判成重大。
   - 拿到正式環境的 1102 樣本後刪掉用不到的那一條（交接確認事項）。
2. 種子版本加 1。
3. `docs/DETECTION-SPEC.md`、`docs/RULES-SPEC.md` 的對應清單同步。

## 批次 T：可替換時鐘

### 現況與核對結果
- Core 與 Web 共 476 處直接讀真實時鐘（150 個檔）。交辦、靜音、觀察中相關約 90 處，分布在 `EfWorkOrderStore`、`EfIssueCaseStore`、`WorkOrder*Service`、`IssueOwnerAdminService`、`IssueHandlingCommandService`、`DayHandlingCommandService`、`HandlingHistoryQueryService`、`DispatchContext`、`MailNotificationService`、`WorkOrderOutboxStore` 等（清單暫定，以 grep 為準）。
- 專案已有 `TimeProvider` 的用法（`PrtgClient`、`PrtgAddressResolver`）。
- 這些類別在正式碼都由 DI 建立；測試專案直接 `new` 的約 100 處。
- 第一階段有三個情境因此無法模擬：S3、S9、S13。

### 根因
到期、逾期、起算日都由正式碼自己讀真實時鐘，測試沒有介入點。

### 定案
1. 交辦、靜音、觀察中三條路徑的「現在」與「今天」一律取自 `TimeProvider`。正式站台註冊系統時鐘，行為不變。
2. 建構式的時鐘參數放最後、可省略（省略＝系統時鐘）。理由：測試專案約 100 個建構點不必跟著改；正式碼漏接由第 4 項的守門擋下。
3. 「本地現在」「本地今天」的取法只寫一份共用的小函式，各類別不各自換算。
4. 守門測試：列入範圍的檔案不得出現直接讀真實時鐘的寫法；範圍清單寫在測試裡。
5. 情境驅動器把假時鐘接到「第 N 天」；S3、S9、S13 拿掉略過。
6. 範圍外約 380 處不動（明確不做）。

## 批次 B：「不再打擾」

### 現況與核對結果
- 判定只有一份：`DispatchContext.DismissedKeys`（`:236`）——每台主機每個問題取建立最晚的案件，狀態是不處理、誤報或已知雜訊就擋。沒有過期，也沒有解除。
- 消費端兩處：夜間派工的閘門 4（`WorkOrderDispatcher.cs:77`）與日層級指派的預覽與落盤（`DayHandlingCommandService.cs:365`）。
- 會寫入不處理類狀態的系統動作兩條，都經 `WorkOrderCoordinator.AdminClose`：靜音代為結案固定寫「不處理」（`IssueOwnerAdminService.cs:306`）；管理者代為結案可選四種結案狀態（`WorkOrderCommandService.cs:393`）。
- `IssueCase` 沒有欄位能分辨這些情況；「誰在哪一天結的」已經在處理歷程（`RecordHandlingLog`）裡。
- 待派頁對這個閘門只顯示排除台數（E3-08）。
- 代為結案對話框沒有後果說明、預設「已處理」（E2-03、E1-41）。
- 處理人的回覆表單沒有說明「不處理、誤報、已知雜訊」會讓這台主機的這個問題不再派工（前端 grep 無相關文字）；只有說明書有寫。
- 案件授與只看「是否曾是處理人」（`EfIssueCaseStore.HasCaseOnHost`、`IssueKeysOnHost`），不看取消（E6-11）；消費端是 `VisibilityService`，再由約 20 個查詢點使用。

### 根因
系統動作與處理人判定寫進同一個狀態欄，閘門分不出來；閘門是單向的，沒有繞過路徑，畫面上也沒有任何地方說它存在。

### 定案
1. **案件加一個欄位：這次結案是否擋住之後的派工**（可空的是非值；名稱暫定）。只有三個地方會寫它：
   - 靜音代為結案 → 否。
   - 管理者代為結案 → 依對話框的勾選。
   - 恢復動作 → 否。
   - 其他情況（處理人回覆、升級前的舊資料）不寫，維持空值，空值視為「是」——現行行為不變。
   - 不另存「結案來源」：畫面要顯示的「誰結的、哪一天」從既有處理歷程讀，不重複存一份。
2. **閘門規則**（仍只有 `DismissedKeys` 一份）：最近一件案件以不處理類結案，而且該欄位不是「否」，才擋。
3. **管理者代為結案**：選不處理類時出現「這台主機的這個問題之後不再自動派工」勾選框，預設不勾。選「已處理」時不出現。
4. **恢復入口**：待派頁列出被閘門擋住的項目，依問題分組，每列有主機、先前結案狀態、結案的人與日期；可單筆恢復或整個問題一起恢復。需要指派權限，寫稽核。恢復後下一趟夜間派工照常判斷。
5. **後果說明寫在動作發生的地方**：
   - 代為結案對話框：說明處理人會收到通知、選不處理類且不勾時問題再出現會重新派工、不想再收到可勾選或改用靜音；不預設結案狀態；確認鈕文字寫出動作。
   - 處理人回覆表單：選不處理、誤報、已知雜訊時顯示一行「這台主機的這個問題之後不會再派給任何人；需要恢復請找管理者」。
6. **取消收回授與**：取消的案件不算案件授與（`HasCaseOnHost`、`IssueKeysOnHost` 兩個查詢一起改）；結案的照舊保留。

### 單向閘門的繞過路徑
- 處理人誤判為不處理 → 管理者在待派頁恢復。
- 管理者勾了不再派工後反悔 → 同一個入口。
- 升級前被靜音代為結案卡住的舊資料 → 入口列得出，由管理者決定。
- 恢復之後處理人又回不處理 → 那是新案件，欄位是空值，閘門重新生效。

### 改動
1. 案件模型、兩個後端的資料表與升級（`docs/DB-SPEC.md` §A 同步）。
2. `WorkOrderCoordinator.AdminClose` 多一個「是否擋住之後的派工」參數（必填，不給預設值）；兩個呼叫端各自傳值。
3. `DismissedKeys` 規則。
4. 待派頁的清單與恢復端點。
5. 代為結案對話框、處理人回覆表單。
6. 案件授與的兩個查詢。
7. `docs/WEB-SPEC.md` §9.4b 的閘門段落與授權段落。

## 批次 D：派工資格

### 現況與核對結果
- 候選人池只收「啟用中且具處理能力」的使用者；可見主機只替「在派工池且未暫停」的人計算（`DispatchCandidate.cs`）。
- 三條路徑各自判斷（`WorkOrderDispatcher.cs`）：
  - 續掛：只看單可續掛、範圍涵蓋，完全不看處理人。
  - 問題負責人：在池內快照、未暫停；刻意不檢查可見主機。
  - 自動派工：在派工池、未暫停、看得到這台主機。
- 自動派工的「看得到」包含案件授與（E3-15，評估時標「待確認」）。
- 主機停用後，進行中成員仍算進徽章與負載看板（E3-07）。
- 停用處理人時沒有進行中單的提醒（E3-05）；處理人授權被移除後單上沒有標示（E3-06）。
- 上報原因在詳情頁看不到（E2-12，可能只是 UI 資料集缺資料）。

### 根因
「這個人現在能不能接這台主機的這個問題」沒有單一判定；案件授與是為了讓人打開自己的處理紀錄，卻被當成一般的主機可見。

### 定案
1. **資格判定只寫一份**，放在派工決策內，分兩層：
   - 基本資格：啟用中、具處理能力、未暫停。三條路徑都要。
   - 看得到這台主機：續掛與自動派工要；問題負責人不要（維持現狀，是刻意設計）。
   - 自動派工另外要求在派工池（現狀）。
2. **派工用的可見主機不含案件授與**：只算群組授權與主機負責人（問題負責人的範圍是管理者明確指定，同樣計入；見執行紀錄 D-1）。規則仍只在 Web 計算後交給 Core。
3. 候選人快照替「有可續掛單的處理人」也算可見主機。
4. **續掛被擋就往下走**問題負責人與自動派工；原單標示「續掛已停止」與原因（處理人已停用／暫停接單／看不到新主機）。處理人恢復資格後，之後新出現的主機照常續掛；被擋期間已派給別人的不追回。
5. **管理者明確交辦不受影響**：建單時指定看不到的主機仍可建立（現狀是提示不擋）。自動續掛要求看得到，是因為不該由系統自動把授權給出去。
6. **停用主機**：其進行中成員不算進處理人徽章、負載看板與 KPI 的台數，成員列標「主機已停用」。先普查報表與儀表板是否同樣計入，同型一起改。
7. **停用或暫停處理人時**：回應帶進行中單數，畫面提示並連到已篩選的交辦總覽。
8. **交辦單詳情**顯示「處理人目前看不到 N 台」（讀取時計算）。
9. **E2-12**：以真實上報流程確認詳情頁看得到上報原因；看不到才修。

### 現況與核對結果

- 改派併入既有單時，目標處理人收到的是「建立」（E3-14）。
- 所有信件沒有網址，系統沒有站台網址設定（E1-02）；上報信寫的頁面名稱與導覽不同（E1-16）；新交辦信沒說要做什麼（E1-43）。
- 健康整體狀態（`HealthService.cs:442`）前端沒有消費端；多個畫面上有警示的條件沒有併入（E6-08）。
- 導覽已有一條健康告示：具維護或開發監看能力的人進頁時查一次、不輪詢（`layout.js` 的 `loadHealthBanner`），目前只講排程資料過期。
- 資料保留清除失敗不傳出，執行紀錄永遠寫成功（E6-05）。
- PRTG：已對應主機的裝置被清除、感測器全部回空，同步結果都是成功且沒有警示（E5-06、E5-07）。

### 根因
通知種類是逐次需求加上去的，沒有以「誰需要知道什麼」盤點過；系統層的失敗與保護生效只寫記錄檔，沒有匯到人會看的地方。

### 定案
**C1 處理人知會**（既有通知佇列加種類，沿用每人一封摘要）
1. 管理者代為結案：通知該單處理人，帶結案狀態、原因，以及問題再出現會不會重新派工。
2. 靜音造成的暫停：通知該單處理人，帶靜音迄日與「到期自動恢復」。靜音造成的代為結案只發結案那一則。
3. 管理者提前解除靜音：通知處理人已恢復。靜音自然到期不另發通知（暫停通知已寫明迄日）。
4. 改派併入既有單：目標處理人收到「追加」。

**C2 管理者提醒**（同一套摘要，收件人是管理者）
5. 夜間派工結束後彙整三類：上報超過 N 天未處理的成員、本趟派不出去的問題、上報時沒有任何收件人的單。任一類不是 0 就進管理者的摘要；交辦總覽顯示同一份數字（郵件關閉時這是唯一管道）。
6. N 是新設定（暫定預設 3 天，0＝不提醒）。同一個成員每 N 天至多提醒一次。
7. 上報信沒有收件人時當下寫一筆稽核。

**C3 信件連結與文字**
8. 新設定「站台網址」（含子應用程式路徑）。有填時每種信件附連結；沒填時信件與現行相同。連結只由一個共用函式組出。
9. 連結的目的地由信件種類決定：交辦類連到「我的交辦」或該交辦單；取消通知連到「我的交辦」，不連到已收回授與的主機；管理者類連到交辦總覽或待派頁。
10. 儲存時驗證是 http 或 https 的完整網址；網址只取自這個設定，不取自請求標頭。
11. 信件文字：頁面名稱與導覽一致；新交辦信寫明要做的事；高風險信指名頁面。
12. 診斷匯出把站台網址去識別化。

**C4 系統層出聲**
13. 健康整體狀態的判定只有一份，併入清單（暫定）：遷移卡死、PRTG 新鮮度可疑、主機日恢復需要注意、最近一趟失敗、郵件收件人被暫停、保留清除失敗、PRTG 感測器全部回空、已對應主機的裝置被清除。

## 批次 E：技術原文不外洩

### 現況與核對結果
- Web 的控制器與服務有 82 處 `ex.Message`；已確認外洩的有 PRTG 規模估算、立即派工失敗組、快照待寫檔檢查（E6-09）、AI 額外請求欄位的 JSON 錯誤（E1-39）。
- Core 的錯誤訊息有以類別名開頭的（「WorkOrderCoordinator：…」約 20 處，E3-13）。
- 訊息直接寫內部代碼：core／standard／test、conservative／aggressive、「目錄版本權杖」（E1-40）。
- PRTG 逾時的訊息是英文例外原文（`PrtgClient.cs:290`、`:509`，E5-04）；PRTG 回 400 與 XML 錯誤時原文沒有帶出（E5-02）。

### 根因
沒有「什麼訊息可以給使用者看」的單一規則：攔到例外就把原文往外傳。

### 定案
1. **規則**：只有領域例外（`DomainException` 與已登錄的專屬例外型別）的訊息可以給使用者；其他例外給寫好的中文說明，原文只進記錄檔。不新增例外型別階層。
2. 82 處逐一分類：攔的本來就是領域例外的保留；會攔到一般例外的改成上面的規則。分類表寫進執行紀錄。
3. Core 的訊息拿掉類別名前綴。
4. 內部代碼改成畫面上的顯示名稱。
5. PRTG 失敗依失敗種類給中文說明（逾時、連不上、認證失敗、伺服器放棄），說明文字只有一份對照；原文附在後面。400 時帶出 PRTG 的錯誤訊息（截斷到欄位上限）。
6. 守門測試兩條：把 `ex.Message` 放進回應的寫法只能出現在白名單；給使用者的訊息不得以英文識別字加冒號開頭。

|---|---|---|

## 批次 F：角色、導覽與說明章節權限

### 現況與核對結果
- 導覽的「我的交辦」對所有登入者顯示（`layout.js:40`，`requires: null`）；沒有處理能力的角色看到「目前沒有被指派的工作」（E3-12、E2-10）。
- 頁面的授權寫在 `PagesController` 的 `[Permission(…)]`，多個能力是「任一」。
- 說明章節的 `requires` 只支援單一能力（`HelpContentService.cs:44`）；排程章寫 Maintain，頁面允許 DevMonitor 或 Maintain（E1-35）；權限異動章沒設，頁面需要 ConfirmPermission（E1-36）；稽核章寫 Maintain，頁面是 ViewAudit（E1-37）。
- 章節大多沒有 `href`，章節與頁面的對應沒有寫在任何地方。
- 六章標題與導覽名稱不同（E1-38）。
- 「我的交辦」的分頁標題先顯示通用名再被前端改掉（E2-11）。

### 根因
導覽、頁面、說明章節的權限條件各寫一份，沒有互相核對。

### 定案
1. 「我的交辦」的導覽條件改成具處理能力（含只靠主機負責人取得的）。沒有處理能力的人直接開自己的網址時，頁面說明原因。管理者看別人的頁不受影響。
2. 說明章節的 `requires` 支援「任一能力」的清單；排程、權限異動、稽核三章改成與頁面相同。
3. 守門測試：章節與頁面的對應表寫在測試裡（只有測試用，不進執行路徑）；每個對應到頁面的章節，條件與該頁 `[Permission]` 相同。
4. 六章標題改成含導覽名稱；守門測試檢查對應到導覽項目的章節標題含該項目的顯示文字。
5. 分頁標題由伺服器端給正確名稱。
