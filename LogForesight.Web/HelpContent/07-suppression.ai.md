# 告警抑制（AI 參考指引）

## 頁面基本資訊與存取架構

- **頁面路徑**：
  - 主要管理介面：`/admin/rules` 之第三分頁「告警抑制」。
  - 詳情頁快捷入口：`/records/{hostId}/{date}` 各重點問題、趨勢告警與關聯訊號旁之「抑制」捷徑按鈕。
- **存取權限**：需要 `Capability.Maintain`（`admin` 與 `serverAdmin` 角色具備）。
- **後端端點**：
  - 抑制清單查詢：`GET /api/rules/suppressions`，對應 `RulesController.GetSuppressions`。
  - 規則型抑制建立／移除：`POST /api/rules/{ruleId}/suppressions`、`DELETE /api/rules/{ruleId}/suppressions`。
  - 大範圍影響面預覽：`GET /api/rules/{ruleId}/suppression-preview?scope={scope}&hostGroupId={id}`。
  - 通用目標型抑制建立／移除（絕對路由）：`POST /api/suppressions`、`DELETE /api/suppressions`（供簽章、關聯模式、總量目標使用）。

## 核心設計哲學：關閉「要不要吵」，不是「要不要記」

LogForesight 將「系統偵測」與「主動示警」完全解耦：
- **抑制的影響**：
  - 關閉 Console 輸出、郵件通知與風險報告的警報。
  - 排除於日風險等級判定（`ComputeRuleBasedRisk` 不再因被抑制的訊號而將當天升級為高/中風險日）。
- **完全不影響的底層行為**：
  - 事件**照常聚合統計**。
  - 規則**照常命中並寫入 `RuleId`**。
  - 趨勢與關聯層**照常計算**。
  - 歷史分析紀錄**照常完整入庫**。
- **透明度呈現**：在風險日詳情頁（`/records/{hostId}/{date}`）中，被抑制的告警以獨立的「已抑制的告警」區塊收合呈現，維運人員可隨時展開檢視該訊號在當天實際發生的次數與時段，徹底避免產生無法追溯的永久監控盲區。

## 四種抑制目標型別（`SuppressionTargetTypes`）

抑制設定由 `TargetType` 決定比對目標，涵蓋系統中所有可能產生告警的維度：

```
[抑制目標型別]
  ├─ 1. Rule（全規則型）：整條規則命中結果靜音
  ├─ 2. Signature（問題簽章型）：特定來源+EventId+類型之簽章靜音
  ├─ 3. Correlation（關聯模式型）：特定跨log攻擊鏈/故障鏈模式靜音
  └─ 4. Volume（音量/趨勢量型）：整體錯誤量或安全稽核量突增靜音
```

| TargetType | 比對欄位 | 適用對象 | 影響的計算與防護機制 |
|---|---|---|---|
| **`Rule`**（全規則型） | `RuleId` | 命中指定規則的所有事件 | 標記 `LogIssueSignature.Suppressed`，排除重大旗標與嚴重度對日風險之拉升。支援 Host／Group／Site 三種範圍。 |
| **`Signature`**（問題簽章型） | `SignatureKey`<br>（來源＋EventId＋類型） | 未命中規則之 Other 類別事件簽章 | 針對特定未知問題簽章精準靜音，不影響同一來源的其他 Event ID。僅支援 Host 範圍。 |
| **`Correlation`**（關聯模式型） | `CorrelationPatternId`<br>（19 種關聯 Pattern ID） | 跨 log 組合比對出之攻擊鏈與故障鏈模式 | 命中的關聯模式整批自 `correlations` 移除，不參與風險判定。**影響面極大**，建立時強制要求填寫原因並跳出強警告。僅支援 Host 範圍。 |
| **`Volume`**（音量/趨勢量型） | `VolumeKind`<br>（`error` 或 `audit`） | 整體錯誤量或安全稽核事件量之突增趨勢 | `TrendAnalyzer` 略過對應類別的總量暴增判定，不再觸發總量趨勢告警。僅支援 Host 範圍。 |

## 三種生效範圍（`SuppressionScopes`）與支援矩陣

### 1. 生效範圍定義
- **`Host`（單一主機）**：僅對指定的單台主機生效。
- **`Group`（主機群組）**：對指定主機群組**當前與未來加入的所有成員**動態生效（非建立當下的快照）。
- **`Site`（全站）**：整個環境所有主機全域生效。預設到期天數為 **30 天**（避免全域長期遺忘）。

### 2. 範圍支援矩陣與服務層防護

| TargetType | Host（單台） | Group（群組） | Site（全站） |
|---|---|---|---|
| **`Rule`** | ✓（支援） | ✓（強制影響面預覽） | ✓（強制影響面預覽，預設 30 天） |
| **`Signature`** | ✓（支援） | ✗（服務層拒絕） | ✗（服務層拒絕） |
| **`Correlation`** | ✓（支援） | ✗（服務層拒絕） | ✗（服務層拒絕） |
| **`Volume`** | ✓（支援） | ✗（服務層拒絕） | ✗（服務層拒絕） |

- **防護設計**：非 `Rule` 型的抑制目標目前在後端服務層（`RuleAdminService.AddSuppression`）一律強制限制僅支援 `Host` 範圍，防止繞過 UI 直接呼叫 API 造成全站關聯或總量監控失效。

### 3. 大範圍影響面預覽（`PreviewSuppression`）
- 在為 `Rule` 建立 `Group` 或 `Site` 範圍的抑制前，系統會先呼叫預覽端點，試算並顯示：
  - 預計影響的主機總台數。
  - 過去 14 天內該規則在這些主機上累計命中的總次數。
- 提供管理者明確的數據依據，防止誤操作導致大規模監控失效。

## 到期機制與解除管理

- **到期設定（`ExpiresAt`）**：建立抑制時可指定到期天數（留空為永久生效）。
- **到期不自動刪除原則**：
  - 當抑制設定到達 `ExpiresAt` 時，系統自動恢復該訊號的正常告警與風險升級，但**資料庫內的抑制設定紀錄不會自動刪除**。
  - **排程執行提示**：每次分析啟動時，若偵測到已過期的抑制，日誌輸出會標註「抑制已到期，恢復告警」。
  - **多層範圍提醒（`StillSuppressedElsewhere`）**：若某條單機抑制已過期，但該主機所屬群組或全站仍有生效中的抑制，系統會提示「此規則仍受其他範圍抑制中」，避免維運人員產生解除無效的誤解。
  - **人工清理決策**：過期紀錄保留於管理列表中，等待管理者確認該問題已徹底修復後再手動點擊刪除。

## 告警抑制 vs 已知雜訊記憶（`NoiseMark`）

系統中存在兩種「雜訊處理」機制，其層級完全正交、互不取代：

| 比較維度 | 告警抑制（`RuleSuppression`） | 已知雜訊記憶（`NoiseMark` / 處理狀態） |
|---|---|---|
| **操作層級** | **批次分析與風險判定層** | **Web UI 待辦與處理狀態層** |
| **生效位置** | 規則維護 > 告警抑制分頁 | 風險日詳情頁 > 處理狀態標記為「已知雜訊」 |
| **對風險等級的影響** | **會改變風險等級**（排除於高/中風險日判定） | **完全不影響風險等級**（當天該是高風險仍是高風險） |
| **對畫面的影響** | 告警文字收合至「已抑制告警」區塊 | 隔天新出現同問題時，處理狀態自動預填為「已知雜訊」 |
| **生效範圍** | 支援 Host、Group、Site（Rule 型） | 僅限單一主機單一簽章 |
| **使用時機** | 該訊號已確認無危害，不想再收到任何警報與升級 | 該問題仍需記錄於風險中，但不想每天手動填寫處理狀態 |

## 常見問答與邊界狀況（Q&A）

- **Q: 昨天新設定了一條全站抑制，為什麼回頭看前天的主機日詳情，它仍然顯示為「高風險日」？**
  - **A**: 抑制設定僅對「設定時間點之後」執行的分析作業生效。歷史分析紀錄為事後不可改寫的客觀證據層，系統絕不會因為新增抑制設定而回溯改寫過去已經結算的日風險等級。
- **Q: 為什麼在詳情頁針對某個關聯訊號點擊抑制時，系統要求必須填寫原因？**
  - **A**: 關聯訊號代表跨 log 的攻擊鏈或故障鏈組合（如暴力破解後成功登入），將關聯模式抑制等於關閉了一整類複雜威脅的自動警報，影響層面極大。因此系統強制要求維運人員填寫審核原因，並記錄於稽核日誌中。
- **Q: 刪除某一條抑制設定後，先前被抑制的主機日會自動重新補發警報信嗎？**
  - **A**: 不會。解除抑制只會讓未來的分析執行恢復正常告警判定，過去已經完成分析的歷史主機日不會觸發補發郵件。
