# 排程作業（AI 參考指引）

## 頁面基本資訊與存取架構

- **頁面路徑**：`/admin/runs`（選單標題為「排程作業」；後端亦對應 `/admin/schedule`）。
- **存取權限**：需要 `Maintain` 能力（`Capability.Maintain`，管理員角色可存取）。
- **後端端點**：
  - 狀態輪詢：`GET /api/admin/schedule/status`，回傳當前執行狀態（`SchedulerRunState`）。
  - 手動觸發：`POST /api/admin/schedule/run`，觸發立即執行（`SchedulerService.TriggerNow`）。
  - 中止執行：`POST /api/admin/schedule/cancel`，發出取消訊號中斷進行中的執行。
  - 歷程查詢：`GET /api/admin/schedule/runs?page={page}&pageSize={pageSize}`，取得歷史執行紀錄清單。
  - 單次歷程明細：`GET /api/admin/schedule/runs/{runId}`，取得指定執行的完整輸出日誌與統計。
  - 設定更新：`PUT /api/admin/schedule/settings`，更新排程時間窗與開關設定。
  - 台數預覽：`POST /api/admin/schedule/preview-targets`，依選取範圍與補跑條件試算預計執行的主機台數。

## 觸發方式與排程機制

### 1. 排程自動觸發（Scheduled Runs）
- **每日執行窗口**：最多可設定 4 組時間窗口（包含起始時間 `Start` 與結束時間 `End`），支援跨午夜區間（例如 `23:00` 至 `05:00`）。
- **輪詢機制**：背景排程服務每 60 秒檢查一次當前時刻是否落在啟用中的時間窗口內。當進入 Start 時刻時自動觸發一次完整分析作業。
- **優雅停止（Graceful Stop）**：當系統時間到達 End 結束時刻時，排程服務會對進行中的分析發出取消訊號，正在處理的主機日完成當前步驟後安全收尾，未完成的主機日由下次排程自動接續處理。
- **全域開關**：勾選「啟用排程」並儲存後立即生效，取消勾選則停止所有自動定時觸發。

### 2. 立即執行手動觸發（Immediate Runs）
- **執行入口**：排程作業頁頂端「立即執行」按鈕，或單一主機詳情頁（`/hosts/{id}`）的「指定主機更新」按鈕。手動觸發不受排程時間窗口限制。
- **分析範圍（Scope）**：
  - `All`（全部主機）：包含所有 NetIQ 主機與本機主機（若本機分析已啟用）。
  - `NetiqHosts`（指定 NetIQ 主機）：可選取特定網段或全部 NetIQ 主機，不執行本機分析。
  - 單一主機：僅針對指定主機執行指定日期區間的分析。
- **條件補跑選項（`onlyIncompleteHostDays`）**：
  - 控制項文字：「只補跑失敗或未執行的主機（略過已成功且有 AI 分析的）」。
  - **待補判定標準**：主機日資料庫中「完全無分析紀錄」，或「已有紀錄但標記為 AI 待補（`AiPending`）」。
  - **不視為失敗的例外情況**：
    1. 低風險日：系統設計上低風險日預設不主動呼叫 AI，因此沒有 AI 分析屬正常現象，不列入失敗。
    2. 純統計模式：全站未設定 AI 服務（或清空位址）時，所有主機日均無 AI 分析，此選項在此模式下只補跑完全缺漏的日期。
  - 適用情境：AI 服務曾短暫斷線導致部分主機日降級為統計模式（畫面上顯示「AI 待補」徽章），可利用此選項精準回補缺失的 AI 分析，無需重跑已成功的正常主機日。
- **互斥控制（Mutex）**：全站同時間僅允許一個分析執行個體（跨行程互斥）。若已有作業在執行中，再次觸發會被拒絕並回傳 HTTP 409 Conflict，不會排入等待隊列。

## 分析執行流程與資料管道

每次分析執行依序推進以下階段：

```
[啟動]
  │
  ├─ 1. 清理過期歷史（依資料保留設定清理超期紀錄與日誌）
  │
  ├─ 2. 缺漏日期探測（首次執行探測近 120 天建立基準；日常執行探測近 14 天）
  │
  ├─ 3. Sentinel 事件批次抓取（多日誌頻道平行掃描取得缺漏區間事件）
  │
  └─ 4. 逐日推進分析（由舊到新日期順序，已分析日期自動跳過具冪等性）
        │
        ├─ [本機主機分析] ──> 同步呼叫規則/趨勢/關聯 ──> 同步呼叫 AI ──> 寫入結果
        │
        └─ [NetIQ 機房分析]
              ├─ 階段一（統計段）：規則/趨勢/關聯即時計算 ──> 立刻寫入資料庫
              └─ 階段二（AI 消化段）：白話摘要/體檢敘事 ──> 排入背景佇列依序消化
```

1. **過期資料清理**：每次執行啟動時，第一步先依據「系統設定 > 資料保留」的天數門檻清除過期的歷史紀錄、稽核日誌與風險暫存資料。
2. **缺漏日期探測**：若為系統首次執行，自動回溯檢查近 120 天以建立完整的歷史趨勢基準線；日常例行執行則檢查近 14 天（通常僅缺昨日）。
3. **並行資料管道**：本機主機分析與 NetIQ 機房分析採**並行管線（Parallel Pipeline）**運作，兩路同時開跑以縮短總耗時。執行日誌中本機日誌前綴標示 `[本機]`。
4. **AI 降級容錯機制**：若 AI 呼叫發生例外、逾時或連線中斷，該主機日自動標記為統計模式（`AI 未分析`）並正常寫入資料庫。規則比對、頻率趨勢分析與跨 log 關聯訊號不受任何影響，系統不會因 AI 服務故障而中止執行。

## NetIQ 機房分析兩階段與佇列背壓機制

### 兩階段解耦設計（Two-Stage Decoupling）
為避免上千台主機的批次分析被 AI 推論速度拖慢，NetIQ 機房分析採用兩階段處理：
- **第一階段（統計段）**：規則比對、歷史趨勢比對、跨 log 關聯等確定性運算完成後，立即將分析紀錄寫入資料庫。此時畫面上該主機日標記為「（統計已完成，AI 分析排隊中）」。
- **第二階段（AI 消化段）**：AI 白話摘要與體檢敘事封裝為背景工作項目，排入記憶體 FIFO 佇列（`AiFollowupQueue`，容量上限 200 件）由背景工作者依序消化並非同步補寫回資料庫。

### 進度條與狀態指示器
執行中的狀態卡（`#schedule-status`）依據後端回報的 Phase 動態繪製三條獨立進度軌：
1. **本機進度軌（Local）**：顯示「本機分析　X / Y 主機日」，僅在有本機分析工作時顯示。
2. **NetIQ 主進度軌（NetIQ）**：顯示「NetIQ 機房分析　X / Y 主機日」，代表搜尋抓取與統計段進度。
3. **AI 子進度軌（Sub-Progress）**：顯示 AI 背景消化進度，依狀態呈現兩種 Phase：
   - `netiq-ai`（AI 正常消化中）：標籤顯示「AI 白話分析補寫中」，單位為**件**（例如 `15 / 200 件`）。
   - `netiq-backpressure`（佇列滿載背壓）：當佇列累積達 200 件上限時，Sentinel 搜尋主線暫停推進以避免記憶體溢位，標籤切換為「搜尋暫停：AI 佇列消化中」，單位為**件**。
   - **背壓進度即時回報**：背壓期間子進度數字為 `已完成＋已放棄的 AI 件數 ／ 已排入佇列的件數`（`AiCompleted + AiAbandoned / AiQueued`），前端每約 2～3 秒輪詢更新一次。每當背景消化完一件 AI 工作，數字即時遞增推進，向管理者明確展示佇列正在消化，消除過去版本因顯示主機日數字且只報一次而造成「畫面卡在同一個數字不動」的誤解。

### 本機主機與佇列序列化互動
- 本機主機的 AI 呼叫採同步執行，並與 NetIQ 背景佇列共用同一個 `AIService` 序列化請求佇列（AI 服務同一時間僅處理一個推論請求，避免地端 GPU 或雲端 API 連線被搶佔）。
- 若 NetIQ 佇列已有工作項在推論，本機分析會排隊等待，此時本機進度條短暫停留屬正常現象。

## 分析本機主機開關（`AnalyzeLocalHost`）

- **開關位置**：排程作業頁面「分析本機主機」核取方塊（預設為勾選開啟）。
- **停用後的行為**：
  - 排程自動執行與手動「全部主機」立即執行均完全跳過本機 Web 主機，僅處理 NetIQ 機房主機。
  - 立即執行的台數預覽不再計入本機。
  - 主機詳情頁對本機主機隱藏「指定主機更新」按鈕。
  - 執行矩陣總表上，本機主機的空白日期會標示「本機分析已停用」而非「未執行」，避免管理者誤判為排程漏跑。
- **適用情境**：LogForesight 站台主機自身無重大安全監控需求，或已將該主機納入 NetIQ Sentinel 統一收錄。停用本機分析可將 AI 推論時間全數保留給 NetIQ 機房主機。

## 執行監控、郵件通知與大規模上線

1. **執行監控與歷程**：
   - 即時顯示目前是否有作業在跑、耗時累計、各軌進度百分比與件數。
   - 歷史紀錄表列出過往每次執行的起訖時間、觸發來源、範圍、主機日處理數、成功/失敗狀態與耗時。
   - 點擊「日誌」可展開詳細標準輸出，高風險或重大事件會以突顯樣式標註。
2. **郵件通知連動**：
   - 執行結束後若於「系統設定 > 郵件通知」啟用摘要信，會自動彙整該次執行結果並寄送。寄信過程之失敗僅記錄警告，絕不影響分析產出。
3. **大規模上線建議 SOP**：
   - 初次登錄數百至數千台主機時，建議先於「系統設定」清空 AI API 位址，以「純統計模式」執行歷史回補。
   - 待完整 14～120 天統計基準建立且耗時符合預期後，再設定 AI 服務並啟用夜間排程，平穩轉入日常運作。

## 常見問答與邊界狀況（Q&A）

- **Q: 為什麼排程執行時，主進度條停住，子進度條顯示「搜尋暫停：AI 佇列消化中」？**
  - **A**: 這是 NetIQ AI 兩階段管線的「背壓節流機制」。當第一階段搜尋與統計產出工作項的速度遠快於 AI 推論速度，導致記憶體佇列累積達上限（200 件）時，搜尋引擎會暫停發送新查詢，等待背景 AI 消化佇列中的工作。此時子進度條會顯示當前已消化的件數（如 `45 / 200 件`）並持續推進，這是正常保護機制而非系統當機。
- **Q: 為什麼本機分析進度條在中途停住了幾分鐘？**
  - **A**: 本機分析與 NetIQ 機房分析共用同一個 AI 服務的請求序列化通道。若 NetIQ 佇列中正在進行深入分析推論，本機分析會等待該次推論完成後才發出請求。若本機不需要監控，可關閉「分析本機主機」開關以完全釋放資源給 NetIQ。
- **Q: 若在分析執行途中點擊「取消執行」，未完成 AI 的主機日會遺失嗎？**
  - **A**: 不會。第一階段統計結果在計算當下已寫入資料庫；取消時尚未完成 AI 的主機日會保留「AI 待補（`AiPending`）」狀態。下次排程或手動勾選「只補跑失敗或未執行」時，系統會自動辨識並將這些主機日重新排入佇列補齊 AI 分析。
- **Q: 為什麼勾選「只補跑失敗」，低風險日沒有 AI 摘要卻被略過了？**
  - **A**: 系統預設策略中，低風險日因無異常風險訊號，不主動呼叫 AI 推論以節省運算資源與 API 成本。因此低風險日無 AI 摘要屬於正常完成狀態，並非分析失敗，補跑邏輯會正確將其略過。
