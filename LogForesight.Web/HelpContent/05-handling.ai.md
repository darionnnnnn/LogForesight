# 處理狀態與案件（AI 參考指引）

## 頁面基本資訊與存取架構

- **頁面路徑**：
  - 風險日詳情頁處理控制項：`/records/{hostId}/{date}`（右側處理狀態卡與彈窗）。
  - 個人工作頁面：`/my-tasks`（側欄「我的交辦」）。
  - 處理人員工作頁面：`/handlers/{userId}`（全域可查看指定人員的工作負載）。
  - 使用者詳細管理頁面：`/admin/users/{id}`（管理員檢視特定人員之可見主機與交辦歷程）。
- **存取權限與能力劃分**：
  - 狀態標記與說明更新：需要 `Capability.Handle`（`user` 與 `admin` 角色具備）。
  - 指派與改派處理人：需要 `Capability.Assign`（僅 `admin` 角色具備）。
  - 跨主機批次統一標記：需要 `Capability.Assign` 且 `Capability.Handle`（僅 `admin` 角色兼具）。
- **後端端點**：
  - 日層級處理狀態更新：`PUT /api/records/{hostId:long}/{date}/handling`，對應 `DayHandlingCommandService.Update`。
  - 單一問題狀態設定：`PUT /api/records/{hostId:long}/{date}/handling/issues`，對應 `IssueHandlingCommandService.SetIssueStatus`。
  - 批次問題狀態設定：`PUT /api/records/{hostId:long}/{date}/handling/issues/batch`。
  - 日層級指派處理人：`PUT /api/records/{hostId:long}/{date}/handling/assign`，對應 `DayHandlingCommandService.Assign`。
  - 跨主機案件批次指派：`POST /api/handling/issue-cases/bulk-assign`。
  - 處理人跨主機批次回覆：`POST /api/handling/issue-cases/bulk-status`。
  - 跨主機統一標記結案：`POST /api/handling/issue-cases/bulk-close`。
  - 個人工作負載查詢：`GET /api/handlers/{userId:long}/workload?includeResolvedDays={bool}`。

## 處理狀態模型與四種結案原因

對外呈現三大頂層狀態，其中已處理與處理中具備精細的子狀態劃分：

```
[處理狀態]
  ├─ 1. 未處理（unhandled）
  ├─ 2. 處理中（in_progress）
  │      └─ 【無法處理】（上報狀態，案件維持進行中，通知全體 admin）
  └─ 3. 已處理（resolved，已結案）
         ├─ 已解決（resolved）：故障排除或修補完成
         ├─ 不予處理（wont_fix）：評估後風險可接受，決策不處置
         ├─ 誤報（false_positive）：正常業務行為被規則誤判
         └─ 已知雜訊（known_noise）：確認為日常背景雜訊
```

### 1. 「無法處理」（Cannot Handle / 上報機制）
- **定位**：處理人評估後發現自身權限不足、需跨部門協調或需外部原廠支援，標記此狀態進行問題上報。
- **核心語意（不是結案）**：
  - 案件**維持進行中（`in_progress`）**，未結案計數不減少。
  - 標記時**強制必填原因說明**。
  - **即時通知聯鎖**：若系統設定已啟用郵件通知，系統會立即發送上報通知信給所有 `admin` 群組成員，提示管理員介入協調或重新指派。
- **「無法處理」vs「不予處理」之差別**：
  - **不予處理（`wont_fix`）**：結論性結案——「經評估確認此問題在當前環境下不值得耗費資源處理，正式結案」。
  - **無法處理**：進行中求助——「這件事必須被處理，但我無法獨立完成，請管理員介入支援」。

## 跨日問題案件（Cross-Day Issue Cases）機制

為避免同一個硬體或安全問題連續發生數週時，維運人員每天必須重複點擊指派與標記，系統設計了自動化的「跨日問題案件」模型：

- **案件唯一鍵**：`(HostId, IssueSignature)`（單一主機上的特定問題簽章）。
- **生命週期與自動掛載**：
  1. **首次指派建案**：當某主機日的某個問題第一次被指派處理人時，系統自動建立一個進行中的 `IssueCase`。
  2. **歷史未結案回溯**：建案當下，系統自動向前回溯該主機在資料庫中同一個問題**所有尚未結案的歷史主機日**，一併掛入該案件。
  3. **未來新日誌自動掛入**：每日夜間批次分析產出新紀錄時，若發現該主機該問題已有進行中的案件，自動將新的一天掛入案件中，處理人無需每天手動重新認領。
- **狀態雙向擴散（Status Propagation）**：
  - 處理人在案件涵蓋的任一天標記處理狀態或說明，變更會**自動同步展開**至該案件所涵蓋的所有主機日。
  - 當標記為結案類狀態（已解決／不予處理／誤報／已知雜訊）時，該 `IssueCase` 正式結案關閉。
  - **結案後重發**：若結案後未來該問題再次發生，系統會將其視為全新事件並開啟新的獨立案件，不破壞舊案件的歷史留痕。
- **專屬承擔與改派防護**：
  - 進行中案件跨日只歸一人專屬處理。若其他管理員重複執行指派，系統會維持原處理人並回報「已由 ○○○ 的案件涵蓋，未變更」。
  - 若需更換負責同仁，必須透過「案件改派（Reassign）」流程執行。

## 負責人優先序與自動化聯鎖矩陣

當夜間批次分析產出問題時，處理狀態與處理人的自動推導遵循嚴格的優先順序：

```
1. 人工手動標記狀態（最高優先，絕對不可被自動化覆寫）
   ↓
2. 進行中的跨日問題案件（Issue Case，自動繼承處理人與處理中狀態）
   ↓
3. 問題檔案機房結論（IssueProfile 啟用 AutoApply 時，自動套用結案結論）
   ↓
4. 問題負責人（IssueProfile 負責人名單恰好 1 人時，自動建案並指派給該員）
   ↓
5. 主機負責人（WebHost.OwnerUserIds，無上述規則時之最後兜底）
```

- **問題負責人恰好一人原則**：若「問題檔案」設定了多位負責人，系統不隨機猜測，不會自動建案，而是將通知寄給全體問題負責人，等待人工認領。

## 案件授與（Case Assignment Access Grant）

- **設計目的**：當管理員將某台主機上的特定問題交辦給不在該主機授權群組內的工程師時，避免對方因權限不足而無法查看與處理。
- **最小化窄授權邊界**：
  - 該處理人獲得對**該特定主機日之特定問題簽章**的檢視與處置權限。
  - **無法查看同主機日之其他無關問題**。
  - **無法查看當日 AI 全文總覽敘事**（保護整機業務機密）。
  - 詳情頁明確標示「您以案件處理人身分檢視」。
  - **歷史存取保留**：案件結案後，該處理人仍永久保留對自己曾經處理過之案件紀錄的檢視權限，以供後續稽核與覆盤。

## 個人交辦工作台（`/my-tasks`）

- 側欄「我的交辦」提供處理人個人的專屬工作儀表板：
  - 列出當前指派給自己的所有進行中案件與未結案風險日。
  - 統計「可見主機數」、「處理中案件」、「已結案案件」與「逾期項目」。
  - 支援依主機、逾期狀態快速過濾並一鍵下鑽至詳情頁處理。

## 常見問答與邊界狀況（Q&A）

- **Q: 為什麼一個問題明明已經修好了，隔天排程跑完後卻又冒出「未處理」？**
  - **A**: 請確認先前結案時是否正確標記為「已處理」並選擇了結案原因（已解決等）。若先前僅標記為「處理中」，案件仍處於進行中狀態；若先前已結案，但隔天同一主機再次產生了該問題的 Event Log，系統會判定為「故障再次復發」並建立新的未處理紀錄。
- **Q: 被指派為案件處理人的同仁，登入後為什麼在「主機清單」和「儀表板」看不到那台主機？**
  - **A**: 這是「案件授與」的正常安全行為。案件授與只賦予該員針對「被交辦的單一問題」的窄檢視權，不會將整台主機加入該員的一般可見主機清單，因此主機清單與儀表板總覽不會受到影響。該員可直接在「我的交辦（`/my-tasks`）」中點擊進入處理。
- **Q: 管理員在問題查詢頁執行「統一標記」時，會影響已經有同仁在處理中的案件嗎？**
  - **A**: 不會。「統一標記（`BulkCloseIssue`）」在後端具備防護機制，僅會套用於「尚未有人接手、無進行中案件」的主機日；已經建立跨日案件或有處理人的紀錄會被安全略過並在預覽中明確列出，確保不會覆蓋同仁進行中的工作。
